⚠ Where delete is NOT a download, and must not pretend to be

1. ⚠⚠ DELETE MUST NOT FEED THE ETA ACCUMULATOR

The accumulator settled 07-25 is tiles downloaded ÷ execution time. A delete removes 50,000 tiles in seconds. If deletes are added to it, tiles-per-minute is inflated by orders of magnitude and every subsequent download estimate collapses toward zero.

Rule: only DownloadType.AREA, CORRIDOR and MAP_SOURCE_REFRESH contribute to the accumulator. DELETE contributes nothing, ever. This is the single most damaging mistake available in this feature, and it would present as "the ETA went crazy" days later with no obvious cause.

2. Segmentation exists for a constraint delete does not share

Downloads segment at ceil(sizeTiles/50000) because a big area takes hours and must survive interruption. A delete of the same area is ~18 indexed statements and completes in under a second. Segmenting it would mirror a solution to a problem delete does not have — and would multiply queue rows for no benefit.

Recommendation: one entry per slot, no segmentation.

3. Destructive, and irreversible

A download is additive and safe — the worst case is wasted bandwidth. A delete cannot be undone (the tiles came from paid Esri requests). The gated confirm with scope and count built in Phase 0b is the right pattern — reuse it, do not invent a second one. The confirm should state the exact tile count that will be removed, per source.

4. The prompt's "replace existing tiles" checkbox is meaningless here

Source selection is meaningful — "delete SAT, keep TOPO" is a real intent. Replace is not. Open decision: a delete variant of the dialog, or a mode flag that hides the checkbox. Prefer the variant — a mode flag inside a shared dialog is how refreshMode ended up carrying two meanings.

Stage by stage

Stage 1 — launch

Same bbox draw the area download uses. Entry point is a DELETE action beside SAVE MAPS, or a mode on the existing draw. Open: where it lives in the UI.

Stage 2 — count, then confirm

⭐ Count with the real predicate, not an estimate. The download path sizes with quickEstimate, which answers "how many tiles SHOULD be there". A delete must answer "how many ARE there" — those differ, often hugely, on a partially-downloaded area.

SELECT COUNT(*) FROM tiles
 WHERE zoom_level=? AND tile_column BETWEEN ? AND ? AND tile_row BETWEEN ? AND ?

One indexed count per zoom, ~18 queries, instant. That number goes in the confirm dialog AND becomes the entry's totalTiles, so the panel row shows honest progress.

Stage 3 — enqueue

One QueueEntry per selected slot: downloadType = DELETE_AREA_TILES, priority = 0, label = "DEL <slot>" (matching the DL/CORR convention already on screen), bbox carried in the existing north/south/east/west fields. No new entry fields are needed.

Stage 4 — dispatch

launchWorker gains one branch: DownloadType.DELETE_AREA_TILES -> ConvoyDeleteWorker. The Data.Builder already passes entry_id, bbox, refresh_slot and label. No geom_hash, no refresh_mode.

Stage 5 — the worker

Structure copied from ConvoyDownloadWorker: validate inputs → markFailed + Result.failure() on a blank slot → init managers → showProgress → derive the tile ranges from the bbox using the same ConvoyTileCalculator call the download uses → delete → progress → markComplete.

⭐ Deriving with the same calculator is the correctness guarantee — it is what makes "delete what I downloaded" true by construction rather than by two functions agreeing to stay in step.

⚠ RAW z/x/y, NO FLIP. MBTilesStore stores raw (comments at :98 and :122). Using the flipped TMS convention here would silently delete the wrong rows and look like a partial success.

Stage 6 — the delete itself (THE decision)

Option A — per-tile loop (literal mirror of the download)

  • + identical structure and progress granularity; cancellable at any tile
  • − ~50,000 individual statements for a large area

Option B — range delete per zoom (recommended)

DELETE FROM tiles
 WHERE zoom_level=? AND tile_column BETWEEN ? AND ? AND tile_row BETWEEN ? AND ?
  • + ~18 statements instead of 50,000, riding the existing UNIQUE INDEX tile_index; sub-second
  • + wrap in one transaction → all-or-nothing, no half-deleted area
  • − progress per zoom level (18 updates) rather than per tile; cancellation between zooms only

18 progress updates is ample for an operation measured in seconds. The per-tile loop's fine granularity exists because downloads run for hours.

⭐ A bbox is a CONTIGUOUS RECTANGLE in x/y at every zoom — that is what makes the range form exactly equivalent to the loop, not an approximation. It is only true because the source geometry is a rectangle; a corridor delete could not use this form and would need the tile-set loop.

Stage 7 — completion

markComplete(entryId, deletedCount, 0) after the transaction commits.

⚠ Do not repeat the two corridor-worker defects: (1) markComplete firing before the work stops — the 07-24 captures showed jobs marked Done still counting; (2) a zero result returning blind success. For delete, zero tiles removed IS a legitimate outcome (nothing was there) — but it must say so ("0 tiles removed"), not look like a completed deletion of a full area.

⚠ Space does not come back on its own

SQLite frees pages inside the file; the .mbtiles stays the same size on disk. There is no VACUUM anywhere in MBTilesStore. So without a further step: user deletes an area, storage does not move, the tool looks broken.

  • Measure first — free and exact: PRAGMA freelist_count × PRAGMA page_size = reclaimable bytes. Turns a blind "compacting…" into "delete freed 1.2 GB — reclaim it now?", and lets you skip the vacuum when it is not worth the churn.
  • ⚠ VACUUM catch-22: needs roughly the file's own size in free space — so it fails exactly when it is most needed. Check free space before offering it.
  • Better primitive: VACUUM INTO '/path/compacted.mbtiles' (SQLite 3.27+, fine on Android 11+) — writes a compacted copy to a path you choose, then delete + rename. The original is untouched until the copy succeeds.
  • Age the problem out: set PRAGMA auto_vacuum=INCREMENTAL in initSchema for NEW files, then PRAGMA incremental_vacuum(N) releases pages cheaply and interruptibly. Can only be set before tables exist — existing stores need one full VACUUM to convert.
  • VACUUM cannot run inside a transaction, and the handle is cached (handles HashMap at :40) — it wants the same close/reopen discipline deleteSource already uses at :187.
  • ⛔ External storage cannot be vacuum scratch. Drive is a network API with no seek; removable media is SAF-only under scoped storage and SQLite needs a POSIX path. Archiving to external is fine — that is a plain file copy.

Recommendation: reclamation is a SEPARATE, EXPLICIT action — not automatic at the end of every delete. Deletes should stay fast and safe; compaction is slow, space-hungry, and occasionally impossible.

⚠ Open questions — answer before writing code

  1. ★ Are a slot's layers separate .mbtiles types? SAT carries three layers. If types are per-layer, the delete must loop the slot's layers exactly as the download does — otherwise it clears base imagery and leaves the transportation and places overlays behind, which would look like a failed delete. This is the one question that can invalidate the whole design; settle it first.
    grep -n "insertTile\|isOverlay" ConvoyDownloadWorker.kt ConvoyTileDownloader.kt
  2. Is there a tile cache above MBTilesStore? If the WebView/Leaflet layer holds bitmaps in memory, deleted tiles may keep rendering until it is invalidated — and the user concludes the delete did not work.
  3. Per-tile loop or range delete (Stage 6). Recommendation: range.
  4. Reclamation policy: never / offered / automatic. Recommendation: offered, with the freelist measurement shown.
  5. Confirm dialog: delete variant, or shared dialog with a mode flag. Recommendation: variant.
  6. UI entry point for the delete bbox draw.

Verification plan

  • Count before / after per zoom with the range predicate — should go to zero inside the box.
  • Tiles just OUTSIDE the bbox survive — the off-by-one that a range delete makes easy. Test with an area adjacent to one you keep.
  • File size unchanged without vacuum — expected, and the reason reclamation is a separate action.
  • Freelist grows by roughly the deleted volume — proves the pages were actually released internally.
  • Map display over the deleted area falls back to NET or blank, not stale cached tiles.
  • Re-download the same area and confirm it fetches rather than skipping via hasTile — the round trip that proves the rows are genuinely gone.
  • ★ ETA sanity after a delete — run a download afterwards and confirm tiles/minute is unchanged. This is the check that catches delete leaking into the accumulator.

Related tool — deleteSource() already exists

MBTilesStore.deleteSource(type) at :186 removes the cached handle, closes it, and drops the whole .mbtiles file. Space returns instantly, no vacuum.

⭐ For TEST RESET this is the better tool than a bbox delete — it gives a guaranteed-empty baseline rather than leftovers you then have to reason about. Bbox delete is the shipping feature; whole-source drop is the reset button. Worth confirming whether it is reachable from the UI today, since clean devices are what make the SAT-15 measurement trustworthy.
