Storage migration — design

2026-09-11 · two releases · nothing built yet

Why this exists

Google rejected the All Files Access declaration on 09-10 — "Access to device storage not required." An appeal and a 30-day extension request are both filed. ⚠ This design does not depend on how they answer: the work is the same either way, and it is the thing that makes a refusal survivable rather than a crisis.

⛔ AND IT IS WORTH DOING ANYWAY. App-private external storage needs no permission, no declaration and no review. Everything that can live there should, so the permission covers only what genuinely needs it.

\u26d4 RELEASE 3 CANNOT REPAIR A DEVICE THAT SKIPPED RELEASE 2

Without the permission, release 3 cannot list or read Documents/GroupTrack. It cannot see the orphaned store, cannot check whether the migration ran, and cannot clean anything up. \u26a0 A rider who skipped 2 has 17 GB stranded on their device that neither they nor the app can use.

\u26d4 AND THERE IS NO WAY BACK. Play serves only the current build, so they cannot reinstall 2 from the store. A sideloaded APK is signed with the local key while Play builds are signed by Play App Signing \u2014 same package name, different keys \u2014 so it will not install over the top, and uninstalling first wipes the data being rescued.

What release 3 can do

  • Detect it indirectly. Release 2 writes a completion record to INTERNAL storage; release 3 reads that. \u26a0 Absent means either "skipped 2" or "new install" and the app cannot tell which \u2014 so the wording must cover both without alarming a new rider.
  • Tell them plainly: the maps are in a place this version cannot reach, they need downloading again, and the folder can be removed with a file manager to reclaim the space. Documents/ is visible to any file manager even though Android/data is not.
  • Ask, and take their word. \u26a0 The app CANNOT verify the folder was removed. The prompt must read "I've removed it", never "confirm removal" \u2014 do not imply a check that did not happen. A "no" brings the reminder back on the next open.

\u2b50 The real mitigation is the gap, not the detection

Ship 2 as early in the extension window as possible and 3 as late as it allows \u2014 roughly three weeks of runway for riders to update. \u26a0 And with THIRTY TESTERS rather than thousands, you can simply tell them. That is a real advantage of being small right now.

\u2b50 COMPLIANCE AND LAUNCH ARE SEPARATE (Fred, 09-11)

Google needs to see the compliant build published, not installed by the public. \u2b50 Promoting release 3 to closed testers inside the 30-day window satisfies them.

\u26d4 SO OPEN TESTING AND THE ANNOUNCEMENT WAIT until the storage question is fully settled \u2014 they are not on Google's clock. Fred: "no app open launch until 3 is ready." The first build the public ever sees should be the settled one, not a build that will require an urgent update.

\u26a0 Track ordering bites here. Internal outranks closed outranks open \u2014 a tester left on the internal list keeps getting internal builds whatever else is published. \u2b50\u2b50 THE GOVERNING PRINCIPLE (Fred, 09-11): "internal storage mirrors the directory structure of external storage, so we are just changing external for internal, not remapping everything."

Everything below the root keeps its name and its nesting. getExternalFilesDir() returns an ordinary File path, so the same API, the same subdirectories and SQLite all work unchanged. \u2b50 The migration is a recursive directory copy and the code change is ONE ACCESSOR returning a different base. No path rewriting, no per-file logic.

\u26a0 This is also what keeps the scope from growing. The moment the design starts mapping old names to new ones, back up.

Where it runs

In StartupHousekeeping.run(), FIRST — ahead of ensureDefaults and SpatialDbManager.init().

⛔ ORDERING IS THE WHOLE SAFETY ARGUMENT. MapSourceManager, SpatialDbManager and the tile store all resolve paths when they initialise. If the move happens after any of them has opened a file, they are holding handles to the old location and writing to a directory that is about to disappear.

⭐ The gate blocks until run() returns, so nothing downstream ever sees a half-moved state. That property is why this belongs in housekeeping and nowhere else.

⚠ Post-authority, pre-everything. The move reads shared storage, so it cannot run before all-files access is confirmed — the same reason everyLaunch sits after the gate.

The checklist

Fred: "we do it all in housekeeping, a checklist of what is being moved so no interruptions." A manifest of items, each marked done as it lands. An interrupted move resumes at the first unfinished item rather than starting over.

⛔ Where the checklist lives

In INTERNAL storage, not in the directory being moved from. Put it in the source and it vanishes with the move it is tracking.

\u2b50\u2b50 TWO PHASES \u2014 NOTHING IS DELETED UNTIL THE APP HAS RUN FROM THE NEW LOCATION

Fred, 09-11: "we should not delete original files until we verify that everything is running on internal, then activate directory deletes on what we moved." \u2b50 Right, and it is materially safer than deleting per item: a failed migration then costs DISK SPACE rather than DATA.

PHASE 1 \u2014 copy and verify. Per item:

  1. Copy source \u2192 destination.
  2. Verify. Row count for a database, byte size for a file. \u26a0 NOT existence \u2014 a zero-byte file exists.
  3. Record the item as copied-and-verified in the checklist.

\u26d4 Nothing is deleted in phase 1. At the end of it the data exists in BOTH places and the app switches to reading the new root.

PHASE 2 \u2014 delete, on the NEXT launch. If the app starts again, it started from internal storage, opened its databases and drew its map. \u2b50 That is the proof. Only then does it delete the sources the checklist recorded as verified.

  • \u2b50 One launch of proof, no judgement calls. Not a launch count, not a health score \u2014 the app ran, so the copy is good.
  • \u26a0 Delete only what the checklist named. Never walk the old directory and delete what is found: maps/ lives there and must survive.
  • \u26a0 During the gap ~415 MB exists twice. Harmless, and it is the price of the safety.

\u26a0\u26a0 MARK AFTER, NEVER BEFORE. A marker written before the work is how a crash mid-operation leaves the app believing something finished that did not. clearTrailsOnce writes its marker after the clear for this reason, and the 08-16 reinstall wipe happened because a guard and the thing it guarded had different lifetimes.

\u2b50 Every step is idempotent: a copy that already happened verifies and moves on; a delete of something already gone is a no-op; an interrupted run resumes at the first unfinished item.

⛔ Close the databases first

An open SQLite database copied mid-write produces a corrupt file, and the corruption is not visible until something reads the damaged page.

So: close → copy → verify → delete → reopen at the new root. SpatialDbManager holds spatialDb and extensionDb as fields and has an initialized flag — both need resetting so the reopen resolves the new path rather than returning the stale handle.

⚠ THIS IS THE SAME SHAPE AS THE FALLBACK LOCK FIXED 09-10: an initialized flag that outlives the state it describes. Check it explicitly rather than assuming the reopen re-resolves.

Release 2 — the tile decision

If the appeal succeeds: MBTiles stay public. The rider keeps a map store that survives an uninstall and that they can see, back up and move between devices. Nothing further to build.

If it is refused: the permission comes out of the manifest, and the MBTiles have to go somewhere. Two options, and the choice is about time:

  • Copy them internal. They are a handful of large files, not millions of small ones, so a copy is feasible — hours, on wifi, with progress. ⚠ Needs 60 GB free on the destination at the same time.
  • Abandon them and re-download. ⭐ MBTiles makes discarding a store trivial — a few file deletes, instant. But the rider loses days of downloading.

⛔ AND THE FINAL BUILD MUST MIGRATE DURING THE UPDATE ITSELF, while access still exists. Once the permission is out of the manifest the app cannot read the old location — a rider who ignored every prompt still needs their data to survive.

⚠ Do not delete an abandoned map store automatically. Deleting 60 GB of the rider's data because of a settings change is not something the app should do quietly. Leave it; they can remove it with a file manager, which is one of the arguments for shared storage in the first place.

What the rider is told in release 2

⭐ The honest version, and it is much better than it first looked:

Your trails, tracks, routes and waypoints move with you — your whole riding history. Your downloaded maps do not, and will need to be downloaded again.

⚠ Name the cost in time, not gigabytes. "60 GB" means less to a rider than "a few days of downloading on wifi." They know what waiting feels like.

⚠ And say that the app works the same either way. The only differences are what survives an uninstall and whether they can see their own files. Otherwise the choice reads as "the good one and the crippled one."

The code

\u2b50 TWO accessors, not one

\u26d4 GIVE THE TILE STORE ITS OWN ACCESSOR IN RELEASE 1, separate from the general root. Release 2 then becomes a one-line change \u2014 point it at the new base \u2014 rather than reopening the migration. And release 3 removes it entirely.

\u26a0 ConvoyConfig:34 holds the tile path. In release 1 it keeps resolving to the PUBLIC root while everything else moves. That mixed state is what the app ships in for up to three weeks, so it has to work deliberately rather than by accident.

One accessor for everything else

Today there are TWO functions building the same path independently — SpatialDbManager.groupTrackDir() and SpatialDbManager.dbDir() — plus eight hardcoded Environment.getExternalStorageDirectory() sites.

⚠ That duplication is the same pattern that produced the palette bug: more than one source for one truth, and nothing keeping them in step.

A single GroupTrackStorage.root(ctx), and everything else becomes a caller. dbDir() keeps its directory-create and .nomedia behaviour, delegating the path.

⚠ Open questions

  1. The canary dir in the authority gate. It probes Documents/GroupTrack to test write access. ⛔ If the app no longer uses public storage, what is the gate still gating? The whole gate may become unnecessary in the internal-only build — which would be a simplification, but it is load-bearing today and wants thinking about separately.
  2. Does the tile store need the permission to READ an existing public store? Release 1 leaves MBTiles public while everything else moves internal. That mixed state must work, and it is the state the app ships in for up to 30 days.
  3. What verifies a database copy? Row count is right but means opening the copy, which means a second open/close cycle. Byte-for-byte is simpler and catches truncation. ⚠ Size alone would pass an empty schema — but an empty schema cannot arise from a copy, only from a create.
  4. Free space. 310 MB needs 310 MB free before the delete. Check first and abort cleanly rather than filling the device.

⛔ Do not build yet

This is a design, not a plan to start today. ⚠ The immediate work is the map key palette — finished and committed — and the release that is already built and waiting on Google.

⭐ And the 09-10 lesson applies directly: "we spiral down into layers of complexity rather than up to levels of simplicity." Release 1 is 310 MB of files moving between two directories. If the design starts growing progress dialogs, rollback engines and preference screens, back up.
