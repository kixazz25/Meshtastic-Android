C3a + C3c — the worker

  • One worker does trails AND points in a single dedup session and writes one ledger record. Fred: “one import so we do not have to parse code to import separately.”
  • Trails route through SpatialDbManager.insertTrail (INSERT / DROP / ALIAS). Points go to a new reference_points table created by the import (CREATE TABLE IF NOT EXISTS — a new empty table needs no migration and no schema_version bump), with UNIQUE(geom_hash).
  • Points must NOT go in waypoints. Those are user-authored: editable, deletable, listed, V3-shared. 3,674 OSM localities would bury the user’s own waypoints and make “remove all OSM data” impossible.
  • beginDedupSession() is mandatory — resolveByGeom and sourceUidSeen read in-memory HashMaps. Skip it and every trail looks new: 89,536 duplicates with nothing reporting an error.
  • Counters: found · inserted · aliased · dropped · geometryChanged · errors · points_*. Fred: “processed should equal added, rejected, and dupes identified” → tally assertion with balanced: true/false recorded per type.
Re-import inserts a second trail; it does not update geometry. updateExistingFeature never touches geometry, bbox or geom_hash — its own comment says so. The stronger reason is not the count: routes snap by lineId, so replacing geometry would silently orphan every saved route touching that trail.

C3b — scope selection and the area round trip

As built, where it differs from the pre-build spec

The specification called for map_area and selected_area in the ledger. As implemented, pending_import carries scope plus a single bbox, and row 3 uses a Row3Choice enum (FULL / AREA). Whole state derives its bbox from OsmImportStage.trailExtent().

The panel’s rule is one line, and it held: on every derive, if a pending bbox is present → launch. Checking on derive rather than on open is what prevents Row3Choice resetting on reopen and wiping a bbox the user had already drawn. That was a real bug, caught before it shipped.

Whole state is not a separate code path

The extent comes from the trails themselves, so every trail overlaps it by definition and a full-extent area import returns exactly what SELECT * would. Testing whole state IS testing area. Confirmed: 89,536 overlapping on the full extent, matching extract.kept exactly.

The area cycle

  1. Row 3 → SELECTED AREA → IMPORT writes pending_import with a null bbox and closes the panel.
  2. ConvoyMapViewerScreen sees the close, positions the planning map on the state extent, ticks Import OSM and opens the draw panel.
  3. The drawn bbox arrives at onAreaSelected, is written to the ledger, the draw panel closes and the OSM panel reopens.
  4. The derive effect finds the bbox and raises the confirm.

The draw completing IS the submit — there is no separate OSM execute button. Verified: 25,400 trails in the drawn box against 89,536 whole state.

⭐⭐ The handoff mechanism already existed. TrailImporter has writePendingArea / readPendingArea / clearPendingArea. The OSM handoff is the second instance of a shipped mechanism, not a new invention. Found via the navigation xref. The recurring lesson of this project, again: the file already knows.

No flag in the map screen

Both panels are flags in one screen, so no navigation is involved. A persistent mode flag was rejected because of the routeMode leak — two back paths, one gated. R1 (stage derived from disk) means nothing needs preserving across the gap. osmAwaitingSlug is derived from disk and guards against a stray draw filling the wrong record.

No AreaDrawPurpose

ConvoyDownloadPanel already carries intent in checkbox state (Download Tiles / Import Trails / Remove Tiles). An Import OSM row was added; the checkboxes ARE the routing.

OSM never becomes a QueueEntry. It shares the drawer, never the queue. An import measured in ROWS would poison the tiles-per-minute yardstick exactly as deletes would. OSM never touches onExecuteDownload and cannot reach the queue.
Area filters WHICH rows go, never geometry. Overlap, not containment; a boundary trail comes over WHOLE. Clipping would change the WKT → change geom_hash → break dedup against a later whole-state import.

C4 — cleanup

  1. Enumerate and size the working files.
  2. Archive the ledger by RENAME — osm/<slug>/ledger.json → osm/history/<slug>_<date>T<time>.json, via OsmImportLedger.archiveLedger().
  3. OsmImportStage.discardState() sweeps the zip, gpkg and skinny, then the directory.
⭐⭐ Order is load-bearing: rename BEFORE the sweep. discardState deletes ledger.json along with the data files, so a rename afterwards would have nothing to rename. history/ sits OUTSIDE osm/<slug>/ and the sweep cannot reach it. That is why rename beats copy: the record is safe before anything destructive runs, and a copy leaves a window where both exist and the wrong one is deleted.
If the rename fails the sweep does not run. Losing the run record to keep a cleanup on schedule is the wrong trade; the files can go on a later pass.

Measured on the first real cleanup: 3 files, 422 MB removed (utah-latest-free.gpkg.zip 314 MB, ready_for_import.db 108 MB, ledger.json), record kept as utah_2026-07-29T135649.json.

Decisions taken on the day

  • No cleanup screen. Row 4 is a process that executes. Fred: “it has to be selected to run after imports. button goes green after imports.”
  • Row 4 arms off imports[] being non-empty — derived, not a flag, so it survives navigation and reflects what actually happened.
  • Acknowledging the recap closes the panel. Correct rather than merely convenient: cleanup removed the working directory, so statesInFlight() is empty and the panel would derive back to row 1 anyway.
  • Cleanup does not auto-roll after import — it waits to be selected.
⭐ REVERSAL — no multi-area from one download. Fred 07-29: “no multi areas from one download. areas are downloaded to support a ride and we are killing downloads after import process.” Rationale: “3 minute download vs cascading complexity for imports.”
This reverses the 07-28 decision that kept the extract alive so a second area could be drawn from it. The trade was weighed and taken: carrying extract lifetime across imports means a driver that reasons about which areas share a download, and cleanup that has to know whether anyone still needs the file. That complexity compounds; the download does not. The state machine collapses back to acquire → extract → import → cleanup, once through, nothing surviving between runs.
Consequence: the reprocess-driver cost model moves from per state to per import. The “group by state, replay all area records from one download” idea assumed the extract persisted.
Optional-retain seam is marked in the code (Fred: “if we have any issue we can make removing the downloaded file optional”). Keeping the ZIP alone (~330 MB) makes a re-import a 40-second re-extract instead of a 3-minute download — the middle option if the trade ever looks wrong in the field.

Dry-run mode — proposed and rejected

I pushed for a dry-run before the first write, on the grounds that it would give the full INSERT/ALIAS/DROP distribution across all 89,536 rows and test the balance assertion before any row existed.

Fred killed it with the decisive objection: a dry run cannot see the case that matters — “an issue in a trail in this run that was simulated as added but is duped within db.” resolveByGeom and sourceUidSeen read in-memory HashMaps filled by beginDedupSession(). A dry run reproduces a stale session faithfully and reports “added” for a row that will collide on the real write. It simulates the decision, not the database’s response to it.

The real run catches exactly that, immediately, via UNIQUE(geom_hash) and the balance assertion. And recovery is cheap: all imported trail rows carry source_id='osm', so a bad import is a laptop DELETE ... WHERE source_id='osm' on a sacrificial device. Points differ — they carry no source_id; reference_points is OSM-only by construction, so that is a full-table delete.

Do not re-propose dry-run mode.

What did ship instead, because no undo exists in-app: a confirm dialog naming the trail count and the four coordinates.

# 🔴 C3b — THE NEXT BUILD (full specification)

Everything below was settled in conversation 07-28 and is not re-litigated.
This section exists so C3b can be written without re-deriving any of it.

## The handoff mechanism — why JSON and not Compose state

Row 3 offers **WHOLE STATE** or **SELECT AREA**. Area requires the planning map,
which means the OSM panel must go away and come back.

**Fred's design (07-28):** row 3 simply *closes the panel*. The map's bbox
submission *relaunches* it. There is **no flag in MVS**, no `AreaDrawPurpose`
enum, and no navigation change.

> ⭐ **Why this works:** R1 — stage is derived from disk, never stored. The panel
> can be destroyed and recreated and lands in exactly the same place. That rule
> was written for crash recovery; this is an unplanned payoff.

> ⚠ **Why a flag was rejected:** the `routeMode` leak. There were two back paths
> and only one was gated — the on-screen BACK bypassed the `BackHandler`
> entirely. A `osmAwaitingBbox` flag in MVS has the identical shape, and every
> exit path would have to clear it. Closing the panel means there is nothing to
> leak.

## The ledger record — uniform, both scopes

```json
"pending_import": {
  "scope": "state",
  "chosen_at": "2026-07-28T22:41:09",
  "map_area":      { "s": 36.99, "w": -114.05, "n": 42.00, "e": -109.04 },
  "selected_area": { "s": 36.99, "w": -114.05, "n": 42.00, "e": -109.04 }
}
```

- **`map_area`** — ALWAYS the state extent. Positions the planning map. 5% margin
  so the box occupies ~95% of the view.
- **`selected_area`** — what actually gets imported.

| scope | map_area | selected_area |
|---|---|---|
| state | state extent | state extent (identical, written immediately) |
| area | state extent | `null` until the draw fills it |

**THE PANEL'S RULE IS ONE LINE: on open, if `selected_area` is present, launch.**

Both paths converge there. The map never has to ask where to open — the answer
is in the record regardless of scope. The importer never has to know which
scope it is.

> ⭐ **Whole state is not a separate code path.** The extent is derived from the
> trails themselves, so every trail overlaps it *by definition*. A full-extent
> area import returns exactly the rows a `SELECT *` would — identically, not
> approximately. One function, exercised two ways. **Testing whole state IS
> testing area.**

> ⚠ **This bends R1 knowingly.** R1 said the ledger never decides what runs next.
> "User chose area and hasn't drawn yet" is not derivable from any disk artifact,
> so it genuinely must be stored. The STAGE stays IMPORT throughout — this is a
> sub-state inside it, not a competing stage.

## The area cycle, step by step

```
1. Row 3 tapped
   -> dialog: WHOLE STATE / SELECT AREA / cancel

2a. WHOLE STATE
   -> extent = OsmImportStage.skinnyExtent(ctx, slug)
        SELECT MIN(min_lat), MIN(min_lon), MAX(max_lat), MAX(max_lon)
        FROM osm_trails            (sub-second over 89,536 rows)
   -> setPendingImport(scope="state", map_area=extent, selected_area=extent)
   -> OsmImportWorker.enqueue()
   -> panel STAYS OPEN, progress rows appear under row 3

2b. SELECT AREA
   -> setPendingImport(scope="area", map_area=extent, selected_area=null)
   -> showOsmPanel = false                 (panel closes; MVS is underneath)
   -> open the download panel with "Import OSM" CHECKED
   -> map framed to map_area with 5% margin

3. User draws + submits
   -> ConvoyMapViewerScreen bbox handler sees osmChecked
   -> slug from OsmImportStage.statesInFlight().firstOrNull()
   -> OsmImportLedger.setPendingBbox(ctx, slug, s, w, n, e)
   -> showOsmPanel = true                  (panel relaunches)

4. Panel opens, sees selected_area present
   -> OsmImportWorker.enqueue()            (KEEP makes a double-enqueue a no-op)
   -> progress rows under row 3

5. Import completes
   -> appendImport() writes the record AND removes pending_import
   -> row 3 ticks, row 4 arms
```

> ⚠ **Clearing must be airtight.** The trigger is "selected_area present" and the
> panel re-derives on every refresh. A pending record that outlives its import
> re-enqueues on every panel open. `appendImport` removes it; `enqueueUniqueWork`
> with `KEEP` makes a duplicate enqueue harmless in the meantime — but the
> removal is the actual fix, not the KEEP.

> ⚠ **Row 3 must SHOW the pending state.** `WAITING FOR AREA — draw one, or
> cancel`, with a visible cancel. An invisible mode is precisely the `routeMode`
> failure. If the user picks area, gets distracted, and returns tomorrow, the
> panel must explain itself.

The panel already carries intent in checkbox state — **this is why
`AreaDrawPurpose` is unnecessary**:

```

Remove Tiles      red     removeTilesChecked
Import OSM        orange  osmChecked          <- NEW ROW
```

`Draw Area` is enabled when any is checked (`ConvoyDownloadPanel.kt` ~:243).
The caller dispatches on whichever ones are. **The checkboxes are the routing.**

New row needs:

- added to the `enabled =` condition on Draw Area
- ⚠ **`osmAvailable: Boolean`** — disabled when no skinny exists. Same mechanism

- bbox display line mirroring `"Trails: $trailSourceCount sources found"`:
  **`"OSM: 8,412 trails in area"`** — indexed count off `ix_osm_trails_bbox`,
  instant, appears the moment the box is drawn.

> ⭐ **The count IS the confirmation.** The user sees exactly what they are
> committing to before submitting, so a confirm dialog adds nothing. (Whole-state

> ⚠ **Checkboxes are not mutually exclusive.** Tiles + OSM both checked = one
> draw does both. Arguably a feature. But dispatch must handle combinations, and
> **OSM must never become a `QueueEntry`** — see the yardstick warning below.

## ⛔ OSM MUST NOT ENTER THE DOWNLOAD QUEUE

Share the **drawer**. Never the queue.

`DownloadQueueManager.submitDownload` is not involved. The yardstick averages
tiles-per-minute; deletes were excluded from it precisely because a different
unit poisons `avgMinutesPer100` and every later download estimate collapses
toward zero. **An OSM import measured in ROWS does exactly the same thing.**

Same UI, separate pipeline.

# 🔴 C4 CLEANUP — settled, not written

## The ledger is RENAMED, not copied

```
osm/utah/ledger.json  ->  osm/history/utah_2026-07-28_224109.json
```

- **Rename replaces the delete.** `finalizeAndDelete` currently removes the
  ledger; now the rename IS the removal. If the rename fails, the ledger stays
  put — cleanup cannot destroy the record even by accident, because deletion is
  not a separate step that could succeed on its own.
- **Nothing is serialized twice**, so the archived record is byte-identical to
  what the import wrote.
- ⚠ **`history/` sits OUTSIDE `osm/<slug>/`** — CANCEL and cleanup both remove
  `osm/<slug>/` wholesale and would take the history with it. (This is also why
  `discardState` is deliberately non-recursive.)
- ⚠ **Never pruned.** A few KB each. Chosen, not overlooked.

## ⭐ C4 NO LONGER AUTO-ROLLS AFTER IMPORT

**This reverses an earlier decision and the reason matters.** C3→C4 auto-roll was
settled when whole-state was the only scope. With area scope it is wrong:
import Moab, cleanup fires, skinny deleted — a second area costs a 630 MB
re-download, defeating the entire point of area scope.

**Cleanup is explicit.** Row 4 arms after import; the user decides when they are
done with the state. Whole-state import may *suggest* it.

## History is per-run, never aggregated

Fred 07-28: *"the history is just that, results of one run at one moment in
time."*

- **History = what a run did.** One file, one run, read on its own.
  **No cross-run arithmetic anywhere.**
- **The database = what exists now.** "How many OSM trails do I have" is
  `COUNT(*) FROM trail_properties WHERE source_id='osm'` — asked of the DB,
  never derived from history.

> ⚠ Summing runs produces a number that *looks* like inventory and is not. A
> re-imported area contributes inserts and dupes that add up to nothing
> meaningful. Better no total than a misleading one.

A history browser (list by state + timestamp, open one run, show its counters
and whether they balanced) is a later, cheap feature — the filenames already
carry both filter keys.

# 🔨 C3b — GATED BUILD (applied 07-29, not yet verified on device)

`patch_c3b_row3_scope_2026-07-29.py` — 7 anchors, dry run clean, applied.
Backups `.bak_20260729_100043`.

## What it does
- **Row 3 launch line carries two values** — FULL STATE / SELECTED AREA, checkbox
  glyphs, rendered in the `rows.forEach` loop rather than inside `StageRow`
  (StageRow is shared by all four rows; only row 3 has a choice).
- **IMPORT is disabled until one is selected** — `enabled = !busy && skinnyExists &&
  importScope != null`. Fred 07-29: *"one must be selected for import button to function."*
- **FULL STATE derives the extent and writes `pending_import`; SELECTED AREA writes a
  null bbox.** Both go through `setPendingImport`, one channel.
- **Then it STOPS at a CANCEL-only recap** showing scope + the four bbox values
  individually + the overlap count. Nothing calls `OsmImportWorker.enqueue`.

## ⭐ Why the gate is where it is
It stands exactly where `enqueue()` will go, so **C3c is a swap, not a rewrite** —
which is the point Fred made on 07-29: *"it keeps us out of the weeds of rewriting a
section because of behaviour issues."* C3b's job ends at *correct `pending_import` on
disk at the right moment*; C3c's begins by consuming it.

## ⭐ The recap READS BACK from disk
It does not print what it meant to write — it re-reads via `pendingBbox`. A transposed
pair shows up in the S/W/N/E lines instead of being masked. Four values labelled
individually, never a joined string: `36.99,-114.05,42.00,-109.04` hides what
`S 36.99 / W -114.05` makes obvious.

## ✅ PASS CRITERION — exact, from the 07-28 ledger
Utah `extract.kept = 89536`. **A FULL STATE recap MUST show `Trails overlapping: 89536`.**
Every trail overlaps its own extent by definition. Any other number means the extent
query or the coordinate order is wrong.

## ⚠ CANCEL does NOT clear the pending record
Deliberate. The record stays on disk so the panel can be reopened to confirm the rule
re-derives off the same values, and so the JSON can be read between runs.

## Findings that drove the build
- ⛔ **`subset_meta` has NO extent.** Seven keys only: `source_file`, `classes`,
  `feature_count`, `built_at`, `wkt_format`, `hash_algo`, `attribution`. So
  `OsmImportLedger:222` (*"whole state writes its bbox straight from subset_meta"*)
  describes an intention that was never built. **Extent now derived by
  `OsmImportStage.trailExtent()`** — `SELECT MIN(min_lat), MAX(max_lat), MIN(min_lon),
  MAX(max_lon) FROM osm_trails`, covered by `ix_osm_trails_bbox`. ⭐ More correct than a
  stored value anyway: the extent comes from the trails themselves, which is *why* whole
  state is not a special case.
- **No 5% margin on `selected_area`.** The margin was specced for positioning the map;
  the import filter wants the true extent. Padding a box that already contains
  everything only widens it.
- ⚠ **`scope` at `OsmImportPanel.kt:95` is `rememberCoroutineScope()`.** The import
  choice is named `importScope` so it cannot shadow it.
- **`LaunchedEffect(refreshTick)` is the derive moment** (R5). The launch rule belongs
  there. Panel re-entry re-composes it, so the relaunch-after-draw path needs no new
  machinery.
- **Only `clickable` was missing from imports** — `padding`, `sp`, `Dispatchers`,
  `launch`, `withContext` were already present, so the panel already does
  `scope.launch { withContext(Dispatchers.IO) }` in the style the patch uses.
- **Nothing touches the skinny.** Both new helpers open `OPEN_READONLY`; C4 is still a
  stub. The skinny is stable across every test cycle, so **no restore is needed between
  runs** — `setPendingImport` overwrites the record wholesale rather than accumulating.

## ⚠ Uncertain until the build lands
`material3` vs `material` for the recap `AlertDialog`/`TextButton`, and whether the
two-value line inherits a readable colour on the panel background. Both are
compile-or-eyeball fixes, not design problems.

`patch_c3b_area_draw_2026-07-29.py` — 7 anchors, dry run clean, applied.
Backups `.bak_20260729_114606`.

⭐ **BOTH PANELS ARE FLAGS IN ONE SCREEN.** `showOsmPanel` (MVS:149) and
`showDownloadPanel` (MVS:225). `OsmImportPanel` is called at **MVS:962** — it is
not a route. So the whole round trip is state changes in `ConvoyMapViewerScreen`:
no navigation, no `ConvoyRoutes` entry, no `AreaDrawPurpose`. Fred 07-29:
*"if you close the import process as this is launched you will be on the planning
map, just need to refresh the position."*

**The trip:**
1. Row 3 SELECTED AREA writes `pending_import` with a null bbox, closes the panel.
2. `LaunchedEffect(showOsmPanel)` sees the close, reads DISK (R1 — nothing is
   passed), and if a record is awaiting a draw: positions the map on the state
   extent + 5% and opens the download panel with IMPORT OSM ticked.
3. User draws. `onAreaSelected` sets `downloadBbox` as it always has.
4. `LaunchedEffect(downloadBbox, …)` writes `setPendingBbox`, closes the download
   panel, reopens the OSM panel — where row 3 finds a bbox and GATES.

- ⭐ **THE DRAW COMPLETING IS THE SUBMIT.** No OSM execute button. Fred 07-29:
  *"relaunch import and close area selection when the area is processed."*
- ⚠ **`onAreaSelected` is a `@JavascriptInterface`** (MVS:480) with no slug and no
  coroutine scope — disk I/O there would run on the JS thread. It keeps doing only
  what it does today; the reaction happens in composable scope.
- ⛔ **OSM never touches `onExecuteDownload`**, so it cannot reach the download
  queue. An import measured in ROWS would poison the tiles-per-minute yardstick.
- ⛔ **THE 5% PAD WAS REMOVED — see the FIX 6 section below.** I claimed it
  "sidestepped" FIX 6 because `fitBounds` pads nothing. **Wrong** — the drift comes
  from padded values being SAVED, not from the fit function. Fred 07-29: *"if we
  remove your 5% of use fit we have no issues."* The OSM path now passes the raw
  extent.
- ⚠ **Padding is PER AXIS** — `(n-s)*0.05` and `(e-w)*0.05` separately. One figure
  would skew tall or wide states. Utah is nearly square so it would have hidden.
- ⚠ **`osmAwaitingSlug` is the guard** that stops a stray area draw from filling
  someone else's record.

## ⭐⭐ THE XREF FINDING THAT DE-RISKED THIS — the handoff already exists

Fred 07-29: *"i would use the navigation xref doc to identify the import trails
function and then the functions where used to trace what is called."* That found:

**`TrailImporter.kt` already has `writePendingArea`:645 / `readPendingArea`:668 /
`clearPendingArea`:680**, consumed by `ConvoyTrailSourceScreen:75/:83`. The
download panel writes a pending area to JSON, navigates, and the target screen
reads it back — **exactly what `OsmImportLedger.setPendingBbox` / `pendingBbox` /
`clearPendingImport` does.** MVS:1737 is the working template.

⭐ **The OSM handoff is the SECOND INSTANCE of a shipped mechanism, not a new
one.** Built from first principles it would have worked and nobody would have
known there was a pattern to match.

⚠ **FIVE coordinate orderings are now in play. Named arguments at every call
site, never positional:**

| Thing | Order |
|---|---|
| `OsmImportLedger` pending record | `s, w, n, e` |
| `OsmImportStage.trailExtent()` | `[s, w, n, e]` |
| `ImportScope.Area(...)` constructor | `south, west, north, east` |
| `ImportScope.asLedgerString()` | `west,south,east,north` |
| `DownloadBbox(...)` | `north, south, east, west` |
| `TrailImporter.writePendingArea(...)` | `north, south, east, west` |
| `fitBounds([S,N],[W,E])` | S,N then W,E |
