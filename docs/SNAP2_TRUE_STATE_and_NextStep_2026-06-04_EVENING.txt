THE ONE THING TO BE CLEAR ABOUT — snap-2 is NOT done
----------------------------------------------------------------
"snap-2" = the feature where route points SNAP TO TRAILS (a tapped point
adjusts onto the nearest trail/track geometry). 

THAT TRAIL-SNAPPING IS NOT IMPLEMENTED / NOT WORKING ON DEVICE.

What we actually built is the FRAMEWORK to get a route created and saved, using
the SIMPLE case: drop points -> STRAIGHT LINES between them -> name -> save to
spatial DB -> redraw. That framework works and is committed. It is the scaffold
that snap-2 will hang on. It is NOT snap-2 itself.

Plain status:
  WORKS (committed):
    - +ROUTE opens the Route+ toolbar
    - New Route -> name dialog -> Start (naming now on the New Route button)
    - Tap map -> drops points -> connected by STRAIGHT LINES (point-to-point)
    - Save -> writes route to spatial DB (insertRoute), redraws magenta,
      persists across a Routes toggle
    - Undo removes last point
  DOES NOT WORK / NOT BUILT:
    - SNAP TO TRAIL: points do NOT adjust to trail geometry. They stay where
      you tapped. The snap() call was wired into onMapTap in a patch and it
      COMPILED, but it was NEVER tested/proven on device, and the observed
      behavior is straight lines, not snapping. Treat snap-to-trail as
      UNPROVEN / effectively not implemented.

----------------------------------------------------------------
NEXT STEP — implement and PROVE snap-to-trail
----------------------------------------------------------------
This is the actual snap-2 work, on top of the working framework:
  1. Verify the snap path is even reached: does onMapTap call
     RouteManager.snap(...) and does it return a non-null SnapResult when a
     trail is on screen near the tap? Add a Log.d at the snap call and on the
     result; tap near a known trail; read logcat.
  2. Verify the viewport query feeds snap REAL geometry:
     queryTrailsByViewport / queryTracksByViewport must return rows with usable
     "geometry" for the current view. If the lists are empty (wrong bounds,
     zoom < display min, DB not init), snap has nothing to match -> always
     falls back to freeVertex (straight line). CHECK THIS FIRST — most likely
     cause of "no snapping."
  3. Verify snap math: snap() finds nearest point on a line within radius
     (30 m literal). If geometry is present but nothing snaps, the radius or the
     nearest-point math is the suspect (tune radius; check lat/lon vs lon/lat
     ordering in the geometry parse).
  4. Verify the snapped point is what gets added: snapToVertex(s) result must be
     the vertex added + drawn, not the raw tap.
  Prove on device: tap ON a visible trail -> the point lands ON the trail line,
  not at the fingertip. Only then is snap-2 real.
