THE ITEM KEY — a Julian date plus the description (JULIANKEY-2026-11-15)

Fred, 2026-11-15 07:47–07:48: "I would prefer a Julian method so we know how old the item is. the older, the less detailed and relevant the item is ... approaching to[o] months need to be reapproved and deemed still relevant" and "we could ma[p] entries on a Julian date so the description and the Julian date represent the item".

THE KEY IS C28-YYDDD PLUS THE DESCRIPTION. No sequence number — the description carries the rest of the identity, so nothing is ever renumbered and the tie to a commit cannot be broken by renumbering. C28-26319 is release 2.8, 2026 day 319 = 2026-11-15. Age is one subtraction, visible wherever the key appears. A commit closing an item reads DONE: 26319 <description>.

⚠ UNIQUENESS WITHIN THE DAY IS REQUIRED. Because the description carries the identity, two items created the same day must not be describable by the same words — otherwise nothing can tie a commit to one of them. When a match is ambiguous the tooling reports the ambiguity and refuses to guess, exactly as it refuses to infer anything else.

⚠ THE DECAY IS LOSS OF CORRECTNESS, NOT LOSS OF INTEREST. An item's problem definition and anticipated solution are written against the code AS IT WAS. After weeks of refactoring the file:line references may no longer resolve and the anticipated solution may name something that no longer exists. Measured examples from this week alone: the start-of-day script's "Droid 2 is on Utah time" note went stale in a day, and MBTilesStore's header still documents five tile types that have not existed since the vector move.

⛔ THE 60-DAY GATE. At 60 days an item is REAPPROVED OR DROPPED, and the review asks three specific things: (1) does the defect still exist, (2) do the file:line references still resolve, (3) is the anticipated solution still the right shape. Reapproval re-dates the item with a note; it does not silently extend it.

Grouping falls out of the key: the checklist is ordered by Julian day, newest first, so current work is at the top and items approaching the gate sink to the bottom where the review catches them. The document sorts itself by relevance.

The 127 KB imported verbatim from the master on 11-15 has NO keys yet. Items get a key as they are re-authored into this format — which gives that job a unit of progress: items WITH a key, versus prose still to read down.

3 · UPLOAD RULES

  • Only rider trails travel: source_id = RIDER AND shared = 1. shared defaults to 0, so a filter bug omits rather than leaks — the right failure direction for a licensing constraint. The rider-trail category exists to be this firewall.

4 · DOWNLOAD RULES — THE AREA IS THE UNIT

  • It is an ACQUISITION, not a sync — each source is authoritative for its own layer, so there is no merge and no conflict resolution in either direction.
  • THE RULES: trails update always · maps update always · the artifact list goes UP and only new artifacts come down. No timestamps, no versions, no cursors — the device's own list is the delta, which keeps the server stateless about the device.
  • Order: area create → area trails → rider created trails → tracks, routes and waypoints → maps. Base trails first because rider trails are matched against the real trails only (excludeRider = true).
