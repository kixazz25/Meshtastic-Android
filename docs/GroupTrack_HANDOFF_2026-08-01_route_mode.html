⭐⭐ THE GOVERNING SPECIFICATION — settled 07-31, do not re-derive

ConceptMeansRule
Persistencestate RECREATION — position, zoom, artifact display states, checked rowsBoth maps write on every screen refresh. Restores the map as you left it.
Route modeACTIVELY PLOTTING POINTS RIGHT NOW ⭐ FALSE ON EVERY MAP ENTRY, BOTH MAPS. Armed ONLY by user action — Route+, Draw, or a recovery Continue. Never by persistence.
Draft filea route was not finishedDrives a message and the resolver. Never arms anything.

THE TAP RULE, entire: route mode OFF → tap opens artifacts. Route mode ON → tap places a route point, nothing else consumes it.

⭐⭐ THEREFORE POPUPS NEVER NEED SUPPRESSING. If the tap does not reach the artifact layer, no popup can open. Every unbind / stash / restore / bind-gate in the codebase solves a problem that correct tap routing makes impossible.

⚠ Route mode is an ACTIVITY, not restorable state. A file on disk means a route is unfinished; route mode means points are being placed now. Conflating those two is the whole mess.

⭐ THE KEY DESIGN DECISION — file operations only

Fred: "we can even write a separate section of code for that instance that just renames or deletes the json without touching the route state."

The resolver renames or deletes a FILE. It does not open Route+, arm route mode, load geometry or draw a build line. That removes the whole reconciliation problem — entry sets route mode off, the prompt resolves the file, route mode stays off.

⚠ And it likely makes :1472 deletable — the recovery arming exists to RESUME a draft, and if resolution does not resume, nothing needs it. Confirm with the step-1 toast first.

The logic

unnamed draft exists?
  no        → return
  <2 points → delete silently, LOG IT, return
  ≥2 points → prompt: Save (name it) / Discard
              → rename or delete the file
              → return

⭐ The <2-point silent discard matters: a draft with one point or none carries nothing worth recovering, and prompting for it is noise. ⚠ But log it — it is the only trace that a crash occurred, and losing it hides how often that happens.

Called from TWO places

Planner entry and Route+ launch. One resolver, two callers. ⭐ Route+ cannot start with the slot occupied because the resolver has already cleared it — the unnamed slot is single-occupancy.

⚠ Named drafts do NOT block Route+. They are parked, not in the way.

⚠ "Save" here means keep the file and give it a name — not "resume and save properly". So it needs the route-name dialog, not a plain confirm. Label the button to match.

⚠⚠ THE HARD REQUIREMENT — visible + snappable + non-interactive

During a route draw you must SEE trails, SNAP to them, and NOT TAP them. Three concerns the code currently collapses into one flag.

⛔ Hiding layers is not a workaround — snap is fed from queryTrailsByViewport, and with trails hidden there is no snap and no guidance. Tracks were removed from snap on 07-30 (snapTrailsOnly — a track is one geometry, so snapping pulled the whole thing).

⚠ And the SVG approach will not work. sub._path.style.pointerEvents — the line commit 43ab77e16 deleted — is an SVG DOM property, and both maps moved to L.canvas on 07-31. Canvas paths are not DOM elements. The canvas mechanism is:

lyr.eachLayer(function(sub) { sub.options.interactive = !on; });

⚠ VERIFY THIS FIRST — it is the one unknown between the spec and the patch. Stateless, survives layer rebuilds, and replaces the stash/restore block entirely.

⚠ Trails have no onTrailTap bridge on either map — they can only ever produce a popup. That is a gap, not a bug.

⛔ Route drawing is BLOCKED as of 07-31. Before canvas the tap was SHARED (popup AND vertex — messy but usable); now the artifact consumes it and no vertex lands. ⚠ Canvas did not break the suppression — it removed the accident that was masking it. Reverting canvas is the wrong trade: it would restore a broken mechanism to a merely tolerable failure mode while giving back the trail hit-rate fix (3 hits in 40 taps at z18).

🔴 STEP 5 — HIDDEN ARTIFACTS CONTRIBUTE NOTHING

Fred: "hide keeps them from being placed on the map, not just invisible" — a hidden type must not participate in taps, proximity, snap or selection. Visibility IS the selection.

Observed defect

Trails OFF, tap a track on the planner, get a list of TRAIL names.

Cause: hideTrails() does map.removeLayer(trailLayer) and sets trailsVisible = false — it does NOT null the variable. The proximity scan at grouptrack_map.html:831 calls checkLayer(trailLayer, …), which skips only on null. A detached-but-populated layer is still fully walkable.

⚠ It also explains "occasionally the detail panel instead" — the scan is a MAP-level click handler racing the layer's own handler.

⚠ And behaviour depends on HOW you turned it off: clearTrails() nulls the variable, hideTrails() does not.

The fix

⛔ Do NOT null on hide — the retained variable is a CACHE. loadTrails rebuilds from a fresh GeoJSON payload, so nulling means a full query and rebuild per toggle. At 10,000 trails that is a visible cost.

function checkLayer(layer, visible, typeName, color) {
  if (!layer || !visible) return;

Four call sites, both maps. Correct regardless of which path turned the type off.

⚠ There is also a DUPLICATE proximity scan — a pure-JS copy at :813 running alongside the restored Kotlin path, so two popups race per tap. Knowingly accepted on 07-30. A third, dead copy sits at :74-123 inside a src-bearing script tag whose inline content the browser ignores.

⚠ NAMING COLLISION — know this before reading the code
