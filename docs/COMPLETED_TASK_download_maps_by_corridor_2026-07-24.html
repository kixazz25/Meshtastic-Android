The full record for the corridor feature, from the measurement that motivated it through the cutover that retired the bbox path for tracks. The Living Master entry is gone — this is the record. The headline

PROVEN ON DEVICE Tester track "bar 10" — the ~100-mile figure-7 that started this whole investigation:

ModelTiles queued (3 sources)Notes
bbox (old)1,000,000+~95% empty desert; Fred: "8 hours to download an area that will not be ridden"

≈90% reduction. Built, queued and downloaded end to end on the planning map. G1–G4 all compiled first try (14m03s).

⚠ Three caveats that must travel with this number.

  • Bar 10 is the BEST CASE. It is the longest, thinnest track available, so it shows corridor at its most favourable. A compact track's bbox is already close to its corridor and the gain there will be modest. When quoting this to testers, say so — the headline comes from the worst-shaped track.
  • This is BEFORE the z-cap. If TOPO+ really tops out at z15, a meaningful slice of its 21,000 is requests that will 404. That saving compounds on top of this one and must be measured separately — two variables, two measurements.
  • The 894,507 planning baseline was not the comparable number. 894,507 was sizeTiles (the SAT-sizing figure); the real bbox total queued across all sources was higher, over a million. The two were never the same quantity.

The 65K/21K/21K split is per source and uneven because of layer counts, not different geometry — same corridor, SAT carrying 3 layers where the others carry fewer.

Why bbox was the wrong model

Measured 07-23. Bar 10 is a single path ~100 miles long with a ~10-mile spread at the top — "like a figure 7". It alone accounted for 22% of all tiles in a 10-track import (894,507 sizeTiles → 18 cells per source). Its bounding rectangle is ~100×10 miles while the ridden corridor is ~half a mile wide.

⚠ Segmentation was never the bug. Every split in the 07-23 trace satisfied ceil(sizeTiles/50000) exactly. Four theories died on inspection before the real finding landed. The MODEL was wrong, not the math — which is why no amount of tuning the splitter would ever have helped.

⭐ THE RULE

Anything TRACK-based or ROUTE-based submits a CORRIDOR download. User-DRAWN area downloads keep the BBOX. The user drew a rectangle → the rectangle is the request. The user picked a track or route → they want the line and its immediate surroundings, not the rectangle enclosing it.

Architecture — the decisions that shaped it

⭐⭐⭐ downloadType SELECTS THE WORKER

Fred: "so the downloadType would specify the worker. great design when we get to the delete function." launchWorker dispatches on type and enqueues a different Worker class — dispatch at the boundary, not a branch inside shared logic (patch F).

DownloadTypeWorker
AREAConvoyDownloadWorker
CORRIDORConvoyCorridorWorker (new)
MAP_SOURCE_REFRESHConvoyDownloadWorker (refresh branch)
DELETE_AREA_TILESConvoyDeleteWorker (when written)

⭐ Why declaring the 4th enum value early paid off. Delete removes tiles rather than fetching — opposite direction, different completion semantics, no network. A shared-worker model would need a flag threaded through a download worker plus branches inside it. With type-selected workers it is simply a third worker that never touches the network, and nothing existing changes. It also makes priority 0 coherent: deletes run first because they free storage.

⛔ CORRIDOR IS NOT FITTED INTO THE AREA MACHINERY

Claude drifted there twice — first a downloadType parameter threaded through submitDownload, then "add a branch to ConvoyDownloadWorker" — and Fred overruled both: "why are we fitting this into the area download box. it is its own code? does not exist?" and "convoy download worker would be replaced by a corridor version?" None of the corridor path existed; it is all new code ALONGSIDE the area path. ConvoyDownloadWorker was not touched.

⭐ Only TWO shared artifacts were affected

  1. QueueEntry gains geomHash: String = "" so an entry can name its track — written only by the corridor process, read only by the corridor worker, therefore inert to everything else. Existing readers use opt* defaults and ignore unknown keys; the four existing construction sites needed no edits.
  2. launchWorker picks the Worker class by type.

That is the whole footprint. Buffer width needs no field — it is a constant (the half-mile getTrackBbox already uses).

⭐ What the entry carries — Option B

⛔ Run-boxes were RULED OUT. Fred: "cannot use boxes, the startup time for new area requests is long 5-10 seconds added to every new bbox request. not workable." 30 run-boxes = 3–5 minutes of pure startup overhead before a tile moves — worse than the problem being solved.

⛔ Option A (serialize the tile list into the entry) was REJECTED — a 60K-tile list is megabytes per entry in download_queue.json, the one file with no recovery path on a release build.

⭐ Option B shipped: the entry stores a geometry reference — geomHash + downloadType=CORRIDOR (+ bbox for display/progress). The worker re-derives the tile list at run time. Startup cost is paid once per corridor entry, not per box.

Persistence concern is mitigated by hasTile(): the mbtiles store is the source of truth for what is already down, so a corridor entry re-derives its list on resume and simply skips what landed. The tile list never needs persisting.

⚠ Accepted duplication — deliberate, and it has a cost

ConvoyCorridorWorker duplicates progress (updateProgress), completion (markComplete), notifications, and the downloadTiles call. Different tile derivation, same plumbing. Cost: a change to any of that plumbing now lands in two places. Traded deliberately for the clean split — but see the open refresh-completion issue below, which is exactly this cost coming due.

Derivation — the model

The standard GIS name is buffering a linestring, but for tile downloading no polygon is needed: walk the line's points and, for each, emit the tiles within the buffer radius at each zoom, deduped into a SET. Overlaps and self-intersections (the figure-7 doubles back on itself) collapse automatically. No join geometry, no self-intersection cases.

  • Buffer width = the same half-mile the bbox path already used — getTrackBbox pads 0.00724° lat and 0.00724/cos(midLat) lon (SpatialDbManager:1915). Keeping the same value made the PoC directly comparable to the old baseline.
  • ⚠ WKT coordinate order is lon lat — SpatialDbManager:1763 flips with parts[1], parts[0]. Getting this backwards puts the geometry in the wrong hemisphere.
  • Geometry shapes: tracks are MULTILINESTRING or LINESTRING; routes are plain LINESTRING. Parse model copied from wktToGeoJsonCoords (SpatialDbManager:340-361), which handles both — strip prefix/suffix, and for MULTI split on "),(" then trim parens. It returns a JSON string so it was not directly reusable; a sibling returning POINTS was written instead.
  • ⭐ MULTILINESTRING matters: disjoint segments are walked separately and buffered independently. That is precisely the case where the bbox spans the empty gap between segments and the corridor does not.

⭐ The corridor worker filters PRE-FETCH

The open question from 07-23 — does hasTile() skip the request or only the write? — resolved: MBTilesStore.hasTile is at MBTilesStore.kt:136; ConvoyDownloadWorker:61 filters and sizes totalTiles off the filtered list (:65), so the refresh branch genuinely skips requests, while the main path (:111-117) has no filter at all and downloads everything.

So the corridor worker copies the :61 pattern. Without it a resumed corridor would re-request every tile from Esri and only then find it already had them — full network cost paid twice, real money on per-tile pricing. It also makes totalTiles honest: remaining work, not the whole corridor.

The cutover (patch H) — two decisions worth keeping

1. The area button was DELETED, not flagged off

The side-by-side existed to produce the comparison, and it has. Leaving a disabled path behind is exactly how gridCells and downloadMapsForTrackHash both survived their own replacements and later masqueraded as live code — two dead functions this project has already had to chase down.

The onDownloadMaps parameter stays on the composable — the two screens still pass it and removing it would touch call sites for no benefit — but nothing renders it, so the area path is unreachable from the artifact panel. Deleting the parameter is a separate cleanup if it ever matters.

2. The import swap was a LOOP, not a substitution

The old call was one submitDownload covering all slots. Corridor is one entry per source, so the import loops the slots. Everything needed was already in hand at ConvoyTrackOps:586 — gh (computed one line earlier), downloadMapSlots, replaceExisting. getTrackBbox is no longer called there.

⚠ Ten tracks × three sources = 30 queue rows, not 10. That is the same shape the area path already produced (submitDownload looped slots internally), so the panel needed no change — but the row COUNT is per track per source, and testers will see it.

⚠ enqueueCorridor DERIVES the corridor to get its tile count, so a large import does that work per track per source on the IO thread. Already an IO thread at that call site, so no new threading — but a 10-track import will spend real time in derivation before the first tile moves. If that reads as a hang to a tester, it isn't; it is the cost Option B deliberately pays once per entry instead of 5–10s per run-box.

Untouched: area downloads from the map (draw-a-box) work exactly as before. The cutover changed only the artifact panel and the importer.

⛔ Patch I — a wrong diagnosis worth recording

The bug: the shared ConvoyDownloadConfirm popup renders mid-panel on CONVOY and overflows the bottom — its buttons unreachable unless the device is rotated to landscape. Planning shows the same dialog centred and fully accessible.

The diagnosis (wrong): one missing modifier.

convoy    ConvoyScreen.kt:2014        modifier = Modifier.padding(16.dp)
planning  ConvoyMapViewerScreen:1569  modifier = Modifier.align(Alignment.Center).padding(16.dp)

It looked like the same drift pattern as the 07-22 queues-panel width bug — two hand-mirrored call sites where one lost a modifier the other kept. Patch I simply added .align(Alignment.Center) to convoy's chain.

It did not compile: 'fun Modifier.align' cannot be called in this context with an implicit receiver.

The real cause: Modifier.align() is a BoxScope extension — it only exists inside a Box. Planning's dialog sits in a Box; convoy's sits in a Column (ConvoyScreen ~1495). The missing modifier was never drift between mirrored call sites; it was a consequence of different containers.

⭐ THE LESSON: the symptom matched a known bug, the cause did not. Pattern-matching to a bug this project has already seen is a hypothesis, not a diagnosis — and here the previous bug's shape actively misled, because the fix that worked last time was scope-illegal this time.

Patch J — bring a Box rather than borrow scope

Box(Modifier.fillMaxSize(), contentAlignment = Alignment.Center) {
    ConvoyDownloadConfirm( ... )
}

contentAlignment centres the child without needing the scope extension, so it works regardless of what encloses it. fillMaxSize makes the Box the whole viewport, so "centre" means centre of the screen — which is what stops a tall dialog running off the bottom. The dialog's own modifier = Modifier.padding(16.dp) was left alone; only its placement was ever wrong.

Anchor design note: patch J's anchor spans the whole call — open paren through the closing brace of the enclosing if — so the wrapper's braces cannot land in the wrong place. That is the one way this class of fix fails twice.

⚠ Convoy freeze — why this was allowed. ConvoyScreen.kt is frozen, but the freeze protects a LAYER, not the file: the Kotlin↔JS↔Leaflet↔self-saving-setView↔shared-MapStateStore tangle. This is a Compose layout wrapper around an overlay dialog — nothing near the WebView, the JS bridge, or map state. Same reasoning as the 07-22 queues width fix, which shipped clean.

The route corridor is a NEW capability with nothing legacy to preserve — build it right the first time, no migration risk.

Open items this task leaves behind

These are live in the Living Master; recorded here so the corridor context travels with them.

  • OPEN Refresh does not log as a completed job (found 07-24). Bears directly on the corridor ETA — see the Living Master entry. The accepted per-worker duplication means completion is called separately by each worker, so this class of miss can exist independently in ConvoyCorridorWorker.
  • OPEN Per-source z-level download limits — maxZoomForSource() is a stub returning DOWNLOAD_ZOOM and ignoring its argument, so everything pulls to z18 including sources capped at 15. corridorTiles inherits the same gap — it has no source awareness either, so fixing the stub alone will NOT fix corridor; the source must be passed in.
  • METHOD The xref docs index declarations. onDownloadMaps is a lambda parameter and appears in none of them — same class as the earlier @JavascriptInterface miss. xref for candidates, grep for call sites.

Durable lessons

  • When the math is right and the answer is still wrong, check the MODEL. Segmentation was provably correct at every split; the rectangle was the wrong shape for a line. Four theories died before anyone questioned the geometry.
  • Dispatch at the boundary, not inside shared logic. Type-selects-worker meant corridor cost two shared-artifact changes and touched ConvoyDownloadWorker not at all — and delete-area now costs nothing existing.
  • Delete the replaced path in the same commit. This codebase has already been misled twice by dead functions that outlived their replacements.
  • A matching symptom is not a matching cause. Patch I failed because the previous bug's fix was scope-illegal in the new container.
  • Measure one variable at a time. The corridor number and the z-cap number must not be taken together, or neither is attributable.
