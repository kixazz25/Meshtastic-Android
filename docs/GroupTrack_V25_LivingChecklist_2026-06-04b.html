E3. WRITE-FUNCTION DATA CONTRACT (so in-progress JSON mirrors it)

The completed-save consumes the RouteManager VERTEX chain (the only true source of shape). Each Vertex: lat, lon, lineId(String?), lineType(String?), segmentIndex(Int, -1 if free), t(Double 0..1), snapped(Boolean). It produces wkt + bbox via buildWktAndBbox and writes insertRoute(name,wkt,bbox...). The completed DB row stores ONLY wkt+bbox+name (resolved geometry) — it throws away HOW the route was built.
The DRAFT (in-progress) JSON must NOT throw that away — it stores the FULL vertex list so resume = true editing (undo to a snapped vertex, know which legs ride a trail, re-slice), not redrawing a frozen line. wkt is always re-derivable from vertices; the reverse is not. Draft schema (future build): 
{ schemaVersion, draftId, name|null, createdAt, updatedAt, method,
  vertices:[ {lat,lon,lineId|null,lineType|null,segmentIndex,t,snapped}, ... ] }
  // NO wkt/bbox in draft — DERIVED at graduation by replaying buildWktAndBbox.
RESUME = parse → addVertex(Vertex(...)) each → drawBuildLine. GRADUATE = identical Build-1 onSaveCompleted path + delete draft JSON. The ONLY writes ever: create draft JSON (Save in-progress) · overwrite draft JSON (Save with changes) · insertRoute+delete-draft (Save as completed, graduation). A route is EITHER a draft-file OR a DB-row, never both.

E4. ENGINE FRAMING (route creation is its OWN complex birth process)

STATES: Route(base) → New → In Progress → Completed. ACTIVITIES: Save, Discard (drive transitions). CONDITIONS: ≥2 pts? · new vs resumed · draft-on-disk? · delete-saved=NO · resave=YES may ALIAS per §K/§L. ACTIONS (reusable black boxes, params+execute): JSON write/open/delete · spatial-DB add/update/delete. Everything in-memory until deliberate Save. Each artifact has its OWN creation process — route is the COMPLEX one (heavy human contact); importing a trail / dropping a waypoint / recording a track are different. Completed tracks have their own lifecycle too (later).
