GroupTrack — Reinstall Procedure

Protecting map and trail data across an uninstall / reinstall · 2026-08-03
Manual procedure. Automation is a separate discussion.

Why this procedure exists

The failure it prevents

On 2026-08-01 a reinstall destroyed the spatial database — roughly 89,000 trails. The mechanism:

  1. The app was reinstalled over existing data in Documents/GroupTrack/.
  2. Android showed All-Files access as GRANTED — the grant record survives an uninstall because the package name is unchanged. The new install did not actually hold that authority; the OS denied at the filesystem layer while the permission screen reported it on.
  3. The app therefore could not read the existing databases, and its create-if-missing open wrote empty schemas over them.
  4. It then reported 0 trails, 0 tracks, 0 waypoints, 0 routes as though that were normal.

Why it cannot simply be checked for

Environment.isExternalStorageManager() returns true in this state and is wrong. The permission API reads the stale grant record; the filesystem enforces the truth. There is no API question that returns the right answer.

And the ordering cannot be fixed by blocking startup: the app must run before it can be granted authority, so refusing to start until it can read would deadlock a reinstalled device permanently.

Hence a procedure: put the data out of reach until the app has been granted authority properly.

What is at risk

The data surviving is why the failure is possible. It is still there after an uninstall; the app just cannot see it, and then overwrites it. There is no backup — the map databases are 50–60 GB.

⭐ THE PROCEDURE

⛔ Do this BEFORE the install, not after

Once the app has run and written blank databases over the real ones, renaming is too late. The rename must happen while the app is uninstalled or before the new install is launched for the first time.

STEP 1 — Rename both data directories. Using X-plore or any file manager: 
Documents/GroupTrack   →   Documents/GroupTrack.bak
My Tracks              →   My Tracks.bak
Renaming is instant regardless of size — it does not copy 50–60 GB. Do not move them to another volume.
STEP 2 — Confirm the originals are gone. There must be no Documents/GroupTrack and no My Tracks remaining. If either still exists, the app will find it and the procedure has not worked.
STEP 3 — Install the app. 
adb -s [serial] install -r [apk]
Plain -r, never -d. If it prompts first-install questions on an already-installed app, cancel — that is a version-code regression, a separate problem.
STEP 4 — Launch the app and let it complete first run. It will create fresh, empty GroupTrack and My Tracks directories. This is expected and is the point of the procedure — it is creating blanks in a place where there is nothing to destroy.
STEP 5 — Grant All-Files access, properly. Settings → Apps → GroupTrack → Permissions → Files and media → Allow management of all files.

⚠ If it already shows as granted, toggle it OFF and back ON. A stale grant record from the previous install is exactly the condition that caused the data loss. Toggling forces a real re-grant.

STEP 6 — Verify the app actually has authority. Do not trust the Settings screen. Confirm the app can genuinely read and write: open a map, record a short track, or check that it lists what it created in step 4. A behavioural check is the only proof.
STEP 7 — Close the app completely. Force-stop it. It must not be running while the directories are swapped.
STEP 8 — Delete the blank directories the app created. 
Documents/GroupTrack     ← delete (the empty one from step 4)
My Tracks                ← delete (the empty one from step 4)
⚠ Check they are empty first. If either contains anything you created between steps 4 and 7, move it aside before deleting.
STEP 9 — Rename the backups back. 
Documents/GroupTrack.bak   →   Documents/GroupTrack
My Tracks.bak              →   My Tracks
STEP 10 — Launch and verify the data is back. Check the trail count, the tracks list, and that maps draw from the stores. A count of zero means stop and investigate — do not download, do not import, do not let the app write anything until it is understood.

Verification commands

Before starting — record the current sizes so you can compare afterwards:

MSYS_NO_PATHCONV=1 adb -s [serial] shell ls -la /sdcard/Documents/GroupTrack/*.db
MSYS_NO_PATHCONV=1 adb -s [serial] shell ls -la /sdcard/Documents/GroupTrack/maps/

After step 9 — the same command must show the same sizes. A spatial DB in the hundreds of KB rather than tens of MB means it has been replaced with an empty schema.

If the procedure was missed

Symptom: the app reports 0 trails / 0 tracks after a reinstall

Stop immediately. Do not download, import, or record anything — every write makes recovery harder.

Check whether the databases were actually overwritten or are merely unreadable:

MSYS_NO_PATHCONV=1 adb -s [serial] shell ls -la /sdcard/Documents/GroupTrack/*.db
  • Tens of MB — the data is intact and this is an authority problem. Grant All-Files (toggle off and on), restart, re-check.
  • Hundreds of KB — an empty schema has been written over it. The map stores (.mbtiles) are usually still intact since they are opened differently; the spatial DB is not recoverable without a rebuild.

⭐ A complete data-model rebuild — OSM import, trails, tracks, waypoints — was measured at under one hour on 08-01. Painful, not fatal.

Related, and still owed in code

This procedure protects whoever remembers to run it. Two code changes protect everyone else, and neither blocks anything:

  • REFUSE-TO-CREATE. SpatialDbManager must never create-if-missing on a path it cannot verify. A failed open must abort, not write an empty schema. This alone would have prevented 08-01 and costs nothing at runtime.
  • ROW-COUNT SANITY + .lastgood copy. After each successful startup, copy the DB. A startup reporting zero rows where the previous run reported 89,000 is a red flag the app should raise, not report as normal.

⚠ Also outstanding: SpatialDbMgr logs the literal ${spatialFile.absolutePath} — string interpolation is broken, so the DB path never appears in the log. That is the diagnostic that would have made the 08-01 loss obvious immediately.

Why the rename works when checking does not

Every detection approach fails because the app creates blanks before authority arrives, and the permission API reports the wrong answer at exactly that moment. The rename does not detect anything — it removes the data from the path the app will write to until authority is real. Nothing to detect, nothing to destroy.
