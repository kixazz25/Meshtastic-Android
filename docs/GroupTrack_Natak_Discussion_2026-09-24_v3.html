GroupTrack + Nucleus — discussion document

v3, 2026-09-24 (evening). For the Thursday call with Nathan (Natak). Section 7 is what was proven on devices today; v3 adds the TAK test and two new questions (send interval, fixed frequency slots).

1 · Where GroupTrack is today

  • One JSON file per ride. A ride leader creates it once; it is emailed to riders; every apply, on every device, starts from it. A real sample from our app was sent on 09-23.
  • Names: a network's id is also its Meshtastic channel name and its Wi-Fi SSID. A rider's callsign is also their radio's long name, taken from their own GroupTrack profile.
  • Ride networks: id Group + 6 generated characters, an explicit 256-bit key, and a Wi-Fi password (proposal: a real word of 8+ letters, new each ride).
  • The GroupTrack default network (setup and home network, never used for riding): channel GroupTrack. Set and verified on a real T1000-E on 09-23; two radios on it see each other.
  • Apply: GroupTrack writes only the fields it manages; it records the radio's full configuration before and after, and reports any other differences to the user rather than changing them.

2 · Boot profiles and reaching a unit

A Nucleus will serve more than GroupTrack. We would like each unit to hold a small set of boot profiles and start in the selected one:

  1. GroupTrack default
  2. GroupTrack last used (the last ride config applied)
  3. Your team configuration
  4. Meshtastic local emergency net
Questions. How is the boot profile selected today (API, setting on the unit, physical control)? Can GroupTrack set it? If your apply restarts the unit, does it come up in the new config even when the boot profile is "default"?
Reaching a unit on a ride network: with internet, your tailnet (what does a tablet need to join it?); without internet at a trailhead — boot profile 1, or GroupTrack kept up permanently beside the ride network? Can a unit run two Wi-Fi access points at once plus its mesh between boxes? Can its radio keep GroupTrack as a secondary channel while the ride is primary?

3 · Apply — your code as our model

Our new apply for app-attached radios: a config-only factory reset (keeps Bluetooth pairing), then the required fields written: region, modem preset, hop limit, TX power, frequency slot, channel name, key, role, owner (long name = callsign), with psk_random off and owner_short not written.

Request. A sample of your code that applies config to a radio (any language). What we most want to match: the write order and whether you batch in one admin session; set-channel vs channel URL; reboot, reconnect and how you confirm the values took; anything learned the hard way (firmware differences, ordering, timing).
Also: the endpoint and exact format for an apply request; a token on write requests; your values for meshName and wifiChannel; the length limit on owner.
Send interval: how often a radio reports its position (GPS or TAK) is not among the eleven fields. After a config-only reset it falls back to the firmware default, which is infrequent. What sets the position / TAK send interval on your radios -- does your apply write it (and smart-position settings) too?
Frequency slot: do any of your units run a fixed frequency slot? Every ride file carries frequencySlot 0 (frequency derived from the network name); a unit pinned to another slot would be on a different frequency and hear nobody, so the file's value must win at apply.

4 · Traffic in the mixed network

  • Each device transmits once, in one message type: app-attached radios send TAK-format messages only (their own position broadcast off); standalone T1000-E radios send Meshtastic position only; devices on the Nucleus Wi-Fi send TAK-format messages on the multicast groups you named (239.2.3.1:6969, 224.10.10.1:17012).
  • No device translates one type into the other (that would double airtime). Every GroupTrack app reads both and shows one entry per device.
  • Radios relay all traffic on the channel, keeping the original sender's node number.
Proven today: one radio in TAK_TRACKER role (sending TAK PLI on port 72) and one in TRACKER role (sending ordinary position on port 3), on the same ride channel. Both tablets showed both radios moving; a tablet following the TAK radio as its lead drew its track; tracks saved normally. GroupTrack turns an incoming TAK position into the same node position a GPS report produces, so every existing feature works on either.
Our direction: standalone radios may use TAK_TRACKER (cadence set in the radio); app-attached radios will have the app compose and send the TAK message, so the send interval can adapt while riding (moving vs parked, group size) without rewriting the radio's config.
Questions. When your bridge relays a TAK packet over LoRa, does the Meshtastic from show the Nucleus's radio or the original sender? Does the bridge carry ordinary Meshtastic position packets (port 3) as well as TAK? Which TAKPacket-SDK version do you run, and do V2 packets on port 78 pass through firmware 2.6.11? In pli.speed, what is the unit (m/s?)? pli.altitude is HAE — do you convert to sea level anywhere?
On the Wi-Fi side: what exactly does your box put on 239.2.3.1:6969 -- CoT XML events, TAK protobuf, or both? Which fields does it fill (uid, callsign, point, track, group), and is the uid stable per device? We will receive it on the tablet and treat it exactly like the LoRa TAK report.

5 · Airtime, preset, range and group size

Airtime is set by the modem preset and the packet size, not by the device: any radio at the same preset takes the same time. Calculated with the standard LoRa (Semtech) formula, coding rate 4/5 to 4/8:

Preset30-byte packet50-byte packet80-byte packet
LONG_FAST (SF11, 250 kHz)0.48–0.63 s0.64–0.89 s0.85–1.2 s
MEDIUM_FAST (SF9, 250 kHz)0.13–0.17 s0.18–0.25 s0.24–0.35 s
SHORT_FAST (SF7, 250 kHz)0.04–0.06 s0.05–0.08 s0.08–0.11 s

A position is roughly 30–50 bytes on air; a TAK V1 packet roughly 50–80 (callsign strings); V2 compression narrows the gap. The figures we had seen (≈0.25 s GPS, ≈0.09 s TAK) match MEDIUM_FAST and SHORT_FAST respectively — so most of that difference is the preset, not the message type.

Channel load = riders × airtime per report ÷ interval. At a 3-second interval, keeping the channel under a practical ~35%:

PresetAirtime per report (typical)Riders at 3 s within ~35%
LONG_FAST≈0.64 sabout 1–2 (2 radios ≈43%, 4 ≈85% — saturated)
MEDIUM_FAST≈0.18 sabout 5–6
SHORT_FAST≈0.05–0.08 sabout 13+

Range trade (published comparison for the T1000-E, to be verified in the field):

LONG_FASTSHORT_FAST
Typical direct range (T1000-E)2–4 miles0.5–1 mile
Ideal line of sight7+ miles≈2 miles
Sensitivity−133 dBm−121 dBm (12 dB less)
Throughput≈1.07 kbps≈10.9 kbps
Constraint: every radio on a ride channel must use the same preset — it is part of the channel, like the name and key. On one ride, standalone T1000-E riders and TAK riders share one preset, so a fast preset shortens the T1000-E's already antenna-limited range.
Working plan (field test in Utah, January): small group with T1000-Es → LONG_FAST, 5 s, smart position; mid-size → MEDIUM_FAST; larger group with a Nucleus → SHORT_FAST. The preset is a per-ride value.
Questions. For your 0.09 s and 0.25 s figures: which preset, how many bytes, V1 or V2, measured or calculated? Which preset do you run, and what range do you see on it in the field, in what terrain? What antennas do your radios use? What group size do you plan for at a 3-second interval?

6 · A radio-only unit with an external antenna, to replace the T1000-E

The T1000-E is the only standalone radio GroupTrack supports, and we intend to sunset it: its credit-card antenna limits range on every preset, and most of all on the faster presets that larger groups need. Would Natak package a radio-only unit with an external antenna as its replacement?

What it would need to do for GroupTrack riders:

  • Meshtastic firmware at a version we can pin, and configurable by GroupTrack's apply over Bluetooth or USB (same fields as section 3).
  • GPS on board, so it can report position as a standalone radio, and pair with the GroupTrack app to send TAK-format messages when a phone is attached.
  • An external antenna connector — vehicle-mounted antenna for UTVs, a whip for riders.
  • Power: 12 V vehicle power with a battery for off-vehicle use.
  • Built for OHV use: dust, vibration and water resistance; a mount.
  • Ships on the GroupTrack default (channel GroupTrack), ready for any GroupTrack user to set up.
Questions. Is this something you build or would build? Which radio module and antenna options? Expected range on LONG_FAST and SHORT_FAST with the external antenna? Rough unit cost, lead time and volumes? Could it run the same boot profiles as a Nucleus?

7 · Proven on devices, 2026-09-24

  • A ride created on a tablet drives real radios. A ride was created from a route on the planning map, stored as its JSON file, and applied from that file to two T1000-E radios. Both radios landed on the ride's own network (id GroupC9K7XE, the ride's generated 256-bit key, LoRa values from the file) and exchanged positions and text.
  • The GroupTrack default is set from a real radio: channel GroupTrack, frequency derived from the name, and two radios on it see each other. Our apply of the default is the base; a ride's apply is the overlay.
  • The ride file travels by email. Sent from one tablet as an attachment (proven). On the receiving tablet it is stored unchanged and its route (with trailhead, recipe and narrative) comes in through our normal import, and the maps for the route's corridor download (proven, including from a cold start).
  • The rider's own radio, from the emailed file. The receiving tablet applied the imported ride to its own radio; both radios landed on the ride's network and exchanged positions and text.
  • TAK and GPS together. A TAK_TRACKER radio and a TRACKER radio on one channel: both seen moving on both tablets, the lead track drawn from TAK data, tracks saved (see section 4).
  • Ride lifecycle, settled: a ride is planned (a name), in progress, completed (route, trailhead, future date, description) and then sent. Once sent, only its date, time and description change; its network never does. Resending to late riders is always allowed.
  • Not yet: the app sending its own TAK messages (next), receiving CoT on the Nucleus Wi-Fi, and the minimal apply for app-attached radios and the Nucleus -- which is why section 3 asks for your apply code.
What this means for the Nucleus: every value your apply needs is already in the ride file's network block, generated once per ride and carried unchanged to every device. Nothing on your side has to generate or derive anything.
