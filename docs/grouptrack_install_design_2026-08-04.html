GroupTrack — Install & Reinstall Design

Design conversation, 2026-08-04 · NOT BUILT — this is the agreed design, not code
Supersedes the manual-only approach in grouptrack_reinstall_procedure_2026-08-03.html, which remains valid as the fallback for anyone who does not use the in-app path.

1 · The problem this solves

What happened on 2026-08-01

A reinstall destroyed the spatial database — roughly 89,000 trails. The mechanism:

  1. The app was reinstalled over existing data in Documents/GroupTrack/.
  2. Android reported All-Files access as GRANTED — the grant record survives an uninstall because the package name is unchanged. The new install did not actually hold that authority; the OS denied at the filesystem layer while the permission screen said otherwise.
  3. The app could not read the existing databases, and its create-if-missing open wrote empty schemas over them.
  4. It then reported 0 trails, 0 tracks, 0 waypoints, 0 routes as if normal.

⚠⚠ There is no backup. The map databases are 50–60 GB.

Why the obvious defences do not work

The permission API cannot be trusted. Environment.isExternalStorageManager() returns true in this state and is wrong. It reads the stale grant record; the filesystem enforces the truth. There is no API question that returns the right answer — only a real read attempt does.

Blocking startup until the app can read would DEADLOCK the device. The app must run before it can be granted authority, so refusing to start until it can read means a reinstalled device can never be recovered. This was proposed and correctly rejected.

The app cannot act at uninstall time. Android has no uninstall hook. ACTION_PACKAGE_REMOVED is broadcast to other apps — your own process is already gone. A companion app could hear it, but only after removal, which is too late to be useful: the danger is not the uninstall, it is the next install running blind.

2 · ⭐ The design — GroupTrack triggers its own uninstall

The key realisation

The app can uninstall itself. Intent.ACTION_DELETE / ACTION_UNINSTALL_PACKAGE launches the system uninstall dialog — and at that moment the app is alive and holds authority. So it can do the dangerous bookkeeping itself, while it still can.

That converts the ten-step manual procedure into two taps.

The flow

1 · User taps "Prepare for reinstall" in the app.
2 · The app renames its own data directories — it has authority right now, so this simply works: 
Documents/GroupTrack  →  Documents/GroupTrack.bak
My Tracks             →  My Tracks.bak
Renaming is instant regardless of size — it does not copy 50–60 GB.
3 · The app fires the uninstall intent on itself. The user confirms the system dialog.
4 · User installs the new build and launches it. The app finds no GroupTrack/, creates fresh empty directories, and completes first run. This is expected and is the point — it is creating blanks where there is nothing to destroy, because the real data is out of reach under .bak.
5 · The All-Files grant is requested FIRST, before anything touches the database. See §3 — this is the ordering half of the design and it matters as much as the rename.
6 · After the grant, the app attempts a REAL READ of the .bak directories. Not isExternalStorageManager() — an actual read. That is the only proof that authority is real.
7 · If the read succeeds and .bak exists → prompt: "Found your previous data. Restore it?"
8 · On confirm: verify the blank directories are EMPTY, delete them, rename the .bak directories back.

⚠⚠ THIS IS THE REVERSE-RISK MOMENT. Everything up to here protected against overwriting real data with blanks. This step DELETES directories. If the empty-check is wrong, it deletes the wrong thing. Refuse if non-empty, log what was found, and ask — a user who recorded a track or downloaded tiles between steps 4 and 7 has real data in those "blanks".

3 · ⭐⭐ The ordering fix — grant BEFORE the database

This is the half that prevents 08-01 rather than working around it

The 08-01 failure was an ordering failure. The app opened the DB before authority was real. It did not prompt, because it tested and the test lied.

So: make the All-Files prompt UNCONDITIONAL on first run, and put it FIRST. Fred: "we never got the prompt in the failed install as the app looked like it had authority. probably should not be a test but unconditional grant there."

⭐ The app already knows it is a fresh install — it is already asking first-run questions. That IS the signal. No new detection is needed: move the grant to the front of the existing first-run sequence, before SpatialDbManager opens anything.

Cost: one extra tap for a user who already has the permission. Against losing 50–60 GB, that is not a close call.

⚠ A reinstall-over-existing-data IS a fresh install from the app's point of view — which is exactly what you want here: grant first, then the behavioural read finds either the .bak directories or the real ones.

Verify behaviourally, then recover

After the prompt, attempt a real read. If it still fails, the app is in the stale-grant state — and it should say so, at the moment it matters, with the recovery step: toggle All-Files access OFF and back ON in Settings.

⭐ And if that does not clear it, the message must say: "Reinstalling is safe — your maps and tracks are stored outside the app and are not removed." That single sentence turns a data-loss panic into a two-minute fix. Nothing in the app currently says it.

4 · The first-run marker

Where it lives, and why not in shared storage

A small JSON recording first-run state — but it must go in app-private storage (filesDir), NOT Documents/GroupTrack/.

⛔ The trap, if it went in shared storage: that file lives in the very storage the authority question is about. If All-Files is not granted the app cannot read it — so "file absent" and "cannot see the file" look identical. That is precisely the confusion that caused 08-01, reproduced in a new file.

✅ filesDir needs no authority and is always readable. And it is wiped by uninstall, which makes it a better signal, not a worse one:

marker ABSENT + data PRESENT in Documents/ = a reinstall over existing data. That is the detector 08-01 needed, and it comes free with the same file.

Contents: a status field and the version code — {"status":"in_progress"} → {"status":"complete","version_code":N}. Keeping it after completion (rather than deleting) answers both questions with one file: has setup run? and is this a reinstall? It also gives crash recovery — if the app dies mid-first-run the marker survives as in_progress, and the next launch knows setup never finished.

5 · Still owed in code, regardless of any of the above

The procedure and the flow protect whoever uses them. These protect everyone else, and neither blocks anything:

  • ⭐⭐ REFUSE-TO-CREATE. SpatialDbManager must never create-if-missing on a path it cannot verify. A failed open must ABORT, not write an empty schema. This alone would have prevented 08-01 and costs nothing at runtime. It is the single highest-value item on this page.
  • ROW-COUNT SANITY + .lastgood copy. Copy the DB after each successful startup. A startup reporting zero rows where the previous run reported 89,000 is a red flag the app should raise, not report as normal.

✅ Already fixed 2026-08-04: SpatialDbManager :166/:168 logged the LITERAL ${spatialFile.absolutePath} because the $ was backslash-escaped — so the DB path never appeared in the log. That was the diagnostic that would have made the 08-01 loss obvious immediately.

6 · Open questions

  • What if the user cancels the uninstall dialog? The directories are already renamed and the app is still installed — it would find no data. Needs an undo path: on next launch, if .bak exists and the app is clearly NOT freshly installed, offer to rename back. (Doing the rename only after removal is confirmed is not possible — the app cannot observe its own uninstall.)
  • Uninstalls done from Settings or the launcher bypass the button entirely. The manual procedure stays documented as the fallback, and refuse-to-create covers the case where neither was used.
  • ⚠ Worth verifying on Droid 2 rather than assuming: that an uninstall really does leave Documents/GroupTrack/ intact. It should — public shared storage — but Android has changed storage behaviour repeatedly, and this entire design rests on that assumption.

Why the rename works when checking does not

Every detection approach fails for the same reason: the app creates blanks before authority arrives, and the permission API reports the wrong answer at exactly that moment. The rename does not detect anything — it removes the data from the path the app will write to, until authority is real. Nothing to detect, nothing to destroy.
