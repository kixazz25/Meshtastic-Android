GroupTrack — Session Recap
2026-07-23 · INTERNAL · git purge + pushed · corridor design settled

Headline

The repo is unblocked and pushed — six large .db blobs purged from history, .git ~1GB → 82MB, and ~130 commits finally off the laptop and onto GitHub. Then the 62,000-tile mystery closed: segmentation was never broken — every split was mathematically correct. The real finding is that a bbox is the wrong model for a line feature, measured concretely: one ~100-mile figure-7 track was 22% of an entire 10-track import, its bounding rectangle ~95% empty desert. That produced a settled design for corridor downloads and a two-phase build plan.

What happened

  1. Git purge. Backed up with git bundle after cp -r failed twice — critically, cp -r silently didn't copy .git, which would have been a worthless backup. Found SIX large blobs where memory said three; the sixth only surfaced after the first purge pass. Cleared a stale refs/original/ from a prior abandoned rewrite, purged, verified nothing above 40MB remained, re-added the remote filter-repo strips, force-pushed, and added a *.db guard.
  2. 62K investigation closed. Captured a logcat trace of the tester's import. The pre-existing SEGMENT logs carried the answer: 72 segments per source × 3 sources = 216 ≈ the 215 queued, every split obeying the 50K ceiling. Four of my theories died on inspection — the bypass had zero callers, satLayers self-initialises, the old 12-mile calc isn't reachable, and the tracks aren't oversized. The model was wrong, not the math.
  3. Corridor design settled. Track-based and route-based downloads use a corridor; user-drawn areas keep the bbox. Two self-contained functions sharing one isolated prompt. Option B for the entry — store a geometry reference, let the worker re-derive tiles — after Fred ruled out run-boxes on the 5-10s-per-bbox startup cost.
  4. Queue work scoped as Phase 1. DownloadType field, real ordering (there is none today), filter-scoped deletes with confirmation, and the scrolling fix — built and certified before corridor.
  5. A live incident. Replace-map-source spawned 3287 continental-US entries that resurrected after Cancel All, and we confirmed there is no recovery path on a release build — Android 13+ blocks all third-party access to Android/data.

Decisions locked

  • Track/route → corridor; drawn area → bbox.
  • Two self-contained functions, shared isolated prompt, no branching — the caller knows which it is, so each passes its own onProceed.
  • Option B — entry stores geometry reference + type; worker re-derives. Run-boxes rejected on startup cost; tile-list-in-entry rejected on JSON size.
  • A real downloadType field, not a label prefix — "we cannot bastardize the name for expediency."
  • The filter scopes deletes, with scope+count labels and a gated confirmation.
  • Queue first, certified, then corridor.
  • git bundle is the backup method, never cp -r.

Lessons

  • Isolate with data, not theory. Four of my hypotheses died on inspection in one day. The trace settled in minutes what argument couldn't.
  • Fred's pushback was right repeatedly — that "no other Kotlin usage" didn't rule out JS callers; that the numbers didn't add up; that run-boxes would be unusable at 5-10s each. When the person who runs the app says it doesn't match, re-derive.
  • Verify generated code produces VALUES, not just that it parses. My logging patch balanced its braces perfectly and printed literal $sizeTiles.
  • A backup that doesn't verify isn't a backup — cp -r reported errors but still looked like it had run.
