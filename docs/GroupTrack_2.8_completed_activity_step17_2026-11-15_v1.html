🧮 GtMath — Android's math on the iPad (the platform rule found today; it governs all shared code)

  • How it was found (07:17–07:37): the 11-09 15e iPad report had 13 rows about times. Fred 07:17: "we have prided ourselves on resolving every difference" — find it, don't accept it. MATHPROBE (a TEST-ONLY probe: the haversine's every step, Droid vs iPad, bit for bit) showed the FIRST differing step was cos (one last bit: droid …5006, iPad …5005), then everything after it. Apple's libm and Android's give different last bits on some inputs; a distance one bit different moves a track property, a rider-trail cut and anything hashed from it.
  • The rule: shared code never calls kotlin.math sin / cos / asin / hypot / pow / tan / atan / sinh / ln — it calls GtMath. Android: GtMath = java.lang.Math, unchanged by construction. iPad: GtMath = Android's OWN algorithms in plain Kotlin:
    • cos / sin: FreeBSD msun (Android's libm) — GtMathPort; asin / hypot: fdlibm — GtMathPort. Proof MATHPROBE/MATHPORT: 6,000,000 Droid values (C, S, A, H 1,500,000 each), iPad 0 DIFF (08:13).
    • pow: Arm optimized-routines pow (what Android's libm compiles), with platform.posix.fma for the fused steps — GtMathPow. First tried x·x for pow(x, 2.0): MATHPOW (08:32) showed Android's Math.pow(x, 2.0) is NOT x·x on 1,266 of 1,500,000 (Android's pow is not correctly rounded) → gtmath2b replaced it with the port: 0 / 1,500,000 (09:50). Apple's own pow would differ on 2,305.
    • tan / atan / sinh (+ the exp / expm1 they use): fdlibm, line for line from JDK 21 FdLibm.java — GtMathFdlibm (common code; its huge-argument reduction shares GtMathPort.kernelRemPio2, made internal). StrictMath = the Droid on these, proven by MATHTILE.
    • ln: Arm optimized-routines log (N = 128 table, POLY 6 / POLY1 12, with fma where clang contracts one expression) — GtMathLog (iosMain). glibc aarch64 = the Droid.
  • MATHTILE (16a, 16:57): the tile math the save-by-area writes run, on real inputs (every track point's latitude and every 7th trail's, 400,000 latitudes, + seeded random): Apple differed on tan 158,960 / 400,000, ln 647, sinh 29,336, atan 6,943, lat2tile-before-2^z 25,040, stored box edge 15,899. C. THE HARNESS WORK PAPERS — intent, purpose, method, and how we verify (HARNESSREG-2026-11-15)

Fred, 2026-11-15 07:55: "every harness intent purpose and meth[o]d should be a bullet[.] how we verify will be important as we trouble shoot a[nd] by then it will be to[o] late to remember."

The timing is the whole argument. A harness is built when its question is fresh and is DOUBTED months later, when a cert disagrees or a port is revisited — and at that moment the two things nobody can recover from the code are what it was actually proving and what it deliberately excluded. A green run with forgotten scope is worse than no run: it reads as proof of something it never tested.

Same lesson as METHODTRACE: write it while standing in it, because that is exactly when it feels too obvious to write.

THE VERIFICATION RULES THAT APPLY TO EVERY HARNESS

  • PASS = # TAG done: N SAME, 0 DIFF on the Droid AND 0 DIFF on the iPad, with cross-device keys reported COMPARED — and TWO CLEAN RUNS, byte-identical reports. One clean run is a coin toss on anything timing- or ordering-sensitive.
  • Read the verdict from the REPORT FILE, never from the terminal. The terminal redraws old scrollback and a pasted result often repeats an earlier run (recorded 11-09).
  • EXPECTED_DIFF is keyed on EXACT KEYS, never on a fixture name. Keyed on the fixture, every real divergence reports as DIFF and every agreeing key reports as STALE — measured 11-14, it would have failed a passing cert.
  • ONE formatter, ONE newSide, in commonMain. Anything duplicated per side can differ per side, and then a HARNESS difference reads as a SERVICE difference. Learned three times on 11-14: a private formatter, per-side read-back defaults, per-side mtime seeding.
  • Doubles are compared TWICE — toRawBits() for the computed value and the decimal string for what is written, because Double.toString() is platform-specific.
  • Every compared key must be a DECISION the service makes, never a sampled observation — and every scenario must terminate. Simulate and show both before building the harness.
  • A cert proves "does it behave the same?", never "is it right?" It says nothing about the arguments callers pass. Register Entry 1 was certified at 0 DIFF on 1,938,346 values while carrying a satellite constant and being called with the wrong zooms.
