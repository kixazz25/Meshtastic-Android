⛔⛔ The correction that matters — discard was never diverged

Fred: "the issue was standardizing the discard function. i have seen no divergence in discard. our divergence is in save correct?" — and the code agrees.

onExit (~1646) and the in-progress dialog (~1775) both do all five operations, identically. No drift. The "six variants of discard" plan was built on a survey table that counted SAVE sites and LIST-MANAGEMENT sites as discard variants.

  • ~1834 resolver presents the discard CHOICE when an in-progress file is found on entry — nothing loaded yet, so its omissions are correct.
  • ~1923 picker is the In-Progress list, a reminder when more than one autosave exists. "Not part of the discard process." Nothing to tear down.
  • ~1539 and ~1717 are saves, not discards — and save-as-WIP renames, so it correctly has no deleteDraft.
  • setRouteMode "just does not belong in the discard function" — it is ambient exit behaviour that got copied in because it sat nearby.

⚠⚠ A guard that was never reached — second time in two days

ConvoyViewModel.setGpsInterval already wrapped setConfig in try/catch, logging "Failed to set GPS interval" — and the app still died. setConfig returns before the binder throws, so the exception fires outside the try block.

⭐ When a guard exists and the failure happens anyway, the guard is not being reached — check that before adding another one. Yesterday's latched gate state was the same shape: code that reads correct, behaves otherwise.

Two more things banked from that crash:

  • R8-minified stacks are actively misleading. That trace named coil3, okhttp3, RoomRawQuery and UsbKt — all nonsense. Trust only frames naming real behaviour; file attribution is a hint, not a fact. It sent Claude to the wrong file twice.
  • Find a UI element by its LABEL. Greps for "meter", "broadcast" and "Slider" all missed it. grep -n '"INT"' found it in one shot.

  • 160,628 trails: OSM 112,696 (70%) + UGRC 47,932 (30%). No BLM data at all. OSM rows carry geometry and name only.

  • The scenic layer is already imported — reference_points, 16,992 rows: peak 6,051, spring 4,855, cliff 525, volcano 131. No new ingestion needed for v1.
  • 68% of OSM tracks carry no grade, and grade5 is the largest graded group. ⛔ fclass as an exclusion filter is withdrawn — but it has a better use as the speed input.
  • BLM publishes what nothing else does: state OHV Designation polygons (Open/Limited/Closed) and national GTLF route designations. ⭐ "Limited" means stay on designated routes. ⛔ BLM land only — outside it the layer is silent, and silence must not read as "open."
  • v1 is carried by scenic + loop + variety + envelope. "Trail quality and difficulty" was named first and is not available.

Default speed range: 12–18 mph for 45–60 mile planning, from 31 filtered tracks. Fred's SWAG of 12–17 was essentially right.

⭐⭐ But the mechanism is not what it looks like. Claude read the rising trend as terrain. Fred's explanation is better and simpler: "a break or two and lunch on a short ride is a higher percent of the total time." So avg_speed_mph is an elapsed-time average including stops — which is exactly what a day-planner wants, and removes the need for a separate stopped-time parameter. ⚠ It also means the short bands measure lunch, not riding — do not extrapolate 6.1 mph downward.

Parameters: speed range (estimation only) and distance bounds (the hard constraint, upper and lower) both user-adjustable with defaults in settings. Time is derived and reported as a range, never a point figure.

⚠ Track data quality, found in passing: max_speed_mph pins at 199–200 constantly · one row shows 99,379 ft gain on 57 miles · one row 0.0 hours on 50 miles · several rows at 47–66 mph avg are almost certainly trailer miles.
