🔴🔴 00-ROOTCAUSE (08-11) — THE THREE ROOT CAUSES. FIX THESE, NOT THE SYMPTOMS.

Fred named these after the 08-11 Droid 1 collapse. Everything else that day was downstream of one of them.

1 — AREA DOWNLOAD REQUESTS GROUND THAT HAS NO TILES

Fred: "download area must stream real tiles in existence by zoom for x lon and lat."

The area path derives a bbox and calculates the whole rectangle. The existence check happens later, per tile, inside the worker — so the QUEUE fills with a continent of work, most of which is then skipped one tile at a time. Droid 1: 3,287 jobs, ETA 194 days.

⚠ Why it went continental: the scope comes from the store’s EXTENT. With Utah coverage and any stray tile near New Hampshire, that extent spans coast to coast and the refresh covers all of it. ⛔ And it is not just a Fred problem — any rider who travels between download regions gets the same result.

⭐ THE FIX: scan what actually EXISTS and refresh only that. Query the store for stored tiles, group them into jobs, download those. A cell with no tiles never enters a job, so disjoint regions stay disjoint and corridors stay corridors — by construction, not by inference.

⚠ z16 is the vetting level (Fred): ~490 m, roughly a third of corridor width, so a skinny track is traced rather than smeared. z12 (~7.7 km) would drag in ground never downloaded.

⚠ PAYLOAD: a job cannot carry hundreds of thousands of tile keys in inputData. It must carry a re-queryable range and let the worker re-derive at run time — the same constraint that shaped corridor jobs.

⭐⭐ THIS RETIRES THE MANDATORY DELETE IN OPTION 2. The delete existed because the area pass inferred scope from a bbox and boxed corridor ground. Tile-for-tile refresh has no area pass — nothing infers shape, so corridor geometry cannot be lost. Coverage never drops either, because INSERT OR REPLACE overwrites in place. Fred: "we do not need a delete ... this function should be refresh a map source, all tiles." ⚠ Option 1 (clear and start over) stays for people who want it.

2 — CANCELLING 3,287 QUEUED JOBS ANR’d THE APP

The cancel walks every entry — removing it from the list, cancelling its WorkManager id, and saving the queue file — on the main thread. Thousands of writes, UI blocked, ANR.

⭐ CANCEL WORKERS may be gentler than CANCEL ALL, since it stops workers rather than walking entries. ⚠ The real fix is moving the walk off the main thread and batching the saves.

⭐ Related, already queued: HIDE completed and cancelled entries on hold-and-cancel — the tester’s panel was too congested to find live activity. Hide, NOT remove: the estimator and the yardstick both compute from completed rows.

A fresh install runs setup, believes it has All-Files authority when it does not, cannot see Documents/GroupTrack/, reads that as a new device, and writes empty schemas over real data.

⭐ THE FIX — TWO PER-CONNECTION PRAGMAS (MBPRAGMA-2026-08-09C, written, not built)

d.execSQL("PRAGMA secure_delete=OFF")      // stop zeroing freed tile blobs

Anchored in ensureSchema(), which runs on EVERY open (MBTilesStore.db() :64) — not only on creation.

⭐⭐ WHY THERE IS NO DISTRIBUTION PROBLEM — the question Fred raised. Both are PER-CONNECTION: they are not stored in the database file, they apply fresh at each open, and they touch nothing already written. ⚠ Why ensureSchema and not inside the delete function. The delete WOULD work — the handle is cached (handles[type]) so one pragma would hold for all 88 tracks. ⛔ DO NOT TURN JOURNALING OFF. No rollback means a crash leaves an UNDEFINED database — 5.3 GB, no backup, storage already throwing ioctl denials. Same exposure class as the 08-01 loss. PRAGMA synchronous = NORMAL is the safe lever if one is ever needed.

🔴 00-INSTALL (08-04 designed, UPDATED 08-09 — NOT BUILT) — SELF-UNINSTALL FLOW + THE ALL-FILES AUTHORITY DEFECT AND ITS FIX

PURPOSE: remove the new-install data-loss exposure that destroyed ~89,000 trails on 08-01.
STATE: DESIGN AGREED 08-04. No code.
DOCUMENT OF RECORD: grouptrack_install_design_2026-08-04.html — full design, flow, and reasoning.
SUPERSEDES: the manual-only approach in grouptrack_reinstall_procedure_2026-08-03.html, which stays valid as the fallback for anyone not using the in-app path.

The key realisation

The app can uninstall itself. Intent.ACTION_DELETE launches the system uninstall dialog — and at that moment the app is alive and holds authority, so it can do the dangerous bookkeeping while it still can. Ten manual steps become two taps.

THE FLOW: user taps "Prepare for reinstall" → app renames Documents/GroupTrack → .bak and My Tracks → .bak (instant regardless of 50–60 GB) → fires the uninstall intent on itself → user installs the new build → All-Files grant requested FIRST, before anything touches the DB → REAL READ of the .bak dirs → prompt to restore → on confirm, verify the blanks are EMPTY, delete them, rename back.

⭐ WHY RENAMING BEATS DETECTING: every detection approach fails for the same reason — the app creates blanks BEFORE authority arrives, and the permission API reports the wrong answer at exactly that moment. The rename does not detect anything; it removes the data from the path the app will write to until authority is real. Nothing to detect, nothing to destroy.

⭐⭐ The ordering half — grant BEFORE the database

08-01 was an ORDERING failure. The app opened the DB before authority was real, and did not prompt because it TESTED and the test lied — Environment.isExternalStorageManager() returns true in the stale-grant state and is wrong. It reads the stale grant record; the filesystem enforces the truth. No API question returns the right answer — only a real read attempt does.

Fred: "we never got the prompt in the failed install as the app looked like it had authority. probably should not be a test but unconditional grant there." → make the All-Files prompt UNCONDITIONAL on first run and put it FIRST. The app already knows it is a fresh install — it is already asking first-run questions. No new detection needed.

⛔ REJECTED — AND WHY: blocking startup until the app can read would DEADLOCK the device. The app must run before it can be granted authority, so refusing to start until it can read means a reinstalled device can never be recovered. Also rejected: acting at uninstall time — Android has no uninstall hook; ACTION_PACKAGE_REMOVED goes to OTHER apps and arrives too late anyway. The danger is not the uninstall, it is the next install running blind.

The first-run marker — filesDir, NOT shared storage

⛔ THE TRAP if it lived in Documents/: that file sits in the very storage the authority question is about. Without All-Files the app cannot read it, so "file absent" and "cannot see the file" look identical — the exact confusion that caused 08-01, reproduced in a new file.

✅ filesDir needs no authority and is always readable, and is wiped by uninstall — which makes it a better signal, not a worse one:

marker ABSENT + data PRESENT in Documents/ = a reinstall over existing data. That is the detector 08-01 needed, free with the same file.

Contents: {"status":"in_progress"} → {"status":"complete","version_code":N}. Retaining it after completion answers both has setup run? and is this a reinstall?, and gives crash recovery for a first run that dies midway.

DOCUMENT OF RECORD: grouptrack_allfiles_fix_strategy_2026-08-09_v1.html. CORRECTS the permission reasoning in 00-INSTALL above, which assumed a stale grant left over from a previous install.

The defect, located in code

ConvoyScreen.kt:145   mutableStateOf(!Environment.isExternalStorageManager())
ConvoyScreen.kt:151   if (!Environment.isExternalStorageManager()) { ... }
ConvoyScreen.kt:433   ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION
OsmImportStage.kt:575 Environment.isExternalStorageManager()

ONE FAULT, NOT TWO: THE TEST ASKS THE WRONG SOURCE. isExternalStorageManager() reads the AppOps record. In the failure state that record says granted while the filesystem refuses. So the expression initialises the dialog flag to false and the prompt never fires. Fred: "the app said it had all authority, the checkbox was yes, but the app did not have all authority."

⭐ THE POSITION OF THE CHECK IS CORRECT AND MUST NOT BE MOVED. An earlier draft of this section claimed the check ran too late because it sits inside a Composable. Fred disproved it: it works on every new install. On a new install the value genuinely reads no, the prompt fires, the grant lands, and the DB is built afterwards. Same code, same position, correct outcome — the ONLY difference on the broken path is the API lying. The fix is a substitution, not a restructure.

⭐⭐ WHY IT HAPPENS — THE CHANGE IS ACTED ON, NOT THE VALUE

AOSP: storage access is enforced by a per-process mount view, not by the permission record. A mount namespace is created for each app at Zygote fork time and the appropriate view bind-mounted in. Then — critically — "when permissions are granted, vold jumps into the mount namespace of already-running apps and bind mounts the upgraded view into place", and downgrades always result in the app being killed.

"WHEN GRANTED" — THE ACTION FIRES ON THE TRANSITION. Nothing recomputes the mount view from the current value. That is Fred's question answered, and it explains every observed behaviour:

New installno → yes✅ event fires
The broken stateyes → yes ⛔ no event — nothing happens
Uninstall + reinstallfresh fork✅ view computed at fork
Toggle off then onyes → no → yes✅ two events

⭐ THIS IS WHY OPENING THE SETTINGS SCREEN ON ITS OWN DOES NOTHING — Fred's point, and it is right: entry state and exit state are identical, so there is no transition to act on. The transition has to be manufactured.

⚠ CAVEAT — NOT PROVEN. The AOSP passage says runtime permissions. MANAGE_EXTERNAL_STORAGE is an AppOp / special access, not a runtime permission. If the vold path does not cover AppOps at all, then no in-place grant ever updates the mount and only a fresh process fork works — meaning reinstall really is the only cure. ⚠ Several mechanisms proposed during the 08-09 session were wrong and were corrected against observed behaviour. THE FIX — in build order

STEP 1 — REPLACE THE TEST. Never ask the API. The only truthful question is a real read of a path All-Files actually governs. filesDir/cacheDir always work, so reading those proves nothing.

fun hasRealStorageAccess(): Boolean = try {
    val d = File(Environment.getExternalStorageDirectory(), "Documents/GroupTrack")
    d.exists() && d.canRead() && d.list() != null      // plain File I/O — NO SQLite
} catch (e: Exception) { false }

⛔ "Cannot see it" and "it is not there" get the SAME treatment — treat invisibility as UNKNOWN and refuse. Reading invisibility as emptiness is exactly what built blanks over real data.

⚠ Same substitution at :151 and OsmImportStage.kt:575.

STEP 2b — LOOP BACK. THE READ IS A GATE, NOT A ONE-SHOT CHECK.

⭐⭐ THE APP NEVER PROCEEDS BECAUSE THE USER CAME BACK FROM SETTINGS. IT PROCEEDS ONLY BECAUSE A READ PASSED. fun gate(): Boolean {                    // ONE function, called at EVERY entry

    runPanelCycle()                      // Panel A → settings → Panel B → settings

  • on resume from the settings screen — every return, both trips
  • before any SpatialDbManager open
  • before any MBTilesStore open
  • before any import, download or migration run
  • on app resume from background — authority can be lost while the app lives

⚠ THE FAIL PATH NEVER FALLS THROUGH. If the final read fails, the app shows Step 4's message and stops there.   • Fresh-install marker in filesDir — row counts, DB sizes, last-good timestamp. Private storage is wiped by a fresh install; external storage is not. Marker absent + external DB present = a fresh install just happened over existing data → stop, report.
  • Row-count sanity. A database that held 89 k trails yesterday reporting 0 today is not a valid state.
  • Belt and braces: copy to grouptrack_spatial.db.lastgood after each successful startup.

🆕 2.7 FEATURE — TRAIL GAP FILL FROM RIDDEN TRACKS (Fred 07-31)

THE PROBLEM, in Fred's words: "trying to draw a route using bits of a track you have already ridden but trails still do not show."

Route building composes from trails. A stretch you have ridden but which the trail collection does not cover exists only inside a track — and a track cannot be composed with, because it is stored as ONE geometry. So when planning, you cannot see all your real choices even though you have the ground truth on the device.

⭐ These are not a new class of artifact. Fred: "they are trails that simply do not appear in that collection. you need a trail to ride." Same table, same rendering — the collection is just missing a piece.

⭐⭐ DISPLAY FIRST, INSERT SECOND — the shape that makes it tractable

Fred: "may be simpler to have a function that shows the map with a colour segment that is missing and can be added."

Show uncovered stretches as an overlay; the rider decides which become trails.

  1. For tracks in view, compute which point runs have no trail within tolerance
  2. Render those runs as a distinct overlay
  3. Tap the track → artifact detail panel → Add Trail Segment
  4. Only then does anything enter the trails table

⭐ This removes three problems at once, which is why it is better than automatic insertion at import time:

  • Tolerance stops being critical. A false positive is visible noise the rider ignores, not a duplicate trail silently written to the DB.
  • Naming resolves itself — the user is looking at it.
  • Nothing accumulates against dedup, and GPS wobble never becomes authoritative geometry by accident.

⭐ And it is useful before the insert step is written at all. Simply SEEING where ridden ground is missing from the collection answers the original frustration; adding it becomes optional.

Design detail settled 07-31

Detection. Sample the track's points; for each, test distance to trail geometry returned by queryTrailsByViewport for a small bbox. Consecutive points with nothing within tolerance form an uncovered run. Discard runs below a minimum length.

⭐ RouteManager.snap(lat, lon, trails, tracks, 30.0) already performs this proximity test and returns null when nothing is near — "null" IS "uncovered", so detection is mostly free.

Tolerance 20–30 m, matching the existing snap radius. ⚠ Too tight and GPS wobble alongside a mapped trail reads as uncovered, producing a shadow trail parallel to a real one — that is the failure mode to design against, and it is the argument for showing rather than auto-inserting.

Naming — Fred's rule: inherit the name ONLY if the trail either side of the gap carries the same name. Both endpoints agreeing is strong evidence it is one trail; disagreeing means it connects two, and inventing a name there would be wrong. Otherwise leave it unnamed.

⚠ Unnamed is correct, not a fallback. Fred: "most of our trails are unnamed now and named would have a major trail connotation." A named trail SIGNALS significance to a rider, and today's ORDER BY sorts named first — so auto-naming gap fills would both inflate that signal and outrank real named trails at low zoom.

Colour. ⚠ Dashed is already taken — tracks are #39FF14 dashed, routes #FF00FF dot-dash, trails carry carto_code colours. A solid line in an unused colour will read more clearly than another dash pattern.

🔴 OPEN QUESTION — which gap, when a track has several

The detail panel opens for the WHOLE track, but uncovered stretches are specific sub-ranges. A track with three gaps makes "Add Trail Segment" ambiguous — and that is exactly the case that motivated this.

⭐ Fred's motivating case: several tracks named Broken Ridge in one area. From a route-planning standpoint that is unusable, because you can only select whole tracks. Segmenting the uncovered stretches makes it a set of distinct short pieces you can assemble — and "which Broken Ridge" stops mattering, because you are choosing a STRETCH, not a name.

Likely resolution: the overlay lines are separate L.polyline objects, so each can carry its own point-range identity and pass that through — rather than routing everything via track_id alone.

⚠ Worth measuring before building

How much would this actually find? Utah now carries 89,536 OSM trails. If ridden tracks are 95% covered, this produces stubs and the effort is not repaid; at 40% it is a substantial feature.

⭐ Measurable PC-side in minutes against the spatial DB — sample a track's points, test distance to trail geometry, report the uncovered fraction. No app code. And measure it on the Broken Ridge area specifically, not statewide — that is the case that motivates it.
