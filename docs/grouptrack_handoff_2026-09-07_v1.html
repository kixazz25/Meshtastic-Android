⭐ Rider trails — what got built

The four pieces

RiderTrailScanner.ktPure. No database, no Android, no geometry serialisation. A line-for-line port of ridertrails_2026-09-06_v3.py, so it can be diffed against the prototype. Direction is the test, not distance; a run closes only on a sustained rejoin.

⭐ The 09-07 design change: connectors are part of the trail

v3 wrote connectors as separate lines. Fred: "the connector is the start of the trail and connects to rest of trail points … we are adding one new trail including derived connector."

So a rider trail is anchor node → the ground you rode → anchor node, one polyline. This removes a real failure mode: a run written whose connector write failed was an island the router could not reach.

Three entry points, one function

  • ADD TRAILS FROM TRACKS — blue, under RESYNC TRACKS on the import panel. Always visible.
  • Import stage _ridertrails — two passes, after the sources and before step 8.
  • Trigger in resolveTrackAdd — every genuine INSERT, inline, wrapped so it can never fail the add.

⚠ The five things that decide correctness

  1. ⛔ Candidates PER TRACK, by bbox — never the whole table. Utah is 145,942 trails, ~5.6M segments. The Python indexes all of it because it runs on a laptop; that on a 3 GB device is an allocation that does not come back.
  2. ⛔ AFTER the reload, never at the clear. StartupHousekeeping and clearTrailsOnce only CLEAR — they hand the reload to the import. Scanning an emptied table reads every track as fully off-network and promotes all 3,651 miles.
  3. ⛔ BEFORE step 8, not after. Step 8 classifies by VALUE across every row. Rider trails written after it carry no land_status and no use_type.
  4. ⭐ The dedup is the DIRECTION TEST, not the hash. Two GPS traces over the same ground never hash alike — the same reason OSM and UGRC turned out to be independent surveys. A rider trail written on pass one lies under its own track going the same way, so pass two reads it as on-network.
  5. ⭐ Live data per track. Two riders over the same unmapped ground: the first track's trail is already present when the second is scanned. Index once up front and the same ground is written twice, with different hashes, and nothing catches it.

⭐ TWO PASSES, and why — measured

Droid 1: pass one 1,537, pass two 70, pass three 0.

The second pass is the network settling around the connectors the first one wrote — new anchor nodes exist, so a few runs close at different points. Fred called it: "we had breaks new trails and existing trails for them to connect to." One pass leaves ~5% of the edge geometry unsettled; two converge every time. The import stage runs both.

⛔ NO SCANNED FLAG — dropped 09-07

The earlier design had a field on the track extension. Fred killed it: "no need to flag them as run." It never needs re-running unless trails were cleared and reloaded, so there is no state to keep — and the flag would have been reset on every run of the job that used it. Do not re-propose a column for this.

The four import-path fixes

⛔ Three of these were already broken. Nobody was watching those rows.

  1. The loop could not dispatch a stage. It skipped classify by testing process == "classify_land_and_use" — one hardcoded string. The rider stage hit Unknown process type, was marked FAILED, and then ran and succeeded further down. ⭐ Now skipped by id prefix: stage ids start with an underscore, catalogue ids never do, so the next stage is handled by construction.
  2. Neither stage had a status lifecycle. Sources do in_progress → publish → work → completed → publish. The stages did none of it. ⚠ Classify has never written its own status since 09-03 — it recorded 147,836 rows classified as "status": "pending", "imported": 0. That is not just a red row: a run that cannot report cannot be resumed, and resumable imports read the manifest.
  3. My own error: the rider stage wrote "done", a string nothing else in the file uses and the panel does not treat as finished.
  4. Ten silent minutes in step 7. ⭐ The progress was never missing — OsmExtractWorker publishes done/total/eta every two seconds under osm_extract_progress. It goes to OsmImportPanel; the picker reads downloadDetailFlow. Two channels, and the rider is watching the other one. awaitWorker already polls the WorkInfo and threw the data away — it now decodes it into the flow the picker renders. Fixes both worker stages.

⚠ The stale "$changed road(s) -> residential" log line was also corrected. Nothing has become residential since 08-31.

⚠⚠ How to retrigger a clear-and-reload — this was never written down

The gates are dotfiles in /sdcard/Documents/GroupTrack/. ⛔ ls -la | grep mark finds none of them — no name contains "mark". Use plain ls -la.

Release procedure — five hand-edited steps

Nothing prompts for any of these, and every one has been missed at least once.

  1. The release label in ConvoySettingsScreen.kt. ⚠ The open track reads 2.7.14 while the docs say 2.6g — worth reconciling.
  2. __htmlVersion in both map HTML files. Still 2026-09-03a — needs the bump.
  3. The schema marker in StartupHousekeeping, when the trail schema changes.
  4. ⭐ Copy the three documents into assets/.
  5. ⭐ Increment the revision in every document filename.

Worth remembering

  • ⛔ Anchors from cat -A, never from a terminal dump. Cost a patch today: the step 8 header has two box dashes before and thirty-four after; I counted twenty-two off a sed dump.
  • ⛔ Patch guards must strip comments before checking. Fired again — the purity check found computeGeomHash inside the comment warning against duplicating it. The guard was right to refuse; the check was wrong.
  • ⛔ Read what exists before writing something new. Four greps were spent hunting RESYNCH; the button says RESYNC and the dialog is titled SYNC TRACKS. The navigation xref had neither. ⚠ That is the case for extending the xref to assets/*.js and *.html.
  • ⛔ Fixing a symptom without reading what else keys off it. The stage-skip removed the red rows and left them stuck, because skipping the row also skipped its whole visible lifecycle.
  • ⭐ Check file timestamps before trusting a pull. Two stale DBs were reported as showing zero unnamed tracks; the live device had 423.
  • Do not paste multi-line commit messages into Git-Bash. An apostrophe opened a continuation prompt. One line, detail in the docs.
