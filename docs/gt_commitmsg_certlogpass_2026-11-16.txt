WHAT CHANGED HERE -- the corpus is now an APP ASSET, not a pushed file.
  app/src/main/assets/gt_logcert_corpus_2026-11-16.tsv   (93,780 bytes, 994 cases)
  GtCertLog reads it with app.assets.open(name), the pattern Cert17g1c / Cert17e1 / CertSchema /
  GtMapSpec already use, and the MacTest supplies its own reader off _data/cert exactly as
  GtCertTrail15fMacTest and GtCertImport15eMacTest do.
WHY, and it is not tidiness:
  - the asset ships INSIDE the APK, so the Droid and the Mac cannot read different corpora. That
    is the failure that would silently invalidate a comparison rather than fail it.
  - there is no push step to mis-scope. v48's push block was inserted inside
    `if [ "$MODE" = osm15g ]` and never ran for certlog, which is why the first run reported
    NO-CORPUS. With an asset there is nothing to push and nothing to get wrong.
  - the 1455 '$' characters never pass through Kotlin source escaping. Fixtures-in-code (the
    Cert17mbtiles pattern) would have required escaping every one of them as ${'$'} -- 1455
    chances to corrupt the very characters under test. Measured before choosing, not assumed.
  - the report now carries the corpus length, line count and hash, so each side can PROVE which
    input it read.
ALSO: the cases the Droid actually used are printed into the report between
"# CERTLOG cases-used begin/end" (Fred 08:38: "write your test cases to a print file and test from
there"), so a later difference can never be blamed on the two sides reading different input.

NOT YET EXERCISED: today's run went through the PUSH path, because the installed build (0830)
predates this patch. The asset path is proven only once a build carrying it runs certlog.

THE TEMPLATE FOR THE REMAINING NINE SEAM TYPES. Reusable unchanged: corpus-as-data in a TSV,
OldSide / newSide() through ONE shared runner emitting (key, value), the driver doing the
SAME/EXPECTED/DIFF comparison, the MacTest loading only the Droid's SAME lines and asserting 0,
the fenced-logcat pass, and the asset delivery. Seam-specific: the TSV's columns (the values that
control that seam) and the two Side implementations. Format decided from prior art, not invented:
line-oriented TSV in, line-oriented .txt out, flat field=value fingerprints -- because a
difference then localises to ONE line, which a single JSON document or a DB file cannot do.
Per-seam fingerprints where there is no return value:
  NOTIFY     channel, title, text, icon, importance, ongoing, autoCancel, actions, group, progress
  INTENTS    action, type, extras, flags
  WORKMGR    worker, tag, constraints, inputData
  GRAPHICS   op, width, height, config + a pixel hash; expect platform divergence, record EXPECTED
