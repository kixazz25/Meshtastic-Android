1. Product Vision
GroupTrack is an off-grid awareness platform for any group activity in areas without cell service — off-road vehicles, hikers, mountain bikers, overlanders, search and rescue, hunting parties. The platform provides real-time group position awareness over LoRa mesh radio, organized ride management, community track sharing, and radio configuration — all without requiring cell or internet connectivity during the activity itself.

GroupTrack
RideState — Rules, Touchpoints, and Phase B Implementation Plan
March 30, 2026  |  Branch: feature/convoy-event-ride  |  Phase B Thursday
1. Overview
RideState is a computed enum in ConvoyViewModel that drives three aspects of app behavior: map display, survey trigger, and public track repository eligibility. It is computed every tick from two inputs: the active node count on the mesh, and whether a formal ride record exists that matches the current radio channel name and today's date.
RideState controls behavior through conditional checks at specific touchpoints. It does not replace any existing V2.4 logic — it gates new V3.0 behavior alongside the existing code. V2.4 behavior is the default in all states.
⚠  RideState is declared in ConvoyViewModel.kt as of Phase A. It is computed but nothing reads it yet. All behavioral rules below are Phase B implementation tasks. No V2.4 behavior has changed.
2. The Three States
2.1 RideState Detection Logic
RideState is computed in ConvoyViewModel tick loop after ConvoyEngine.compute() runs. Two inputs are required:
1. Node count — from state.nodes.size (already computed each tick)
2. Channel name match — radioConfigRepository.channelSetFlow.first().settings.firstOrNull()?.name
The organized ride check loads all rides from ConvoyEventStore and matches on both channelName AND eventDate == today. This dual match prevents stale rides from triggering ORGANIZED state if the same channel name is reused on a different day.
★  The channel name is the bridge between the radio configuration and the ride record. When an organizer creates a ride, a unique channel name is generated (CONVOY-XXXX). When the rider applies the radio config, that channel name is written to the radio. On the next tick, the channel name matches the ride record — ORGANIZED state is triggered automatically.
3. Three Use Cases
Mode 1 is a significant product differentiator — it expands the addressable market beyond organized convoy riders to any trail user who wants offline maps and GPS track recording. No radio hardware required.
4. The Three Controlled Aspects
4.1 Map Display
Key rule for SOLO: when node count <= 1, the GPS trail segments (gpsTrailSegments already computed in ViewModel) are used as the primary map track regardless of trackLeadOnly setting. This is the real-time recording display. No code change needed for the trail itself — gpsTrailSegments already accumulates. The only change needed is the display condition in ConvoyScreen.kt.
4.2 Survey on STOP
The existing showNameDialog in ConvoyScreen.kt becomes a branch: if rideState == ORGANIZED show the survey+name dialog, else show the simple name dialog. The existing simple dialog code stays unchanged as the default path.
4.3 Public Track Repository (GPX Donation)

STATE | CONDITION | DEFINITION
SOLO | Node count <= 1
No ride loaded | One person, no radio connected or no other nodes heard on mesh. Personal GPS mapping mode — equivalent to Gaia GPS or onX. No convoy, no mesh coordination, no database impact.
CONVOY | Node count > 1
No ride loaded | Ad hoc group ride. Multiple radios heard on mesh. No formal ride record in the system. Convoy tracking active. No survey. No database impact. Ride is impromptu — organizer did not pre-create a ride record.
ORGANIZED | Ride loaded
(channel + date match) | Formal ride record exists in convoy_events/ where channelName matches the active radio channel AND eventDate matches today. Full V3.0 platform experience. Survey on STOP. Track donation eligible. Full database impact.
MODE | STATE | DESCRIPTION
Mode 1
Solo Trail Mapper | SOLO | No radio connected or no other nodes heard. User uses GroupTrack as a personal GPS mapping tool. Downloads offline map tiles. Records GPS track in real time — track draws on screen as they ride. Exports GPX. No mesh, no convoy, no database, no survey. No account required.
Mode 2
Ad Hoc Convoy | CONVOY | Radio connected, multiple nodes on mesh. Impromptu group ride — no formal ride created in the system. Full convoy tracking: lead lock, span, HUD, all active. No survey on STOP. Track saved locally, no donation. No database impact.
Mode 3
Organized Ride | ORGANIZED | Organizer pre-created ride in RDS. Rider accepted invite link, maps auto-downloaded, radio auto-configured. Full V3.0 experience: convoy tracking, lead lock, HUD, survey on STOP, track donation offered. All data flows to RDS.
STATE | MAP DISPLAY BEHAVIOR
SOLO | Device GPS trail drawn in real time as rider moves. Track line grows with each GPS point. No convoy nodes displayed (none exist). Imported GPX reference overlay shown if loaded (backlog: GPX-01). Single color trail from device GPS.
CONVOY | Convoy trail from lead cart. All existing V2.4 trail logic unchanged. Lead lock active. Multi-node HUD visible.
ORGANIZED | Convoy trail from lead cart. Route overlay from ride_tracks if route_id set on ride. All existing V2.4 trail logic unchanged.
STATE | STOP RECORD BEHAVIOR
SOLO | Simple track name dialog only. No survey questions. Track saved to tracks directory (filesDir/my_tracks/). No database impact. SAVE disabled until name entered.
CONVOY | Simple track name dialog only. No survey questions. Track saved to tracks directory. No database impact.
ORGANIZED | Full survey dialog: difficulty checkbox (Easy/Moderate/Hard), recommend checkbox (Yes/No), share track checkbox. Track name field below survey. SAVE disabled until name entered. Survey queued locally, uploaded on next connectivity. Track donation processed if share checked.
STATE | TRACK DONATION BEHAVIOR
SOLO | No donation. Track stays on device. No upload to ride_tracks on EC2. No database row created.
CONVOY | No donation. Track stays on device. No upload.
ORGANIZED | Donation offered via share track checkbox in survey dialog. If checked: MD5 computed on device, POST /ride/survey with track_donation payload, stored to EC2 ride_tracks directory, ride_tracks row created with source_ride_id set to the organized ride ID.

GroupTrack
V3.0 Architecture & Migration Plan
Monday Planning Document  |  March 28, 2026  |  AWS Backend Integration
Executive Summary
V3.0 migrates GroupTrack from a fully offline standalone app to a cloud-assisted platform where the AWS backend handles ride creation, user enrollment, and invite distribution while the core mesh radio operation remains entirely offline and unchanged.
The migration strategy is built around one principle: the radio never needs a cloud connection. Everything before the ride (enrollment, ride creation, invite, map download) can use the cloud. Everything during the ride uses the mesh. The app must work transparently in both states.
1. Current JSON Entity Inventory
These are the data entities that exist today as local JSON files. Each must be mapped to the V3.0 hosted model.
1.1 convoy_ride — the .convoy file
Location: app/convoy_events/{UUID}.json
MIGRATION: Rides created locally in V2.4 are recreated in V3.0 by posting to POST /rides. The eventId UUID is preserved as rides.ride_id so existing .convoy files remain valid. No data loss.
1.2 master_config.json
Location: app/src/main/assets/master_config.json — baked into APK. 47 radio config fields across 6 groups. Read-only.
V3.0 STATUS: Unchanged. Stays in assets. Rides only override channel_name and channel_psk. Everything else is master config.
1.3 convoy_apply_list.json
Location: app/src/main/assets/ — defines which fields get written during Apply Radio.
V3.0 STATUS: Unchanged. Stays in assets. Not user-configurable, not ride-specific.
1.4 master.cfg (binary)
Location: app/src/main/assets/ — Meshtastic DeviceProfile binary. 38 fields. Built from master_config.json.
V3.0 STATUS: Unchanged. Not hosted in RDS.
1.5 WorkingConfig (in-memory)
Not persisted. Built at runtime by merging master_config.json + ride JSON + radio reads.

1. Executive Summary
GroupTrack V3.0 migrates from a fully offline standalone app to a cloud-assisted platform. The migration must be built in two completely isolated phases with a hard gate between them — V2.4 Wednesday field test confirmation — to ensure the proven offline radio engine is never destabilized by backend integration work.
