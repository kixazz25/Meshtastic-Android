AI Route Planner — process specification

2026-08-26 · PROCESS-2026-08-26 · the three processes, what each owns, and the documents that specify them

This document is the map of the other documents. Three separable processes came out of the 08-25/26 sessions. Each has its own state, its own screens and its own reasons to fail, and each can be built and tested without the others existing.

  2. Process 2 — Route generation (the engine)
  3. Process 3 — Approval (the map + legend, standalone)

⛔ THE LOCK: ONE BATCH AT A TIME. While open_batch.json exists with state of building or open, no route activity of any kind starts — not the planner, not drawing by hand, not promoting from elsewhere.

⭐ And it REDIRECTS rather than refuses. Tapping Route+ with an open batch opens process 3 on that batch. The rider is put in front of the thing that is in the way, with the tools to clear it. A refusal leaves them holding a problem they did not know they had.

1 Requirement gathering

Owns: everything the rider says before a route exists. Produces: the request half of open_batch.json. Screens: a banner over the map, one instruction at a time.

#StepWhat it gathers
1Welcome, and get on the ground Nothing. It states the outcome — up to six recommended rides, presented together on the area map, named and colour coded, with narratives — then asks the rider to search a town, region or feature, or open a track or waypoint by name.
⭐ "Zoom in where the trails meet a road" is the instruction that matters: it is visible on satellite imagery and needs no local knowledge.
2Name and length The batch name (Panguitch September → Route 1 … Route 6), the shortest ride worth taking, the furthest they will go, and the pace band.
⭐ Two sliders produce a time window — shortest ÷ fastest pace to furthest ÷ slowest pace — and the rider adjusts until it is the day they have.
3Where you will park The staging point. Tap an existing waypoint, or long press one second to create one — SAVE selects it, no second tap.
⚠ Not "trailhead". A staging area is the parking lot; it needs no trail knowledge. Guidance: somewhere several trails leave in different directions, not a dead-end spur.
4Points to cover Up to five pins. Opens by saying the rider has already done enough — "we have enough now to build you a set of rides" — so pins read as refinement, not another hurdle. CONTINUE means both "none" and "finished".
5Finish point A pin, or nothing. The loop question answers itself — no finish pin means a loop. ⭐ Asked at the END, once the rider has seen the ground.
6SearchingHands off to process 2.

⚠ WHAT PROCESS 1 MUST CARRY, each measured:

  • MAP TAPS ON/OFF on the banner. The route toolbar carrying it renders on routeMode && !showAiDesign — while the panel is open it is gone, so a rider mid-flow cannot read a trail name and get back.
  • DONE always renders. It was hidden when feasibility was unknown or the pins busted the ceiling, which removed the only way out of the step.
  • Pins move to the nearest trail and say so — measured 16–150 ft onto named trails. The marker draws at the snapped position, not the tap, or the map contradicts the message.
  • Five pins, not ten. Ten took the tested ceiling from 4 to 11 and the build never finished.

2 Route generation

Owns: turning a request into up to six distinct rides. Produces: drafts, and the results half of open_batch.json. Screens: progress only.

Fully specified in GroupTrack_algorithm_annotated_2026-08-26.html — every step, the rule it applies, and the measurement behind each constant. In outline:

corridor (ceiling/3)  →  graph  →  candidate starts within 600 yds, edge-split
  →  collapse to one origin per component  →  attach features via spatial grid
  →  rider pins as high-value features, split onto their trail
  →  distance matrix  →  out-and-back filter  →  pairwise table + tested ceiling
  →  working array: features earn their way in  →  enrich the top 20
  →  dedupe (same origin+features · any origin · 75% shared trails)  →  six

⭐ MEASURED ON DEVICE 2026-08-26, Birch Spring / Pass Creek: 12 trails → 1 network, tested ceiling 4, enrichment to 7 features, six routes between 79.0 and 80.0 miles against an 80-mile ceiling, in four seconds.

The morning of 08-25 produced one route to Brian Head from an origin 613 ft away down a single spoke.

3 Approval — ⭐ STANDALONE

THIS IS A PROCESS IN ITS OWN RIGHT, not the tail of the planner.

It reads open_batch.json and the drafts it names. It does not care how they were produced. That means it opens from Route+ whenever a batch is open — after a crash, days later, from a cold start — and it is testable against a hand-written JSON file with no engine run at all.

The panel is a legend

Not a results list. A legend ties what is drawn to what it is called, so each row is the route name in the same colour as its line.

ElementBehaviour
Name, in the route's colour⚠ Colour alone cannot be spoken about or listed; a name alone cannot be found on a map. Both.
Tap the nameOpens that route's narrative.
Show / hide⭐ The comparison tool. Six over the same ground is spaghetti — look at two, look at three. Free and reversible: it is how looking works, not a decision.
Select⚠ Multi-select. A rider who finds two good rides keeps both.
Save selectedPromotes the chosen routes; the rest are cleared. Batch resolves.

  "name":       "Panguitch September",
  "created_at": "2026-08-26T14:22:11Z",
  "state":      "open",            // building | open  (resolved = deleted)

  "staging":  { "lat": 37.7235, "lon": -112.6130,
                "waypoint": "Birch Spring staging" },
  "band":     { "miles_low": 55, "miles_high": 80,
                "mph_low": 12, "mph_high": 18 },
  "pins":     [ { "lat": 37.7301, "lon": -112.5998,
                  "moved_ft": 33, "onto": "Horse Valley Road" } ],
  "finish":   null,                // null = loop back to staging

  "routes": [
    { "n": 1, "draft": "Panguitch September Route 1", "colour": "#4FA3E3",
      "miles": 79.7, "features": 7, "retrace_pct": 18, "state": "offered" }
  ]
}

⭐⭐ THE PINS ARE SAVED WITH THE FEATURE DATA, NOT SEPARATELY (Fred, 2026-08-26). Every route in the batch records what it reaches, and a rider's own place appears in that list alongside the natural features, marked as theirs.

Why it matters: when the six routes are drawn, the rider needs to see each one relative to what they asked for. "This route reaches two of your three places and picks up a spring on the way" is the sentence the approval panel has to be able to write, and it can only write it if the pins live in the same structure as the features.

Per-route features, pins included

"routes": [
  { "n": 1, "draft": "Panguitch September Route 1", "colour": "#4FA3E3",
    "miles": 79.7, "hours": [5.5, 6.6], "retrace_pct": 18,
    "state": "offered",

    "features": [
      { "name": "Your place 1", "class": "userpin", "mine": true,
        "mile": 6.2, "moved_ft": 33, "onto": "Horse Valley Road" },
      { "name": "Asay Knoll",   "class": "peak",    "mine": false, "mile": 14.8 },
      { "name": "Boy Scout Spring", "class": "spring", "mine": false, "mile": 31.0 },
      { "name": "Your place 2", "class": "userpin", "mine": true,
        "mile": 44.7, "moved_ft": 19, "onto": "FSR 082" }
    ],
    "yours_reached": 2, "yours_asked": 3
  }
]
FieldWhy it is there
mine⭐ The legend and narrative can style a rider's own place differently and lead with it. Without this flag they are indistinguishable from a peak.
mileWhere on the ride it falls. The narrative already lists features in order; the rider's places should be findable in that order.
moved_ft, onto⚠ The honest record of the snap. Measured 16–150 ft onto named trails. A rider seeing "your place 2, moved 19 ft to FSR 082" knows exactly what the app did with their tap.
yours_reached / yours_asked⭐⭐ The number that decides whether a route is worth keeping. Pins are high-value features, not a membership rule — a device run took two of three. The rider must be able to see that at a glance rather than reading four feature lists to work it out.

⚠ THIS IS WHAT MAKES THE COMPARISON MEAN ANYTHING. Six routes over the same ground differ mostly in what they reach. If the panel can say "three of your three" against "one of your three", the choice is obvious. Without the pins in the feature data it can only show mileage and a count, and the rider is back to guessing.

Rules

RuleWhy
The file carries the REQUEST, not just the results Staging, band, pins and where each pin was moved to. ⚠ Without it a rider cannot tell why a route came back as it did — which is exactly what cost 08-25.
Per route: offered → saved or discarded The batch resolves when none is still offered — and the file is then deleted.
Resolved → the file is DELETED ⭐ Fred, 08-26: no history. Once the rider has kept what they wanted and the rest are cleared, the batch has no further use — the saved routes are the record, and they carry their own feature lists. Keeping resolved batches would accumulate files nobody opens and put the pins in two places.
⚠ Deliberately UNLIKE the import manifests, which are kept because an import can fail silently and be discovered days later. A batch cannot: the rider is standing in front of it when it resolves.
Lives WITH the drafts it describes ⛔ Not in a swept directory. The trails-clear marker went into a folder emptied at startup, vanished, and the clear ran on every launch for days.
Always escapable ⚠ A batch left open by a crash would block the planner forever. Reopening offers "discard this batch and start again", and the file is safe to delete by hand.

⚠ RESOLUTION MUST BE EXPLICIT AND REVERSIBLE UNTIL CONFIRMED. Six routes deleted by an accidental back-press is the same class of loss as the autosave-discard bug that cost six divergent teardown copies.
