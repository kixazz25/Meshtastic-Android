GroupTrack 2.8 — the native iPad app — v14 (2026-11-10 19:50)

Started 2026-11-05/06 on the Mac. 2.7e is released and locked; 2.8 is the iPad.

1. What 2.8 is

  • 2.8 ends with a deployed native iPad app (roadmap, Fred 10-22). 2.9 = one-way data sync Android → AWS (services layer only, no paygate). 3.0 = AWS services: paygate (e.g. the first 200 users free for a year), Mac/PC planning station against the AWS model, map-licensing review.
  • Two phases (Fred 10-02): Phase 1 — GroupTrack on iPad with group functions off (riding solo: map, search, AI routes, rides, imports, recording, manual/help). Phase 2 — the GroupTrack Group Comm plugin (mesh radio, group awareness).
  • The goal: an iPad app that looks and feels as much like GroupTrack on Android as technically possible (Fred 10-02).

9. THE METHOD — Fred 11-06

  1. Move the whole model, then the screens. The non-screen layer is built first, so every service is waiting when its screen arrives (Fred 11:48, 11:52).
  2. Screens like the documentation. Wire the whole presentation layer as placeholders generated from the manual's screen tree (the same ids as GroupTrack's menu handlers, e.g. map.backup, map.export_routes) — each shows "<id> — not yet on iPad". Then chase them one at a time, walking the manual's layers. Placeholders left = progress (Fred 11:51).
  3. CERTIFICATION = THE SCREEN PROCESS, COMPARED WITH TODAY'S RESULT. A service is proven only when a screen process that calls it gives the same result as the Droid on the same data; certifying the screen process certifies every service it calls. Builds, logs and number checks are fault-finding, not certification (Fred 11:53–11:55).
  4. After each model batch the Droids are re-walked through the same screens — the Android app runs on the shared code, so its certification proves the move.
  5. One shared module in the main repo on 2.8, used by Android and iPad; the spike is a test bench only.
  6. Order of the map pieces (Fred 11:36–11:38): map store (done) → spatial database (done in the spike) → the filter (FilterModule / TrailFilterState) so completeness is judged type by type against the database counts above → map settings (map_keys.json, trail colours) → Map menu → 3D (DEM). The map display includes public and restricted areas.

18. Platform rules for shared code (found 11-06 … 11-09) — every port follows them

  • Numbers to text: never Kotlin's own Double/Float toString or string templates for anything stored, hashed, compared or synced — GtJava.jd (Java's Double.toString on both platforms). Text to numbers: GtJavaParse. Times: GtTime. JSON: GtOrgJson.
  • Geometry text and its hash: only GtGeom (points in → WKT + geom_hash out; comma with no space, lon first). Geom B (the Android copies onto GtGeom) is still to do, area by area.
  • Regex on file text: GtRx.findAll, never Regex.findAll (on Android Kotlin's findAll copies the whole text per match — quadratic).
  • Regex whitespace: GtRx.WS, never \s (Android = Unicode White_Space, iPad = ASCII; [\s\S] is fine). 30 uses still to sweep: GtGpxParse 10, GtImportConverter 19, GtRoute 1, GtGeom.parse 1 — one pass + re-cert.
  • JVM-only library calls (e.g. Map.putIfAbsent) do not compile for the iPad — the iOS compile check runs before every build.
  • Decoded invalid UTF-8 differs by platform — nothing stored, hashed or synced may come from reading a binary file as text.
  • Directory listing order is not defined (java.io.File.listFiles vs okio list) — where order decides a result, sort by a defined key.
  • Math (11-10, the GtMath rule): shared code calls GtMath for sin / cos / asin / hypot / pow / tan / atan / sinh / ln — never kotlin.math. Android = java.lang.Math (unchanged); the iPad = Android's own algorithms ported to Kotlin, proven bit for bit (§23). Math.toRadians / toDegrees = × Android's constants (GtJava.toRadians / toDegrees).
  • Java collections whose ORDER is an output (11-10): a java.util.HashMap's iteration order decides 2.7e's box order in queueSquaresNamed — shared code reproduces it (GtJavaHashMapLong), never Kotlin's HashMap where order reaches a result.
  • Certs: every startup job that touches a database is on GtCertGuard before a cert runs (15f: GtUtahPrivate.startup ran on OLD's copy); cross-device fingerprints leave out android_metadata; snapshot sizes are of the MASKED text; snapshots skip SQLite side files.
  • Files: a file time before 1970 is refused as java.io.File does (D14).

23. GtMath — Android's math on the iPad (11-10)

  • How it was found (07:17–07:37): the 11-09 15e iPad report had 13 rows about times. Fred 07:17: "we have prided ourselves on resolving every difference" — find it, don't accept it. MATHPROBE (a TEST-ONLY probe: the haversine's every step, Droid vs iPad, bit for bit) showed the FIRST differing step was cos (one last bit: droid …5006, iPad …5005), then everything after it. Apple's libm and Android's give different last bits on some inputs; a distance one bit different moves a track property, a rider-trail cut and anything hashed from it.
  • The rule: shared code never calls kotlin.math sin / cos / asin / hypot / pow / tan / atan / sinh / ln — it calls GtMath. Android: GtMath = java.lang.Math, unchanged by construction. iPad: GtMath = Android's OWN algorithms in plain Kotlin:
    • cos / sin: FreeBSD msun (Android's libm) — GtMathPort; asin / hypot: fdlibm — GtMathPort. Proof MATHPROBE/MATHPORT: 6,000,000 Droid values (C, S, A, H 1,500,000 each), iPad 0 DIFF (08:13).
    • pow: Arm optimized-routines pow (what Android's libm compiles), with platform.posix.fma for the fused steps — GtMathPow. First tried x·x for pow(x, 2.0): MATHPOW (08:32) showed Android's Math.pow(x, 2.0) is NOT x·x on 1,266 of 1,500,000 (Android's pow is not correctly rounded) → gtmath2b replaced it with the port: 0 / 1,500,000 (09:50). Apple's own pow would differ on 2,305.
