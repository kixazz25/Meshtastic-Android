3 · Convoy architecture — findings that cost the day

⭐ Convoy is a PERSISTENT composable. It has no entry event.

Fred: "convoy map is a persistent function it underlies all activity. it never goes away."

This is the fact that made most of the day's route-mode work futile. Every anchor proposed for a "convoy entry reset" assumed an entry that does not exist:

  • onPageFinished — fires once per page load, and the page loads once
  • onViewportChanged — fires on every viewport event, not per entry
  • LaunchedEffect(Unit) — never recomposes
  • The [Fix2] block at ~732 whose comment says "re-entry" — it means re-reads the JSON fresh instead of trusting cmSeed, a staleness concern, not a lifecycle event. It sits inside onPageFinished's postDelayed(600).

Conclusion: convoy needs no reset. The planner resets on entry, and convoy's tap handler resets at tap time. Both are sufficient. Do not re-litigate this.

4 · The two convoy breaks — both mine, both the same shape

⛔ LESSON 1 — ?: return inside an argument exits the whole function

The morning's observe patch added to onPageFinished:

android.widget.Toast.makeText(view?.context ?: return, ...)

This reads like a null-safe accessor. It is an early exit from the entire override. When view was null it bailed before tile setup, setTileUrl, the persisted-frame restore, and drawPersistedState. Convoy drew nothing. No error, no log, no JS exception — just silence.

It also displaced the original guard: val ctx = view?.context ?: return had been rewritten to view.context, moving the null check earlier into a place where failing it is catastrophic.

⛔⛔ LESSON 2 — @JavascriptInterface methods run on a BACKGROUND thread

onViewportChanged is a @JavascriptInterface method. evaluateJavascript and Toast.makeText both require the main thread and throw when called off it. The throw aborts the rest of the method — including the processViewport call that draws every artifact.

The existing code already knew this. It wraps its work in Thread { } and SpatialDisplayManager uses main.post { } for every evaluateJavascript. Two patches added today ignored that pattern:

webViewRef.value?.evaluateJavascript("window.__routeMode = false;", null)   // line 890
android.widget.Toast.makeText(context, "ROUTE MODE OFF <- CONVOY reseed entry", ...)

Both removed. var routeModeResetLogged remains at ~247, now unused — harmless, comes out with the rest of the instrumentation.

RULE: anything touching the UI or the WebView inside a @JavascriptInterface method must go through Handler(Looper.getMainLooper()).post { }.

Process failure worth naming

A blanket git checkout 00826fb55 -- ConvoyScreen.kt was proposed and executed on the claim that it "only costs toasts." It also removed the reseed block. The surgical alternative — restore from af17c85dd and delete the three offending lines — was available the whole time and is what finally worked. Prefer targeted removal over blanket revert when the file contains a day's work.

5 · ⛔ DATA LOSS INCIDENT — 2026-08-01 ~11:41 device time

What happened

An adb install -r -d registered as a fresh install rather than an update. The app lost all-files authority. On next launch SpatialDbManager opened the spatial DB, was denied, and its create-if-missing path wrote empty schemas over the existing databases.

Evidence, device log 11:44:04.805:

avc: denied { ioctl } for path=".../grouptrack_spatial.db" dev="fuse"
ioctlcmd=0xf50c scontext=u:r:untrusted_app:s0:c178,c256,c512,c768
tclass=file permissive=0 app=com.grouptrack.android

I/SpatialDbMgr: Spatial DB: 0 trails, 0 tracks, 0 waypoints, 0 routes

Result: grouptrack_spatial.db = 118 KB, grouptrack_data.db = 208 KB, both rewritten at 11:41. ~89 k trails and all artifacts gone. The app reported zero rows and carried on as if that were normal.

Fred: "11:41 was the first set of install questions. I should have pulled the plug then."

⭐ 2.6e BLOCKER — the defect, independent of what triggered it

  • Never open with create-if-missing when the file already exists. Check existence first; on a failed open with a file present, surface an error and stop.
  • Verify access behaviourally, not by permission API. The app believed it had all-files access while the OS denied the ioctl. Attempt a real read.
  • Fresh-install marker. Write a marker into filesDir (row counts, DB sizes, last-good timestamp). Private storage is wiped by a fresh install; external storage is not. Marker absent + external DB present = a fresh install just happened over existing data → stop, report.
  • Row-count sanity. A DB that had 89 k trails yesterday reporting 0 today is not a valid state.
  • Belt and braces: copy to grouptrack_spatial.db.lastgood after each successful startup.

A Play Store update could produce the same sequence on a user's device, silently. This outranks the panel work.

⭐ OPERATIONAL RULES — effective immediately

  • Install with plain -r. Never -d. Without -d, a regressed version code makes the install fail with an error instead of silently downgrading. The failure is the warning you want.
  • If an install prompts first-install questions on an already-installed app: CANCEL. Do not proceed.
  • Ten-second check after any install: adb shell ls -la /sdcard/Documents/GroupTrack/*.db — spatial DB in the hundreds of KB rather than tens of MB means it has been replaced.

Note: the standing -r -d convention in the environment file is now superseded. Update it.

Why the install registered as new — UNRESOLVED

versionCode is git-derived: gitVersionProvider.get().toInt() + vcOffset (app/build.gradle.kts:65). A derived code that can regress, combined with -d, forces the downgrade path which resets app identity.

Two earlier installs the same day (08:32, 10:47 builds) were fine. The 11:41 one was not. dumpsys evidence for that specific install was overwritten by the 12:05 recovery install — firstInstallTime and lastUpdateTime both read 12:05.

Signing key ruled out — same AAB key for three months, two successful installs the same day.

Next step: grep -rn "gitVersionProvider" --include=*.kts . — determine what it derives from and whether it can decrease. Fix by pinning the version code for local test builds, or by bumping VERSION_CODE_OFFSET. Single-build override available: -Pandroid.injected.version.code=NNNNNNNN.

Recovery — the good outcome

Complete data model rebuilt in under one hour: OSM import, Utah state trails, tracks, waypoints. GPX files in my_tracks/, tiles in maps/, OSM extracts in osm/ and the per-map JSONs all survived — only the two DBs were replaced.

This is a measured fact worth carrying into the delete-by-source decision (§7): full reconstruction is cheap.
