W2 · iPAD: A LINKABLE FRAMEWORK THE REAL NEXT WORK

Problem, precisely: grouptrack-shared declares iosArm64() and iosSimulatorArm64() and compileKotlinIosArm64 passes (18 s, first run 11-14) — but there is no binaries.framework { } block, so the module produces nothing an Xcode app can link against. Compiling is not producing.

APPROACH (write changes here AS THEY HAPPEN, not at EOD): smallest linkable artifact first, then grow it — a static binaries.framework for one target and a stub app that calls the three ported objects, before any screen, any XCFramework, any dependency manager. Rationale: the step 17 lesson was that a proven method repeated is what goes fast, and we have no proven method on the iPad side yet — so the first job is to establish one cheaply, not to build the real thing. This approach is a candidate, not a rule; if it shifts while we work it, the shift gets written in this box the moment it happens.

Research still owed, and it forks the answer:
· Plain framework or XCFramework? One binaries.framework per target is enough for a stub on one device; an XCFramework is what a distributable needs. Start with the former, know we will want the latter.
· Static or dynamic? Static links simpler and avoids embed-and-sign; dynamic is required if more than one consumer ever loads it.
· ⭐ Compose Multiplatform or not — this is the fork that matters. Fred stated 11-06 he prefers Compose MP for the iPad screens over SwiftUI. Compose MP changes what the Xcode side consumes and brings its own Gradle plumbing. Decide this before writing the Gradle block, or the block gets written twice.
· How does the app consume it — direct framework reference, SPM, or CocoaPods? Direct is least machinery for a stub.

Scope of the first step: Gradle only. No app code, no screens. Then a stub Xcode target that links it and calls GtMapState, GtMapRecipe and GtMBTiles against real data.
Verification: ./gradlew :grouptrack-shared:linkDebugFrameworkIosArm64 produces a .framework; the stub app launches on the iPad and reads Droid 1's corpus (seeded by Xcode → Devices and Simulators → Replace Container; physical devices side by side, not a simulator).
Constraints: deployment target iOS 16 so one binary runs on both iPad Pros. Paid developer account in place, so no 7-day re-signing.
⚠ What this CANNOT tell us: anything about step-3 removals — iOS has no callers of Android objects. It tells us what is missing for iOS, which is the forced ordering the V3 sequence needs.
