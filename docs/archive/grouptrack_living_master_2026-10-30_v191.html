The process (Fred 15:23, 15:26):

  1. Build the recipe for recreation from the tiles on the phone — always the first step, whatever version the user came from. The tiles are the truth, so an old install with no recipe is covered the same way (Fred: "I would suggest rebuilding json as first step of the process").
  2. No tiles → it is a new install: go straight to the standard install process.
  3. Tiles found → convert: queue every vector + elevation job from the conversion recipe, then delete the old map stores (SAT, SAT_LABELS_*, TOPO, TOPO+). Queue-then-delete (agreed 15:34): the VEC/DEM downloads do not touch the raster stores, and a kill at any moment leaves either the old maps or queued jobs — never neither. (Supersedes the 10-29 "delete the raster directories first".)

Untouched by the process: tracks, trails, routes and waypoints (Fred 15:26) — they live in the spatial DB, not the map stores. VEC / DEM stores already on the phone (Droid 1) are kept; the recipe only fills gaps.

Recovery — belt and suspenders (Fred 15:34–15:54):

  • The queue is the restart (Fred 15:34: "if it is killed the queues should pick up where the conversion died. that was the purpose of the queues."). Jobs are persisted; nothing extra is built for restart.
  • The conversion recipe stands until the next daily recipe replaces it, and no daily recipe is written while the conversion's jobs are still in the queue (a recipe taken mid-rebuild records less coverage than the user had). Failures → resubmit. Fred 15:51: "as long as replace is no — no damage on re run." Verified in code 15:55: VEC/DEM jobs queue with refreshMode=false → the normal path, where ConvoyTileDownloader ~174 skips any tile MBTilesStore.hasTile already holds; only the refresh path sets forceOverwrite=true.
  • Maps › "Restart map conversion" (Fred 15:54, name agreed: "perfect. belt and suspenders"): requeues vector + elevation from the saved conversion recipe (not that day's), replace off, any number of times.
  • The conversion stays until the next release install (Fred 15:52; CODE RULE 3): an ungated startup entry point with no "done" marker. It decides from what is on the phone — raster stores present → convert; none → step aside. After a conversion the rasters are gone, so later starts pass straight through. A start killed between queue and delete simply runs again (pending jobs skipped by the queue, stored tiles by the downloader). Restart map conversion leaves with it.

2. Principles (Fred, 10-18 to 10-21)

  • One map. The planning map is folded in; the Ride Planning / Back to Ride switches are retired.
  • A launch layer over the existing features. Each process gets ONE first screen that takes every value it needs (defaults from the ride and settings), then runs to the end with no further screen prompts. The only stop kept is the confirm before something that cannot be undone.
  • Two layouts. Group adds a lot of complexity and is used by some. Android only is the default; Group adds the Group button, CHECK IN, the GROUP readout, other carts and the lead track. One switch decides which.
  • Riders ride in landscape and pan in portrait. In landscape, panels open as a side panel so the map stays in view.
  • Every control shows an icon and its text on an opaque background, readable on any map. No hover, no long-press meanings.
  • North up only. Leaflet cannot rotate, and Hybrid labels are baked into the imagery (heading-up needs a rotating map engine: not 2.7c).
  • Show/hide is FILTER, how lines look is KEY: as onX and Gaia do, the filter is on every view.
