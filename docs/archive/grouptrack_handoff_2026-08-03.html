5 · ⭐⭐⭐ THE COLUMN FILE — design session, and what it revealed

The split (Fred's architecture, unchanged)

CATALOG = map_sources.json in assets. Sources, templates, layers, default_slots. Ships with the app, read-only, replaced every release. This is what made the {s} fix reach existing users — had the catalogue been copied to user space on first run, no existing user would have received it.

COLUMN FILE = the user's table. Slot → source, plus the active key and the URL template. A mapping table, not a replication of the catalogue.

Why this is not a reversion of 79251ae72

That commit killed an external file that held the whole catalogue, URLs included — a stale copy served stale URLs and broke tile downloads. The column file holds three rows and points at names. Different thing.

The five catalogue rules (Fred)

  1. Names never change. A rename is a tombstone plus a new entry appended at the bottom.
  2. Only the URL value is mutable, applied at release.
  3. Deletes tombstone — entries never leave the list, so sequence holds.
  4. The user owns slot assignment, active slot, and API keys. Everything else seeds from the catalogue.
  5. A scheme change is a delete-and-append, not a URL edit (Claude's addition, accepted) — different projection or max native zoom means the tiles already in that column's store stop matching the template.

⭐⭐ What the blast radius actually found

1 · defaultSlots is not a constant. It is mutable in-memory state.

:50   private var defaultSlots: List<SlotConfig> = emptyList()
:118  defaultSlots = slots                    <- loaded from the asset
:142  defaultSlots = listOf(...)              <- hardcoded fallback
:218  defaultSlots = defaultSlots.toMutableList().apply { ... }   <- the user's slot change

Line 218 is the user's selection. Nothing persists it. Six read sites — :153, :163, :172, :187, :215, :273 — all funnel through this one field, which is why the fix is smaller than the FIX 1/2/3 framing suggested: you do not convert the readers, you change where the field is loaded from.

2 · The asset is read exactly ONCE per process

init() guards at :72 with if (initialized) return, set at :119. Every ensureInit() call returns immediately after the first. Nothing else opens map_sources.json. So the asset cannot be overwriting a selection mid-session, and no tripwire is needed — reading the code answered it.

3 · ⛔ THE ORDERING HAZARD — ensureInit() / loadFallback()

ensureInit() at :282–286 calls loadFallback() when not initialized — and loadFallback() sets initialized = true at :147. So:

  • any getter fires before init(context) → hardcoded Esri loads → initialized = true
  • the real init() runs later → sees initialized already true → returns immediately and never reads the asset
  • the process runs entirely on hardcoded Esri, announced by a single Log.w nobody is watching for

That would look exactly like the reported symptom — slot 1 back on Esri, no explanation. It is an ordering bug, independent of persistence.

⭐ Fred's call: "sounds like a trap … i am afraid of why it is there." Rather than remove it blind, phase 1 logs the request with a stack trace naming the caller and refuses to write the column file at all when fallback ran. Nothing removed, nothing commented, no risk — and if it fires, the caller names itself.

4 · Resolution is LATE, and the job carries a slot name

[W] ConvoyDownloadQueue.kt:706   .putString("refresh_slot", entry.refreshSlot)
[R] ConvoyCorridorWorker.kt:52   val slotName = inputData.getString("refresh_slot") ?: ""
[R] ConvoyDownloadWorker.kt:39   val refreshSlot = inputData.getString("refresh_slot") ?: ""

The worker resolves slot → source → URL at execution time. A slot that changes between queue and execution silently redirects the download — and stores are keyed by the layer's cache_dir, so the wrong tiles land in the store you believe holds the right ones. No error. Quiet success against the wrong source.

⭐ This is why the column file is load-bearing, not merely correct: it makes late resolution safe.

5 · Fred's mechanism for the download failure

"esri would not work when the connection was established with google … the reason for the failure." If the downloader holds a client configured for the Google host and the slot re-resolves mid-run to an Esri template on a different host, in-flight requests aim at the wrong endpoint and fail silently — which is exactly what "CORR SAT failed" with no exception and no HTTP status looks like.

⚠ Hypothesis, not finding. Unknown whether the downloader keeps a persistent client per host or builds a request per tile. Per-tile would mean contamination rather than failure. Both disappear once resolution is stable, which is the useful part.

6 · The verification loop was itself the contamination loop

Fred's method for confirming tiles were being replaced was to view offline maps of that column — which required switching sources to flush the cache. Switching sources is what triggers the re-resolve. So checking whether the swap was working is what broke the swap, and repeating the check repeated the damage.

⭐ This likely also explains the refresh "reset" (5%→4%). A job re-resolving mid-run and restarting its accounting against a different tile set would look exactly like a percentage going backwards. Retest after phase 2 — a free measurement that may retire a P0-shaped item.

Two other things found

The write hook already exists. updateSlotSource() at :213 already calls saveExternalJson() at :221 — an empty body. Persistence was one function to fill, no new call sites.

ConvoyMapSourceScreen.kt:59 claims something untrue: "Writes slot changes to external Documents/GroupTrack/map_sources.json." It does not. The comment describes the feature being built now, left behind when saveExternalJson() was gutted.

An orphan local: ConvoyMapViewerScreen.kt:97 — var activeSource by remember { mutableStateOf("SAT") }, never synced to the global, and it drives the map-bar highlight via isActive = activeSource == label. The UI can show SAT highlighted while the source is something else. Convoy has no equivalent. Independent of the file work.

What the patch does — five anchored edits

EDIT 1 · Column-file plumbing, inserted after apiKeysFile(): columnFile() → Documents/GroupTrack/map_slots.json, currentVersionCode(), syncColumnFile(), readTerminated(), writeColumnFile(), terminatedColumns().
EDIT 2 · syncColumnFile(context) called at the END of init(), after the asset parses so defaultSlots and sources are populated.

EDIT 4 · setActive() persists the active key. It was in-memory only, defaulting to "SAT" at :53.
EDIT 5 · loadFallback() records that it was requested — sets a flag and logs with a stack trace. Its own behaviour is unchanged.

The rules the patch encodes

ConditionAction
Column file absentSeed from defaultSlots + catalogue, stamp version code
Present, same version codeLoad only. No install pass.
Present, different version codeINSTALL PASS — refresh url_template per column from the catalogue by source_id; mark status: "terminated" where the source is gone; slot assignments never touched; re-stamp
Present but unreadableLOG AND STOP. No seed, no overwrite.
Fallback ranNO WRITE AT ALL. Log and return.

Why "unreadable ≠ absent" is not pedantry

Treating a read failure as absent is the create-if-missing shape that destroyed the spatial DB on 08-01 (~89k trails). All-Files access has been observed reporting true while denied. If an unreadable column file were treated as absent, seeding would overwrite the user's assignments with catalogue defaults — the exact bug being fixed, arriving through the back door.

Design points inside the patch

  • Stores the URL TEMPLATE, not a resolved URL. resolveUrl() at :277 injects {key} at use time, and keys are persisted separately in api_keys.json.
  • Atomic write — temp file then rename. A truncated column file read at worker start is a mystery a week later.
  • map_slots.json, not map_sources.json. externalJsonFile() at :66 already claims that name and it is the file 79251ae72 killed.
  • The install pass carries the user's assignment forward — priorById wins over slot.sourceId. A release may retire a source; it may not repoint a column the user chose.

DECISION OWEDWhat "terminated" means

The patch currently marks a column terminated when its source_id is not found in the catalogue. Fred's rules call for an explicit tombstone instead — a status field on the catalogue entry, so a retired source stays in the list and keeps the sequence. That is an asset change plus one line here. Absence works today because nothing has been retired yet; the explicit tombstone is what rule 3 requires.

Terminated-source behaviour, as settled

  • The installer expires the source and stops. Notification is somebody else's task.
  • On map load with a terminated column, the selector fires. User picks or cancels; cancel means it returns next restart.
  • The column keeps serving its current maps throughout — offline tiles are unaffected, nothing blanks, nothing blocks an off-grid start.
  • A terminated column is unchecked and not selectable for new downloads or refresh.

8 · Lesson of the day

⭐⭐ The method is trusted. The mistake was not removing the instrumentation.

Fred, correcting the record: "the breakthrough on route was trapping the state and visually seeing what triggers were failing. i chose the method is trusted. the mistake was not removing the instrumentation when we finished."

So the lesson is not "instrumentation is expensive." It is:

  • Instrumentation is temporary by definition. It comes out when the task closes, in the same commit that closes it — not on a cleanup list where it accumulates until it does damage.
  • All three of this week's rendering failures happened in the window between "found it" and "someday we'll clean that up."
  • The mechanical rules still hold — Log.d not Toast, nothing in an argument position, off-main-thread awareness — but those are about what you write, not whether.

⚠ Live instance: showProximityPopup and the Kotlin onProximityTap are dead but still present. Same pattern, smaller stakes. They come out with their caller.

⚠ And one about direction

Fred called the direction on the FIT bug — "every fiber of my body blames proximity" — while my elimination of that code range was wrong twice. Recorded because the reasoning pattern matters more than the fix: I was scanning for one shape of evidence (function name() and reported the range clean when the scan could not have seen what was there.
