⭐⭐ THE ARCHITECTURE DECIDED AT END OF DAY (Fred) — TWO-TIER STAGING

Fred: "end with an import spatial DB we can use the download map regions tools to draw areas to be imported from second spatial DB."

A STAGED reference DB sits on the device; the LIVE spatial DB holds only what the user deliberately pulls. The user draws an area with the existing region tools and imports just that area's trails across.

⭐ This solves the volume problem outright. 106,879 trails never need to land in grouptrack_spatial.db — so the worry about tripling the viewport bbox-scan working set disappears. The full state costs disk, not query time.

The subset schema ALREADY supports it: every row carries min_lat/max_lat/min_lon/max_lon with a bbox index, so an area query against the staged DB is fast. Built for the import step; exactly what this needs.

It also makes the 50-state ambition clean — each state is another staged file and nothing changes app-side. Fred: "we need a process that is repeatable for other states … identify the state, download and process without intervention." DISCUSS AFTER the three states are imported.

⭐ THE FINDING THAT MATTERS — and the cost of the Geofabrik path

OSM is the ONLY source in the database carrying motorized_allowed. Measured on the live DB:

UGRC has 49,098 trails and not one carries a motorized value. Neither does NPS. For an OHV app that reframes OSM from a coverage supplement into the only source of legal-access data.

⚠ BUT THAT FIELD DOES NOT SURVIVE THE GEOFABRIK PATH. The free roads layer columns are osm_id, code, fclass, name, ref, oneway, maxspeed, layer, bridge, tunnel — confirmed against the real file. No motor_vehicle / atv / 4wd_only / surface at any price (surface is commercial-only; the access tags do not exist in either tier).

What is gained instead: fclass carries track_grade1..5, real OHV difficulty data, and it is present on every track rather than sparsely tagged. Utah: track 49,499 · grade5 9,840 · grade3 5,507 · grade2 3,868 · grade4 3,479 · grade1 327 · path 15,563 · bridleway 1,471.

⛔ motorized_hint in the subset is INFERRED from fclass — a track is physically wide enough for a vehicle, a footway is not. That is PHYSICAL CAPABILITY, NOT LEGAL ACCESS. It sits in its own column so it can never be mistaken for the real field. Do not map it onto motorized_allowed without deciding, deliberately, that an inference is acceptable there.

📄 ALLDOCS — ROOT CAUSE FOUND AFTER TWO WEEKS

Not one HTML doc had ever reached GroupTrack_AllDocs.txt. Every section marker was === GroupTrack_*.docx ===; zero HTML markup anywhere.

Cause: Step 4's HTML-folding loop (added in V13) was CORRECT — but Steps 2/3 copy into $DOCS with the glob "$DOWNLOADS"/GroupTrack*."$ext", and bash globs are CASE-SENSITIVE. Filenames like grouptrack_*, SCOPING_*, BLUEPRINT_* matched none of it. V13 fixed the folding; the copy filter silently starved it.

Fixed via patches O → P → Q: collect by EXTENSION not name prefix (a prefix whitelist is the same bug in a new coat), drop json, exclude the script's own generated outputs (a stale Downloads copy would CLOBBER the fresh xref), skip (n) duplicates, 10 MB cap, 45-day recency window.

⚠ WHAT WENT WRONG TODAY, AND WHY (worth not repeating)

⭐ THE SINGLE BIGGEST CAUSE: every HTTP failure looked identical. httpGet read only inputStream, which THROWS on any non-2xx, and logged ex.message — which for several common exceptions IS THE URL. So a timeout, a rate limit, a rejected query and an OOM all produced the same line. Overpass had been explaining itself in the response body the whole time, into a stream never opened.

The moment patch V landed, the answer appeared immediately: HTTP 504 Gateway Timeout — "Dispatcher_Client::request_read_and_idx::timeout. The server is probably too busy." Nothing was broken after the launchMode and bbox fixes; the public Overpass instances were simply overloaded all afternoon.

  • ⛔ I switched the endpoint to kumi.systems on a hunch that it was the faster mirror. It refused every request for hours. Overpass Turbo then answered the SAME query against the main endpoint in seconds. Changing a working default on an untested assumption cost most of the afternoon.
  • ⛔ I sized cells from one bad sample. A 63-second query on a congested server became "3-mile cells", which for Utah is 29,299 cells. The real capacity, measured in the browser: 2,658 ways over 900 square miles in a couple of seconds. ~640× the area I had assumed was the limit.
  • ⛔ I chased alternatives for an hour — PBF (needs a node index; no maintained Android library), Bunting Labs (right shape, EXPIRED CERTIFICATE on the endpoint), BBBike (right output, request-and-email). Fred's original instinct — bulk extract, process locally — was correct; I just picked a QUERY api when the job needed an EXTRACT service.
  • ⚠ My laptop certificate failures were REAL but unrelated — Python (stale CA bundle), curl (HTTP 000), Chrome (ERR_CERT_DATE_INVALID on buntinglabs). Clock was correct. Android uses the system trust store and was unaffected throughout.
