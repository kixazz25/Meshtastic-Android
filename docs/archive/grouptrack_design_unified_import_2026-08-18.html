GroupTrack — Unified Trail Import — Design Spec

Authored 2026-08-18. Captures the full design as discussed. This document is the build reference.

ONE SENTENCE: Merge all trail import paths into a single bbox-driven pipeline that processes every available source, enriches existing records via upsert with alias preservation, and is triggered automatically on fresh install or manually from Map Features → Import Trails by Area.

1. The Two Entry Points

1A. Fresh Install (Authority Gate)

  • Trigger: Authority gate detects trails AND waypoints tables both have zero rows.
  • GPS auto-detect: Location permission is already granted (cleared by the gate). Get a GPS fix, intersect against state bboxes from the shipped Geofabrik asset. Pre-select the detected state.
  • UI: "Based on your location, your Home state is [State]." Two buttons: LOAD [STATE] TRAIL DATA (primary) and Select a different Home state (opens state picker).
  • Processing: Geofabrik downloads the whole state file directly (already segmented by state — no bbox filtering needed). All other sources use the state bbox to filter. ALL sources run, NO checklist.
  • Completion: Gate re-checks → trails > 0 → gate clears → rider sees Ride Map with trails loaded.

1B. Post-Install (Map Features → Import Trails by Area)

  • Entry: Map Features panel → "Import Trails by Area" (renamed from "Import Trails").
  • Action: Opens the download panel with "Import Trails by Area" pre-checked (passed in, not user-selectable on the panel — row stays greyed on the download panel itself).
  • Bbox: Rider draws a rectangle on the map using the existing bbox drawing function.
  • Confirmation: Shows drawn bbox coordinates, a map of the area, which states are intersected, and a flat list of all sources with estimated counts.
  • Processing: Geofabrik downloads each state that intersects the drawn bbox (may be multiple). All other sources use the drawn bbox. ALL sources run, NO checklist.
Both paths are identical except for how the area is defined. Fresh install = state picker (Geofabrik uses whole state file). Post-install = drawn bbox (Geofabrik uses bbox-intersected state files). Same controller, same source loop, same upsert, same progress UI.

3. Source Model

Sources are flat — not tiered by state vs federal vs OSM. Each source is a data provider with a format. The pipeline dispatches to the right handler per format.

Source Discovery

Intersect the area bbox against each catalog source's bbox (CatalogSource.boundaryN/S/E/W). If they overlap, the source has trails in the area and gets processed.

Source Record (existing CatalogSource data class)

FieldPurpose
idUnique source identifier
nameDisplay name ("Utah UGRC Trails")
agencyData provider
formatProcessing format: Geofabrik GPKG, ArcGIS REST, GeoJSON, Shapefile
scopeCoverage scope
boundaryN/S/E/WSource coverage bbox
trailCountEstimated trails in source

Processing Order

  • Order does NOT affect correctness — upsert rules guarantee the same result regardless.
  • OSM (Geofabrik) processes last as an efficiency choice — 70% of OSM trails have minimal data, so downloading 663 MB last avoids it entirely when other sources already covered the trails.
  • Typical import: 4–7 sources depending on the area.

4. The Upsert Rules

THIS IS THE CRITICAL CHANGE. Current code: INSERT OR IGNORE INTO trails (...) ON CONFLICT(geom_hash) DO NOTHING. A duplicate from a richer source is SILENTLY SKIPPED. New rule: enrich existing records.

Field-Level Rules

ConditionAction
New geom_hash — trail not in DBINSERT the full record. Tag with source name.
geom_hash matches, existing field is blank/empty/"Unnamed"UPDATE with incoming data. "Unnamed" is treated as blank.
geom_hash matches, existing field is non-blankKEEP existing data. Do not overwrite.
geom_hash matches, both have a real name (not "Unnamed")Keep existing name. ADD incoming name as an ALIAS.
geom_hash matches, existing is "Unnamed", incoming has a nameREPLACE "Unnamed" with the real name. Do NOT alias "Unnamed".

SQL Shape

INSERT INTO trails (geom_hash, name, trail_type, surface_type, source_id, ...)
VALUES (?, ?, ?, ?, ?, ...)
ON CONFLICT(geom_hash) DO UPDATE SET
  name = CASE 
    WHEN trails.name IS NULL OR trails.name = '' OR trails.name = 'Unnamed'
    THEN excluded.name
    ELSE trails.name
  END,
  trail_type = CASE
    WHEN trails.trail_type IS NULL OR trails.trail_type = ''
    THEN excluded.trail_type
    ELSE trails.trail_type
  END,
  surface_type = CASE
    WHEN trails.surface_type IS NULL OR trails.surface_type = ''
    THEN excluded.surface_type
    ELSE trails.surface_type
  END,
  source_id = excluded.source_id
  -- source_id always updates to most recent source

Alias insertion is a separate step after the upsert: if geom_hash matched AND both old and new names are non-blank and different, insert the incoming name into the aliases table.

Two Levels of State

LevelValuesMeaning
Manifest (process_state)in_progress / completedIs this import run finished?
Source (status)pending / in_progress / completedPer-source progress

in_progress source carries last_item for recovery pickup. completed source carries imported count.

Controller Loop

  1. Build the manifest from bbox intersection against catalog + Geofabrik asset.
  2. Write to Documents/GroupTrack/imports/import_[date]_[area].json.
  3. Loop: find first source where status != "completed" → dispatch to its process wrapper → on success mark "completed" + write count → update JSON on disk → next.
  4. All completed → set process_state = "completed" + completed_at → show summary → done.

Recovery on App Restart

  1. Authority gate scans Documents/GroupTrack/imports/ for any JSON with "process_state": "in_progress".
  2. Found → "A trail import for [area] was not finished. Complete now?" — Yes / Not Now.
  3. Yes → find first source where status != "completed". If in_progress, resume from last_item. If pending, start fresh. Upsert on geom_hash absorbs anything already in the DB.
  4. Not Now → proceed to Ride Map. Same prompt next launch.
Incomplete import check runs BEFORE zero-data check in the gate — a half-finished import means they already started and should finish.

History

Completed manifests stay on disk. They accumulate as a record of what was imported, when, from which area, how many from each source:

Documents/GroupTrack/imports/
  import_2026-08-18_utah_state.json       ← fresh install
  import_2026-09-02_ut-nv-az_bbox.json    ← added a riding area
  import_2026-10-15_colorado_state.json    ← trip to Colorado

11. Open Questions

  1. Alias table: Does one already exist, or does it need to be created? What schema — (trail_id, alias_name, source_id)?
  2. Recovery on failure: If a source fails mid-import, log it and continue to next? Or halt? (Design says: log and continue, report at end.)
  3. Re-import same area: What happens if the rider imports the same area twice? Upsert handles it (no-ops on existing data), but should the UI warn?
  4. Tile downloads: Should tile map downloads for the area be included as another source in the same flow, or stay separate?
  5. Trail count estimates: Can we show estimated counts before downloading, or show "available" and update during download?
  6. Skip on fresh install: If the rider cancels the state picker, does the gate re-trigger next launch, or let them through with zero data?

12. Build Sequence (Suggested)

  1. Geofabrik State JSON Asset — mine the listing, ship the file. Zero code dependencies.
  2. Upsert SQL — change the one INSERT statement. Test with existing import paths.
  3. Alias table + insertion logic — create table, wire alias check into upsert flow.
  4. Import Controller — the orchestrator loop. Test with existing sources and existing bbox drawing.
  5. Progress UI — step-state display, completion summary.
  6. Menu/panel changes — rename, remove, pre-check wiring.
  7. State Picker + GPS detect — the fresh install screen.
  8. Gate integration — add zero-data condition, wire state picker as resolution.
  9. Bbox Confirmation Screen — coordinates, map, source list.
Every step except #7 and #9 is usable independently. The upsert improves existing imports immediately. The controller can be tested from the existing greyed-out button. The menu changes are cosmetic. The state picker and confirmation screen are the only genuinely new UI.
