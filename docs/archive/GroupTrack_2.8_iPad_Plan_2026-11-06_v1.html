GroupTrack 2.8 — the native iPad app

Started 2026-11-05/06 on the Mac. 2.7e is released and locked; 2.8 is the iPad.

1. What 2.8 is

  • 2.8 ends with a deployed native iPad app (roadmap, Fred 10-22). 2.9 = one-way data sync Android → AWS (services layer only, no paygate). 3.0 = AWS services: paygate (e.g. the first 200 users free for a year), Mac/PC planning station against the AWS model, map-licensing review.
  • Two phases (Fred 10-02): Phase 1 — GroupTrack on iPad with group functions off (riding solo: map, search, AI routes, rides, imports, recording, manual/help). Phase 2 — the GroupTrack Group Comm plugin (mesh radio, group awareness).
  • The goal: an iPad app that looks and feels as much like GroupTrack on Android as technically possible (Fred 10-02).

2. Decided (from the design corpus, 07-04 … 11-05)

#DecisionSource
D1One map page for all platforms. The 2.7e MapLibre GL JS page (assets/vecmap) runs in a WKWebView on iPad/Mac; per platform only the native pieces differ (tile/asset serving, the SQLite database, files, GPS, Bluetooth). Doing 2.7e on Leaflet would have baked Leaflet into the layer iPad waits on.2.7e plan 10-29; 07-04
D2GroupTrack stays a standalone app; the radio is a plugin. GroupTrack owns all screens; the comm side is headless services behind an API (values in, mesh functions run, results out). Ride radio settings handed over as WHAT; the comm side decides HOW.10-02, 10-08, 10-12
D3The iPad radio plugin = our own open-source fork of the Meshtastic-Apple mesh code, headless — no base Meshtastic install, no Meshtastic menus. Bluetooth first (the iTAK model); Wi-Fi radio↔iPad set aside (range).10-02, 10-08
D4CoT is GroupTrack's data format; the comm layer does the wire encoding per transport (compact TAK packet on mesh, TAK protocol on IP).10-03
D5Prove iPad radio set-up from the same ride config data before writing plugin code — a blocker found early if it fails.10-02
D6The Android app is never rebased on experimental mesh code; 2.7e stays on its proven integration. Emergency 2.7e fixes only on 2.7e-support.10-02; 11-05
D7One unknown at a time: prove the environment with known-good artifacts before adding KMP, then KMP before iPad code.07-04
D8GroupTrack needs a Wi-Fi + Cellular iPad (Wi-Fi-only iPads have no GPS chip). No SIM or plan needed; the first fix is slower without data.11-05
D9Google Play only on Android; the App Store for iPad (Apple Developer Program, Fred enrolled 11-05).10-19; 11-05

6. First steps (proposed order)

  1. ☐ Build and run Meshtastic-Apple unchanged in the Simulator (proves Xcode + Swift + the mesh code; shows its minimum iPadOS) — clone into its own folder, never into the GroupTrack repo.
  2. ☐ A minimal iPad shell: a SwiftUI app with one WKWebView that loads the 2.7e map page from the app bundle (tiles/fonts through a URL scheme handler) — the first GroupTrack map on iPad, in the Simulator.
  3. ☐ The entanglement inventory of the 181 Kotlin files (pure / Android-only / screen) → decides O1 and the size of the shared module.
  4. ☐ KMP spike: one pure-logic piece (e.g. RideCalc or the route-recipe model) built as a shared module and called from the iPad shell.
  5. ☐ Radio set-up proof (D5) on a real iPad with a radio — Bluetooth needs real hardware.
  6. ☐ Then the phase 1 build list, panel by panel.

Rules carried over: one command at a time; dated Python patch scripts with marker guards; never reuse a filename; code rules 1–3; say so first when a tool or process isn't working; the living docs are the record.
