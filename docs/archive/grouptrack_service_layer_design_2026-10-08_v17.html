R7.1 THE BOUNDARY RULES (Fred 10-08 — apply to every service)

  1. GroupTrack owns the panels. GRP Awareness and every GroupTrack screen stay GroupTrack's — same rows, buttons, messages. The comm module has service-level access only: it executes, headless, and returns results. (Rejected 10-08: moving the GRP Awareness panel to the comm side — "not an option".)
  2. Requests go GroupTrack → comm; events come comm → GroupTrack. Every crossing is a sender on one side and a matching function on the other. Actions (connect, pair, disconnect, forget, reconnect, scan, deliver, apply config, open menu) are requests received by comm service functions; what happened (link connecting / connected / lost, radio list, traffic pulse, heartbeat, report received, role, apply result) are events received by GroupTrack event functions.
  3. A request never waits for its outcome. It answers accepted / NotSupported; the outcome arrives later as an event.
  4. Recovery is a request; the action is performed in the comm module; reconnection is an event reported by the comm module. GroupTrack decides recovery is needed (riding with a group, radio silent) and calls CommLink.reconnect(); the comm module runs the attempts; CONNECTING → CONNECTED or a failure comes back as an event; GroupTrack shows green or, after failures, the power-cycle banner.
  5. Only the comm module emits link and radio events; only GroupTrack decides. No hand-set flags from the shell or the tick (today: Main.kt and the tick set GrpAwarenessLauncher.connected / talking / needsRecovery — these become event receivers).
  6. Errors are events with a reason code; GroupTrack owns the words. e.g. LinkFailed(radio, RECOVERY_FAILED, attempts=3) → GroupTrack: "Your radio is not recovering — forget it and pair again" (+ FORGET / PAIR, each a request). Reasons so far: RECOVERY_FAILED, BOND_LOST, PIN_REJECTED, NOT_FOUND, BLUETOOTH_OFF, APPLY_FAILED(+failed checks). No rider text inside the comm module → identical messages on Android, Apple, Nucleus; one place to change wording; errors countable by reason.
  7. No new direct Meshtastic calls in GroupTrack. Anything new goes through the API.
  8. One service at a time, both directions (Fred: "slow and steady"): plan the service (request, event back, error reasons) → one patch → one Mac build + tablet check of that service → commit. The where-used inventory (gen_xrefs_v2.sh → docs/where_used_raw.txt) isolates where and how many before each step and proves removal after (Fred 10-08: use the existing tool, not a new one). To check at first use: the function universe is built from convoy/ only — calls from the shell (Main.kt) may not appear; if so, say so and fix the tool.
  9. Finish line: step 6 (GroupTrack into its own module) — the compiler lists anything left; zero errors = pruning done.

R7.3 The plugin / separate-app model and licensing (Fred 10-08; not legal advice — confirm with a lawyer)

  • How ATAK does it: plugins are loaded by the host (never started separately); Meshtastic's ATAK plugin does not bundle mesh code — it binds to the separately installed Meshtastic app's background service (this repo: mesh_service_example, core/api/MeshtasticIntent.kt). Two programs at arm's length. iOS cannot load plugins at runtime — anything iTAK supports is built in (iTAK's Meshtastic specifics not verified).
  • GroupTrack today and through 2.7b: comm is compiled into the same APK and started by GroupTrack at session start (GroupCommPlugin.start(setup) from the Group riding switch). The whole app is one GPL-3 work — keeping the source public keeps it compliant. In-app separation does not change the licence (§11).
  • The separate-app path (§11 path 2): GroupTrack Comm = our own open-source (GPL-3) build of the Meshtastic code as its own app; it owns the radio and Bluetooth, runs headless as a bound service, provides service-level access; riders need no stock Meshtastic. GroupTrack is its own app talking to it at arm's length. Practicalities: Play cannot silently install a second app → two listings; GroupTrack offers "Install GroupTrack Comm" when the Group riding switch is turned on (riders without a radio never need it); one app holds a radio at a time; the API is versioned and checked at start (capabilities()).
  • Native screens with two apps: GroupTrack requests a comm screen (an intent); it opens ON TOP in the same task, uses the live connection (not a new session), can be styled as a panel over the dimmed map; Back returns to GroupTrack; the outcome comes back as an event. It cannot be EMBEDDED inside a GroupTrack panel (Android does not allow one app's UI inside another's).
  • Confirmed 10-08: the boundary is logically in the right place (radio = comm; panels, rides, decisions = GroupTrack; the API carries no Meshtastic types — the module compiles with nothing from Meshtastic), and the handoffs are compatible with the licensing terms (open-format requests/events = the arm's-length interface path 2 needs).

R5.3 The rules: duplicates and the two boundaries (Fred 10-07)

  • Receive: for each sender (uid), keep the time of the last update processed. An arriving update is processed only if newer than the last seen and the last one is outside the boundary for the path it came on; otherwise dropped — whatever its source. Once a fresh Wi-Fi copy is in, the LoRa copies that follow are not processed. Drop on (uid, time) before any expensive parsing.
  • Send my position: Wi-Fi every 5 s; mesh only if my last update is older than the mesh boundary → a cart on Wi-Fi never sends on LoRa; a cart off Wi-Fi does, automatically.
  • Boundaries = two message cycles (one missed packet never opens the second path), with 30 s with no broadcast as the stationary floor: moving Wi-Fi 2 × 5 = 10 s, mesh 2 × 6 = 12 s; stopped 30 s. OPEN: stopped = 30 s or 2 × 30 = 60 s.
  • Bare radios (already identified) beacon on LoRa themselves, arrive only by LoRa (always processed) and need no positions (no screen).
  • Text: (sender, text) within a window → one message, the same as his store.
  • Same as Nathan? Partly: he rate-limits LoRa per sender and guards loops, but sends every local update to LoRa whatever Wi-Fi delivered, and injects every LoRa position into Wi-Fi with no newer-than check. Our rules live in our translator and need nothing from him. Suggest to him: a receive-side boundary before injecting; holding back LoRa when Wi-Fi delivered and no LoRa-only listener needs it — the Nucleus as a transport-aware router.

R5.4 Can Wi-Fi bypass LoRa? (Fred 10-07)

  • Not with today's design: (1) Wi-Fi needs a box (tablets cannot do device-to-device); (2) our radios broadcast by themselves (TAK_TRACKER) whatever the tablet does — the biggest obstacle; (3) his bridge puts each box's local Wi-Fi traffic ONTO LoRa (rate-limited).
  • Achievable in 2.7b cycle 3 when GroupTrack becomes the sender: the radio's own broadcast turned right down; the app chooses Wi-Fi near a box and LoRa only when the boundary says the Wi-Fi copy did not get through; the bridge interval set long. The box must act as the router (it is the only device on both networks).
  • But for a spread-out ride Wi-Fi does not reach (Fred: "a 10-cart ride with carts a mile apart is an issue, Wi-Fi or not"). The tablet's 5 GHz link to a box is short; LoRa is the network. Wi-Fi/Nucleus = a bonus for clustered situations (staging, camp, regroup, tight convoy); a box's best value on a trail ride may be as a LoRa relay (30 dBm, better antennas) at lead/tail or a high point. Nathan's product has the same stress point: LoRa capacity and hops.
  • Preset: Fred — SHORT_FAST cannot carry trail distances; MEDIUM_FAST is the best we can do (≈ 3× slower than SHORT_FAST); 1 W radios rated 5–20 mi, plan on ~70 % derating. A Nucleus on a GroupTrack ride must run MEDIUM_FAST (radios on different presets cannot hear each other) — implications for his voice.
  • Airtime (rough, to be replaced by the model): one report ≈ 210 ms on air. 10 moving carts: 6 s ≈ 35 % (70–100 % with hop-2 relays — saturated); 11 s ≈ 19 % (40–55 %); 15 s ≈ 14 % (30–40 %); 20 s ≈ 10 % (20–30 %). The interval table (moved to 2.7b) is therefore required for rides beyond 3–4 carts.

C · CoT IS GROUPTRACK'S DATA STANDARD (Fred 10-03)

Fred: "This will move us closer to CoT-layer processing, rather than the cyclic 3-second process that could be showing 6-second-old values." — and: implement CoT for our panels and move to the standard.

  • Freshness: a report is applied the moment it arrives; its age is the network's, known from the message's own time — not up to a tick plus a broadcast interval.
  • CoT's time / start / stale = the validity window: a cart is live until its own report's stale time; the one deadline timer = the earliest stale time in the group.
  • Layer 1 and the panels use a CoT-shaped model (uid, type, time/start/stale, point with accuracy, contact, group + role, track, status) — CoT meaning in GroupTrack's types, no raw XML in screens.
  • Transports pick the wire format: mesh = Meshtastic's compact TAK packet (LoRa cannot carry CoT XML); IP = the TAK protocol. The comm layer converts both ways.
  • GroupTrack's own concepts in a CoT detail extension (ride id, check-in, END) — other TAK apps ignore it.
  • Roles: LEADER→Team Lead · MIDDLE→RTO · TAIL_GUNNER→Forward Observer · RIDER→HQ · team Cyan (2.7a mapping).
  • Interop — ATAK coexistence and partner TAK layers become near-free: a GroupTrack position is a CoT position.
  • Research to confirm: the CoT schema (MITRE / TAK protocol documentation); which CoT fields Meshtastic's compact TAK packet carries over the mesh (the comm layer fills what it cannot, e.g. stale from the reporting frequency).

0 · THE GOVERNING RULE — OPEN PAYLOADS, PRIVATE PROCESSES (Fred 10-02)

Fred: "Every payload and packet handed off between device and services must be open source and then hidden by a process."

  • Open: every payload and packet crossing between a device and a service — the ride package, the config doc, TAK messages, mapLoads, the service contract's plain data — is a published, open format.
  • Private: the work done on it — the planner, the trail model, the corridor method, the configurator — runs inside a process (a plugin, or GroupTrack's 3.0 server) and is not part of the format.
  • This is R2 (plain data) raised to a product rule: what crosses is open; what computes is behind the door.

1 · Why — Fred's decisions, 10-02

  • iPad: GroupTrack stays standalone; a vanilla Meshtastic install + an open-source GroupTrack plugin coordinates the hand-off. Configuration is handed off to Meshtastic ("a clean break").
  • Android: separation stays minimal — one install; the API is built in the same app now and can be separated later; the implementation calls today's proven code, never replaces it. Never rebase Android on experimental mesh code.
  • Shape: "one install, two unaware implementations and a service layer between them." The plugin is a mesh/IP TAK messaging plugin.
  • The line: check-in, radio connect, role swapping, the broadcast frequency of payloads and receiving vanilla TAK-aware packets are services; applying our rules to that data is a GroupTrack function.
  • TAK is fundamental to the process: message formats and exchanges are GroupTrack's; GroupTrack requests frequency and method; the mesh/IP layer implements them — two layers.
  • The config doc requests what; the service decides how. Processes and data are independent of the implementation — don't wait for new hardware (Nathan's): it is a transport behind the wall; the data contract is revised additively or a service is added.
  • Licensing: the GPL fork makes the whole Android app open source — fine now; separation for scale (~40,000) is an open decision; building to this contract keeps that path open (section 11).

21 · Open formats — the ride package and mapLoads

Fred: "Our JSONs are clean, platform-independent hand-offs of ride-related data for GroupTrack and possibly ATAK. The more open, the better the product and the plugin positioning." And: "We will publish a standard API with map-load info, passed as JSON from our payload."

  • Publish the spec (permissive licence): the ride package and the config doc — fields, units, required vs optional; sample files and a validator.
  • Versioned, additive only (formatVersion): new fields may appear; existing ones never change meaning.
  • Built on existing standards: GPX (route, track, waypoints), TAK/CoT (messages), Meshtastic channel URL (network); GroupTrack adds the bundle (date and time, trailhead, notes, mapLoads).
  • The format is open; the data is not always. A private ride carries its network key — the invite stays the secure carrier, sent only to invited riders.
  • GroupTrack shares rides, not trails (Fred 10-02): route descriptions, distances, trail names and features — produced works under OpenStreetMap's licence. The trail database is not distributed → no share-alike. Attribution in every ride package and export: "© OpenStreetMap contributors".

mapLoads — results only (Fred: "they don't own the method; they process the results with their key assets, their trail models")

A job list (Fred 10-02): GroupTrack's map download creates a list of maps by boundaries to be downloaded; partners use the payload — or the API (§23) — to get that list back and queue the downloads in their own job queue, as GroupTrack does in its download queue.

  • Results only — tiles per zoom and map type; no widths, no formula, no algorithm. GroupTrack owns the corridor method.
  • Rows ("x from–to at row y") keep a long corridor small.
  • mapType is a role (satellite, topo) — each app fills it from its own sources.
  • Totals include the area equivalent — the payload proves its own saving.
  • ⚠ While GroupTrack Android is distributed as GPL, the corridor code is in its public source: "the method is GroupTrack's" = originated, maintained, branded. To keep the method itself private, it runs on the 3.0 server (§23).
