**THE GUIDING PRINCIPLE (elegantly simple): "My data is my data; everybody else's data is an alias."** Anything you authored is primary; anything arriving from elsewhere attaches as an alias. Never overwrites anyone. Every rule below follows from this.

**THE UNIFIED RULE (all four artifacts — trails, tracks, waypoints, routes):**
  - **Same name + same geometry → REMOVE** (true duplicate).
  - **New name + same geometry → ALIAS** (keep original + name, attach the new name; no second row).
Same OUTCOME logic everywhere. What differs is only the DETECTION basis per type (below).

**ALIAS RECORD CARRIES A DATE (added 2026-05-31).** An alias is not a bare name — it is a small record: (name + date [+ likely source/who]). The DATE enforces the AWS same-day rule: when a same-geometry contribution arrives, check "already an alias for this geometry on this date?" → YES = skip; NO = add the dated alias. Alias uniqueness key = (geometry + date): ONE alias per geometry per day. Concrete SCHEMA requirement — the alias table/field must include a date.

**NAMES ARE LOCAL-PRIMARY — first-occurrence model, NOT a replicated DB (clarified 2026-05-31).** The AWS store is a FIRST-OCCURRENCE database, not a mirror of everyone's data. Local devices are NOT forced to match AWS.
  - YOUR name stays YOURS. A route you made as "abc" on your device STAYS "abc" — your name, never overwritten. The same physical route may already be known as "def" on AWS (someone got there first). That's fine; "abc" remains your authoritative local name.
  - Aliasing accumulates INWARD, at insert. When you pull an AWS route DOWN and it inserts into your local DB, the AWS name ("def") becomes an ALIAS in your DB; your "abc" stays primary. Whichever side pulls, the incoming name attaches as an alias; the local/first name stays authoritative on that side.
  - So there's no central "canonical name" forced on anyone — each side keeps its own primary name and accumulates the others' names as aliases.

**MANUAL vs AUTOMATED — the core of this goal:** the 82,220→42,451 trail cleanup was a ONE-TIME MANUAL scrub on the PC. That does NOT exist in the product. What must be BUILT is an AUTOMATED dedupe for ALL FOUR artifact types.
**DECISION (resolved 2026-05-31): the local scrub runs ONE TIME DURING INSTALL.** Not every-launch, not a route-build precursor. Clean once, correctly, so by the time route creation runs the data is already clean. (Lowest runtime cost; keeps work off the already-troubled startup path.)
**TWO-LAYER ARCHITECTURE (agreed):**
  - **Layer 1 — install scrub (one-time cleanup of what's there):** apply the unified rule to existing data; fix 'null'/unnamed-trail naming so unnamed trails dedupe correctly on geometry. Contamination eliminated before route creation runs.
  - **Layer 2 — DB-level guard (permanent prevention):** for trails (and routes — see below), the check is a DATABASE FEATURE — UNIQUE(name, geometry) + INSERT OR IGNORE. DB structurally refuses duplicates; NOT scattered app-layer checks.
**ORDERING DEPENDENCY:** dedupe existing data FIRST, THEN add the UNIQUE constraint (can't constrain a table that still has dupes — migration fails). Order = scrub → then constraint.

**ARTIFACT-SPECIFIC DETECTION (four types; unified outcome, per-type detection):**
- **TRAILS → COLLAPSE.** Detect = same (name, geometry). Duplicate dropped. DB-expressible (UNIQUE).
- **TRACKS → ALIAS.** Detect = same GEOMETRY (path). Name varies by ride/day; name-equality is just a SKIP shortcut. (1) same name → SKIP; (2) diff name same geometry → ALIAS (dominant case — same trail, different rides/days). Import AND DBG capture.
- **WAYPOINTS → ALIAS by PROXIMITY.** Single points never share exact coords (GPS drift). Detect = within distance threshold + same real feature → ALIAS. Same outcome as tracks, proximity detection. Import AND DBG capture / waypoint creation.
  - ⚠️ FRAMING (waypoints): proximity THRESHOLD (50m? 100m?) and does TYPE gate the match (two trailheads alias; trailhead vs nearby water source do NOT)? User judgment at framing.
- **ROUTES → SAME DB RULES.** Detect = same geometry (a path, like trails/tracks). Same name+geometry → remove; new name+same geometry → alias. DB-expressible like trails. **SCALE FACTOR:** routes are created by MULTIPLE INDIVIDUALS and ACCUMULATE in AWS as a FIRST-OCCURRENCE store (see local-primary note above). Many people create essentially the same route, named differently. First occurrence holds AWS's name; when others pull it down, AWS's name becomes a local alias while their own name stays primary. Routes get the rule at TWO locations: local DB (UNIQUE like trails) AND the AWS first-occurrence store.
  - **AWS SAME-DAY RULE (added 2026-05-31): two rides with the same geometry on the same day → add only ONE alias.** A group rides the same trail together; many riders' devices capture the same geometry the same day and all push to AWS. Without this, one ride spams the store with N aliases. The rule collapses the same-geometry/same-day cluster to a SINGLE alias contribution. One ride = one alias, even if ten people captured it. ENFORCED VIA the dated alias record (above): alias uniqueness key (geometry + date), so a second same-geometry contribution on the same date finds an existing alias and skips.
    - ⚠️ FRAMING: define "same day" — calendar day vs time window (group straggling past midnight; or two independent riders same calendar day — arguably still one alias since same route). Set alongside the route geometry-match tolerance. AWS-side enforcement is a distinct location from the local install scrub — frame both.
- ⚠️ FRAMING (tracks + waypoints + routes): implies an alias field/table on tracks, waypoints, AND routes, and that record CARRIES A DATE (for the one-alias-per-day rule). Confirm alias storage shape per type.
