3. ⛔⛔ THE ORPHAN BUG — the most consequential find

The trails clear removed 86,969 trails and 303,585 trail_properties rows — three and a half times as many property rows as trails. Fred called it: "the Utah identifiers are in the trails extension db which we did not clear."

⚠ geom_hash is the IDENTITY; trail_id is the KEY. trail_properties joins on trail_id, a UUID minted at insert. Delete the trails and those rows join to nothing, ever.

And the damage was active. TrailImporter:461 inserts with INSERT OR IGNORE on (source_id, source_unique_id). A re-imported trail whose uid a stale row already held was silently ignored — the orphan kept the slot, the new trail got no properties, and nothing reported an error.

Visible in the ledger:

15:41  inserted=30      geomChanged=86893     <- orphans holding the slots
16:41  inserted=86923   geomChanged=0         <- after the corrected clear

9. ⭐ THE PBF INSIGHT — recorded so it is not lost

Fred: "isn't the route id for the table we use the same route id as the protobuf file? Can't we just mine the attributes attached to the route?"

Yes — and it collapses the problem. trail_properties.source_unique_id already holds the osm_id, and the PBF's ways carry the same ids. So the PBF is read for id and tags only; geometry keeps coming from the GeoPackage.

That removes node resolution entirely — the millions of delta-encoded node entries that make a PBF reader hard are never touched. And the mapping is one preprocess at import, written into the skinny DB and carried through C3 in the same insert, so there is no update pass and no window where geometry and attributes disagree.

First task if that path is taken: MEASURE, do not build. A desktop Python pass against a downloaded Utah PBF, reporting how densely the access tags are actually populated. The tags existing in the schema is not the same as them being on the ground — the same rule that caught ohv missing from the GeoPackage.
