Where things stand

The AI route planner is complete and device-proven. Six screens on one pinStep machine; the recipe rebuilds a batch from a saved route in one press; and the cached-graph bug that made a second search in the same area return worse routes is fixed and verified by re-running the exact sequence that produced it.

⭐ THE BUG THAT TOOK TWO DAYS TO SEE

Symptom: the same four pins covered 2 of 4 on one run and 4 of 4 on another, from identical inputs. Deterministic within a session, different across one.

Cause: splitEdgeAt(g, ..) writes into whatever graph it is handed, and a cache hit returned the cached object by reference. So the first run's pin splits became the next run's starting topology.

Fred's observation is what cracked it: "the only difference I am aware of is one was the first run of the day and another followed a previous run in that area." A cold cache was right; a warm one was not.

⚠ It had been flagged on 08-27 and left unproven — "splitEdgeAt mutates the cached graph, which would break recipe determinism SILENTLY — NOT VERIFIED". It did.

Fix: copyOf() on every cache hit. All seven Graph fields, including adj's inner lists, which splitEdgeAt appends to. A copy rather than a cache key, because two identical runs would still hit and the second would inherit the first's splits.

⭐ VERIFIED: the same sequence — trailhead-only search, then the same four pins — now returns two routes with four pins and four with three, matching a cold start.

⬜ SPECIFIED — the startup import check

Fred, 08-29: "record failure on incompletes on app restart — open imports for any reason. Suggest a rerun of that import to correct any issue that may have arisen."

⭐ AN IMPORT STILL OPEN ON RESTART DID NOT FINISH, and that is the whole test. No failure logging is needed at import time: network off, app killed, crash, battery — all look the same and all want the same answer. It cannot miss anything, because it does not depend on the failure path being reached. A process that dies mid-import writes no error but leaves an open record.

⭐ THE MACHINERY ALREADY EXISTS. HomeStateImportController tracks a per-source status and skips "completed" at :259; at :916 it scans the state JSON files for process_state == "completed".

So this is a READ, not new tracking — the same shape as PinFeasibility.unreachable, which had been computed and ignored for days. Find the files whose process_state is not completed, report the source and its date, offer the rerun.

⭐ And :259 is what makes the rerun safe: completed sources are skipped, so a rerun fetches only what is missing and duplicates nothing. The rider risks nothing by accepting.

⭐⭐ OSM DATA REFRESH — clear and reimport, by source, quarterly (2026-08-29)

Fred's plan, and it replaces the incremental-update design below:

"Use the last import date for OSM data as the trigger to refresh. Remind the user to refresh map data — once a quarter is enough. In the startup job: pending map update, execute now or wait. Keeps showing up till the refresh is completed. Good for another 90 days."

⭐ WHY THIS IS BETTER THAN THE INCREMENTAL DESIGN

Clear the OSM-owned rows, reimport, done. No three-way reconcile, no version comparison, and — the hard one — no deletion-detection problem. The 08-29 research spent most of its length on how to tell a deleted way from one that is merely absent from a truncated extract. A clear-and-reload never asks.

⛔ AND IT ONLY WORKS BECAUSE OF SOURCE OWNERSHIP. Clearing every trail would take the USGS rows and anything a rider created. Clearing only what OSM owns is safe by construction — which is what makes the ownership column load-bearing rather than tidy.

The mechanism

PieceBehaviour
The triggerThe last import date for the OSM source. No version checking, no diffing — a date.
The interval90 days. Geofabrik rebuilds daily, but the QA evidence is roughly one change per month across 1,600 trails — quarterly is proportionate to how much actually moves.
Where it appearsThe startup job, beside the incomplete-import check. Same place, same shape.
What it asks"Pending map update — execute now or wait."
If they wait⭐ It keeps showing up until the refresh completes. Same rule as the incomplete-import prompt: the only way off the list is doing the thing.
AfterGood for another 90 days.

⚠ WHAT A CLEAR-AND-RELOAD COSTS, and both are acceptable:

Extension rows attached to OSM trails go with them, if they key on geometry. ⚠ That is the one thing worth settling first — are extension rows keyed by geom_hash or by trail_id? If by id, and the ids are reassigned on reimport, rider notes detach. If the answer is bad, the fix is upstream of this plan.

It is a full state download. Which is why it is quarterly and prompted rather than automatic.

⭐ AND ROUTES SURVIVE REGARDLESS. Fred: "do we build a route because we have two ids? No, we build it with ids. They are not missing." A route's vertices reference trail ids and queryGeomByIds fetches by them, so geometry moving underneath does not break a saved route. The hash question is about joining sources, not about routing.

⚠ THE INCREMENTAL DESIGN BELOW IS NOW A FALLBACK. It stays recorded because the reasoning about way-splitting and id stability is still true, and because if clear-and-reload turns out to cost too much — a rider on a metered connection, or extension rows that cannot survive it — the three-way reconcile is the alternative that was already worked out.
