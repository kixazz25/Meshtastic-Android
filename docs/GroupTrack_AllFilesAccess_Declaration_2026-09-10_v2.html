All Files Access — declaration v2

2026-09-10 · rewritten after reading what OsmAnd actually does

⛔ Why v1 was wrong

v1 argued "there is no alternative that doesn't render the app ineffective." ⛔ That will not survive a reviewer who knows the category. OsmAnd does not have this permission — their request for it (issue #16059) has been open since Dec 2022, labelled "Nice to Have," never granted. They ship offline maps successfully without it, working inside their own folder tree, which they call "certainly a crippling mechanism" but which plainly works.

⚠ So a comparable app proves the alternative is viable. Any declaration built on impossibility invites exactly that comparison.

⭐ What actually gets approved

Google's permitted uses are file management, document management, backup and restore, search on device. OsmAnd's own reasoning in that issue is that they would qualify under those — and they cite a live precedent: MobileSheets, a sheet-music viewer, holds the permission because it "acts as a file manager for your sheet music files … and links directly to them on the device … allowing those files to be organized as desired by the user without them having to be copied or moved."

⭐ That is the shape. Not "my app needs speed" — but "my app manages files the user owns, in place, where the user put them, without copying them."

⚠⚠ Verify these before you submit

The draft below claims things about GroupTrack. ⛔ Only submit the ones that are true of the app as it ships. A declaration that overstates is worse than one that is narrow, because the reviewer can check.

  • Does GroupTrack read GPX files from where the rider put them — a Downloads folder, another app's folder, an SD card — or does it only read from Documents/GroupTrack/? ⭐ If it reads from arbitrary locations the rider chooses, that is the file-management case and it is strong. ⛔ If everything must first be inside Documents/GroupTrack/, you are doing what OsmAnd does and the case is much weaker.
  • Can a rider copy map files in from another device or an SD card and have the app find them in place?
  • Does the app leave the rider's files organized as they chose, or does it move and rename them into its own structure?

⚠ If the honest answers are "only our own folder," then the strongest remaining ground is the 60 GB and uninstall argument alone — and you should expect that to be a harder sell, because Google considers app-private storage the correct answer to it.

Draft A — the file-management case

Use this only if the app genuinely reads and writes the rider's files where the rider keeps them.

GroupTrack manages a rider's off-road navigation files in place on the device: GPX tracks and routes exchanged with other apps and other riders, waypoint files, and offline map stores. It links directly to these files where the rider keeps them, so they stay organized as the rider chooses without being copied or moved into private storage.

The map stores are MBTiles and SQLite. Android's SQLite API requires a filesystem path; the Storage Access Framework provides content:// URIs, which SQLite cannot open. MediaStore indexes only images, audio and video, so it cannot hold or serve this data.

Riders ride off-grid with no cellular coverage, and hold over 60 GB of map data built up over weeks. Files held in app-private storage are erased by uninstall or Clear Data, costing the rider weeks of re-downloading and leaving them unable to see or back up their own data.

GroupTrack is free, captures no user data, and uses only publicly accessible map sources.

Draft B — narrower, if A is not true

Use this if the app only works inside its own folder. ⚠ Weaker, but honest.

GroupTrack is offline navigation for off-highway riders, used where there is no cellular coverage. Its offline map stores are MBTiles and SQLite databases held in shared storage at Documents/GroupTrack/.

Android's SQLite API requires a filesystem path. The Storage Access Framework provides content:// URIs, which SQLite cannot open for reading or writing. MediaStore indexes only images, audio and video and cannot hold this data. The file picker asks a user to select one document, which has no meaning when drawing a single map screen reads many tiles while the rider is moving.

Riders hold over 60 GB of map data built up over weeks of downloading. In shared storage the rider can back it up, move it to a replacement device, and see what is using their space. App-private storage is erased by uninstall or Clear Data, costing them the entire download.

GroupTrack is free, captures no user data, and uses only public map sources.

⚠ Also

  • The listing must document this prominently. Policy requires the core functionality to be in the app's description. ⭐ Check the full description says plainly that the app stores offline maps on the device.
  • The app must clearly prompt for the permission and explain why. The authority gate does — check its wording gives a reason, not just a request.
  • ⛔ Do not include the process complaint about not receiving a prior notice. That belongs in an appeal, not a declaration — here it gives the reviewer something to react to other than your case.
  • ⚠ Check Play Console → Policy status and the Console inbox before claiming you had no earlier notice. Google sometimes delivers these in Console rather than email, and an unread one there would undercut you.

⛔ Decide the fallback now, not in a week

If this is refused again, the path is getExternalFilesDir() — app-private external storage. No permission, no declaration, no review. SQLite works there. It is what OsmAnd does.

⚠ What it costs: the map store no longer survives uninstall or Clear Data. A rider with 60 GB downloaded would rebuild from nothing.

⭐ Worth knowing which way you would go before the answer comes, so a refusal is a plan rather than a crisis two days from launch.
