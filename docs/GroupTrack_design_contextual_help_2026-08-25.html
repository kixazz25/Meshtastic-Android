Contextual help — every panel knows its manual page

Design discussion, 2026-08-25 · HELPXREF-2026-08-25

⛔ SCHEDULED FOR 2.7, NOT 2.6h (Fred, 2026-08-25). Contextual help lands as part of the convoy rewrite / Meshtastic plugin work, where the panel structure is being reorganised anyway — pushing help ids into panels that are about to move would mean doing it twice.

2.6h carries the doc work only: QuickStart revision and bundling, release notes revision, and launching QuickStart on a new install / release notes on an update. This document is the design for what follows.

⭐ Step 1 is still worth doing early though — adding id= anchors to the manual sections is a documentation change with no app dependency, and it makes the ids real before 2.7 needs them.

The problem, from Fred: the documents "go largely unused. i can tell from help questions." Riders ask about things the manual already covers, which means the manual is not reachable at the moment the question forms.

⭐ A rider with a question is looking at the panel that raised it. That is the only reliable context we have, and today it is thrown away — the "?" button opens the manual at the top and leaves them to find their own way.

1. What "focus" means here

Three candidates for "what is the rider looking at", in increasing order of usefulness:

SignalGoodBad
Screen — Ride Map vs Ride Planning Map Always knownFar too coarse. The planning map has a dozen panels.
Topmost panel — whichever composable is showing Matches what fills the screen; already tracked as state (showAiDesign, showWipNotes, routeMode…) Two panels can be open at once; needs an explicit order
Last function invoked — the thing they just did Closest to the question actually being asked Nothing records it today

⭐ RECOMMENDATION: a help stack, not a help variable. Panels push a help id when they open and pop it when they close. Help reads the top of the stack. That handles nesting for free — a dialog over the AI panel over route mode resolves to the dialog, which is what the rider is looking at.

It is also the same shape as the back stack, so it fails in ways riders already understand.

2. The mechanism, concretely

object HelpFocus {
    private val stack = mutableStateListOf<String>()
    val current: String? get() = stack.lastOrNull()
    fun push(id: String) { stack.add(id) }
    fun pop(id: String)  { stack.remove(id) }   // remove BY ID, not removeLast
}

⚠ Pop by id, never removeLast(). Panels do not close in the order they opened — a rider can dismiss the one underneath. Removing the last entry would pop the wrong panel and leave help pointing at something that is no longer on screen.

Each panel does one thing:

DisposableEffect(Unit) {
    HelpFocus.push("route.ai_design")
    onDispose { HelpFocus.pop("route.ai_design") }
}

⭐ DisposableEffect is exactly right here — it fires on composition and cleans up on removal, so a panel cannot leak a help id by being dismissed through an unusual path. That is the class of bug that has cost this project real time (the AI-mode reset, the trails-clear marker): a state that is set on the way in and depends on someone remembering to clear it on the way out.

3. Naming the ids

Ids are anchors in the manual, so they must survive the manual being rewritten. Dotted, hierarchical, named for the function rather than the widget:

map.planning                 the Ride Planning Map itself
map.planning.features        Map Features panel
route.toolbar                the Route+ toolbar
route.ai_design              AI Design panel
route.pin_flow               the guided pin / banner flow
route.detail                 the route DETAIL panel
trails.import                Import Trails
trails.import.area           …by area
tiles.download               tile download queue
radio.config                 radio configuration

⚠ Not screen names, and not button labels. Both change — the 08-18 plain-language pass renamed most of the UI, and any id tied to a label would have broken that day. The function is what is stable.

4. How the manual is reached

The manual already ships in the APK as one HTML file with a filter box. Two ways in:

ApproachHowCost
Anchor jump Manual sections carry id="route.ai_design"; help opens manual.html#route.ai_design Small. Needs an id on each section and nothing else.
Pre-filtered Open the manual with its existing filter box pre-populated Smaller still — the filter already works — but it lands on a list, not the answer.

⭐ Anchor jump. The rider asked about one thing; land them on it. The filter box stays for browsing.

5. ⚠ The part that will rot

An id pushed by a panel with no matching anchor in the manual sends the rider to the top of a 6.8 MB document — worse than the "?" button they have now, because it promised something.

The guard: a build-time check that every HelpFocus.push("…") string has a matching id="…" in the bundled manual, and that every manual anchor is pushed by something. Two greps in release-assets/prepare_release_assets.py, which already verifies markers when it copies docs into assets — so the hook exists.

⚠ It must fail the build, not warn. A warning in a release script is a warning nobody reads. This project's own history says so: PENDING-REDOC 2026-08-06 has ridden along in the manual for nineteen days.

6. What the rider sees

  • The "?" button stays where it is and keeps its meaning — it just lands somewhere useful now.
  • Every first-level function is reachable, because the push happens in the panel rather than being wired per button.
  • Nothing new to learn. No new affordance, no tour, no tooltip layer.

⭐ And it answers the tester report's "dynamic walkthrough" item without building a tutorial framework. The provider asked for interactive tutorials and tooltips. Contextual help gives a rider the right page at the moment they are stuck, which is what a walkthrough is trying to approximate — and it costs a push, a pop and an anchor rather than a framework.

7. Sequence

  1. Ids first, in the manual. Add id= to each section. No app change, no risk, and it makes the ids real before anything depends on them.
  2. HelpFocus + push/pop in three or four panels — AI Design, Map Features, Import Trails, the Route+ toolbar. Enough to prove the shape.
  3. Anchor jump from the "?" button.
  4. The build-time guard, before it spreads to every panel.
  5. Then the rest of the panels.

8. Open questions

  • Does the release-notes link style ("see the manual page for this") use the same ids? It should — one anchor scheme, two consumers.
  • What happens on the Ride Map, where there are few panels and a rider is moving? Possibly help is planning-map only.
  • Should the stack be logged? A count of which ids get help requests is the only honest measure of whether the manual is being read — but it is telemetry, and telemetry was deliberately declined on 08-14 in favour of surveying testers.
