1 · What option 2 is

From the Source Map Migration panel, three options. This document covers option 2 only.

#OptionProtectsBehaviour
1Delete and start overnothing Clear the column, rebuild around tracks, draw new areas. Already built — ConvoySourceClear.kt, commit 27dfb433d, proven on Droid 2.
2Move everything (automatic)the AREA Delete track tiles, refresh the area, re-import tracks. All submitted at once; every image slowly replaced from the new source. This document.
3Move on my scheduleeverything Nothing touched. Convert manually, ground by ground, with Replace tiles ticked. Already built — existing download paths.

⭐ The governing constraint (Fred): these screens process ALL or delete ALL. No partial conversion. That single rule removed the detection logic, the decision matrices and the pickers.

Why the delete is not a loss

Track corridors are deleted and requeued in the same operation. The store ends with the same coverage shape it started with, sourced from the new provider. Corridors outrank area work in the queue, so the re-imports drain before the slow area rebuild even starts.

⚠ The slot IS the store. Column 1 writes to SAT regardless of which source is assigned — which is why Replace tiles exists: old tiles keep rendering until new ones overwrite them in the same store. A source change therefore needs a deliberate migration, not just a repointed URL.

3 · Why the sequence holds

The order is structural, not enforced by priority

Deletes never enter the queue. They run inline while the queue is held, so they cannot race anything — you cannot lose a race you are not in.

⭐ This is what removes the atomic patch. No new DownloadType, no priority mapping, no dispatch branch — so the exhaustive when at ConvoyDownloadQueue.kt:797 never fires, and there is no window where the tree will not build. The earlier 1b/1c plan required exactly that window.

Drain order after release — already correct, no change needed

DownloadPriority        (ConvoyDownloadQueue.kt:36-41)
  DELETE    = 0
  PROMOTED  = 1
  CORRIDOR  = 2     <-- track re-imports drain first
  AREA      = 3
  REFRESH   = 4

Corridors outrank area work, so track coverage returns before the slow area rebuild starts. Area imagery is never absent because the refresh replaces in place.

⚠ The concurrency seam

MAX_CONCURRENT = 2 (:139). Priority governs which job is picked next; it does not stop a running job continuing alongside a higher-priority one. With hundreds queued in order, both slots stay inside the same phase almost the whole time — the exception is the boundary, where the last corridor and the first area job can occupy the two slots together.

⭐ Fred's assessment: acceptable — they are different tracks, so the two jobs at a seam do not touch the same tiles. Recorded so that if a track later shows holes after a migration, this is the first place to look rather than a fact to re-derive.

Considered and not needed: dropping concurrency to 1 while deletes are pending. The inline-delete design makes it moot — nothing is queued to race.

⚠ The interaction mismatch

Every row in this section is a checkbox that arms an area operation — tick "Remove Tiles by Area", then tap Draw Area, and the delete runs against the drawn bbox. Draw Area's enabled tests tilesChecked || trailsChecked || removeTilesChecked || osmChecked.

Corridor delete takes no area and no selection. It is all tracks, immediately. So it does not fit the tick-then-draw idiom.

⭐ Settled: checkbox launches a full-text confirm. Precedent exists in this very section — "Download Tiles by Corridor" routes from its own checkbox (onSelectCorridorTracks()), and the comment states "Routing lives in the checkbox." The tick reverts on dismiss: this is an action, not a state.

⚠ Clear Tile Source needs its warning carried with it

Inside the migration flow the user has chosen an option and been told they lose labels until tiles are replaced. Exposed as a bare panel row, it is the same destructive operation with none of that framing — a one-tap way to drop 5+ GB. The confirm must carry the warning, not just ask PROCEED.

6 · The two numbers at GATE B

FigureMeans
totalTilesDistinct corridor tiles by geometry. An upper bound.
onDiskTotalTiles actually present in the store(s). What the delete will remove, and what GATE C verifies against.
overlapSavingsNaive per-track sum minus distinct — tiles shared by two or more corridors.

onDiskTotal ≤ totalTiles always. The gap is corridor crossing ground that was never downloaded.

⛔ Why this distinction exists — DELETE-BANDING-2026-07-25, MBTilesStore.kt:345-349: a geometry count produced “1,500,000 tiles” for an area holding a fraction of that, leaving a progress denominator the job could never reach. A finished job looked permanently stuck. Showing the geometry number at a confirm would reproduce that as a verification failure.

⭐ countTiles deliberately mirrors deleteTiles line for line — same groupBy { z to x }, same 500-bind chunking, same WHERE shape. A pre-count selecting on different criteria than the delete would read as authoritative while disagreeing with what happens.

7 · Open questions

  • Does enqueueRefresh freeze the bbox onto each entry, or does the worker re-derive it? The “execution order does not matter” property rests on this. It is a reading of the code, not confirmed in the worker.
  • Completion rows before or after the delete? Before means a row survives an app death but claims a completion that has not happened. After means the row is truthful but a crash leaves no trace. Leaning: after, carrying the actual removed count.
  • countTiles performance on a large store. A COUNT per (z,x) group across a full corridor set on Droid 2's 5.3 GB SAT.mbtiles is the one thing in this design that cannot be predicted. First run answers it.
  • Threading. Preview is a DB read plus tile computation per track plus a COUNT per store — background thread only. ⛔ Anything touching the WebView or a Toast from that thread must post back via Handler(Looper.getMainLooper()). Three convoy rendering failures in this arc were instrumentation aborting a method before its real work.
  • Track name on corridor queue rows. Write the name at enqueue; re-resolve at completion and refresh it if the hash still resolves, otherwise leave what is there. Never overwrite a real name with nothing — a completed row is the record that it happened, and a deleted track must not erase it.
