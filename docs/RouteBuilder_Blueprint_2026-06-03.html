A. The model in one paragraph

+ROUTE already exists on the Work-with-Artifacts panel (both maps). Tapping it collapses the artifacts panel and launches the Route+ toolbar in its place. The toolbar offers a single entry — "Start / Continue planning your route" — which opens a source picker (New / Continue in-progress / Copy completed). Three planning methods (point-to-point, draw, suggest) are toggles switchable mid-route, all feeding one shared vertex chain. The build loop is tap-to-place (snap-2) with Add/Undo. Editing is entirely in-memory until a deliberate Save. Exits are explicit and persistence-aware.

B. Snap-2 rule (Method 1, LIVE)

  • Trail-first, strict. Within the radius, if ANY trail is in range, snap to the nearest point-on-line of a trail. Tracks are consulted ONLY when no trail is in range (a trail at 40m beats a track at 5m). Tracks fill gaps where no trail exists.
  • Nearest-point-on-line, not nearest vertex. Radius is in meters (ground distance, haversine).
  • No-snap = free-place. If neither trail nor track is in range, the point lands at the raw tapped coordinate. The segment to it is a straight line (crossing open ground / bridging a network gap). Final geometry, not a placeholder — no deferred snapping.
  • Junction discipline. User drops a point AT each junction and selects the next trail explicitly. Between two consecutive snapped points on the SAME line, the segment is the trail-slice (sub-path of that line). Different line, or free point → straight segment. The route never auto-connects past a junction.
  • WKT is LON-FIRST (LINESTRING(lon lat, ...)) — confirmed against SpatialDbManager.wktToGeoJsonCoords.

D. Persistence model — in-memory until Save

  • While working: in-memory only. The vertex chain lives in RouteManager.vertices. Zero file or DB impact during editing. The on-disk draft (if resumed) stays exactly as opened.
  • In-progress drafts = private JSON in app-internal storage (context.filesDir, NOT the public Documents drive — not synced, not media-indexed, not user-visible as files). Carries the full vertex chain (lat/lon/lineId/lineType/segmentIndex/t/snapped) + name + last-modified. The chain preserves snap provenance so resume restores the builder exactly.
  • Completed routes = spatial DB row (the routes table). Drafts NEVER touch the spatial DB. Only completed routes are eligible for AWS sync — this keeps the shared spatial model clean (no half-built routes propagate).
  • A route is EITHER a draft-file OR a DB-row, never both. The transition is the one moment a delete pairs with an insert.
  • Save = the only write (temp-then-rename for safety; create for NEW, overwrite for RESUMED). Discard = no write (drop memory, file untouched). Delete = remove file. No original-chain snapshot needed — disk is always the last-saved state.

E. Exit model (the part to get right)

Save completed (toolbar, always available, requires ≥2 vertices): buildWktAndBbox → insertRoute → delete draft file if one existed (graduation) → exit. This is the one affirmative "done" save.

Guarded exit — leaving with an un-completed route prompts, and the options depend on origin:

OriginExit options
NEW route (no file yet)Save as draft (create JSON)  |  Discard (no save, nothing was on disk)
RESUMED draft (file exists)Save changes (overwrite JSON)  |  Discard changes (no save, file stays as opened)  |  Delete in-progress (remove file)

F. Work with Drafts

  • List in-progress drafts (name + last-modified) — reads the private draft dir.
  • Resume → load chain into memory → redraw partial route on current map → re-arm toolbar in add-point mode.
  • Delete → remove draft file (nothing in DB to touch — no orphans).

G. Edit-of-existing

Completed routes are immutable (snap provenance is lost once flattened to LINESTRING). To change one: Copy a completed route as the starting chain for a NEW route (original untouched). Rename/delete of completed routes lives on the route maintenance screen (separate open item). True in-place re-edit deferred.
