⭐ THE QUESTION THIS DOCUMENT EXISTS TO ANSWER

What are we reloading? The trails clear and re-import are built and working. Before forty testers spend a Geofabrik download each, the data they pull down should be the data we actually want — and today's is not.

Fred, 08-24: "we are not going to send a release until all these items are addressed. We have the clear and the reload. The question is what are we reloading."

1. The problem

GroupTrack cannot tell a hiking trail from an OHV trail outside Utah. The route explorer will happily build a ride down a footpath, and the map legend — which already names eight categories — describes almost nothing that is drawn.

What we thought we had

The morning's plan was to filter on OSM's access tags: ohv, motor_vehicle, atv, 4wd_only, access. These exist in OpenStreetMap and they answer the question exactly.

They are not in the files we import.

What the data actually holds

PRAGMA against both .gpkg extracts on D:, the roads layer:

osm_id  code  fclass  name  ref  oneway  maxspeed  layer  bridge  tunnel

Ten columns. No access field of any kind. Not ohv, not motor_vehicle, not access, not private.

⚠ THE CAUSE, and it is documented behaviour rather than a bug. Geofabrik's free GeoPackage is derived from their shapefile product, which flattens OSM's open-ended tag model into a fixed schema. Anything outside that schema is dropped at export.

Confirmed independently: "Do not download the Shapefiles, as they strip out the complex access tags needed for OHV/4x4 filtering."

So fclass is all there is

And fclass describes physical form, not permitted use. A track is "unpaved way for agricultural or forestry access" — usually OHV-ridable, which makes it a fair inference, but it is not the statement UGRC makes when it assigns a category.

What the importer keeps today

osm_layers.json, trails layer, nine values — and no road classes at all:

Only three carto codes are reachable by inference — 4, 2 and 6 — and 83% of rows fall into code 4. A legend filter built on this offers eight categories to describe three.

path is the judgment call and it has no right answer from this data. OSM defines it as "narrow way, mode unspecified": excluding it is correct for a SxS or Jeep and wrong for a dirt bike.

Two other fields that are also empty

carto_code and motorized_allowed exist in trail_properties and are populated by the UGRC importer. OsmImportWorker:468 writes both BLANK, deliberately and with a comment saying so.

So every OSM trail renders cyan "Unspecified" — which is every state except the third of Utah that came from UGRC. Fred, 08-24: "two-thirds of our Utah trails are OSM."

2. What was done today, and why it may be discardable

TRAILFILTER-2026-08-24K removed path and bridleway from filter_values. Stops the clearly non-motorized types arriving in future imports.

TRAILCLEAR-2026-08-24L clears trails AND trail_properties once per device, so the home-state picker re-imports under the new filter.

⚠ The filter change did not take effect on the device. Extract kept 87,067 trails before the patch and 87,067 after. Unexplained — most likely an on-disk override at /sdcard/Documents/GroupTrack/config/osm_layers.json winning over the bundled asset, which OsmLayerCatalog is designed to allow. Two commands would settle it and they have not been run.

⭐ AND L FOUND SOMETHING BIGGER THAN THE FILTER

The clear reported 86,969 trails and 303,585 trail_properties rows — three and a half times as many property rows as trails. Accumulated orphans from repeated imports, invisible until counted.

The damage was active, not cosmetic. trail_properties is keyed on trail_id, a UUID minted at insert — NOT on geom_hash. Once trails are deleted those rows join to nothing, and TrailImporter inserts with INSERT OR IGNORE on (source_id, source_unique_id), so a stale row keeps the slot and the re-imported trail gets no properties at all.

Visible in the ledger:

3. The proposal — import from .osm.pbf

Fred, 08-24: "my gut is PBF is a new data type but it more closely matches the USGS codes and we can quickly remap our import."

The .osm.pbf is the untouched OSM data model. Every tag survives, including all the access keys the GeoPackage drops.

It resolves the categories directly rather than by inference

cartolabelOSM tags
1Hiking-Only foot=designated + motor_vehicle=no
2Hiking & Biking foot + bicycle, no motor
4OHV / Road-Concurrent ohv=yes / atv=yes / motorcycle=yes
5Biking-Onlybicycle=designated
6Equestrianhorse=designated
7Stepshighway=steps

Plus 4wd_only=yes, sac_scale (hiking difficulty) and mtb:scale — none of which have any equivalent in what is imported today.

The two questions that were asked, and their answers

QuestionAnswer
Is it available by state? Yes. Same Geofabrik server, same per-state granularity, same directory structure — north-america/us/utah-latest.osm.pbf. GeofabrikCatalog already knows these paths; it is a different extension on the same URL.
How big is it? Smaller, not larger. PBF is compressed binary and is typically well under the .gpkg.zip for the same extract. The download gets cheaper.

4. The approach — ways only, one preprocess

⭐⭐ THE INSIGHT THAT SHRINKS THIS BY AN ORDER OF MAGNITUDE

Fred, 08-24: "isn't the route id for the table we use the same route id as the protobuf file? Can't we just mine the attributes attached to the route?"

Yes. trail_properties.source_unique_id already holds the osm_id, written at OsmImportWorker:483. The PBF's ways carry the same ids. So the PBF is read for id and tags only — the geometry is already imported and correct, and comes from the GeoPackage as it does today.

⭐ THAT KILLS THE EXPENSIVE PART. The hard problem in reading OSM PBF is that a way references nodes by id, so building geometry means resolving millions of node entries — delta-encoded inside dense blocks, unseekable, and the reason a naive reader OOMs. None of that is needed if we never build geometry. Way blocks carry their own tags; node blocks are skipped entirely.

And the mapping happens ONCE, at import

Fred, 08-24: "clear the trails file, download the geopackage and PBF, use the PBF route ids and attributes to update a field that is not used by OSM, and use that field in the import — so we are not running updates after the import with a chance for the values to be different ... all our OSM mapping takes place in one preprocess. One touch point."

  1. Clear trails (built — TRAILCLEAR-L)
  2. Download the .gpkg AND the .pbf for the state
  3. Read the PBF ways only: osm_id → tags
  4. Map tags → carto code in one preprocess, write to a new column on osm_trails in the skinny DB
  5. C3 imports geometry as it does today and carries the classification through in the SAME insert

No update pass. No window where geometry and attributes disagree. carto_code and motorized_allowed are populated at insert from real access tags.

⭐ AND IT MAKES THE fclass WORK UNNECESSARY RATHER THAN INTERIM. No fclass → code table, no path judgment call, no "code 4 by inference". The tags say what the trail is. Everything downstream — router, legend filter, map colour — reads one field and means one thing by it.

Which is the principle held all day: one place where classification happens, not compensations scattered downstream that nobody remembers the reason for.

5. The first task — MEASURE, do not build

Before any of the above, one desktop pass answers whether it is worth doing at all: are the access tags actually there, and how densely?

Python against a downloaded utah-latest.osm.pbf and the extension DB pulled from Droid 2. No Android reader, no Kotlin, no build. It should report:

  • How many stored osm_id values are found in the PBF at all
  • Which access tags appear, and on what fraction — ohv, atv, motorcycle, 4wd_only, motor_vehicle, foot, bicycle, horse
  • The tag combinations, mapped through the existing UGRC 1–8 scheme
  • How many rows land in each category, and how many stay unclassified

⚠ THIS IS THE DECIDING NUMBER. If 90% of Utah's tracks carry no access tag, the proposal changes — the tags existing in the schema is not the same as them being populated on the ground. Same rule that caught ohv not being in the GeoPackage: examine the data before categorising.

5b. The decision, stated plainly

Is fclass filtering worth shipping as an interim, or does the reload wait for proper classification?

The ways-only approach tips this toward waiting. The clear-and-reload is the expensive thing to ask of testers, and it is now built. Asking them to do it ONCE, with data carrying real classification, beats asking twice — and with geometry reuse the PBF work is far smaller than it looked when it seemed to require a full geometry reader.

7. Open, for tomorrow

  1. Why did the filter change not take? Two commands: ls /sdcard/Documents/GroupTrack/config/ and logcat | grep OsmLayers — the catalogue logs OVERRIDE vs ASSET. Matters beyond this one filter: an override that silently wins means ANY shipped config change can be ignored on a device that has one.
  2. Is there a streaming PBF reader for Android? The read that turns this proposal into an estimate.
  3. Does path stay excluded, or come in as code 2 and let the rider filter it? The second makes the legend real and serves dirt bikes; it needs the classification to exist first.
  4. Dead-end spurs. Measured at Panguitch: 1,388 spurs, only 38 carry a feature (2.7%). A "short AND featureless" cut at 300 yd removes 606 and loses none of the 38 worth riding. Separate from classification, cheap, and it is a data problem rather than a scoring one.
