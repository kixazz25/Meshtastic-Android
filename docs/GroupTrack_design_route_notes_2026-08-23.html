3. ⭐⭐ ONE HANDLER — the rule this whole design serves

Fred, 08-22: "one process for all gpx route handling. so our json handler and our import handler can be a common process over command passed from a json or gpx file. same process."

Both formats carry the same two things: geometry and a notes block. GPX wraps them in XML with the JSON behind a marker in <desc>; the draft JSON has them as fields. So the format-specific code is a reader that produces one common shape, and everything after it is written once.

readDraftJson(file)  --\
                        >-->  RouteBundle { name, vertices, notes }  -->  ONE path
readGpx(file)        --/

Export is the same reader in reverse.

⭐ STUB-FIRST applies here. Mark every call site that currently handles a route file, build the one handler, then grep to confirm nothing still does it the old way. This is exactly the case the rule exists for — there are already two import paths and they disagree.

5. 🆕 The one new thing — a route notes database

Fred, 08-22: "no new subdirectories, but a new database for route info data."

⚠ Worth a two-minute decision before writing it, then never revisit: the architecture today is two databases — grouptrack_spatial.db for geometry, grouptrack_data.db for properties and extension data. Trails already follow that split (trail_properties lives in the data DB).

A third DB fileA table in grouptrack_data.db
ATTACH handlingnew, its ownalready solved
Cascade on route deleteneeds its own ATTACH to work at all same connection, works
Authority gate / startupanother file to account fornothing to change
Matches the existing splitno — a third category yes — notes are descriptive, not geometric

⛔ The constraint that decides it: SQLite cross-database triggers DO NOT WORK on this project — grouptrack_data.db must be ATTACHed to the same connection, and file deletes must be app code. A third file inherits that problem again for no benefit.

Recommendation: route_notes as a table in grouptrack_data.db, mirroring trail_properties. If Fred wants a genuinely separate file, it works — it just needs its own ATTACH and its own cascade code.

Proposed table

CREATE TABLE IF NOT EXISTS route_notes (
  note_id      TEXT PRIMARY KEY,     -- uuid
  route_id     TEXT NOT NULL,        -- FK to routes.route_id (spatial db)
  geom_hash    TEXT,                 -- ⚠ see the identity note below
  seq          INTEGER,              -- display order within a route
  kind         TEXT,                 -- 'narrative' | 'leg' | 'feature' | 'caution' | 'rider'
  at_mile      REAL,                 -- null for whole-route entries
  lat          REAL,                 -- null unless the entry is a point
  lon          REAL,
  title        TEXT,
  body         TEXT,                 -- the human-readable line
  payload      TEXT,                 -- the original JSON fragment, kept verbatim
  author       TEXT,                 -- 'generated' | 'rider' | 'server'
  created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_route_notes_route ON route_notes(route_id);

Why kind and author rather than one blob: this is the same table that eventually carries rider observations (the 3.0 work). Fred, 08-22: "history is information, not current fact. it is what it was." A dated observation is a row, newest first, nothing collapsed and nothing deleted. Generated narrative and rider notes are the same structure with a different author.

⭐ And it generalises to trails. Fred: "used a joined logical to service the artifact popup and wallah we have trail notes." Same join shape against trail_id.

6. CREATE — the draft carries its own notes

One file. The existing draft format plus a notes block. Nothing else changes.

  "schemaVersion": 2,                    // ⚠ bumped -- see the compatibility note
  "name": "Panguitch 1",
  "createdAt": "...", "updatedAt": "...",
  "method": "point",
  "vertices": [ { "lat":.., "lon":.., "lineId":.., "lineType":"trail",
                  "segmentIndex":-1, "t":0.0, "snapped":true }, ... ],

  "notes": {
    "generated": "2026-08-22T...Z",
    "summary": { "total_miles": 78.6, "est_hours": [4.4, 6.6],
                 "features": 13, "of_available": 51,
                 "unconfirmed_junctions": 104, "retrace_pct": 25.0 },
    "narrative": {
      "headline": "79 miles, roughly 4 to 6 hours of riding. 8 springs and 5 summits along the way.",
      "stops_in_order": [ "mile 10  Fivemile Ridge -- summit", ... ],
      "ground_covered": "Named trail: Upper Bear Valley Road (16 mi), Showalter Mountain (6 mi)...",
      "before_you_go": [ "About 25% of the ride doubles back on itself...", ... ]
    },
    "legs":     [ { "trail":"Trail Creek", "from_mi":14.0, "to_mi":15.3, "miles":1.3, "pois":[...] } ],
    "features": [ { "name":"Slide Spring", "fclass":"spring", "lat":.., "lon":.., "at_mi":17.7 } ],
    "cautions": [ { "at_mi":9.2, "gap_ft":15.0, "lat":.., "lon":.. } ]
  }
}

⚠ CHECK BEFORE WRITING: does the planner tolerate unknown keys? It should read vertices and ignore the rest — but a strict parser would reject the file, and that is the difference between one line and a rewrite. Verify, do not assume.

⚠ schemaVersion 2. A v1 draft has no notes — that must read as "no notes", never as broken. Absent fields mean old, not broken (the same rule that saved the 08-20 manifests during the sweep work).

7. PUBLISH — graduate, then write the notes

  1. WIP graduates → insertRoute(name, wkt, bbox) → returns route_id
  2. Then the notes block is expanded into route_notes rows, stamped with that route_id
  3. Draft file deleted — the draft-or-DB-never-both invariant

⛔ ORDER IS LOAD-BEARING. The id does not exist until step 1 returns. And the draft must not be deleted until step 2 succeeds, or the notes are gone with no way to recover them. Same stamp-then-move discipline as the 08-21 manifest sweep.

---GTNOTES---
{"summary":{...},"legs":[...],"features":[...],"cautions":[...]}</desc>
  <rtept lat="37.8222" lon="-112.4358"/>
  ...
</rte>

Degrades gracefully. Another app shows the whole <desc> as text — untidy after the marker, but not broken. GroupTrack splits on the marker.

⚠ Escaping. JSON inside XML needs the quotes and brackets escaped once and only once. The export already escapes for GPX — the risk is DOUBLE-escaping, which works in testing and breaks on the first trail name with an apostrophe.

⚠ Size. A full mile-by-mile is several KB in a single attribute. Fine for GPX; confirm nothing downstream truncates.

⛔ KNOWN BUG IN THIS EXACT FUNCTION: Fred, 08-22 — buildGpx() writes a hardcoded label instead of the artifact name. Not yet diagnosed. Fix it in the same pass rather than building notes on top of a defect.

9. IMPORT — the mirror

  1. Parse the GPX (parseGpxRoutes, working as of 08-22)
  2. Split <desc> on ---GTNOTES--- — prose before, JSON after
  3. Geometry → insertRoute → route_id
  4. Notes JSON → route_notes rows, author = 'generated' preserved
  5. No marker present → import the route with the prose as a single narrative note. Never fail an import over missing notes.

⭐ Steps 3–4 are the same code the publish path uses. That is the point of the one handler.

⛔ THE AUTO-IMPORT PATH IS STILL BROKEN — carried from 08-22

Manual from Downloads → Map Features works. Tapping a GPX in email does not — the intent filter routes it to the old track-only function.

The filters live on com.geeksville.mesh.MainActivity — Meshtastic's own activity — and every one declares <data android:scheme="content" />. So the intent hands over a content:// URI while importGpxAllArtifacts takes a File and calls readText/delete on it. The stream must be copied to a temp file first — the same problem the OSM import already solved ("SQLite needs a real path").

⭐ This belongs to 2.7, not 2.6g: GroupTrack behaviour inside Meshtastic's activity is exactly what the mesh separation removes.

TESTER WORKAROUND, works today: save the attachment to Downloads, then import from Map Features → IMPORT TRACKS, WAYPOINTS & ROUTES.

10. DISPLAY — the panel IS the notes

Fred's layout, 08-22: "we have the action share export rename delete etc on the left, trail name up top, but the body is the scrollable attributes."

┌──────────────────────────────────────────────┐
│  Panguitch 1                                 │  <- name
├────────┬─────────────────────────────────────┤
│ SHARE  │  79 miles · 4-6 hours               │
│ EXPORT │  8 springs, 5 summits               │  <- scrollable body
│ RENAME │                                     │     = route_notes rows,
│ DELETE │  mile 10  Fivemile Ridge            │       ordered by seq
│ FIT    │  mile 18  Slide Spring              │
│        │  mile 24  Iron Peak                 │
│        │  ...                                │
│        │  ⚠ 104 junctions unconfirmed        │
│        │  ⚠ 25% doubles back                 │
└────────┴─────────────────────────────────────┘

⭐ This IS the pre-2.6 backlog item "artifact detail shown IN PLACE (inline panel, not popups) on BOTH maps, for routes/tracks/trails" — now with something worth scrolling.

One query, three sources. The panel asks for notes on an artifact. Some rows were generated, some typed by the rider, some will come from the server in 3.0. It does not care.

Same body works for all three artifact types:

  • Route — narrative, mileage, time, features by mile, unconfirmed junctions
  • Trail — source, surface, motorized designation, dated rider observations
  • Track — recorded date, distance, the ride it came from

11. SHARE — what Fred already does by hand

Fred, 08-22: "that is how I have been delivering them" — a GPX and a text summary. The need is proven, not hypothesised.

  • Body: the narrative as plain text. ⚠ Not HTML — clients mangle it, and the narrative is already prose plus a mile-ordered list, which survives as text.
  • Attachment: the one GPX, notes embedded.

⭐ It also softens the auto-import failure: a tester who cannot get the attachment to import still knows what the ride is from the body.
