GroupTrack — Droid 1 Install Procedure

Written 2026-08-01, after the same-day spatial-DB loss on Droid 2.
Droid 1 = 8624SBCEDF00001789 — PRIMARY field device. Its data is the one to protect.

⛔ READ THIS BEFORE INSTALLING ANYTHING ON DROID 1

Today an adb install -r -d destroyed the entire spatial database on Droid 2 — ~89 k trails, all tracks, waypoints and routes. The app did not warn; it reported 0 trails, 0 tracks, 0 waypoints, 0 routes and carried on.

The underlying defect is NOT yet fixed. SpatialDbManager still opens with create-if-missing, so any install that costs the app its all-files authority will overwrite Droid 1's databases exactly the same way.

Recommendation: do not install to Droid 1 until the DB open-failure fix ships — unless you back up first (Step 2 below) and accept the risk.

Pre-flight — three questions that decide everything

Q1 · Is Droid 1 running a SIDELOADED build or a PLAY build?

Since the 07-26 package merge, both are com.grouptrack.android but they are signed with different keys — local APKs with grouptrack-release-key.jks, Play builds with Play App Signing.

You cannot cross from one to the other without uninstalling, and uninstalling wipes tiles and app data. Expect INSTALL_FAILED_UPDATE_INCOMPATIBLE, or Play silently offering nothing.

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell dumpsys package com.grouptrack.android | grep -E "versionCode|versionName|firstInstallTime|lastUpdateTime|installerPackageName"

installerPackageName=com.android.vending → Play build. Null or a shell installer → sideload.

⛔ Decide per device: sideload OR Play. Not both. If Droid 1 is on Play and you want to sideload, that is a stop-and-think moment, not a retry.

Q2 · Is the APK's version code HIGHER than what's installed?

versionCode is git-derived (gitVersionProvider.get() + vcOffset) and can regress. A regression is what turned today's install into a fresh install.

Note the versionCode from Q1. The build prints its own — line 213 of build.gradle.kts logs "Version code is set to:". Let it through the filter:

./gradlew assembleGoogleRelease -x uploadCrashlyticsMappingFileGoogleRelease 2>&1 | grep -E "Version code|^e:|BUILD|FAILED"

If the new one is lower, do not install. Override for that build instead:

-Pandroid.injected.version.code=NNNNNNNN    # pick a value above what's on the device

Q3 · Is USB stable, or should this be wireless?

Droid 1's USB is temperamental — moving the cable drops adb, and a drop mid-install is exactly when things go wrong.

Prefer wireless: Settings → Developer options → Wireless debugging → pair → adb connect ip:port.

Procedure

1

Confirm the device and that only one is attached

adb devices -l

Every command below is explicitly -s 8624SBCEDF00001789. Never run an install without -s when two devices are connected — Droid 2 is the sacrificial device, Droid 1 is not.

2

BACK UP — this is the step that would have saved today

cd /d/grouptrack_backups   # or wherever you keep them
mkdir -p droid1_2026-08-01

adb -s 8624SBCEDF00001789 exec-out run-as com.grouptrack.android true 2>/dev/null || true

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 exec-out \
  "cat /sdcard/Documents/GroupTrack/grouptrack_spatial.db" > droid1_2026-08-01/grouptrack_spatial.db

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 exec-out \
  "cat /sdcard/Documents/GroupTrack/grouptrack_data.db" > droid1_2026-08-01/grouptrack_data.db

exec-out with a shell redirect avoids the MSYS_NO_PATHCONV local/remote path conflict, and does not corrupt binaries the way adb pull can.

Verify the sizes are real before continuing:

ls -la droid1_2026-08-01/

⚠ A spatial DB of 118,784 bytes or a data DB of 208,896 bytes is an EMPTY SCHEMA, not data. Those are the exact sizes the destroyed files came back as on Droid 2. If you see them, stop — the damage already happened.

Also worth having: my_tracks/, state/, route_drafts/.

adb -s 8624SBCEDF00001789 pull /sdcard/Documents/GroupTrack/my_tracks   droid1_2026-08-01/
adb -s 8624SBCEDF00001789 pull /sdcard/Documents/GroupTrack/state       droid1_2026-08-01/
adb -s 8624SBCEDF00001789 pull /sdcard/Documents/GroupTrack/route_drafts droid1_2026-08-01/

Tiles under maps/ and OSM extracts under osm/ are large and survived intact today — skip unless you have time.

3

Record the "before" state

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell ls -la /sdcard/Documents/GroupTrack/

Keep this output. It is your comparison point in Step 7 — file sizes and timestamps for both .db files.

4

Verify the APK is newer than the sources it should contain

cd /c/Users/kixaz/Meshtastic-Android
ls -la --time-style=+%m-%d_%H:%M:%S app/build/outputs/apk/google/release/app-google-release.apk

The APK must be newer than every source file you expect in it. Twenty seconds versus a wasted test session against a stale binary.

5

6

Grant all-files access BEFORE first launch

Settings → Apps → GroupTrack → Permissions → Files and media → Allow management of all files

Not grantable from adb on most builds. Do this before opening the app. If the app launches without it, the failed DB open creates empty databases over the real ones — that is the exact sequence from today.

While you're there, confirm Location → Allow all the time if you intend to record tracks.

7

Ten-second check BEFORE trusting anything

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell ls -la /sdcard/Documents/GroupTrack/*.db

Compare against Step 3.

  • Sizes unchanged, tens of MB → databases intact, proceed.
  • Hundreds of KB, timestamp = now → they have been replaced with empty schemas. Stop using the app immediately and restore from Step 2.

Confirm from the app's own startup log:

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 logcat -d -s SpatialDbMgr:I | tail -5

Expect real counts. Spatial DB: 0 trails, 0 tracks, 0 waypoints, 0 routes means the open failed and the app is running on an empty schema.

8

Cold-launch from the icon and confirm

  • Trails and tracks draw on the convoy map
  • Trails and tracks draw on the planner
  • Artifact lists populate
  • Map opens to the persisted frame, not a GPS fallback to somewhere unexpected

If the databases were replaced — restore

Recovery from a Step 2 backup

Force-stop the app first so nothing holds the files open:

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell am force-stop com.grouptrack.android

adb -s 8624SBCEDF00001789 push droid1_2026-08-01/grouptrack_spatial.db /sdcard/Documents/GroupTrack/
adb -s 8624SBCEDF00001789 push droid1_2026-08-01/grouptrack_data.db    /sdcard/Documents/GroupTrack/

MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell rm -f /sdcard/Documents/GroupTrack/*.db-journal
MSYS_NO_PATHCONV=1 adb -s 8624SBCEDF00001789 shell ls -la /sdcard/Documents/GroupTrack/*.db

Then confirm all-files access is still granted (Step 6) before launching.

No backup? Rebuild is not catastrophic

Measured on Droid 2 today: complete data-model reconstruction in under one hour — OSM import, Utah state trails, tracks, waypoints. GPX files in my_tracks/, tiles in maps/, OSM extracts in osm/ and the per-map JSONs all survive this failure mode. Only the two .db files are replaced.

Standing rules for Droid 1

  • Droid 1 is not a test device. Anything risky, destructive, or unproven runs on Droid 2 first. Droid 1 receives only verified-safe work and real-GPS field testing.
  • Plain -r. Never -d.
  • First-install questions = cancel.
  • Back up the two .db files before any install until the open-failure fix ships.
  • Sideload or Play, not both.
  • Prefer wireless adb — USB drops when the cable moves.
  • Droid 1 holds BLE to T1000-E radios reliably (unlike the budget tablets), so it stays the radio-test device.
