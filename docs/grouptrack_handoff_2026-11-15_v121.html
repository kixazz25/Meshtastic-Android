✅ That one fact is what makes the whole iPad approach viable. @JavascriptInterface is synchronous and can return to JS; postMessage is one-way and cannot. Dispatch: wired for 1 of 11. Only onViewportChanged drives anything; the other ten arrive at onMessage and land nowhere. "Clicks were received" proved the transport, not the processes.

⭐⭐ FRED, 2026-11-15 08:38 — WHAT THIS TEST ACTUALLY IS: "this the foundation layer that all application objects are built upon. really big certification test."

This is not a routine test pass, and sizing it as one would be the mistake. The nine platform sockets plus the shared model are what every application object on iOS stands on — no screen, no map, no import, no ride, no housekeeping can be built above a layer that has not been proven on the platform. 37 tests is the right size for a foundation; the problem is that 36 of them have never run, which means the foundation under the entire 2.8b release is currently UNVERIFIED while the work above it is being planned.

Consequences for how we read the results: a failure here is blocking, not triage — it invalidates whatever sits on it rather than adding an item to a list. A failure in GtFiles, GtClock or GtImportPaths is worth more attention than a failure in any one feature, because every feature inherits it. And the inverse is the real prize: 37 green is the single largest de-risking event available on the iPad side, and it costs one command, because the tests are already written.
Why this matters beyond saving a step: it changes what the iPad programme is. The iPad is not a phase that follows the port — it is a second assertion on each ported seam. Step 17 already shows the shape: the harness lives in commonMain, the Droid runs it, the Mac runs it, value for value. Three of three ports already have an iosTest wrapper. "Stay the course on the steps, and run the iOS test alongside each one" is the iPad programme, and it needs no prototype.
