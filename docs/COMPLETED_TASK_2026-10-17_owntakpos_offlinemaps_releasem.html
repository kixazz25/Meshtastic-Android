CartMotion rules (proposed 07:56, taken as agreed 07:58): the steps are display-only — not stored as track points, never sent, no last-heard or status change, not used for off-track or the 50 m passed rule (only real reports count); catch-up from the last real point to the new one, never projected ahead (consistent with "wait for real fixes"); N = the cart's NORMAL report interval so the steps finish before the next expected report (observed radios ~20 s, configured 6 s / 30 s); a report that arrives early continues from wherever the icon is. The stepping is a short job per received message, not a standing timer. A. Connection (the comm side) — fix first; everything downstream depends on it

A1. Health check ties "radio alive" to GPS — PROVED (#7)

  • Symptom: radio connected, other radio heard, yet RADIO_SILENT -> forced reconnects -> RECOVERY_EXHAUSTED -> FAILCLEAR.
  • Code: MeshCommLink.kt 237-239 (LINKHB-2026-10-05). Once any own TAK report was seen, talking = own report < 45 s. Traffic ignored.
  • Why: T1000-E (TAK_TRACKER) sends its TAK report only with a GPS fix. No fix = no own report = "dead".
  • Proof: Droid 2 07:23:52 one replayed own report, then NONE until 07:32:13; Droid 1's radio heard every 20 s throughout. 07:25:26 RADIO_SILENT own=93s traffic=15s -> reconnect 1,2,3 -> exhausted own=207s traffic=0s. 07:32:21 fix -> own every 20 s -> talking. 0919 log: 20 forced reconnects, 8 exhausted. 0805 log: 6 / 3.
  • 10-15 hid it: each reconnect replayed an own report (own=0s) -> recovered.
  • Fix direction: (1) any traffic = talking [patch_healthtraffic_2026-10-16.py, written, not applied]; (2) a real ping to the radio — a LONE radio with no fix sends nothing over Bluetooth, so traffic alone can't tell alive from dead.
  • Decide: ping design; thresholds (45 s / 120 s / 20 s / 3 tries) owned by whom.

A2. Our reconnect leaves "no radio" stored; start-up never connects — PROVED (#10, #15)

  • Code: recovery and disconnect use setDeviceAddress("n") (MeshCommLink recovery block; group off). Meshtastic connects at start only if the stored device is real.
  • Proof: all six 10-15 installs (radio connected) launched in 17-48 s; all three 10-16 installs after our disconnects never launched; 09:35 restart after a good connection launched in 0.4 s. git diff cc5cbbba9..b17e43677: no connection code changed.
  • A1 multiplies A2: every false RADIO_SILENT is a chance to be stopped with "n" stored.
  • Fix direction: ONE owner of the connection. GroupTrack remembers the last radio and connects at start; never leave "n" stored.
