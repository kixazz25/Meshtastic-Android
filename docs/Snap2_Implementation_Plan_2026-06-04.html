Pre-flight research for the snap-2 logic slice. The toolbar UI is pact-compliant (this session); this plan is the wiring that comes next.
Researched 2026-06-04 from function_universe / where_used / field_crossref · NO code written · walk in and patch
Headline finding: the entire snap-2 path composes from functions that ALREADY EXIST and already compile. No new parsing, no new query, no new geometry code. Two call-site edits + one stub fill. The types line up end-to-end — verified below.

1. The snap data-source question — RESOLVED

The open question was: snap(tapLat, tapLon, trails, tracks, radiusM) needs trail + track line lists at tap time, but the tap handler only has lat/lon. Where do the lists come from?

Answer: query the viewport at tap time. The types match exactly with zero transformation:
  • queryTrailsByViewport(south,west,north,east,limit): List<Map<String,String?>> (SpatialDbManager:265)
  • queryTracksByViewport(...): List<Map<String,String?>> (SpatialDbManager:342)
  • snap() wants exactly trails: List<Map<String,String?>>, tracks: List<Map<String,String?>>
And the KEYS match: snap→nearestPointOnLines reads line["geometry"] (RouteManager:114) and line[idKey] (115), where idKey is "trail_id"/"track_id". The viewport queries return maps with exactly those keys (same maps buildTrailGeoJson consumes via trail["geometry"]). Drop-in.
Recommendation: query the viewport ONCE when route mode is entered (or on viewport change), cache trails+tracks in two vals the tap handler closes over. Re-querying on every tap is wasteful and risks lag. The current map already tracks lastViewportSouth/West/North/East (seen in onEditDisplay) — reuse those bounds. Cache invalidates on pan/zoom (the viewport-change callback already fires).

2. The two edits (exact call sites)

Edit A — snap on tap (replace free-place)

Both screens, the onMapTap bridge. Today (ConvoyScreen ~522-525, ConvoyMapViewerScreen ~476-479):

RouteManager.addVertex(RouteManager.freeVertex(lat, lon))
val pts = RouteManager.routeVertices().joinToString(...) { "[${it.lat},${it.lon}]" }
webViewRef...evaluateJavascript("drawBuildLine('" + pts + "')", null)

Becomes:

val s = RouteManager.snap(lat, lon, cachedTrails, cachedTracks, SNAP_RADIUS_M)
val v = if (s != null) RouteManager.snapToVertex(s) else RouteManager.freeVertex(lat, lon)
RouteManager.addVertex(v)
val pts = RouteManager.routeVertices().joinToString(...) { "[${it.lat},${it.lon}]" }
webViewRef...evaluateJavascript("drawBuildLine('" + pts + "')", null)
Only fires when Add is ARMED (green). The toolbar now owns addArmed; the host must know the armed state at tap time. Cleanest: onAddPointModeArmed already pushes setRouteMode(true/false) to JS — extend it to carry the armed flag, and gate the JS tap-emit on it (tap only emits when armed). Decide next session: gate in JS (cleaner — pan works when disarmed) vs gate in Kotlin.

Edit B — Save completed (fill the stub)

The onSaveCompleted = { } stub at both call sites. Fill with:

// lineGeom lambda: lineId -> that line's WKT -> List<DoubleArray>
val byId: Map<String, String> = (cachedTrails + cachedTracks)
    .mapNotNull { m -> val id = m["trail_id"] ?: m["track_id"]; val g = m["geometry"]
                       if (id != null && g != null) id to g else null }.toMap()
val res = RouteManager.buildWktAndBbox { lineId -> byId[lineId]?.let { RouteManager.parseWktLine(it) } }
if (res != null) {
    val (wkt, bbox) = res   // bbox = [minLat,maxLat,minLon,maxLon]
    val name = "Route " + System.currentTimeMillis()   // naming UX = later
    SpatialDbManager.insertRoute(name, wkt, bbox[0], bbox[1], bbox[2], bbox[3])
    RouteManager.clearRoute()
    // redraw: re-fire route lazy-load so the new DB row draws gold dashed
    // (reuse existing queryRoutesByViewport -> buildRouteGeoJson -> updateRoutes/showRoutes)
    webViewRef...evaluateJavascript("setRouteMode(false); clearBuildLine();", null)
}
parseWktLine(wkt): List<DoubleArray> (RouteManager:42) is EXACTLY the return type buildWktAndBbox's lambda needs. The lambda is a one-liner over the cached maps. No new code.

5. Suggested slice order (smallest first)

  1. Save-completed first (Edit B) using the current free-place tap. This proves the whole spine end-to-end: place free points → Save → buildWktAndBbox → insertRoute → DB row → redraw. No snap yet. Smallest provable win.
  2. Then snap-on-tap (Edit A) + the cache. Now points snap to trails.
  3. Then armed-state gating (Q1) so RED actually pans.
This order means the FIRST build proves "a route reaches the DB and draws" — the highest-value, lowest-risk confirmation — before adding snap complexity. Matches the one-use-case-end-to-end discipline.
