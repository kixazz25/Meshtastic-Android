1. Snap data source — CORRECTED after code review

Fred's read was right: the displayed trails/tracks are NOT retained in a Kotlin var. The lazy-load uses LOCAL vals inside the viewport-change callback, builds GeoJSON, hands it to JS, and they go out of scope:

// ConvoyScreen ~720/726, ConvoyMapViewerScreen ~596/601
val trailResultsRaw = queryTrailsByViewport(south, west, north, east, ...)   // local, dropped after JS
val trackResultsRaw = queryTracksByViewport(south, west, north, east, ...)   // local, dropped after JS
... buildTrailGeoJson -> updateTrails(json) ...   // handed to JS, not kept
But the viewport BOUNDS are retained — lastViewportSouth/West/North/East (ConvoyScreen 200-203; same on the viewer). So the fix is trivial and needs ZERO new state.

Recommended: re-query at tap (option 1)

The tap handler already has the retained bounds. Query the same small on-screen set right there and feed snap():

val trails = SpatialDbManager.queryTrailsByViewport(
    lastViewportSouth, lastViewportWest, lastViewportNorth, lastViewportEast)
val tracks = SpatialDbManager.queryTracksByViewport(
    lastViewportSouth, lastViewportWest, lastViewportNorth, lastViewportEast)
val s = RouteManager.snap(lat, lon, trails, tracks, SNAP_RADIUS_M)
val v = if (s != null) RouteManager.snapToVertex(s) else RouteManager.freeVertex(lat, lon)
RouteManager.addVertex(v)
Why option 1 over retaining a displayedTrails var: (a) zero new state; (b) zero staleness — it always matches the current viewport bounds, which are kept current by the existing viewport-change callback; (c) it's a handful of items (viewport-limited, 50–200 rows), one fast indexed query per tap. The snap radius then narrows that set to what's near the tap. This is exactly Fred's "retrieve from spatial DB for a handful of items."
Alt (option 2), if tap-query lag ever shows: add var displayedTrails/displayedTracks, assign in the lazy-load where the raw lists are built, tap reads them. More state, small staleness window on fast pan-then-tap. Not needed unless profiling says so.

Edit B — Save completed (fill the onSaveCompleted stub)

// build lineId -> WKT lookup from a fresh viewport query (same bounds)
val lines = (queryTrailsByViewport(...bounds...) + queryTracksByViewport(...bounds...))
val byId = lines.mapNotNull { m -> val id = m["trail_id"] ?: m["track_id"]; val g = m["geometry"]
                                   if (id != null && g != null) id to g else null }.toMap()
val res = RouteManager.buildWktAndBbox { id -> byId[id]?.let { RouteManager.parseWktLine(it) } }
if (res != null) {
    val (wkt, bbox) = res                    // bbox = [minLat,maxLat,minLon,maxLon]
    SpatialDbManager.insertRoute("Route " + System.currentTimeMillis(), wkt, bbox[0], bbox[1], bbox[2], bbox[3])
    RouteManager.clearRoute()
    webViewRef...evaluateJavascript("setRouteMode(false); clearBuildLine();", null)
    // then re-fire the route lazy-load so the new DB row draws gold dashed
}
For snapped routes that ride a trail, buildSegments needs the line geometry of the snapped vertices' lineIds — hence the byId lookup. For a first proof with FREE points only (no snap), the lambda can return null and segments are straight lines between points — so Edit B works even before Edit A. That's the slice order below.

3. Slice order (smallest provable first)
