All-Files Authority — Fix Strategy

2026-08-09 v1 · INTERNAL · the 08-01 and 08-08 data-loss root cause
⚠ DESIGN ONLY — no code written. Supersedes the permission reasoning in 00-INSTALL, which assumed a stale grant from a previous install.

1 · The defect, located

Both halves of the failure are on one screen.

ConvoyScreen.kt:145  var showStoragePermissionDialog by remember {
                         mutableStateOf(!Environment.isExternalStorageManager()) }
ConvoyScreen.kt:151  if (!Environment.isExternalStorageManager()) { ... }
ConvoyScreen.kt:433  ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION
OsmImportStage.kt:575 Environment.isExternalStorageManager()

FAULT 1 — WRONG SOURCE OF TRUTH. isExternalStorageManager() reads the AppOps record. In the failure state that record says granted while the filesystem refuses access. So the expression initialises showStoragePermissionDialog to false and the prompt never fires. Fred: "the app said it had all authority, the checkbox was yes, but the app did not have all authority."

FAULT 2 — FAR TOO LATE IN THE CYCLE. The check lives inside a Composable, so it runs when the convoy screen composes: after Application.onCreate(), after the Activity starts, after Meshtastic's setup has run, and after anything that touched storage on the way. The authority request is one of the LAST things in startup when it needs to be one of the first.

2 · Why the record and the enforcement disagree

AOSP: storage access is enforced by a per-process mount view, not by the permission record. Three views exist (/mnt/runtime/default, /read, /write); a mount namespace is created for each app at Zygote fork time and the appropriate view bind-mounted in. Upgrades are meant to be applied to running apps by vold, and downgrades are meant to kill the process.

⭐ So there are two independent sources of truth — the AppOps record (what the API and the settings toggle read) and the mount view (what the filesystem obeys) — and the reconciliation between them has documented gaps. CommonsWare recorded a case where a storage privilege downgrade did NOT terminate the process, leaving a stale view behind.

⚠ HYPOTHESIS, NOT PROVEN. It fits every symptom and it is assembled from AOSP's documented design plus a documented gap — not from GroupTrack's logs. Several earlier explanations this session were wrong. Nothing below depends on this being right.

3 · What is actually at risk

ThingAt risk?
Data in Documents/GroupTrack/ NO. Public shared storage — survives clear-cache, clear-data, uninstall, all of it.
Lost storage access Recoverable. Uninstall + reinstall establishes a proper grant (observed).
The app writing a blank over the real DB THE ONLY PERMANENT LOSS. Everything else is an inconvenience.

⭐ THIS IS THE WHOLE POINT OF THE STRATEGY. We do not have to fix the permission to stop losing data. We have to stop the app proceeding when it cannot see its own files.

4 · The fix, in build order

STEP 1 — REPLACE THE TEST. Never ask the API.

The only truthful question is a real read of a path All-Files actually governs. The app always has authority to filesDir/cacheDir, so reading those proves nothing.

fun hasRealStorageAccess(): Boolean = try {
    val d = File(Environment.getExternalStorageDirectory(), "Documents/GroupTrack")
    d.exists() && d.canRead() && d.list() != null      // plain File I/O, no SQLite
} catch (e: Exception) { false }

⚠ "Cannot see it" and "it is not there" get the SAME treatment. The app must never read invisibility as emptiness — that is precisely the mistake that built blanks over real data. Treat it as UNKNOWN and refuse.

⛔ Plain File I/O only. No SQLite anywhere in this test — an open is the dangerous operation, and it must not happen before the answer is known.

STEP 2 — MOVE IT EARLIER. Application.onCreate().

That is the earliest our code runs: before any Activity, before Meshtastic's setup, before anything touches storage.

⚠ UI cannot be shown from Application.onCreate() — so it sets a flag rather than prompting. The flag is what everything downstream reads; the prompt comes at the first Activity.

⭐ Setting state early is enough, because Step 3 is what actually protects the data.

STEP 3 — REFUSE TO CREATE. The floor under everything.

Gate every DB and tile-store open on the flag. If access is not real: do not open, do not create, do not run setup work.

  • SpatialDbManager — the spatial DB open
  • MBTilesStore — the tile stores. ⚠ The maps survived 08-08 by luck, not by design. Nothing structural protected them.

⭐ This is the only step that does not depend on understanding the permission bug. It works whatever the cause turns out to be, and it converts the worst case from "rebuild 490,000 trails" to "reinstall and carry on."

⚠ ALSO CHECK THE DATABASE ERROR HANDLER. If SpatialDbManager opens without passing a DatabaseErrorHandler, Android's default deletes a database it considers corrupt and recreates it — and an unreadable file is indistinguishable from a corrupt one. A custom handler that logs and throws is a one-parameter change. UNVERIFIED — grep it before building: grep -rn "openOrCreateDatabase\|DatabaseErrorHandler" SpatialDbManager.kt

⚠ Fred restored a real DB by hand and the app zeroed it out and reset it. That is not explained by a missing file — it means something destroyed a populated database it could not open. Until that is understood, Step 3 must sit ahead of every open, not merely ahead of creation.

STEP 4 — SAY SOMETHING TRUE. Only promise what has been observed.

When the read fails:

"GroupTrack cannot reach its map storage.

 Your maps and tracks are safe in Documents/GroupTrack — nothing
 has been changed or deleted.

 The storage permission shows as granted but is not working.
 Uninstall GroupTrack and install it again to fix it."

⚠ Do NOT promise the settings toggle will fix it. Firing ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION opens the same page the app already appears granted on — entry state and exit state are identical (Fred's point, and it is right). Turning it off then on MIGHT force the process kill that reconciles the view, but that has never been demonstrated: by the time it was tried on 08-08 the data was already gone, so nothing was proven.

⭐ Uninstall + reinstall is the ONLY remedy actually observed to work. Say that until something else is tested.

STEP 5 — INSTRUMENT THE REFUSAL SCREEN.

This has now cost data twice and the behaviour is not understood. Put the evidence on screen so the next occurrence is a photograph, not an evening of reconstruction:

  • what isExternalStorageManager() claims
  • whether the plain read succeeded
  • what filesDir contains
  • what is visible in Documents/GroupTrack/, and file sizes if readable
  • what triggered this startup path

⭐ Costs nothing, needs no theory, and captures whatever the cause actually is.

  • Does appops set <pkg> MANAGE_EXTERNAL_STORAGE allow + force-stop restore it? That would isolate record vs process.

6 · Testing — and why it is awkward

⛔ NOT ON DROID 2. It carries 490k Utah trails and a live corridor rebuild. It stopped being a test device on 08-08.

⭐ The state can be reproduced non-destructively: on a spare device, put a small dummy grouptrack_spatial.db and a marker file in Documents/GroupTrack/, then clear cache / reinstall over the top. Observe: does the permission read as granted, does a plain read succeed, does the dummy survive. Same state, nothing real at risk.

⚠ Verify the founding assumption of 00-INSTALL while you are there: that an uninstall leaves Documents/GroupTrack/ intact. It should — public shared storage — but Android has changed storage behaviour repeatedly and the entire rename-based design rests on it.

7 · What this changes in 00-INSTALL

  • KEEP: grant before the database; filesDir marker (not shared storage); refuse-to-create as the floor; the rejection of blocking startup entirely.
  • CORRECT: the doc says the API "reads the stale grant record" from a previous install. It is not stale — the grant was live and the enforcement disagreed. No permission API returns the right answer at any time.
  • CORRECT: "make the prompt unconditional and put it first" is necessary but not sufficient. The user was already granted, so an unconditional prompt shows a permission that is already on and changes nothing. The gate must be a real read.
  • NOTE: the self-uninstall rename flow still only covers the path where the user taps the button. Settings-initiated clear-data and clear-cache bypass it entirely — and that is what bit us both times.
