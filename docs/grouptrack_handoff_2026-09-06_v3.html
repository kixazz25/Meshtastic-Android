What the manual review found today

Five corrections, all from Fred reading it against the app. ⭐ The shape of what happens when a section is written from screenshots rather than conversation.

  • Connect before configuring. Nothing can be applied to a radio the app cannot reach — Connection was filed as entry E, well after the new-radio instructions. Pairing code 1234 unless a unique one came with the device.
  • The automated configuration is T1000-E only. It was buried in "Which radio"; now a boxed statement where a rider meets it.
  • Real range figures. Seeed cite 2–5 km; dense urban or foliage gives 0.5–1.3 miles; line of sight several miles. ⛔ Wear it high, button outward — buried in a backpack is the commonest reason a tracker underperforms.
  • ⭐⭐ The radio menu exists for one problem: another group on the same network in your area at the same time. If that is not happening, go straight to Apply Master Config. The section says so before the five options now.
  • ⛔ Every radio must be moved to a new configuration. Create, distribute, and every rider installs it before the ride — the third is the one that gets forgotten. One rider left behind is invisible to everybody.

⭐ Rider trails — the big one for 2.6h

Proven today in Python, and it works. Broken Ridge and Steamboat gave about 80 miles of new connected ground. Rebuilding a recipe with it in returned genuinely different routes. Fred: "those two trails open up riding all through the area."

What it does

Walk a recorded track. Where it leaves the published trail network and later rejoins it, that whole run is one new trail — unnamed, source rides. A short connector at each end joins it to the node the track came from, which is what makes it routable rather than decorative.

⛔ Three wrong turns, so they are not repeated

  1. Distance alone gives nonsense. "Is a trail within 20 m?" produced 271 fragments from one ride — GPS drift stepping in and out of a threshold.
  2. ⭐ Direction is the test. A trail nearby going the same way is the trail you are on, however the GPS wandered. Undirected — ridden the other way is the same trail. 271 became 69.
  3. ⛔ A run must not end the first time a trail appears. Passing near something, or crossing a road, was cutting one stretch into several. Require a sustained rejoin — 120 m on the network — before closing a run. An out-and-back is ONE trail.

⚠ It cannot be a GPX import

<trk> imports as a track, <rte> is a route, and ConvoyTrackImportScreen does not touch the trails table at all. Trails only come from the catalogue import.

⭐ So this belongs in the app: when a track is saved, find the ground with no trail under it and write those trails directly. Fred: "every track processed should be checked for new unnamed trails to be created."

The rules

  • Unnamed, source "rides". "It doesn't have to be perfect, it has to be honest."
  • Lumped in with every other trail for filtering.
  • ⭐⭐ They travel with the ROUTE, not the state import. "We know it is not on every setup — get a route or a ride that uses it and add it." A state reimport clearing trails does not matter, because they come back with the routes that need them.
  • ⭐ A shared route must carry everything it depends on — waypoints and any rider trails it crosses.

⭐ How it runs in the app — Fred's design, 09-06

  • A field on the track extension recording that this track has been through the add-trails process. ⚠ Without it there is no way to tell a track that yielded nothing from one never examined.
  • A batch process inside the import-trails flow that adds trails from tracks — so it sits with the other trail-data work rather than somewhere of its own.
  • ⭐ A green button under SYNCH, shown only when tracks exist that have not been checked. No badge, no nagging — the control appears when there is something to do and is absent when there is not.

⭐⭐ 2.6h is THE TRAILS RELEASE

Fred, 09-06: "the release is a fundamental redesign and rewrite of trails" — "and route building through those trails."

⭐ That is the framing, not a list of leftovers. Everything in 2.6h is one subject: better trail data, more of it, rider-contributed where the sources are silent, and route building that makes proper use of it.

⚠ And they are not separable. Adding 80 miles of rider trails today changed what the planner returned — the router is only as good as the network under it.

The two big pieces

  • Land ownership for all fifty states. ⚠ The URL pattern is fixed and only the item id changes — but a layer that lists PUBLIC land positively inverts our test, so absence would mean private or unmapped, and marking unmapped trails private hides them under the shipped default. Each catalogue entry needs: item id · which field carries ownership · continuous or positive.
  • Crashed-import restart from the manifest. Step 8 became a real stage in 2.6g, which was the prerequisite.

Release procedure — five hand-edited steps

Nothing prompts for any of these, and every one has been missed at least once.

  1. The release label in ConvoySettingsScreen.kt.
  2. __htmlVersion in both map HTML files.
  3. The schema marker in StartupHousekeeping, when the trail schema changes.
  4. ⭐ Copy the three documents into assets/ — the release notes asset sat three weeks stale because nobody did.
  5. ⭐ Increment the revision in every document filename — Windows appends "(1)" to duplicate downloads and you end up working from the wrong one.

Worth remembering

  • ⛔ Read what exists before writing something new. Five occurrences this week.
  • ⭐ Manual figures: 720 on the LONG edge. Portrait screenshots land at 450×720, median 32 KB.
  • ⭐ Shared content is DUPLICATED in a manual, unlike code. A reader should never have to leave the section they are in.
  • Anchors from cat -A, never sed.
  • Patch guards must strip comment lines before checking for removed strings.
  • TrailFilterState is a plain singleton, not Compose state — every composable reading it needs tick.
