AI components — builder and review/resolve

2026-08-27 · two callable processes, specified for build · supersedes the process-3 sketch in PROCESS-2026-08-26

⭐⭐ THE RECIPE IS THE IDEA THAT MAKES THIS WORK.

Every route carries, inside its own narrative, the complete set of inputs that produced it — staging waypoint and name, the mileage band, the pace band, and every rider pin. A button on that section rebuilds the identical batch.

So discarding five of six stops being lossy. Yesterday Fred saved routes he did not want purely to be able to compare them, because saving was the only way to see them. With a recipe on the kept route, the five that were cleared can be recreated exactly, any time — and the decision to discard costs nothing.

COMPONENT 1 Build routes

Takes the complete requirement set. Produces six named WIP routes, a narrative for each, and the batch state file. Knows nothing about how the requirements were gathered.

Signature

buildRouteBatch(
    batchName:   String,           // "Panguitch September"
    staging:     Waypoint,         // lat, lon, name
    milesLow:    Double,           // shortest ride worth taking
    milesHigh:   Double,           // furthest they will go
    mphLow:      Double,           // 12
    mphHigh:     Double,           // 18
    pins:        List<LatLon>,     // 0..5, may be empty
    finish:      LatLon?,          // null = loop back to staging
): BatchResult

⭐ EVERY PARAMETER IS A RIDER DECISION. Nothing derived, nothing implicit. That is what makes the recipe possible — the parameter list IS the recipe, so the two cannot drift apart.

⚠ And it is why this must be callable, not inlined in a screen. The recipe button calls exactly this function with exactly the stored values. If the screen held any of the logic, a rerun would not be a rerun.

What it produces

  1. Six named WIP routes — Panguitch September Route 1 … Route 6, drafts in the WIP directory.
  2. A narrative per route, ending with the recipe section.
  3. The batch state file, which stops any further route creation until resolved.

⭐ The recipe section

Appended to every route's narrative. It is the rider's own inputs read back, not a description of what the engine did.

── RECIPE ──────────────────────────────────────────────
Built 26 August 2026 from:

  Start        Birch Spring staging   37.72350, -112.61300
  Distance     55 to 80 miles
  Pace         12 to 18 mph  (5.5 – 6.6 hours)
  Your places  3
                 1  moved 33 ft to Horse Valley Road
                 2  moved 19 ft to FSR 082
                 3  moved 115 ft to FSR 082
  Finish       loop back to the start

            [ BUILD THESE ROUTES AGAIN ]
────────────────────────────────────────────────────────
FieldWhy it is in the recipe
Staging waypoint, name AND coordinatesThe name is for the rider; the coordinates are what the rerun uses. ⚠ A waypoint can be renamed or deleted — the coordinates must stand alone.
Both mileage boundsNot the achieved distance. The rider asked for a range and the rerun must ask for the same range.
Both pace bounds⚠ Shown with the resulting hours, because that is what the rider actually set them by.
Every pin, with where it moved to⭐ The rerun uses the ORIGINAL tap, not the snapped point — otherwise repeated reruns would creep along the trail. The moved-to line is the honest record for the rider, not an input.
Finish, or "loop"Null is a real answer and must be recorded as one.

⚠ THE RECIPE MUST SURVIVE PROMOTION. It is written into the narrative, and the narrative travels with the route when it becomes permanent. A recipe that lived only in the batch file would die when the batch was deleted — which is exactly when it becomes useful.

COMPONENT 2 Compare and resolve

⭐⭐ THE WIP TRACKS ARE THE TRUTH, NOT THE JSON. Fred, 08-27.

WIP EXISTING IS THE GATE. The JSON decides WHICH compare. Fred, 08-27:

Route+ tapped
  → WIP exists + batch JSON   →  AI COMPARE   (the six, legend, colours)
  → WIP exists, no JSON       →  the ordinary WIP list
  → no WIP                    →  straight into a new route, no prompt

⭐ And the third line kills the confirm-new-route prompt. Fred, 08-27: "we just selected Add Route+ — we do not need to confirm our intent on a button we just selected." The prompt was standing in for a decision the app can now make properly.

⚠ Plus: delete a zero-point autosave on entry. An autosave with no vertices is not a draft, it is residue, and clearing it at the point of entry means it never reaches the WIP list. ⚠ ZERO specifically — a one-point draft is a rider who tapped once and left.

That is the whole trigger and the whole lock. The batch file is not consulted to decide whether something is outstanding — the drafts on disk answer that directly.

⭐ Why this is better than what was specified yesterday: a JSON that claims six routes exist while the directory holds four is a lie the app would act on. The directory cannot be wrong about its own contents. And a batch file lost to a crash cannot strand the rider, because it was never what held the lock.

What the JSON is actually for

Restarting the compare session, and nothing else.

FieldWhy

⚠ THE JSON IS DISPOSABLE, AND THE DESIGN MUST TREAT IT THAT WAY. If it is missing or unreadable, compare still opens — every route shown, nothing hidden, nothing selected. The rider loses their narrowing, not their routes.

⭐ That is the MARKERFIX lesson applied properly. The trails-clear marker was load bearing and lived somewhere it could vanish. This file can vanish safely by design.

Signature

hasOpenBatch(): Boolean          // are there WIP routes? — the directory decides
openCompare(): Unit              // draw them, restore session state if any

What compare does

  1. Lists the WIP routes on disk
  2. Loads and draws them all, each in its own colour
  3. Restores selections and hidden state from the JSON if it is there
  4. Shows the legend: name in its colour, tap for narrative, show/hide, select
  5. Writes session state back on every change

⛔ COMPARE OWNS THE MAP WHILE IT IS OPEN

Route mode OFF on entry, restored on exit. Fred, 08-27: "it needs to turn Route+ mode off so we do not draw vertexes in this compare function."

⭐ And it is more than a flag. Compare needs the map for its OWN gestures — tapping a drawn route to select it, tapping a name in the legend. With route mode live underneath, every one of those becomes a vertex on a route the rider never meant to edit.

⚠ Restore it to WHAT IT WAS, not to a fixed value. A rider can reach compare from more than one place, and coming back to a different mode than they left is the kind of small wrongness that is very hard to report.

⚠ AND IT TAKES MAP TAPS ON/OFF WITH IT. That control lives in the route toolbar, which renders on routeMode && !showAiDesign — so with route mode off the toolbar is gone. Correct here, since compare does not want vertex editing, but it means compare must supply any map control it needs itself.

⛔ PORTRAIT ONLY, FOR EVERY AI PLANNING FUNCTION

Fred, 08-27: "all AI planning functions should exist only in portrait." Locked on entry to the flow, restored on exit — the same shape as the route-mode rule: the AI flow owns the screen while it is open and hands it back as it found it.

⭐ The compare table is what demands it. Three columns of numbers, stacked under a map — that is a vertical layout, and landscape leaves no room for either half.

⭐ And consistency across the flow matters more than optimising each screen. A rider whose phone flips between steps is fighting the app while trying to think about a ride.

The two exits

ButtonBehaviour
EXITLeaves everything. WIP routes stay, session state is written, route creation stays blocked. ⭐ Route+ reopens exactly this screen with the same routes hidden and the same ones ticked.
SAVE SELECTEDPromotes the ticked routes — writing the recipe into each saved narrative — deletes the unticked WIP routes, deletes the JSON. Route creation is available again.

⭐ THE TWO EXITS MEAN DIFFERENT THINGS AND BOTH ARE NEEDED. EXIT is "I have not decided"; a rider interrupted mid-comparison must be able to walk away. SAVE SELECTED is "I have decided", and it is the only thing that clears the lock.

⚠ Saving nothing is a valid decision — ticked none, pressed SAVE SELECTED: they looked and liked none of them. All six go and the lock clears. ⛔ But the recipe goes with them, so it must say plainly that these cannot be rebuilt afterwards.

⭐ DELETION IS REVERSIBLE — AS LONG AS SOMETHING IS KEPT. Fred, 08-27: "non-selected can be recreated anytime by clicking on the recipe section of the saved track narrative."

Keep one route and the other five are gone — but the kept route carries the recipe that built all six, so BUILD THESE ROUTES AGAIN reproduces the identical batch.

⚠ Identical, not similar. The engine is deterministic: same inputs, same rides. Anything that makes generation depend on time, random seeds or mutable state breaks the recipe silently.

⚠ What must be true for a rerun to be identical

  • Same trail data. A state reimported in between changes the network and therefore the rides. ⭐ Record the trail count in the recipe so a changed corpus is visible rather than mysterious.
  • No random seed. The new engine has none. Request.seed survives from the old greedy and should go with TRIES and BEAM_TOP.
  • The graph cache must not leak between runs. splitEdgeAt mutates the cached graph, so a rerun could inherit synthetic split nodes from a previous search. ⛔ NOT YET VERIFIED, and it would break the recipe silently.
  • The rerun uses the ORIGINAL tap, not the snapped point — or repeated reruns creep along the trail.

⭐⭐ THE RECIPE TRAVELS IN THE GPX — and that changes what a shared route is

Fred, 2026-08-27: "placing the recipe ingredients into the GPX narrative section for every trail is an important detail ... so if you share one route, a user can recreate any other alternative with one button click."

A shared route stops being a line on a map. It carries the ingredients to rebuild its own alternatives. Someone who has never used the planner opens your file, presses one button, and gets the other five rides from your parameters.

⚠ THIS PUTS A REQUIREMENT ON THE GPX ROUND TRIP. The recipe must survive export AND import. If the importer drops or truncates the description field, the recipe dies exactly where it is most useful — on the shared copy.

⭐ Cheap to check and worth doing early: export a route with a long description, reimport it, see what comes back.

The button pre-fills the prompt — it does not replay

Fred, 08-27: "one prompt, so maybe you change the mileage but basically rerun the same waypoint route creation."

⭐ So the recipe is a STARTING POSITION, not a replay button. It lands the rider in the parameters step with everything filled in — staging point, pins, band, pace — and they adjust before running. "Same place, same must-sees, but give me a shorter day" is probably the commonest use, and it is one field changed rather than the whole flow re-entered.

⭐ And it solves the shared case properly. Someone opening your GPX sees YOUR parameters and can adjust them to their own group. They are not stuck with your 55–80 band or your pace.

⚠ Open questions

  • Where does the recipe live physically? Inside the narrative text, or as structured data beside it? Text is simple and survives anything; structured data is what the button needs. Probably both — rendered text for the rider, JSON for the button.
  • Does a rerun replace or add? Rebuilding from a saved route's recipe creates six new WIP routes. Are they the same names — Route 1 … Route 6 — colliding with the saved one? Leaning: the batch name gains a suffix.
  • What if the recipe's staging waypoint no longer exists? The coordinates still work. ⚠ The rerun should say the waypoint is gone rather than silently using a bare point.

⬜ OPEN — creating a trail where the data has none

⛔ THE PROBLEM, found on device 08-27. Fred dropped pins along an existing track — one visible on the map, with trails and roads around it — and routes would not build. The segments he pinned are not in the OSM definitions.

⚠ This is the INVERSE of the roads-near-town problem, and the two will be easy to conflate later. Near town, the trails table contains roads that should not route. Here it is MISSING track that should.

⭐ The real gap is that the picture and the routing data are two different things, and nothing says which is which. The rider sees a track on the satellite tile, drops a pin on it, and the router has never heard of it. Nothing in the interface distinguishes drawn from routable.

⛔⛔ ROOT CAUSE FOUND — THE PLANNER READS TRAILS ONLY. buildGraph in RouteExplorer.kt is one query:

SELECT trail_id,name,geometry FROM trails
 WHERE min_lat<=? AND max_lat>=? AND min_lon<=? AND max_lon>=?

The tracks table is never read. So Fred's pins failed for a STRUCTURAL reason, not a data-quality one — a recorded track is visible on the map and snappable when drawing by hand (vertices carry lineType of "trail" or "track", and the graduation path fetches geometry for both), but the planner's graph is built from trails alone.

⭐⭐ It is not that the ground is missing. It is that the planner cannot read where it lives.

⭐ WHICH REFRAMES THE WHOLE FEATURE. Before building a process for riders to hand-create trails, try the query: bring tracks into the graph alongside trails. Every rider with recorded tracks benefits, and nobody hand-fixes data.

⚠ What it needs deciding: tracks are unvetted rider recordings. A track recorded riding a trail is good routing data; one recorded in a truck on the highway is not — and that is the same roads-vs-trails problem arriving by a different door. Some rule has to say which tracks count.

⚠ And the graph rules must hold — wktPoints, the dedup, and the junk classifier all assume trail-shaped input.

⭐ The create-a-trail process below stays as the FALLBACK, for ground that is genuinely absent from both tables.

⭐ PROTOTYPE IN PYTHON FIRST — the coverage test

The rule Fred wants: "use trails unless trails do not exist and tracks do." Trails are the better data wherever they exist; a track only earns a place in the graph where it is filling a gap.

⭐ The test is geometric, per track: sample points along it and ask how many fall within a few yards of an existing trail.

mostly covered      → drop it, the trail is better data
mostly not covered  → include it, it is filling a gap

⭐ And the spatial grid already answers this cheaply. It is the same proximity question that took feature lookup from 5.8s to 0.1s, with different input — and tracks in a corridor are few, because they are the rider's own recordings.

⭐⭐ THE TARGET IS A PER-SEGMENT UNION, NOT A PER-TRACK ONE. Fred, 08-27: "we would really want to build our graph tables with a union of data, with trails defaulting and tracks filling missing segments."

That is a stronger rule than include-or-drop a whole track, and it is the right one. The graph is assembled from both tables with trails winning wherever they exist; a track contributes only the stretches where no trail does.

for each track:
    where a trail already covers it   →  contribute nothing
    where no trail covers it          →  contribute that segment

trails DEFAULT · tracks FILL

⭐ It removes the awkward case rather than handling it. A recording that runs along a known trail and then continues past where the data ends stops being a judgement call — the covered part is dropped and the continuation is kept, because that is simply what the rule says.

⭐ And it is honest about provenance: every edge in the graph comes from the better source available for that piece of ground, rather than from whichever whole object won a threshold.

⚠ WHAT IT COSTS OVER THE WHOLE-TRACK VERSION: splitting on coverage means finding the boundaries, not just scoring a fraction — walk the track's points, mark each covered or not, and cut where the answer changes. splitEdgeAt already cuts edges for pin snapping and candidate starts, so the machinery exists.

⚠ Two things the prototype has to settle: how short a fragment is worth keeping — a 20-yard gap between two trails is noise, not a segment — and whether the fragments actually CONNECT at their ends, because a filled segment that does not meet the trails either side of it fills nothing.

⭐ Whole-track include/exclude is still worth running FIRST, as one line of the same prototype: if tracks make no difference even when added wholesale, the per-segment version is not worth building.

⚠ THE ORIGINAL AWKWARD CASE, kept for the record — a recording that runs along a known trail and then continues past where the data ends. Dropping it loses the useful part; keeping it whole duplicates the trail.

The clean answer is to SPLIT it, and the engine already knows how — splitEdgeAt exists for pin snapping and for edge-splitting at candidate starts.

⚠ But splitting on coverage is more than a first cut needs. Whole-track include/exclude proves the idea; the split follows if the boundary case turns out to matter in practice.

⭐ SCOPED TO AI MODE ONLY

buildGraph is the planner's own function and nothing else calls it. Manual route drawing already handles both types on its own path — vertices carry lineType, and the graduation path fetches trail and track geometry separately.

⭐ So this is a UNION in one query, inside one function, with no other caller to consider — tried and reverted cheaply, with the manual path untouched either way.

⚠ It needs a lineType on each geometry. The graph carries trail_id and treats every id as a trail; an unmarked track id would send route-saving to the wrong table. The convention already exists on Vertex.

⭐⭐ THE RECIPE IS THE CONTROL — Fred, 08-27

"If I save one of these routes we can use the recipe to duplicate the run, subbing tracks for missing trails."

⭐ That turns the prototype from a demo into a controlled experiment. The recipe is exactly the parameter set the engine takes — anchor, both mileage bounds, both pace bounds, pins, finish. Run it twice against the same DB, changing only whether tracks are in the graph, and every difference in the output is attributable to that one change. Nothing else moved.

The process

The rider selects the missing part of a track they can see, and the app makes it a routable trail. Unnamed, because it has no name to give it.

⭐⭐ IT GOES IN AS ITS OWN TRAIL SOURCE. Fred, 08-27: "I think it is a different trail source so it can survive."

That solves the hard part with machinery that already exists. Imports are per-source, so a user source is simply never one of the sources a state reimport touches — it survives by construction, not by remembering to protect it.

⛔ And survival was the risk that decided the design. A created trail sitting in the trails table alongside OSM data would vanish on the next state reimport, and routing would quietly break again with no explanation. Worse than not offering the feature.

⭐ It gets more for free: the source appears in the import record, so created trails are countable, inspectable and separable. And the data stays honest — a rider-drawn connector is not OSM data and should not claim to be.

The rule

rider taps a pin
   ├─ not reachable over existing trails   → REFUSED, toast says why
   ├─ would push the minimum route past the
   │  distance ceiling                     → REFUSED, toast says why
   └─ otherwise                            → accepted, count goes up
DecisionWhy
Validated AT DROP, not at search⭐ One pin against a graph that already exists — cheap. And the rider learns immediately instead of at the end.
Refused, not accepted-then-removed⛔ A pin that is placed and later dropped has already been NUMBERED. Remove it and everything after renumbers under the rider's finger — and a toast naming "point 2" then points at what used to be point 3. Refusing at drop means it never becomes a point at all.
Toast, 5 seconds, with the reasonTwo different reasons needing two different responses: unreachable is only fixed by pinning elsewhere; too far is also fixed by raising the mileage.
The pin that breaks it is the pin refused⚠ The mileage test is ORDER-DEPENDENT: pins 1–4 may fit and the fifth push it over. The fifth is refused. A rider who would rather have dropped the second removes it and re-drops. Simple rule beats a cost-ordered eviction the rider cannot predict.

⭐ AND IT DELIVERS "NO SURPRISES" EARLIER THAN PLANNED. With every pin validated at drop, every pin on the map is one that will be honoured — the count the rider sees IS the count in the routes. No reconciliation report between DONE and the search, and nothing silently missing from the enriched results.

⚠ STEP 4's NARRATION MUST CHANGE. It currently promises "I will stop and advise you to remove that pin" — that was written before this decision. The system refuses the pin itself, so the wording becomes something like: "Any point I cannot reach over existing trails, or that would push the ride past your distance, I will refuse and tell you why."

⛔ THE REACHABILITY HALF DOES NOT EXIST YET. assess() validates DISTANCE between points that can be connected. It does not check whether a route over existing trails can reach a pin at all.

⚠ And it is the same root cause as the 08-27 device finding: buildGraph reads FROM trails only, so a pin on a visible TRACK is unreachable by construction. Until tracks are in the graph, "I cannot reach that pin" will sometimes mean "that trail is real but I cannot see it".

⬜ SUPERSEDED — an unreachable pin must be named before the search runs

⛔ WE VALIDATE DISTANCE, NOT REACHABILITY. Fred, 08-28: "we currently validate distance between points that can be connected, but we do not warn that points are not reachable. We want to fix that."

assess() checks whether the pinned points fit inside the mileage band. It does not check whether a route over existing trails can reach a pin at all — so a pin on ground the graph cannot serve passes validation and then quietly fails, or drags the whole search somewhere it should not go.
