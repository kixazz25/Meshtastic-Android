UPDATE 2 — THE DATA-SOURCE LEAD (sharpens Step 1; Fred's recall)
----------------------------------------------------------------
IMPORTANT prior-context Fred recalled at session end:

The viewport queries queryTrailsByViewport / queryTracksByViewport were built
for the LAZY-LOAD DISPLAY (limit what draws to the bounding box). That display
path WORKS — trails/tracks DO show on the map viewport-aware.

For SNAP, the design was to REUSE those same bounding-box queries to feed snap
its candidate trails/tracks at the tap. BUT we discussed, and NEVER CONFIRMED,
whether that query actually RETURNS DATA in the SNAP context. The snap queries
were effectively never ACTIVATED/PROVEN against real returned rows.

=> This makes "STARVING FOR DATA" (Step 2A) the PRIME suspect, and gives a
   precise test: trails clearly DISPLAY on the map, but does the SNAP path get
   the same rows?

THE ONE NUMBER THAT DECIDES IT — from the Step 1 SnapDiag log:
   trails=N at the tap, WHILE trails are visibly displayed on the map.
     - trails=0 while trails are visibly drawn -> the DISPLAY query gets data but
       the SNAP query does NOT. The two call paths differ. Compare them directly:
         * What bounds does the DISPLAY/lazy-load pass vs what the TAP path passes
           (lastViewportSouth/West/North/East — are they current at tap, or
           0.0/stale because route mode was entered before a viewport event)?
         * Argument ORDER at each call site: queryTrailsByViewport(south,west,
           north,east). A swap in ONE path explains data-there-but-not-for-snap.
         * Same DB instance / init state in both paths.
     - trails>0 at the tap -> data is fine; move to snap math/radius (Step 2B):
       raise 30m -> 60-80m to confirm, check lon/lat vs lat/lon in parseWktLine.

So Step 1 is not just "is there data" — it's "does the SNAP path get the data the
DISPLAY path already proves exists." Diff the two call sites if trails=0.
