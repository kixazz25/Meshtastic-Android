Structure — components now, designed for separation

Decided 2026-09-21 (Fred): build as components inside GroupTrack, designed knowing the end state may be a separate plugin — to protect GroupTrack's own code from open-source licence exposure. Components cost nothing extra today; these rules keep them extractable.

⚠ Scope of the rules (Fred, 2026-09-21): GroupTrack's existing patterns — ViewModels through the fork's Hilt setup, NodeRepository and the other repositories, the theme and resources from org.meshtastic.core.* — inherit from the fork. Pulling them apart just to compile would be a large refactor for no rider benefit. So the rules do not mean "untangle existing code". They mean "don't add to the tangle":

  • core starts empty and stays small — data types and interfaces only, pure Kotlin and coroutines. Nothing in it needs to inherit from anything.
  • Existing code stays where it is, with its inheritance — untouched except where the master system is deleted.
  • Anything that must inherit — a ViewModel, a Hilt module, a screen — lives in the app or mesh, never in core.
  • Meshtastic's enums stay on the mesh side; core uses the plain values the JSON already has ("US", "SHORT_FAST", "TAK") and mesh maps them.

⚠ The honest limit: this protects new GroupTrack code. A full plugin extraction later would still mean untangling the existing convoy code from the fork — a real cost, but a later one, which this design stops from growing.

#RuleWhy
R1Two new packages outside the fork's: com.grouptrack.core and com.grouptrack.mesh — not under com/geeksville/mesh/GroupTrack's original work stays visibly separate from GPL-derived code
R2One direction only — for core, which holds new code only: core never imports Meshtastic or com.geeksville; mesh depends on core, never the reverseThe boundary the licence question turns on
R3Only plain data crosses — the position record, config, base, apply result (§A–§F). No MeshPacket, Node or TAKPacketV2 in core⭐ Data that crosses a package boundary as plain values can cross a process boundary later, unchanged
R4One wiring file — a single Hilt module binds core's interfaces to mesh's implementationsBecoming a plugin = replacing that one binding with a client for the separate app
R5Asynchronous interfaces — suspend functions and FlowsAnything that later crosses a process boundary is asynchronous anyway
R6A check that fails loudly — a dated script run before every build fails if any core file imports Meshtastic or com.geeksvilleTurns R2 from a promise into a fact

🔴 Check the TAKPacket-SDK's licence early. If it is GPL like the rest of Meshtastic, it lives strictly on the mesh side; core keeps its own TAK-shaped position record and the conversion happens inside mesh — which is the design anyway.

Method — replace, reroute, prove, delete by compiler

  1. Build the new apply process beside the old one — new files only; the old path keeps working.
  2. Reroute the entry points — the menu buttons and ConvoySettingsPanel point at the new process; the old screens become unreachable but stay.
  3. Prove on devices — a T1000-E over Bluetooth, a radio over USB.
  4. Delete in one commit, on its own branch — the routes, screens, objects and assets together. The compiler is the inventory: every remaining reference is a build error. Reverts cleanly.
  5. Stored-data cleanup and the leftovers sweep.
