⭐⭐⭐ THE ONE-LINE SUMMARY

Nothing is typed. One generated value names the ride's network AND its Meshtastic channel; everything a device needs — that value, the keys, the radio parameters — arrives in the ride config and is applied automatically.

⭐ PREFERRED PATH: the Nucleus-based IP attach. Join the node's network, the config comes down, the device applies it to itself and its radio. The other delivery paths exist so nobody is stranded, not because they are the plan.

⭐⭐⭐ 0 — How it fits together

Five diagrams, read in order: the devices, a config's life, a rider at the event, positions during the ride, and the two identities. The sections after them hold the detail each diagram points to.

0.1 — What connects to what

Three kinds of device. Tablets run GroupTrack and are where every decision is made. Nucleus nodes form the WiFi mesh and each carries a LoRa radio. Meshtastic radios form the LoRa mesh. Solid lines are data; dotted lines are local links — Bluetooth, USB and LoRa.

Detail: sections 1, 5 and 6.

0.2 — A config's life, start to finish

Complete any time — the node stores nothing. Distribute to riders ahead. Apply just before the ride — the node saves its current config to history first. At the event, riders who didn't pre-apply pull it from the node. Restore after the ride from the node's history. GroupTrack initiates every step.

Detail: section 7.

0.3 — A rider at the event

Every path ends at Ready except radio-only — which still appears on every map, by design, but gets nothing else. The first question is asked of the ride object: was this radio's config applied from the leader's ride object? The answer is derived, not stored — the radio's channel and key fingerprint compared with the ride object — so it can't go stale. A rider who set up at home is asked to do nothing.

Detail: sections 1 and 7.

0.4 — Positions during the ride

The app sends a TAKPacket carrying the rider's callsign; a radio-only rider sends Meshtastic's own position. Both reach every participant by two paths — straight over LoRa, and through the Nucleus onto the WiFi mesh. Natak stops storms on the network; GroupTrack drops the duplicate in the app.

Detail: sections 2A and 6.

0.5 — Two identities, never mixed

The ride's identity is one generated id that names the channel and the network and sets the frequency. The rider's identity is their callsign — their GroupTrack user id — carried in every TAKPacket. The radio's own name no longer matters.

Detail: section 1.

1 — The identifiers

⛔⛔ WE DO NOT OWN THE CHANNEL ID. That is a hard stop from Meshtastic — its length, format and semantics are theirs and can change.

ValueOwnerVisible toRule

⭐ Two identities, never mixed: the RIDE's and the RIDER's. The generated id, the network and the frequency belong to the ride and change every ride. The callsign belongs to the rider and never changes with a ride. ⛔ So the network config sent to the node never carries the radio's long or short name — and with the callsign in the TAK payload, GroupTrack doesn't set them either — in Natak's API, owner and owner_short are excluded from anything a ride sends.

⭐ RADIO-ONLY IS SUPPORTED, NOT EQUAL — BY DESIGN (Fred, 2026-09-21: "price of entry"). A radio used without the app appears — its position on everyone's map, under whatever the radio happens to be called. That keeps the promise that you can hand someone a radio and they show up. Everything else needs GroupTrack: the rider's callsign, the ride config applied for them, routes, maps and the group view. That difference is the incentive to own the app and participate, so no effort goes into polishing the radio-only path — it has to work, not be good.

⚠ The one thing the floor still depends on: whether Natak's bridge carries a radio-only rider's positions onto the IP side at all. "Appears" is the minimum, so that answer matters even though nothing above the minimum does.

⚠ For the V3 schema: users.user_id is a generated char(36) code, not a name. The callsign is the rider-facing identity — a callsign column alongside that code, not a replacement for it.

🔴 OPEN — unique within a ride? Two riders both called "Fred" would look identical on every map. The radios' node ids still tell them apart underneath, so this is a display decision: warn when a callsign is already in use in the ride, or show a short suffix.

⭐⭐ ONE VALUE, THREE THINGS. The generated id is the Meshtastic channel name, the WiFi network name — and, through Natak's frequency_slot 0 (frequency derived from the channel name), the radio frequency too. Two nodes given the same ride config land on the same channel, the same network and the same frequency, with no human input anywhere.

🔴 OPEN — the network password. With nothing typed, it must also arrive in the ride config: either carried as a value, or derived with the Meshtastic PSK from one ride secret (the KDF below). Decide which, and confirm Natak's node config accepts a network password we supply.

⭐ Generating the channel id removes the truncation trap. An 11-character limit does not matter when the value is generated to fit rather than derived from something a human typed — and if Meshtastic moves the limit, only the generator changes.

⚠ THE KEYS ARE DERIVED, NOT SHARED. A WPA2 passphrase and a Meshtastic PSK differ in format and length and cannot be the same value. One password feeds a KDF; each transport gets a correctly formatted key. ⛔ The derivation must be identical on every build and versioned from day one — two riders on different releases deriving different PSKs from one password is a silent, total failure.

🔴 OPEN: what makes the generated id unique, and across what scope? Two clubs generating independently must not collide — central issuance, or enough entropy that collision is negligible.

⭐⭐ 2A — WHAT CHANGES WHEN WE MOVE TO TAK PACKETS

Most of these 48 fields exist to MANAGE AIRTIME — how often a packet is sent, how far a rider must move before one is, and what other mesh traffic competes. Fred 09-20: "most of our config has to do with changing values to optimise packet delivery, distance requiring packet send, frequency of packet send, and minimising any other mesh activity."

⭐ Once the APP emits TAKPacket, cadence and distance become APPLICATION decisions — changed in a release, not on a device.

⛔⛔ BUT THE RADIO DOES NOT STOP DOING ITS OWN THINGS. If it keeps broadcasting its own Position packets (portnum 3) alongside the app's TAK packets (V2 on port 78 — see 2B), airtime DOUBLES rather than falling. So the TAK move is not "fewer settings" — it is some settings turned DOWN OR OFF to stop the radio competing with the app.

⛔⛔ AND THAT COLLIDES WITH A CORE PROMISE. A radio ATTACHED to the app should suppress its own position broadcast. A STANDALONE radio with no phone MUST keep broadcasting, or it vanishes — and "hand someone a radio and they appear" is a core promise of this product. Same fields, OPPOSITE settings, depending on whether an app is present.

🔴 SO THE CONFIG CANNOT BE ONE VALUE PER FIELD for position. Either two profiles (app-attached / standalone), or the app toggles the radio's own broadcast when it connects and restores it when it disconnects. Decide before building.

⭐⭐⭐ The synthesis: TAK payload + channel URL = any radio, set up automatically

With the app emitting TAKPacket, what a radio needs per ride shrinks to transport — channel name, key, region, modem preset, hop limit, transmit power. That is almost exactly what a Meshtastic channel URL already carries: the channel settings and the LoRa settings together, in Meshtastic's own format for moving a configuration between radios.

⭐⭐ So the TAK move may make the channel URL the whole ride config for ANY Meshtastic radio. That removes what tied automatic setup to the T1000-E — a saved device image with values injected into it. No image, nothing device-specific.

⚠ The one setting a channel URL does not carry is the radio's own position broadcasting — the two-profile problem above. That lives in the radio's role and position settings. Natak's radios run the TAK role, which may cover it.

⭐ The TAK-era ride config could be as small as a channel URL plus a role. 🔴 Test on a T1000-E and one other Meshtastic radio before relying on it. If it holds, it simplifies GroupTrack, simplifies what Natak's node has to hand out — his eleven radio fields are nearly the same set — and lets the website stop saying other radios are set up by hand.

⭐⭐ 2B — COMPRESSION — answered 2026-09-21

v19: the questions this section used to list are now answered from Meshtastic's own published work. The short version: V2 TAK packets, zstd with a shared dictionary, compressed by whoever creates the packet — and the dictionary version must match everywhere.

The old way is being retired

The original ATAK plugin (V1, TAKPacket, portnum 72) compressed the strings inside a packet with unishox2. It had two known problems: a decompressed field could overrun its buffer (a remotely reachable stack overflow, meshtastic/firmware issue #3841), and on high-entropy text it grew the message — 220 bytes to 245 in that report.

In April 2026 Meshtastic moved ATAK traffic to ATAK Plugin V2 (firmware PR #10105): a new TAKPacketV2 format on its own port, unishox2 removed from the firmware entirely, and compression handed wholly to the client apps.

How V2 works

[ flags: 1 byte ][ payload ]
  0xFF        → payload is a raw, uncompressed TAKPacketV2
  0x00–0x3F   → payload is zstd-compressed; bits 0–5 name the dictionary
The firmware passes the payload through unchanged.

Compression is done by TAKPacket-SDK (github.com/meshtastic/TAKPacket-SDK) — the SDK Natak uses. zstd at level 19 with two pre-trained dictionaries: general traffic (512 KB) and aircraft (4 KB). ⭐ It never makes a packet bigger: when the raw packet is no larger than the compressed one, it sends it uncompressed with the 0xFF flag.

The five questions, answered

QuestionAnswer
What method?zstd with a shared pre-trained dictionary, via TAKPacket-SDK.
Does the app compress, or the bridge?Whoever creates the packet. GroupTrack for its riders; Natak's bridge for CoT arriving from the IP side. Radios only pass it through — no double compression.
Is a position report compressed?Only when that makes it smaller — decided per packet. A short PLI goes uncompressed.
What about truncation?V2 carries typed fields (position, chat, shapes, routes) rather than raw CoT XML; the SDK drops only display-only detail.
Actual on-air size?🔴 Still worth measuring — but it can never exceed the uncompressed size.

⛔⛔ The rule that matters most: the dictionary version must match exactly

TAKPacket-SDK 0.9.0 introduced a new dictionary that is wire-incompatible with older versions and requires a lockstep upgrade. In August 2026, iPhone users on SDK 0.5.1 could not read V2 packets from Android on 0.9.1 (Meshtastic-Apple issue #2348). The failure is silent — packets arrive and simply do not decode.

⭐ Same class as the key derivation rule in section 1: GroupTrack and every Nucleus must pin the same SDK version, and upgrade together. A ride where two participants run different dictionaries is a ride where they can't see each other, with no error anywhere.

⚠ Two corrections to this document

  • Portnum 72 is V1. Earlier sections say TAKPacket on portnum 72. V2 has its own port — 78, per the Apple app's issue report. Meshtastic's Apple app chooses V1 or V2 on every send by checking the connected radio's firmware version; GroupTrack needs the same check, or a minimum firmware.
  • The fork carries V1. The atak.proto in GroupTrack's fork is the V1 TAKPacket. The upstream Meshtastic Android app is already on TAKPacket-SDK 0.9.1 — so V2 is something to pick up from upstream, not to write.

  2. Does the bridge send V1 or V2?

4 — Process flows

F1 — CREATE CONFIG (leader)

Mesh Radio menu. Builds a file holding the config: generated channel id, derived keys, region, preset, hop limit, and whatever position parameters survive the TAK move. Saved under ride name + date, owned by club, leader or ride.

F2 — APPLY CONFIG

List available configs → select → archive current state FIRST → apply to the radio and/or to the Nucleus.

⭐⭐ F3 — REQUEST OVER THE NETWORK (the preferred path)

⛔ NOBODY PUSHES. THE RIDER REQUESTS; THE LEADER'S NODE RESPONDS. The request is the consent — no endpoint exists for a stranger to reconfigure someone's radio.

  1. Rider connects to the network — they already hold the name and password.
  2. Rider REQUESTS the config from the leader's node.
  3. Node returns it.
  4. Device applies it to itself and its radio, archiving first.

F4 — RESTORE

⭐ Select an earlier named config and apply it. Same flow as F2. Nothing extra exists.

⭐ THE LOCAL CONFIG STORE — and why RECEIVE ≠ APPLY

A rider may receive a config a month or two before the ride. Importing it must leave it stored and inert; applying is a later, deliberate step. ⭐ That store is a local version of the hosted database — and the backend, when it returns, delivers INTO it rather than replacing it.

Interim delivery by email

GPX for tracks and waypoints goes by email and loads through the existing import process; maps follow the geometry. ⛔ Decide whether the config travels with it — a config carries derived keys, and an emailed key is forwardable.

⭐⭐⭐ 7 — The config lifecycle: complete, apply, restore

GroupTrack initiates every step. The Nucleus completes configs it does not keep, applies them only when told, and keeps its own history so any earlier state can be restored.

⚠ Corrected 2026-09-21 (v6). v5 had the node store a staged config until the ride. That fails because rides can be set months in advance: one staged slot would tie the node up for months, and several upcoming rides could not be prepared at once. Completing a config and applying it are now separate.

1 — Complete (any time, including months ahead)

GroupTrack sends the ride config down. The node validates it, computes its derived values, and returns the finished config. The node stores nothing. GroupTrack keeps the completed config in its library and can distribute it to riders immediately.

⭐ GroupTrack compares what came back with what it sent — anything the node rejected or adjusted surfaces at home, not at the trailhead.

🔴 Needs a new endpoint. Today PUT /api/v1/config always replaces the saved config, and apply?dry_run=true compares against what is saved. Ask: a validate-and-derive call that returns the completed config and saves nothing — e.g. POST /api/v1/config/complete.

2 — Apply (just before the ride)

The leader selects the ride in GroupTrack's Apply config list. GroupTrack sends the completed config down and the node:

  1. writes its current config to a history file, labelled and timestamped;
  2. applies the new one.

A dry run first shows the leader what will change. The node restarts onto the ride network, and GroupTrack rejoins it on its own — it generated the network ID.

Today: PUT /api/v1/config → POST /api/v1/apply?dry_run=true → POST /api/v1/apply. 🔴 Ask: save the previous config to history as part of every apply — in one step on the node, so no apply can happen without the previous state being kept.

3 — Restore (after the ride)

GroupTrack reads the node's history, the leader picks an entry, and the node reapplies it — which itself goes through step 2, so the ride config is kept in history too.

🔴 Ask: history endpoints — list the entries (label, saved at), read one, reapply one. e.g. GET /api/v1/config/history, GET /api/v1/config/history/{id}, POST /api/v1/config/history/{id}/apply.

⭐ Why the history lives on the node, not in GroupTrack

Only the node knows its true previous state. Its config may have been set from Natak's own web UI, from another leader's tablet, or before GroupTrack was ever used — and the leader's tablet may be lost or replaced. A history kept on the node survives all of those. GroupTrack's job is to navigate it, not to be it.

What the history must capture

  • Both halves of the node — the WiFi mesh identity and the radio. A restore that brings back one without the other leaves a node split across two networks.
  • A label GroupTrack can show — the ride name and date (or "Home, 2026-09-20" for a node's own setup), so the leader picks from names, not timestamps. 🔴 Ask: a free-text label field in the config that validation accepts and history keeps.

At the event — the rider's steps

  1. The leader applies the ride config to the node (step 2). The node comes up on the ride network.
  2. The rider's tablet joins that network — ⭐ by scanning the leader's QR code, nothing typed.
  3. GroupTrack pulls the config from the node. API: GET /api/v1/meshtastic/config — channel name, key fingerprint, LoRa settings, and the channel URL.
  4. ⭐ Decision: was this radio's config applied from the leader's ride object? The ride object is the reference; the radio is the evidence. The answer is derived, not stored — the radio's channel name and key fingerprint compared with the ride object's config — because a stored "applied" flag goes stale the moment the radio is used on another ride or reset. If it matches, the rider pre-applied at home and is simply ready. Nobody is asked to redo something that's already right.
  5. If not, GroupTrack applies it to the rider's radio over Bluetooth or USB, saving the radio's own settings first.

⭐ Worth testing: this may not need to be T1000-E only. The channel URL is Meshtastic's own way of moving a configuration between radios — it carries the channel, its key and the LoRa settings, and the fork already handles channel URLs. If it covers the ride's essentials, riders with other Meshtastic radios could be set up automatically at the event too, rather than by hand. Test before promising it — the website currently says other radios are set up manually.
