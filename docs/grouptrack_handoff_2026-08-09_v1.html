⭐ RECOVERED — the 08-07 discussion that was never documented

Found in the transcript at 2026-08-07 20:30-20:40, during the first corridor delete run. Fred remembered it existed; none of it had been written down.

  • The number was a BATCH SIZE, not a journal mode: batch into moderate transactions, one commit per 25-50k deletes. Not 88, not one giant one.
  • ⛔ An explicit warning against what was proposed again today. SQLite's own docs: the write-ahead option works best with smaller transactions, is slower above ~100 MB, and can fail outright above a gigabyte. A 617k-tile delete is a very large transaction — so "one big transaction in WAL" was named the worst combination available.
  • ⭐ The reasoning that was lost: SQLite executes millions of statements per second, so 1.1M delete attempts cannot take ten minutes on statement cost — pointing at commit overhead (fsync per transaction).
  • Fred asked about turning journaling off and back on. Answer then: it leaves an undefined state on a crash, on a store with no backup — same class as the 08-01 loss. synchronous=NORMAL was the safe lever, and it is now in the patch.
