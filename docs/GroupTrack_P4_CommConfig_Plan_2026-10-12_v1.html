4. Decisions for Fred

D1 — steps: four patches as above, each tablet-checked and committed (proposed), or fewer, larger ones. P4.1 is the safest first move: same behaviour, the adapter just changes home.
D2 — Meshtastic settings types stay on the comm side: GroupTrack sees only the ride file (JSON), the callsign, and plain change rows (setting, was, becomes). Proposed: yes — the same rule as P2's radio list.
D3 — progress words: the comm side reports progress as steps (group n of m · writing · radio restarting · reconnected · setting ticked / failed), GroupTrack turns them into the words on screen. Proposed: yes ("GroupTrack owns the words").
D4 — the radio restart during apply: the writer's own disconnect → wait → reconnect cycle and the keep-alive (P2.3) must not fight. Today the keep-alive could count the writer's deliberate disconnect as a failure. Proposed: while the comm side is applying, its keep-alive holds (as with Bluetooth off) — the comm side owns both, so it can.

5. Tablet checks (each step, both droids)

  1. Work with Rides → Apply ride to radio → GroupTrack default: the change list, apply, every setting ticked.
  2. CHECK IN to a ride whose network differs: the radio is set up (about a minute), then checked in — no error.
  3. CHECK IN again: "Radio ready for this ride".
  4. No scheduled ride: back to the GroupTrack default; "Keep my radio as it is" leaves it.
  5. Callsign for this radio (a guest's name): the radio's name changes; your profile does not.
  6. Saved configs: list, compare two, restore one (P4.3).
  7. GPS button: a new interval applied, the radio restarts and reconnects (P4.4).
  8. Throughout: no "reconnect N" from the keep-alive during an apply (D4); COMMHEALTH quiet.
