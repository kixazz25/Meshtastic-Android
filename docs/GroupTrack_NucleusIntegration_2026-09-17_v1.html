GroupTrack ↔ Nucleus — integration design v1

2026-09-17 · Companion to Communications Layer Design v7. That document is the architecture; this one is the WORKFLOWS, the API surface, and what needs to be built on each side. Self-contained.

⭐⭐⭐ THE CHANGE THAT DRIVES EVERYTHING ELSE:

The APP generates the payload. The radio becomes a transport.

Today a radio's own config decides its behaviour — broadcast interval, distance threshold, what gets sent. Changing any of it means reconfiguring hardware, per device, per rider.

⭐ With GroupTrack emitting TAKPacket directly, the radio carries what the app hands it, at the rate the app chooses. Frequency, content, who is included, and what a separated rider receives all become APPLICATION decisions — changed in a release, not on a device.

⚠ What does NOT change: the radio still needs its channel, PSK and region — transport-level settings, now set once per ride rather than tuned per rider. And airtime is still airtime. The app choosing the rate does not create capacity; measured congestion at 3–4 radios on a 3-second update is a physical limit. ⭐ What changes is that we can now respond to it in software.

⛔⛔ AND THE MODE TRAP. The protobuf comment is explicit: wifi_enabled — "Enable WiFi (disables Bluetooth)". It is one or the other. A radio that joins WiFi loses BLE permanently until something changes that flag — and if the network is not there, it is unreachable by any means and needs a physical reset. A one-way door.

⚠ High-power + WiFi is not a consumer option. Station G2 is discontinued; the G3 successor is ~$159 and out of stock — and above 1 W on US915 requires an FCC Part 97 amateur licence. Not something to recommend to a club. RAK's 1 W kit ($39) is Part 15 but is nRF52, so no WiFi.

⭐⭐ One name, one password, both transports

The rider sees TWO FIELDS. The channel name IS the network name.

⚠ But the KEYS are DERIVED, not shared. A WPA2 passphrase and a Meshtastic PSK have different formats and lengths — they cannot be the same value. One password feeds a KDF; each transport gets a properly formatted key.

⛔⛔ THE DERIVATION IS THE SINGLE POINT EVERYTHING RESTS ON. It must be identical on every build and versioned from day one. Two riders on different releases deriving different PSKs from the same password is a silent, total failure.

⚠ Check the Meshtastic channel-name length limit before fixing the naming scheme — a network name that truncates differently puts riders on different channels.

⭐ WORKFLOWS

W1 — Leader creates a ride config (at home, has internet)

  1. App generates the config record: name + password → derives WiFi key and Meshtastic PSK.
  2. Stored against the owner — club, leader, or this ride.
  3. ⭐ GroupTrack is the SYSTEM OF RECORD for network identity.

W2 — Leader configures their own radio (at home) — ⭐ USB

  1. Radio connected by USB-OTG. ⭐ Works in either mode; cannot brick.
  2. App applies channel name + PSK + region from a picker listing configs by owner: 
    Apply configuration
  CLUB    Southern Utah UTV
  LEADER  <leader name>
  RIDE    Sand Hollow 03 Oct   (expires 10 Oct)
  3. For an ESP32 radio, optionally also the WiFi credentials.

⚠ This picker is a LEADER'S tool. A rider never chooses — they get the config the ride references.

W3 — Leader provisions the Nucleus — 🔴 NEEDS NATHAN'S API

  1. Tablet joins the node's current AP.
  2. POSTs the network identity (name + key) to the node's local endpoint.
  3. Node provisions its own WiFi mesh AND its attached Meshtastic radio.
  4. Node reboots (~60 s) and comes up on the ride network.

⛔ CHICKEN-AND-EGG, AND IT IS INHERENT: to reach the API the tablet must already be on the node's AP. So this CHANGES a network, it does not create one from nothing. The node ships with a default AP; the leader joins it and pushes the ride identity. ⚠ The node then drops every client — the app must expect the disconnect, not treat it as failure.

🔴 AND A MANAGEMENT INTERFACE MUST SURVIVE THE CHANGE, or a wrong push strands the node exactly as a bad WiFi config strands a radio.

W4 — Bootstrapping a rider's ESP32 radio onto WiFi — the mode trap

⛔ A fresh radio has no SSID and Bluetooth on. BLE is the ONLY way in. Enabling WiFi turns BLE off — one shot.

⭐ SAFE PATH — use the tablet's own hotspot as a setup jig:

  1. Tablet raises its hotspot. ⭐ It created the network, so it knows both the SSID and the key — Android will not reveal a saved password for any other network.
  2. Configure the radio over BLE to join THAT network.
  3. Radio reboots; BLE goes off; it joins.
  4. ⭐ Verify over TCP immediately — a known-good network we control, so a failure is visible at once rather than at a trailhead.

⚠ App must handle the gap: wait for the reboot, discover by mDNS (address is not fixed), and say plainly if it does not come back — a radio that fails to rejoin is invisible on both transports and the rider needs to know to reset it, not to assume the app is broken.

🔴 OPEN: does NetworkConfig hold ONE SSID or several? The proto shows a single wifi_ssid/wifi_psk pair — which means switching networks needs BLE, which is off. That circularity must be solved. ⚠ USB is the escape hatch and is the strongest argument for it.

W5 — Rider joins a ride

  1. Rider receives the ride definition — route, trailhead, maps, and network identity.
  2. Tablet joins the ride network.
  3. Rider's radio is already on the ride channel (configured at home, or by the leader).
  4. ⭐ Riders always assume the config of the network they join. Nothing to choose.

W6 — Running

  1. App emits TAKPacket (portnum 72) at the app-chosen cadence.
  2. Nucleus module converts, compresses, forwards to LoRa; and receives, decompresses, delivers back over the AP.
  3. ⭐ Both meshes run in PARALLEL with deduplication (Natak): every CoT packet goes over WiFi AND LoRa, LoRa rate-limited. "The polling required to get quick network switching between wifi and Lora is very tough to get right."

🔴 STILL OUTSTANDING FROM THE LAST EXCHANGE

⭐⭐ Does the bridge relay ONLY TAKPacket, or does it generate a CoT event for ANY Meshtastic position it receives?

A plain T1000-E with no phone attached still broadcasts its position on portnum 3. Being able to hand someone a radio and have them appear — with no app at all — is a core promise of this product. If the bridge only carries portnum 72, that rider is visible to LoRa riders and invisible on the IP mesh.

⚠ And Natak asked US a question we owe an answer to: what is our packet size? He runs small packets at a high-speed LoRa preset. If we are on a slower preset, that alone could explain our congestion at 3–4 radios against his calculated 25. ⭐ Checkable in our own config — and the preset belongs in the ride config alongside channel and PSK.
