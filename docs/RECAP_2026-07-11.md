# GroupTrack — Session Recap — 2026-07-11

## Headline
Drove Route+ persistence from design through three builds to on-device testing. The SAVE side is verified working. The RESTORE side hit a real bug (stuck-armed route mode) that made the map unusable — and out of diagnosing it, a cleaner recovery design emerged: a **recovery-file dialog on map open**. That is the plan of record going forward.

## What happened, in order
1. **Phase-1 (writes)** confirmed: per-point draft save verified on device (33 clean snapped vertices); WIP-save verified byte-identical.
2. **Phase-2 (state recovery) built** — wired routeState into the map-state JSON, seeded the armed flag from persisted state, guarded the convoy follow behavior, added auto-naming. Green build after fixing a snapshot-argument slot error (routeState is the 5th constructor arg, not the 4th).
3. **On-device test exposed the break:** route-add stuck armed → every map tap/pan/search drops a point, add-toggle dead, phantom first point at launch. Also: the map didn't reposition to the route on return.
4. **Diagnosis:** verified via field cross-reference that the only GPS-driven view on convoy is a single center-on-point (setView at zoom 15), not a bbox construction. The stuck-armed state came from seeding the flag from persisted state + the follow-guards.
5. **Design converged** (Fred's reasoning): armed == app running; map location is the thing that matters; the state JSON self-corrects on every draw, so there's no stale-state to manage. Therefore: **on map open, if a recovery file exists, pop a dialog → OK loads the route, arms route-add, and positions on the route's first vertex — after the map draw completes.** Resolution (save/discard) is the clearing. Build it as shared components for convoy + planner.
