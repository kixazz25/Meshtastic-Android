GroupTrack 2.8b — EOD 2026-11-26: THE AI ROUTE DIVERGENCE, SOLVED

WHY THIS DOC EXISTS. The Droid-vs-iPad route divergence, open since 11-24, was closed on 11-26 between 21:37 and 00:30 by instrumenting the engine and measuring every stage on both devices. Everything below is measured on device or computed from the captures — no inference is presented as a finding, and where a conclusion is a deduction it says so. Captures: ~/Downloads/aistage_droid1.txt (207 lines) and ~/Downloads/aistage_ios.txt (214 lines), recipe Broken Ridge 37.89530033364326 / −113.6615177552898, 55–80 mi, 12–18 mph, build 2026-11-26_2307_mac_5ff9812f8_UNCOMMITTED.

0 — THE ANSWER, IN ONE PARAGRAPH

There is no code difference and no math difference. One engine in commonMain, identical database, identical graph, identical Dijkstra distances to sixteen significant digits, identical scores, identical pair verdicts, and the identical seventeen-stage execution sequence on both platforms. The entire divergence is the order in which an unordered collection is iterated, reaching a decision at two points. The deeper finding is that neither device chooses well: both evaluate only 9 of their ~15 reachable features, both spend ~40% of their admission budget on features already measured as unreachable, and not one distinct ride was ever rejected on merit anywhere in the pipeline on either device — the missing rides were never built.

1 — WHAT WAS PROVEN IDENTICAL (so it is never re-chased)

  • One engine. GtRoute.kt is commonMain, 2,794 lines. Android's RouteExplorer.kt is 176 lines with four delegate calls. iosapp/ holds eight Swift files and zero route code.
  • Discovery: the same 30 rows / 29 names, zero field differences — fclass, lat, lon, snap distance and the graph node id. The graph build assigns the identical node to the identical feature.
  • Dijkstra: 0 mismatches across all 14 features usable on both. Blawn Mountain out=34.70848380055364 back=34.70848380055364, both platforms.
  • Solo scores: 0 mismatches, and both platforms report exactly two distinct values, 2.0 and 3.0.
  • Pair verdicts: identical. 41 pairs rejected on both; 10 Droid-only, every one involving Rock Spring (absent from the iPad's 24); zero iPad-only.
  • Execution sequence: identical. 17 stage blocks, same order, including running the origin loop twice in the same place. The capture is append-only, so line order is execution order.
  • The two Android devices are certified identical for this corridor: reference_points byte-identical (31,379 rows, checksum match), 229,354 shared trails with zero geom_hash differences, and 0 of the 14 differing trails lie inside the corridor box.
  • ⚠ The 60 apparent differences in the pair table are the a/b label swap — same numbers, swapped fields, because pool order decides which feature is a. The only genuinely different values are a_b legs at the 17th significant digit, because with a and b swapped one platform computes dist(a→b) and the other dist(b→a). The same effect appears within one platform: Blue Knoll out=29.139993036381906 against back=29.13999303638191. No verdict changed.

4 — DEFECTS FOUND, WITH LINES

  1. :2192 — the admission key cannot discriminate. scoreSet on ONE feature returns the bare class weight: 60.0 pin / 3.0 peak,cliff,volcano / 2.0 spring / 1.0 other. 21 of 24 features return 3.0. A stable sort over one repeated key is a pass-through of hash order.
  2. :2139-40 — the ceiling shrink is order-decided. Same cause, and it is the 2-vs-4.
  3. :2192 + :2201 — ranked is not filtered by usability. It is built from all 24 and the loop admits from it, so 7 of 16 Droid admissions and 6 of 15 iPad admissions are spent on features already measured as unreachable — while 6 and 5 reachable features go unevaluated.
  4. :2201 — workingMax = 40 is dead code. ranked holds at most 24 (plus pins), so the guard cannot fire without 17+ pins. It has never executed. And the comment block describing maxPoi sits above it; val maxPoi = 24 three lines below is undocumented. "41 never needed" dates the 40 to a 56-feature world — before the cap existed.
  5. :2202 — the only stop that can fire is the survivor count. So the engine is structurally guaranteed to stop on candidates found, never on features considered. Measured: admitted=16 found=29 not_evaluated=8 next_would_have_been=Pink Knolls (Droid) and admitted=15 found=49 not_evaluated=9 next_would_have_been=Iron Mountain (iPad) — both stopped one step short of a feature they then had to enrich in anyway.
  6. :2334 — enrichment convergence is never deduped. found dedupes by feature set when a seed is added (:2239); enriched.add has no such test. Measured: 7 of the iPad's 20 enrichment slots and 4 of the Droid's produced the identical ride. 12 and 7 of the twenty candidate slots hold rides the engine already had.
  7. :2419 — VARIATIONS = 2 contributed nothing. Entries at PASS 3 equal take(20) exactly on both, so zero variations survived.
  8. :1993 — the cap runs before reachability is known, so 11 unreachable features occupy array slots while 3 are discarded untested.
  9. PASS 3 is innocent. Every kill on both devices had max_overlap of exactly 1.000 — exact duplicate leg sets. The 0.75 threshold never fired on a distinct ride. No distinct ride was eliminated on merit anywhere in the pipeline.
  10. Enrichment draws from the full 24, not from working (:2296). So "this feature appears in a ride" is no evidence of admission. Iron Mountain and The Tetons are admitted on neither device and appear in rides on both.
  11. Cand.score is never a comparator key. :1808, :2271 and :2459 are all feature count DESC, then miles DESC. So USERPIN_BASE = 60.0 buys a rider's own pin nothing in ranking.
  12. assess() diverges from the build above 8 pins. It uses heldKarp (exact) and a different corridor box (corridorBoxFor); the build uses orderTour, exact only to 8 points then greedy. The panel can promise a pin set the build will not honour. Its doc also says only milesHigh is read while PinFeasibility.underMiles is defined against milesLow.

The engine has no principled basis for deciding which candidates deserve evaluation. ⭐ AND THE PRINCIPLE WAS WRITTEN DOWN THE SAME DAY, in ENRICH's own commit message: “a 3.0 peak that pairs with nothing is worthless while a 2.0 spring in five good sets is essential.” That is the whole answer — a feature earns its slot by appearing in a combination that works — and it is what Fred restated as ARRAYCONTRACT-2026-11-24 and again tonight. It has never been the implementation.

⭐⭐⭐ AND THE CLEANEST FRAMING OF ALL (Fred, 00:31): NEWENGINE ALREADY FIXED THIS BUG, ONE LEVEL DOWN.

NEWENGINE-2026-08-26's own diagnosis was “all 2500 restarts began down the same spoke” — nearestNode returned a node 613 ft away with ONE spoke, so every restart of the randomised greedy went down the same path and every other direction was structurally excluded. Tonight's defect is the same sentence with one noun changed. Hash order decides which features are admitted, the loop stops at twenty survivors, and every feature after the stop point is structurally excluded — six on the Droid, five on the iPad, all reachable, all scoring 3.0, none ever judged.

And NEWENGINE's fix is the fix. It did not make the arbitrary choice smarter; it removed the choice — “candidate starts are every trail within 600 yards… rather than nearestNode… origins collapse to one per component keeping the alternatives.” Exhaustive in place of arbitrary.

⇒ Tier 1 item 3 is NEWENGINE's principle applied to feature admission: admit every reachable feature and the arbitrary order stops mattering. Not a better comparator — no comparator. The engine's own author solved this class of bug on 08-26 at the origin selection and left the identical pattern at the feature selection, four commits later the same day.

7b — ⭐⭐ WHY THE RESEQUENCE IS THE CHEAP FIX: MAXPOI BUDGETED THE WRONG RESOURCE

[stated] Fred, 00:34, recalling NEWENGINE: “I remember the relief because it [halved] our processing by hav[ing] starting and endpoint and combos of features to replace the dijkstra that was performed — dramatically reduced. Almost like the routes were built first and evaluated based on points and mileage, because we weren't asking create any possible route, only route between our points.” Correct, and the measured figure is better than halved: 67.8s → 3.8s (NEWENGINE-2026-08-26).

THE ARCHITECTURE, and it is the thing to protect: the engine never searches for routes. It fixes the terminals (origin + features), runs one Dijkstra per terminal, once, at :2039 — and after that every combination is a chained sum of pre-computed distances. orderTour only ever calls dist(a,b) = dij[a].dist[b], a hashmap lookup. No graph search happens during route evaluation. The out-and-back filter and the pair table then bound the enumeration so even the arithmetic is minimised.

⛔ WHICH MEANS MAXPOI CAPPED THE CHEAP RESOURCE. Its justification counts combinations (“24 features at size 5 is 42,504 against 3,478,761 for 55”) — and combinations are free array lookups. The expensive step is the Dijkstra matrix, and it is sized by the number of features in the array. Today: 26 tables (2 origins + 24 features), eleven of them for features the very next stage proves unreachable.

⇒ The resequence cuts the only costly operation in the engine by 35% — 17 tables instead of 26 — while also removing the tie-break that caused the divergence. It is cheaper, more correct, and it restores the architecture's own logic: spend the graph search only on terminals that can appear in a ride.

⚠ The one graph search remaining after the matrix is the fill's penalised re-routing (routeLegs → dijkstra per leg per attempt, up to FILL_STEPS = 10 per ride × VARIATIONS = 2). Tonight measured the VARIATIONS third of that work contributing nothing — see §4 item 7.

8 — THE RECOMMENDATION

Tier 1 — measured, safe, do these.

  1. Reachability before the array. Cap stops firing, pools identical by construction, nine fewer Dijkstra tables.
  2. Order the array by (score DESC, bad-pair count ASC, node id). Fred's rule leads, so springs still sort last. ⭐⭐ The second key is measured at correlation −0.951 with productivity (rides a feature appears in) against distance's −0.372 — and the pair table already exists 86 lines earlier, so it is free. The order it produces puts the seven most productive features in the first seven positions, identical on both platforms because every term is data. ⛔ This also kills the planned fix: RIDEORDER edit 2 ordered by distance and the correction was to flip to farthest-first — but the single most productive feature in the corridor is the nearest (Mountain Spring Peak, 26.2 mi, 14 rides). Both directions of that key are wrong.
  3. Remove the survivorsOf break. After (1) the loop is bounded at 15 iterations, so no cost measurement is needed. All reachable features get evaluated — neither device has ever done that.
  4. Dedupe enriched on the feature set, then backfill from the discarded seeds. Recovers 7 slots on the Droid and 12 on the iPad.

Tier 2 — one decision for Fred. Replace the clique-and-shrink ceiling with an explicit enumeration-size cap. This is the last place hash order reaches the screen, and tonight says low wins: ceiling 2 gave 13 distinct rides worth 66.766, ceiling 4 gave 8 worth 58.320. From a pool of 13, sizes {2,1} is 91 combinations per pass against {4,3,2,1} at 1,092 — twelve times the work for a worse product. It would delete testedCeil and its shrink loop entirely.

⛔ THE ENGINE HAS NO NEGATIVE TERMS AT ALL. Only positive terms (features) and hard constraints (mileage, reachability, pair feasibility). It cannot express that a route is worse for where it goes.

⛔⛔ AND THE FILL IS BIASED TOWARD ROADS BY CONSTRUCTION. :2342 inserts the via-junction with the largest detour that still fits (if (add > pickAdd)). ⭐ All three fixes have existing machinery: retraceOf already computes loop quality; settlement proximity is the same nearest-point query loadPoisGrid already runs; and pen is already a per-edge multiplier Dijkstra honours, with carto_code 100% populated in this corridor. 13b — ⛔ NEW DEFECT: THE TRAIL FILTER FAILS OPEN, AND ITS LOAD TIMING IS PLATFORM-SPECIFIC

Found 00:37 while testing [stated] Fred's hypothesis “old code probably left in place and reimplemented in the ios conversion… they are handled t[o]ta[ll]y differently.” The hypothesis is disproven — RouteExplorer.kt was read in full (176 lines: ~60 comment, the mirrored type declarations because Kotlin has no typealias inside an object, the converters, and seven one-line delegates; no algorithm, no request transformation, no result filtering). And the two TrailFilterState objects are one state with two names: app/…/convoy/ TrailFilterState.kt:5 is import com.grouptrack.shared.filter.TrailFilterState as Shared, a synchronised pass-through (GTBATCH1A-2026-11-06).

But the read found this, in the shared file:

/** ⚠ NULL MEANS NOT LOADED -- it does NOT mean "no filter". */
private var cachedWhere: String? = null
fun whereOrEmpty(): String = cachedWhere ?: ""

buildGraph's filter parameter defaults to whereOrEmpty(). So a route build that starts before load() has run builds an UNFILTERED graph — every trail the rider switched off, private land included — and nothing is logged. It is deliberate (RouteExplorerCertOld:520: “whereOrEmpty(), not where(): a route build can run before a map”), which makes it a safe-looking default that silently widens the candidate set rather than narrowing it.

⚠ AND THE LOAD TIMING IS PLATFORM-SPECIFIC. iOS sets pathProvider and calls load() at panel composition (GtIosPanels.kt:855-866, GtIosHkEnv.kt:162); Android loads through TrailCheck / the map draw off GroupTrackStorage.root(). So which platform routes filtered and which routes unfiltered depends on what the rider opened first in that session. Tonight both reported usable_nodes 4218, so they agreed — but that is a property of this session, not a guarantee, and it is the one place a genuine platform difference could change which trails are routable.

Fix shape: make the route build require a loaded filter rather than tolerate an unloaded one — either load on demand inside buildGraph, or refuse the build and say so. ⚠ Either changes Android's output wherever a build currently runs unfiltered, so Droid 2 gates it. Own task.
