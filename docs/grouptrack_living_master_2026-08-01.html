⛔⛔ 00-DATA (08-01) — DATA LOSS EVENT: THE APP DESTROYED ITS OWN DATABASE. P0.

P0 BLOCKERAn adb install -r -d on Droid 2 cost the entire spatial database — ~89,000 trails plus every track, waypoint and route. The app did not report a failure. It logged 0 trails, 0 tracks, 0 waypoints, 0 routes and carried on as though that were a normal state.

This is not an adb problem. It is an application defect, and a Play Store update could reproduce it on a user's device with no warning and no recovery.

⛔ The mechanism, in order

  1. The install registered as a fresh install rather than an update (first-install questions appeared).
  2. The app lost all-files authority; its SELinux category labels are assigned per-install.
  3. SQLite's lock ioctl on the FUSE-mounted .db was denied — device log 11:44:04.805, permissive=0, so enforced:
    avc: denied { ioctl } for path=".../grouptrack_spatial.db" dev="fuse" ioctlcmd=0xf50c scontext=u:r:untrusted_app:s0:c178,c256,c512,c768 tclass=file permissive=0 app=com.grouptrack.android
  4. SpatialDbManager opens with create-if-missing. The failed open wrote empty schemas over the existing files — same path, same names, replaced in place. Nothing called delete.
  5. The app started clean and presented itself as empty.

Fingerprint sizes — memorise these: grouptrack_spatial.db = 118,784 bytes, grouptrack_data.db = 208,896 bytes. Those are empty schemas. A live spatial DB is tens of MB.

🔴 THE FIX — 2.6e, outranks the panel work

  • Never open with create-if-missing when the target file exists. Check existence first; on a failed open with a file present, surface an error and stop. This one change converts silent data loss into a message.
  • Verify access BEHAVIOURALLY, not by permission API. The app believed it had all-files access while the OS denied the ioctl. The permission query lied; a real read attempt would not have.
  • Fresh-install marker in filesDir — row counts, DB sizes, last-good timestamp. Private storage is wiped by a fresh install; external storage is not. Marker absent + external DB present = a fresh install just happened over existing data → stop, report.
  • Row-count sanity. A database that held 89 k trails yesterday reporting 0 today is not a valid state.
  • Belt and braces: copy to grouptrack_spatial.db.lastgood after each successful startup.
  • Fix the log line. SpatialDbMgr prints the LITERAL ${spatialFile.absolutePath} — interpolation is broken, so the path never appears. That is the one diagnostic that would have made this obvious in seconds.

⛔ TRAP 1 — ?: return inside an argument exits the whole function

android.widget.Toast.makeText(view?.context ?: return, ...)

Reads like a null-safe accessor. Is an early exit from the entire override. Placed in onPageFinished, it bailed before tile setup, setTileUrl, the persisted-frame restore and drawPersistedState. ⛔⛔ TRAP 2 — @JavascriptInterface methods run on a BACKGROUND thread

evaluateJavascript and Toast.makeText both require the main thread and throw when called off it — and the throw aborts the rest of the method, including the processViewport call that draws every artifact.

webViewRef.value?.evaluateJavascript("window.__routeMode = false;", null) // in onViewportChanged android.widget.Toast.makeText(context, "ROUTE MODE OFF <- CONVOY reseed entry", ...)

The existing code already knew this. It wraps its work in Thread { }, and SpatialDisplayManager uses main.post { } for every evaluateJavascript.

RULE: anything touching the UI or the WebView inside a @JavascriptInterface method must go through Handler(Looper.getMainLooper()).post { }.

🆕 2.7 FEATURE — TRAIL GAP FILL FROM RIDDEN TRACKS (Fred 07-31)

THE PROBLEM, in Fred's words: "trying to draw a route using bits of a track you have already ridden but trails still do not show."

Route building composes from trails. A stretch you have ridden but which the trail collection does not cover exists only inside a track — and a track cannot be composed with, because it is stored as ONE geometry. So when planning, you cannot see all your real choices even though you have the ground truth on the device.

⭐ These are not a new class of artifact. Fred: "they are trails that simply do not appear in that collection. you need a trail to ride." Same table, same rendering — the collection is just missing a piece.

⭐⭐ DISPLAY FIRST, INSERT SECOND — the shape that makes it tractable

Fred: "may be simpler to have a function that shows the map with a colour segment that is missing and can be added."

Show uncovered stretches as an overlay; the rider decides which become trails.

  1. For tracks in view, compute which point runs have no trail within tolerance
  2. Render those runs as a distinct overlay
  3. Tap the track → artifact detail panel → Add Trail Segment
  4. Only then does anything enter the trails table

⭐ This removes three problems at once, which is why it is better than automatic insertion at import time:

  • Tolerance stops being critical. A false positive is visible noise the rider ignores, not a duplicate trail silently written to the DB.
  • Naming resolves itself — the user is looking at it.
  • Nothing accumulates against dedup, and GPS wobble never becomes authoritative geometry by accident.

⭐ And it is useful before the insert step is written at all. Simply SEEING where ridden ground is missing from the collection answers the original frustration; adding it becomes optional.

Design detail settled 07-31

Detection. Sample the track's points; for each, test distance to trail geometry returned by queryTrailsByViewport for a small bbox. Consecutive points with nothing within tolerance form an uncovered run. Discard runs below a minimum length.

⭐ RouteManager.snap(lat, lon, trails, tracks, 30.0) already performs this proximity test and returns null when nothing is near — "null" IS "uncovered", so detection is mostly free.

Tolerance 20–30 m, matching the existing snap radius. ⚠ Too tight and GPS wobble alongside a mapped trail reads as uncovered, producing a shadow trail parallel to a real one — that is the failure mode to design against, and it is the argument for showing rather than auto-inserting.

Naming — Fred's rule: inherit the name ONLY if the trail either side of the gap carries the same name. Both endpoints agreeing is strong evidence it is one trail; disagreeing means it connects two, and inventing a name there would be wrong. Otherwise leave it unnamed.

⚠ Unnamed is correct, not a fallback. Fred: "most of our trails are unnamed now and named would have a major trail connotation." A named trail SIGNALS significance to a rider, and today's ORDER BY sorts named first — so auto-naming gap fills would both inflate that signal and outrank real named trails at low zoom.

Colour. ⚠ Dashed is already taken — tracks are #39FF14 dashed, routes #FF00FF dot-dash, trails carry carto_code colours. A solid line in an unused colour will read more clearly than another dash pattern.

🔴 OPEN QUESTION — which gap, when a track has several

The detail panel opens for the WHOLE track, but uncovered stretches are specific sub-ranges. A track with three gaps makes "Add Trail Segment" ambiguous — and that is exactly the case that motivated this.

⭐ Fred's motivating case: several tracks named Broken Ridge in one area. From a route-planning standpoint that is unusable, because you can only select whole tracks. Segmenting the uncovered stretches makes it a set of distinct short pieces you can assemble — and "which Broken Ridge" stops mattering, because you are choosing a STRETCH, not a name.

Likely resolution: the overlay lines are separate L.polyline objects, so each can carry its own point-range identity and pass that through — rather than routing everything via track_id alone.

⚠ Worth measuring before building

How much would this actually find? Utah now carries 89,536 OSM trails. If ridden tracks are 95% covered, this produces stubs and the effort is not repaid; at 40% it is a substantial feature.

⭐ Measurable PC-side in minutes against the spatial DB — sample a track's points, test distance to trail geometry, report the uncovered fraction. No app code. And measure it on the Broken Ridge area specifically, not statewide — that is the case that motivates it.
