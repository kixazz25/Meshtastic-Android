THE CORE BUG — FULLY DIAGNOSED (research-confirmed)

Authority attaches to the UID (security principal), NOT the package (identity), and they can diverge. A running app IS GroupTrack by identity (package/icon/name) but can be a DIFFERENT UID than the one granted all-files access — so it presents as authorized but isn't. isExternalStorageManager()/the toggle read identity-level/stale records (can lie); actual file I/O checks the UID (truth). Data exists (existence doesn't need the grant) but is unreadable (I/O needs the UID grant). Reinstall churn can reassign the UID, stranding the grant.

The fix philosophy: don't trust "am I GroupTrack?" (identity, lies) — verify "can THIS UID actually do the I/O?" (principal, truth) = the write-canary (writes+deletes .authority_probe; scoped storage forbids it in Documents/GroupTrack without real MANAGE_EXTERNAL_STORAGE, so success = ground truth).

2.7 FEATURE — "MOST INTERESTING ROUTE" PLANNER (captured for 2.7)

The feature: user drops vertices/waypoints all over a map → app auto-designs 3-4 DISTINCT rideable routes, each 45-60 miles / 5-9 hours of riding (OHV speeds), that collectively connect all the dropped points. Multi-day trip planning over the trail network.

THE DIFFERENTIATOR: existing nav (Google/onX) optimizes SHORTEST/FASTEST. Ours optimizes the MOST INTERESTING route — the best RIDE, not the quickest path. Borrow the routing machinery (graph traversal — solved) but CHANGE THE OBJECTIVE FUNCTION from minimize-distance to MAXIMIZE-INTERESTINGNESS. The real work = DEFINING "interesting" (product problem = where we win): trail quality/difficulty, scenery, loop-ness, variety, hitting waypoints, within the 45-60mi/5-9hr envelope. Leans on spatial DB (89K trails) + RideCalc (10-15mph → makes it multi-DAY planning). Constrained vehicle-routing problem. Big nav apps can't easily do this (shortest-path, no OHV trail data). NOT 2.6f — 2.7+ / possible premium tier.
