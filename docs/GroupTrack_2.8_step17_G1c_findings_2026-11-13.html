4. The recorded divergence — 6 EXPECTED

2.7e parses with org.json, whose JSONTokener is lenient; the port parses with GtOrgJson over kotlinx, which is strict and says so in its own header:

"NOT REPRODUCED (kotlinx is strict, Android's JSONTokener is lenient): comments, single quotes, unquoted keys, '=' / ';' separators, and text after the first value. Android accepts those; [parse] throws (the golden run marks them EXPECTED)."

Three fixtures feed exactly those cases, over two keys each. OLD finds the tilejson; NEW gives up. Measured, not assumed — the first run reported 58 SAME / 6 DIFF and these were the six. This is the G2g GtConfigs precedent: recorded, not chased.

⭐ Why it is unreachable in practice. GtMapSpec reads context.assets.open("map_sources.json") — the asset WE SHIP, which is well-formed (a strict parser reads it) and contains no comments, single quotes or unquoted keys. ⚠ It is NOT the user-editable external map_sources.json that MapSourceManager.externalJsonFile() reads; that file never reaches this code. The TileJSON comes from OpenFreeMap, serving valid JSON.

⛔ Marking a divergence expected does not mean testing it less. The harness records the base key as EXPECTED and also emits <key>|newonly carrying the port's own answer, so the iPad still compares NEW against NEW on those fixtures — which is why the iPad reports 64 SAME, not 58. And if an expected key ever comes back SAME the harness writes # G1C-NOTE … is STALE rather than passing quietly: that is how an expected-diff list rots into a permanent excuse, and the guard is there to stop it.

5. Two warts reproduced on purpose

The cache. 2.7e caches the resolved tile template in a @Volatile var with no invalidation, so if OpenFreeMap re-versions its path mid-session the stale template is used until the process restarts. Reproduced exactly, and certified as a key: CACHE2 resolves once, then asks again with a DIFFERENT http answer and requires the FIRST one back, with http_calls proving no refetch.

spec() re-reads and re-parses the whole asset on every call. 2.7e does; so does the port.

resetForCert() exists on both sides because resolved is process-wide state: without it the second fixture would answer with the first fixture's template and every later key would be a lie that happens to match. Production never calls it.
