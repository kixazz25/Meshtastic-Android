E3. WRITE-FUNCTION DATA CONTRACT (in-progress JSON mirrors it)

Completed-save consumes the RouteManager VERTEX chain (only true source of shape). Vertex: lat, lon, lineId(String?), lineType(String?), segmentIndex(Int,-1 free), t(0..1), snapped(Bool). Produces wkt+bbox → insertRoute. Completed DB row stores ONLY wkt+bbox+name — throws away HOW it was built.
DRAFT JSON must NOT — stores the FULL vertex list so resume = true editing (undo to a snapped vertex, know which legs ride a trail, re-slice), not a frozen line. wkt re-derivable from vertices; reverse not. Schema (future): 
{ schemaVersion, draftId, name|null, createdAt, updatedAt, method,
  vertices:[ {lat,lon,lineId|null,lineType|null,segmentIndex,t,snapped}, ... ] }
  // NO wkt/bbox — DERIVED at graduation by replaying buildWktAndBbox.
RESUME = parse → addVertex each → drawBuildLine. GRADUATE = identical Build-1 save path + delete draft. ONLY writes ever: create draft JSON · overwrite draft JSON · insertRoute+delete-draft. A route is EITHER a draft-file OR a DB-row, never both.

E4. ENGINE FRAMING

STATES: Route(base)→New→In Progress→Completed. ACTIVITIES: Save, Discard. CONDITIONS: ≥2 pts? · new vs resumed · draft-on-disk? · delete-saved=NO · resave=YES may ALIAS (§K/§L). ACTIONS (black boxes, params+execute): JSON write/open/delete · spatial-DB add/update/delete. In-memory until deliberate Save. Each artifact has its OWN birth process — route is the COMPLEX one; trail-import / waypoint-drop / track-record differ. Completed tracks have their own lifecycle (later).
