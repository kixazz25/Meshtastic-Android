⭐⭐⭐ THE ONE-LINE SUMMARY

Nothing is typed. One generated value names the ride's network AND its Meshtastic channel; everything a device needs — that value, the keys, the radio parameters — is picked up at the ride site and applied automatically.

⭐ PREFERRED PATH: the Nucleus-based IP attach. Join the node's network, the config comes down, the device applies it to itself and its radio. The other delivery paths exist so nobody is stranded, not because they are the plan.

⭐⭐⭐ AGREEMENT 1 — THE MODEL: the flows, and who owns each piece

One diagram, every step in order, every device in its own lane — from the leader creating the ride to everyone putting their radios back afterwards. This is what GroupTrack and Natak agree on before anything else in this document.

⭐⭐ v32 — BELT AND SUSPENDERS. A ride works with or without a Nucleus.

  • BELT: the radio config travels with the ride object and sits in every rider's GroupTrack, stored, not applied. At the ride, each rider selects it and applies it to their radio — back up first — exactly as the leader does. This works with no Nucleus at all, over LoRa alone.
  • SUSPENDERS: if a Nucleus is at the ride, logging in to its network applies the config to any radio that still isn't on it.

⭐ So the Nucleus is an enhancement, not a dependency — it adds the WiFi mesh; the ride never needs it. (This replaces v22's rule that the ride object carries no radio config, which quietly assumed a Nucleus was always present.) Nothing is applied at home unless the rider chooses to, and nothing has to be completed months ahead.

⭐ DECISION (Fred, 2026-09-21) — the network login. It is part of the owner's config — the org's or the leader's — not generated per ride, and it travels in the ride object. The ride network is a private mesh with no internet access and nothing on it but GroupTrack. Accepted: whoever holds the login can read the ride's config. If a login ever leaks, the remedy is the same as rotation — remove the config and a new one is generated.

⭐ The channel is DATA. It lives in the config and GroupTrack applies it straight to the radio — nobody scans it and nobody types it. The QR is only a representation of that same data, for the rare case where the channel has to be entered somewhere GroupTrack isn't, so it goes in without keying errors. The network login gets a device onto the network; the channel data sets up the radio.

⛔⛔ ONLY A COMPLETE RIDE CAN BE DISTRIBUTED. Five things must be assigned: ride name · ride date · radio config (the owner's, or a unique one — the network login is part of it) · route (a route created in GroupTrack, or a track converted to one) · waypoints (at least the trailhead). Email is unavailable until all five are set, and import refuses an incomplete packet.

⭐ Saving is always possible; distributing is gated. A leader can save a ride as a work in progress — built over several evenings — without ever sending half of one. Two checks, deliberately different: save is loose, distribute is strict. Checked 2026-09-21 — and corrected: in the current app a "ride" is just a radio config, so the complete ride object is new work. The pattern already exists in the parked V3 code (behind the V3 flag): ConvoyCreateRideScreen.kt:81–83 has SAVE AS PENDING, enabled by name, date, arrival and rollout times, city and trailhead, with distribution as a later step. It's reference for the build, not running code — and its save check doesn't cover the route or waypoints, so the distribute check still has to be written for all five.

⛔⛔ A RADIO IS ONLY EVER WRITTEN BY AN APPLY. Creating a ride object, emailing it and importing it never touch a mesh radio — however the ride object arrives. Every change to a radio happens in one place, the apply, with its backup in front of it.

⛔⛔ HARD CUT TO A NEW BASE CONFIG (Fred, 2026-09-21). Every radio is first brought to one known base — the TAK-era quiet transport radio — and the ride's required values are added on top: radio config = base + ride values. Nothing from a radio's earlier setup carries forward. The old configs — the 48-field apply list, CONVOY- channels, image-based apply — are not supported; there is no table of old and new side by side.

  • The cutover is the RELEASE (Fred, 2026-09-21). The base config and its apply arrive with 2.7 and do not coexist with 2.6. Moving a radio to 2.7 means reflashing it to 2.7's pinned firmware — the clean slate — then applying base v1 + ride values. Groups move together: a 2.6 rider and a 2.7 rider are on different channels and payloads and won't see each other, so the release notes and group posts say update your app and your radio before the next ride.
  • Firmware gate. Before any apply, 2.7 reads the radio's firmware version. Below the pinned minimum — the version that carries TAK V2 — it doesn't apply; it walks the rider through reflashing.
  • ⚠ The owner's radio name through a reflash. A full erase wipes it. Either update without erasing, or read the name first and put it back afterwards — restoring the owner's own value, not a config writing one. 🔴 Test which reflash path works for the T1000-E — browser flasher over USB, or over the air.
  • The apply is re-base, then add the ride values. The snapshot covers every field the base sets, so restore still writes back exactly what was changed. "Already on it?" means base + ride values match.
  • The base is versioned — base v1. If it changes, radios re-base on their next apply.
  • ⚠ Radio-only riders need a STANDALONE variant — the base quiets a radio's own position broadcasts because the app sends TAK; a radio with no app must keep broadcasting or it disappears.
  • ⭐ The Nucleus radio's base belongs to Natak — his API takes his eleven fields, so GroupTrack sends ride values only and his image is his baseline.

⛔⛔ THE RULE ON EVERY DEVICE: every apply begins with a backup. The node backs up its current config to history; every radio has its own settings backed up before a ride config is written. Nothing is ever overwritten without a way back.

✅ DECIDED 2026-09-21 — a backup is a snapshot of the values we change; restore is writing them back. With the base config, \"the values we change\" = every field the base sets plus the ride values. Because an apply only touches a short list of transport settings, the backup is just those values, read before writing — you don't restore what you never changed. It works the same on any Meshtastic radio and on a Nucleus radio, and it needs fewer writes and reboots than a full-image backup. The existing full-image archive stays as an optional "full backup", outside the ride flow.

⭐ BUILD ORDER — decided 2026-09-21: TAK FIRST

The heavy lifting is radio config and connection, and TAK is what decides how big that problem is: once the app sends positions, the radio's job shrinks to transport and the config collapses. Separating first would mean rebuilding the old 48-field world before cutting it.

  1. TAK in the app — send and receive TAKPacketV2 through the SDK (pinned to the upstream Android app's version; lockstep with Natak when the Nucleus joins), cadence set by the app. The receiver produces the identity layer's own position record, so received TAK and node-database positions reach the map the same way — the map, frozen, receives exactly what it does today. ⚠ Firmware: a minimum version that carries port 78, or a per-send check.
  2. Settle the radio's reduced job — test T3, then define base v1 and its standalone variant.
  3. Hard cut the config — base + ride values, the one apply process, snapshots, the GT generator, no name writes. The ~90 lines of config code in 9 files are replaced, not refactored.
  4. The release is the cutover — 2.7 radios are reflashed and re-based; 2.6 configs are not supported in 2.7. The old config code is removed in 2.7 itself.
  5. The position seam — small by then: two reads in ConvoyViewModel behind a position-source interface, and the IP stub as its second implementation.

⭐⭐⭐ 0 — How it fits together

Five detail diagrams behind the model: the devices, a rider at the event, positions during the ride, the two identities, and applying a config to a radio. The sections after them hold the detail each diagram points to.

0.1 — What connects to what

Three kinds of device. Tablets run GroupTrack and are where every decision is made. Nucleus nodes form the WiFi mesh and each carries a LoRa radio. Meshtastic radios form the LoRa mesh. Solid lines are data; dotted lines are local links — Bluetooth, USB and LoRa.

Detail: sections 1, 5 and 6.

0.3 — A rider at the event

Every path ends at Ready except radio-only — which still appears on every map, by design, but gets nothing else. One check first: is the radio already on the ride's config? If not, the rider selects it in GroupTrack and applies it (belt); with a Nucleus there, logging in applies it to any radio still not on it (suspenders). Derived, not stored — the radio's channel and key fingerprint compared with the config — so it can't go stale. A club member already on the club's config is asked to do nothing. A radio with no GroupTrack gets the ride's channel applied from any GroupTrack device — or entered from its QR, without keying errors.

Detail: sections 1 and 7.

0.4 — Positions during the ride

The app sends a TAKPacket carrying the rider's callsign; a radio-only rider sends Meshtastic's own position. Both reach every participant by two paths — straight over LoRa, and through the Nucleus onto the WiFi mesh. Natak stops storms on the network; GroupTrack drops the duplicate in the app.

Detail: sections 2A and 6.

0.5 — Two identities, never mixed

The ride's identity is one generated id that names the channel and the network and sets the frequency. The rider's identity is their callsign — their GroupTrack user id — carried in every TAKPacket. The radio's long name belongs to its owner — often something meaningful, like Fred & June — and no config touches it.

Detail: section 1.

0.6 — Applying a config: one process, three implementations

GroupTrack's side — not Natak's. Two ways to start it — selecting a config from the local ride definition (leader or rider), or signing in to a Nucleus network — and three implementations: Bluetooth, USB and Nucleus. For radios, the fork already has the connections behind one interface (IRadioInterface: NordicBleInterface, SerialInterface, TCPInterface), and GroupTrack's writes go through the mesh service as admin messages whichever connection is underneath (ConvoyRadioWriter, the setup wizard). For Bluetooth and USB only connecting and reconnecting differ; for a Nucleus, the node performs the backup and the compare itself. Reading, backing up, comparing, writing, verifying and restoring are the same for every radio.

Restore after the ride is the same process with the snapshot as the target. Detail below.

If port 4403 turns out reachable, GroupTrack could also reach the node's radio directly — optional.

The rules the process keeps

  • Read before write, every time — that read is the backup.
  • Write only what differs — fewer settings groups written means fewer restarts.
  • Verify by reading back, not by trusting the write. A radio that restarted onto something else is caught here.
  • On any failure, write the snapshot back and tell the rider in plain words — never leave a radio half-changed.
  • Never write the radio's names — they belong to its owner.

⭐⭐ 2A — WHAT CHANGES WHEN WE MOVE TO TAK PACKETS

Most of these 48 fields exist to MANAGE AIRTIME — how often a packet is sent, how far a rider must move before one is, and what other mesh traffic competes. Fred 09-20: "most of our config has to do with changing values to optimise packet delivery, distance requiring packet send, frequency of packet send, and minimising any other mesh activity."

⭐ Once the APP emits TAKPacket, cadence and distance become APPLICATION decisions — changed in a release, not on a device.

⛔⛔ BUT THE RADIO DOES NOT STOP DOING ITS OWN THINGS. If it keeps broadcasting its own Position packets (portnum 3) alongside the app's TAK packets (V2 on port 78 — see 2B), airtime DOUBLES rather than falling. So the TAK move is not "fewer settings" — it is some settings turned DOWN OR OFF to stop the radio competing with the app.

⛔⛔ AND THAT COLLIDES WITH A CORE PROMISE. A radio ATTACHED to the app should suppress its own position broadcast. A STANDALONE radio with no phone MUST keep broadcasting, or it vanishes — and "hand someone a radio and they appear" is a core promise of this product. Same fields, OPPOSITE settings, depending on whether an app is present.

🔴 SO THE CONFIG CANNOT BE ONE VALUE PER FIELD for position. Either two profiles (app-attached / standalone), or the app toggles the radio's own broadcast when it connects and restores it when it disconnects. Decide before building.

⭐⭐⭐ The synthesis: TAK payload + channel URL = any radio, set up automatically

With the app emitting TAKPacket, what a radio needs per ride shrinks to transport — channel name, key, region, modem preset, hop limit, transmit power. That is almost exactly what a Meshtastic channel URL already carries: the channel settings and the LoRa settings together, in Meshtastic's own format for moving a configuration between radios.

⭐⭐ So the TAK move may make the channel URL the whole ride config for ANY Meshtastic radio. That removes what tied automatic setup to the T1000-E — a saved device image with values injected into it. No image, nothing device-specific.

⚠ The one setting a channel URL does not carry is the radio's own position broadcasting — the two-profile problem above. That lives in the radio's role and position settings. Natak's radios run the TAK role, which may cover it.

⭐ The TAK-era ride config could be as small as a channel URL plus a role. 🔴 Test on a T1000-E and one other Meshtastic radio before relying on it. If it holds, it simplifies GroupTrack, simplifies what Natak's node has to hand out — his eleven radio fields are nearly the same set — and lets the website stop saying other radios are set up by hand.

⭐⭐ 2B — COMPRESSION — answered 2026-09-21

v19: the questions this section used to list are now answered from Meshtastic's own published work. The short version: V2 TAK packets, zstd with a shared dictionary, compressed by whoever creates the packet — and the dictionary version must match everywhere.

The old way is being retired

The original ATAK plugin (V1, TAKPacket, portnum 72) compressed the strings inside a packet with unishox2. It had two known problems: a decompressed field could overrun its buffer (a remotely reachable stack overflow, meshtastic/firmware issue #3841), and on high-entropy text it grew the message — 220 bytes to 245 in that report.

In April 2026 Meshtastic moved ATAK traffic to ATAK Plugin V2 (firmware PR #10105): a new TAKPacketV2 format on its own port, unishox2 removed from the firmware entirely, and compression handed wholly to the client apps.

How V2 works

[ flags: 1 byte ][ payload ]
  0xFF        → payload is a raw, uncompressed TAKPacketV2
  0x00–0x3F   → payload is zstd-compressed; bits 0–5 name the dictionary
The firmware passes the payload through unchanged.

Compression is done by TAKPacket-SDK (github.com/meshtastic/TAKPacket-SDK) — the SDK Natak uses. zstd at level 19 with two pre-trained dictionaries: general traffic (512 KB) and aircraft (4 KB). ⭐ It never makes a packet bigger: when the raw packet is no larger than the compressed one, it sends it uncompressed with the 0xFF flag.

The five questions, answered

QuestionAnswer
What method?zstd with a shared pre-trained dictionary, via TAKPacket-SDK.
Does the app compress, or the bridge?Whoever creates the packet. GroupTrack for its riders; Natak's bridge for CoT arriving from the IP side. Radios only pass it through — no double compression.
Is a position report compressed?Only when that makes it smaller — decided per packet. A short PLI goes uncompressed.
What about truncation?V2 carries typed fields (position, chat, shapes, routes) rather than raw CoT XML; the SDK drops only display-only detail.
Actual on-air size?🔴 Still worth measuring — but it can never exceed the uncompressed size.

⛔⛔ The rule that matters most: the dictionary version must match exactly

TAKPacket-SDK 0.9.0 introduced a new dictionary that is wire-incompatible with older versions and requires a lockstep upgrade. In August 2026, iPhone users on SDK 0.5.1 could not read V2 packets from Android on 0.9.1 (Meshtastic-Apple issue #2348). The failure is silent — packets arrive and simply do not decode.

⭐ Same class as the key derivation rule in section 1: GroupTrack and every Nucleus must pin the same SDK version, and upgrade together. A ride where two participants run different dictionaries is a ride where they can't see each other, with no error anywhere.

⚠ Two corrections to this document

  • Portnum 72 is V1. Earlier sections say TAKPacket on portnum 72. V2 has its own port — 78, per the Apple app's issue report. Meshtastic's Apple app chooses V1 or V2 on every send by checking the connected radio's firmware version; GroupTrack needs the same check, or a minimum firmware.
  • The fork carries V1. The atak.proto in GroupTrack's fork is the V1 TAKPacket. The upstream Meshtastic Android app is already on TAKPacket-SDK 0.9.1 — so V2 is something to pick up from upstream, not to write.

3 — Ownership model

⭐ A RIDE is an EVENT. A CONFIG is a NETWORK IDENTITY. A ride USES a config.

Corrected 2026-09-21 (v23). Orgs and ride leaders each have one assigned config that every one of their rides uses by default. A unique ride config exists only when an org or a leader explicitly asks for one.

Ride belongs toUses by defaultUnique ride config
An org — e.g. Iron County SxSThe org's standard config, for every rideOnly when the org explicitly requests one
A ride leaderThe leader's assigned config, for every rideOnly when the leader explicitly requests one

⭐ The rule — which config a ride uses

  1. A unique config was explicitly requested → that ride's own config.
  2. Otherwise, an org ride → the org's standard config.
  3. Otherwise → the leader's assigned config.

⭐ This settles the old open question — which wins when a ride could use more than one. It's a rule now, not a judgement.

⭐ The schema already carries what the rule needs: rides.org_id says whether it's an org ride, and rides.organizer_id names the leader. A ride only has to record whether a unique config was requested.

⚠ Resolve the default when the config is APPLIED, not when the ride is created

An org ride set up in March and ridden in May must use the org's config as it is in May. If the org rotated its key in April, the ride picks that up automatically. Derived at apply time, never stored — the same rule as the rider's "already on it?" check.

Club riders are set up once

A member applies the org's config once and arrives at every org ride already on it — the check answers yes and nobody touches a radio at the site. A member joining a leader's ride, or a ride with a unique config, moves onto that config for the ride and restores afterwards — the restore path, worth making one tap.

⭐ Configs are never deactivated — they are reused

Most rides use their owner's standing config, so the same config is applied again and again — there is nothing to gain by retiring one. The one exception is deliberate: an owner removing their config to rotate it (below). A unique ride config is kept too: an annual event can reuse last year's.

⭐ It makes the trailhead faster over time: the more a config is reused, the more riders arrive already on it, and the check simply says "ready".

⚠ Expiry belongs to rides, not configs. rides.expires_at ends the event; the config it used lives on.

⭐ Rotation — remove it, and a new one is generated

An org's config and a leader's config both live for months or years, so someone who leaves still holds the key and can still listen.

⭐⭐ The fix is simple (Fred, 2026-09-21): the owner removes their config, and a new one is generated. Because the generated id is the root of everything, the new config means a new channel, a new network name, a new frequency and new keys — a clean break, not an edit. No versions to track, no migration step.

⭐ It costs members nothing. Defaults resolve at apply time, so the next ride uses the new config by itself. Members' radios no longer match, and the usual flow runs — log in with the new login from the next ride object, pull, back up, apply. Someone who has left no longer receives ride objects, so the new login never reaches them — they are simply locked out.

⚠ Two rules that make it hold:

  • Restore offers only configs that still exist in the library. A node's history may still hold a removed config; restoring it would quietly undo the rotation.
  • The key-derivation METHOD is still versioned from day one — that is about the algorithm, not configs. Two builds deriving keys differently can't hear each other. Configs themselves need no versions.

🔴 Decide: who can remove an org's config — any officer, or one designated admin?

⭐ Configs are named — the org's or leader's name and the date it was generated, or a unique ride's name and date — so restore is choosing an earlier entry: the same operation as apply.

4 — Process flows

F1 — CREATE CONFIG (leader)

Mesh Radio menu. Builds a file holding the config: generated channel id, derived keys, region, preset, hop limit, and whatever position parameters survive the TAK move. Saved under ride name + date, owned by club, leader or ride.

F2 — APPLY CONFIG

List available configs → select → archive current state FIRST → apply to the radio and/or to the Nucleus.

⭐⭐ F3 — REQUEST OVER THE NETWORK (the preferred path)

⛔ NOBODY PUSHES. THE RIDER REQUESTS; THE LEADER'S NODE RESPONDS. The request is the consent — no endpoint exists for a stranger to reconfigure someone's radio.

  1. Rider connects to the network — they already hold the name and password.
  2. Rider REQUESTS the config from the leader's node.
  3. Node returns it.
  4. Device applies it to itself and its radio, archiving first.

F4 — RESTORE

⭐ Select an earlier named config and apply it. Same flow as F2. Nothing extra exists.

⭐ THE LOCAL CONFIG STORE — and why RECEIVE ≠ APPLY

A rider may receive a config a month or two before the ride. Importing it must leave it stored and inert; applying is a later, deliberate step. ⭐ That store is a local version of the hosted database — and the backend, when it returns, delivers INTO it rather than replacing it.

Interim delivery by email

GPX for tracks and waypoints goes by email and loads through the existing import process; maps follow the geometry. ⛔ Decide whether the config travels with it — a config carries derived keys, and an emailed key is forwardable.

⭐⭐ The finding with the most leverage: port 4403

The node runs meshtasticd, whose native Meshtastic API is on TCP port 4403. GroupTrack's fork already has a TCP connection type inherited from Meshtastic (DeviceType.TCP, NetworkDevices). So a tablet on the Nucleus network may talk to the node's radio as an ordinary Meshtastic node, with no new transport code.

🔴 Confirm: is 4403 reachable across the mesh, or bound to the node itself? The doc lists it under backend interfaces "for reference".

⭐ Finding the node: the tablet's gateway

Node addresses follow the node id (10.20.<id>.1). A tablet that joins a node's access point is handed an address by that node — so the tablet's own network gateway is very likely its node's address, with no discovery protocol needed. 🔴 Confirm with him.

⛔ Gaps to raise

  1. No authentication. On a ride network, anyone holding the password can reconfigure the leader's node and radio. That is a harder problem for us than for a pre-configured team, because our riders are individuals who join and leave. Minimum ask: a token on the write endpoints (PUT /config, /apply, /meshtastic/config/apply, /channel-url), with reads left open so any rider can still pull the ride config.
  2. Applies are not atomic. Each config group reboots the radio separately, so an error partway leaves it half-changed. ⚠ Mitigation on our side regardless: read before write, apply only changed fields, and on error offer the saved config straight back.
  3. A management path that survives a network change — still unaddressed.

⭐ Participants see every device on the mesh

A GroupTrack participant sees every mesh device through a radio — their own over Bluetooth, or the Nucleus radio over the network — because the app reads Meshtastic's own list of every node heard. Radio-only riders appear either way.

⭐⭐⭐ 7 — The config lifecycle: complete, apply, restore

⚠ Partly superseded — see Agreement 1 (v32, belt and suspenders): the config travels with the ride object and riders select and apply it; a Nucleus, if present, applies it on login. There is no QR step. radio config no longer travels in the ride object and is applied only at the ride site. Where this section describes completing a config ahead, distributing it with the ride, a local config store, or applying at home — Agreement 1 governs.

GroupTrack initiates every step. The Nucleus completes configs it does not keep, applies them only when told, and keeps its own history so any earlier state can be restored.

⚠ Corrected 2026-09-21 (v6). v5 had the node store a staged config until the ride. That fails because rides can be set months in advance: one staged slot would tie the node up for months, and several upcoming rides could not be prepared at once. Completing a config and applying it are now separate.

1 — Complete (any time, including months ahead)

GroupTrack sends the ride config down. The node validates it, computes its derived values, and returns the finished config. The node stores nothing. GroupTrack keeps the completed config in its library and can distribute it to riders immediately.

⭐ GroupTrack compares what came back with what it sent — anything the node rejected or adjusted surfaces at home, not at the trailhead.

🔴 Needs a new endpoint. Today PUT /api/v1/config always replaces the saved config, and apply?dry_run=true compares against what is saved. Ask: a validate-and-derive call that returns the completed config and saves nothing — e.g. POST /api/v1/config/complete.

2 — Apply (just before the ride)

The leader selects the ride in GroupTrack's Apply config list. GroupTrack sends the completed config down and the node:

  1. writes its current config to a history file, labelled and timestamped;
  2. applies the new one.

A dry run first shows the leader what will change. The node restarts onto the ride network, and GroupTrack rejoins it on its own — it generated the network ID.

Today: PUT /api/v1/config → POST /api/v1/apply?dry_run=true → POST /api/v1/apply. 🔴 Ask: save the previous config to history as part of every apply — in one step on the node, so no apply can happen without the previous state being kept.

3 — Restore (after the ride)

GroupTrack reads the node's history, the leader picks an entry, and the node reapplies it — which itself goes through step 2, so the ride config is kept in history too.

🔴 Ask: history endpoints — list the entries (label, saved at), read one, reapply one. e.g. GET /api/v1/config/history, GET /api/v1/config/history/{id}, POST /api/v1/config/history/{id}/apply.

⭐ Why the history lives on the node, not in GroupTrack

Only the node knows its true previous state. Its config may have been set from Natak's own web UI, from another leader's tablet, or before GroupTrack was ever used — and the leader's tablet may be lost or replaced. A history kept on the node survives all of those. GroupTrack's job is to navigate it, not to be it.

What the history must capture

  • Both halves of the node — the WiFi mesh identity and the radio. A restore that brings back one without the other leaves a node split across two networks.
  • A label GroupTrack can show — the ride name and date (or "Home, 2026-09-20" for a node's own setup), so the leader picks from names, not timestamps. 🔴 Ask: a free-text label field in the config that validation accepts and history keeps.

At the event — the rider's steps

  1. The leader applies the ride config to the node (step 2). The node comes up on the ride network.
  2. The rider's tablet joins that network — ⭐ by scanning the leader's QR code, nothing typed.
  3. GroupTrack pulls the config from the node. API: GET /api/v1/meshtastic/config — channel name, key fingerprint, LoRa settings, and the channel URL.
  4. ⭐ Decision: was this radio's config applied from the leader's ride object? The ride object is the reference; the radio is the evidence. The answer is derived, not stored — the radio's channel name and key fingerprint compared with the ride object's config — because a stored "applied" flag goes stale the moment the radio is used on another ride or reset. If it matches, the rider pre-applied at home and is simply ready. Nobody is asked to redo something that's already right.
  5. If not, GroupTrack applies it to the rider's radio over Bluetooth or USB, saving the radio's own settings first.

⭐ Worth testing: this may not need to be T1000-E only. The channel URL is Meshtastic's own way of moving a configuration between radios — it carries the channel, its key and the LoRa settings, and the fork already handles channel URLs. If it covers the ride's essentials, riders with other Meshtastic radios could be set up automatically at the event too, rather than by hand. Test before promising it — the website currently says other radios are set up manually.

🔴 Also to resolve with Natak

  1. Radio settings inside the node's config. /meshtastic/config/apply writes the radio immediately and separately. For one apply — and one history entry — to cover both halves, the radio fields need to live in the node's config.
  2. Which derived values are ride-wide, and which are node-specific? A completed config is shared with riders who may have their own Nucleus. Addresses keyed to node id must be recomputed by each node when it applies, not copied from the leader's.
  3. Riders arriving empty-handed. ⭐ Proposal: a QR code on the leader's tablet at the trailhead with the network credentials — scan, join, pull the config.
  4. Transport for GroupTrack → node. WiFi works today (this API). USB to a Raspberry Pi 4 needs setup on his side. Proposal: WiFi standard, USB only as a wired fallback.
