GroupTrack — Session Recap
2026-07-24 · INTERNAL · queue rebuild + corridor shipped · 2.6d assets in · three defects found on device

Headline

The corridor works, and the number is not close. Tester track bar 10 — the ~100-mile figure-7 that started this whole line of investigation — went from over 1,000,000 bbox tiles to about 107,000 across three sources. A ≈90% reduction, built, queued and downloaded end to end on the planning map. On the strength of that measurement the area button was removed from the artifact panel and track import was cut over, so corridor is now the only path a track takes. Two complete tasks shipped today — the download-queue rebuild that had to come first, and the corridor feature itself.

What happened

  1. Phase 0 + 0b — the queue rebuild. Six patches, one working build: job type and priority as real persisted fields, the first actual ordering the queue has ever had, filter chips that scope destructive actions, gated confirms carrying scope and count, per-row promote, and a real ETA. Scroll took six approaches, five wrong — the answer was that Column + verticalScroll at a fixed height only lays out the rows that fit, so there was genuinely nothing below row 8 to scroll to. LazyColumn was the right shape from the start.
  2. Phase 2 — corridor built, F through G4. Worker dispatch on job type, geometry-to-points derivation, tile-set derivation from points plus buffer, a dedicated ConvoyCorridorWorker, and the wiring. All four compiled first try (14m03s).
  3. Measured on real geography. 65,000 + 21,000 + 21,000 ≈ 107,000 against a bbox needing over a million for the same track. The per-source split is uneven because of layer counts, not different geometry — same corridor, SAT carrying three layers.
  4. Cut over (patch H). Area button deleted from the artifact panel — deleted, not disabled — and track import swapped from bbox to corridor. The import swap turned out to be a loop, not a substitution: the old call covered all slots at once, corridor is one entry per source.
  5. Patch I failed, patch J fixed it. The convoy download-confirm dialog overflows the bottom of the screen. It looked exactly like the 07-22 queues-width drift, so patch I copied planning's .align(Alignment.Center) across. It would not compile — Modifier.align() is a BoxScope extension, and convoy's dialog sits in a Column, not a Box. Patch J wrapped it in its own Box with contentAlignment instead.

Decisions locked

  • The area path is gone from the artifact panel, not hidden. This codebase has already been misled twice by dead functions that outlived their replacements (gridCells, downloadMapsForTrackHash). The composable parameter stays because two screens still pass it; nothing renders it.
  • Corridor stays unsplit for now — one entry per track per source. Splitting is a decision for after real numbers exist across differently-shaped tracks.
  • Route corridors and delete-area deferred, both cheap because launchWorker dispatches on type: each is a new worker that changes nothing existing.

What is pending

  • Install the cutover build on Droid 1 and Droid 2.
  • Corridor downloads still running — waiting on them to confirm the time estimate renders.
  • New bug: refresh jobs never log as completed.

⚠ Three things worth being careful about

1. Bar 10 is the best case, and the number will be quoted. It is the longest, thinnest track available, which is exactly why it shows corridor at its most favourable. A compact track's bounding box is already close to its corridor and will gain far less. When ≈90% gets repeated to testers, that caveat should travel with it — otherwise the first person to run a short loop track reports the feature as broken.

2. The ETA test may not be able to succeed yet. Waiting on corridor downloads to finish assumes the corridor worker stamps completion. But the refresh bug found today is precisely a job that never registers as complete, and the corridor worker deliberately duplicates the completion plumbing rather than sharing it — that was an accepted trade at design time, and this is that trade coming due. A five-minute read of whether ConvoyCorridorWorker calls markComplete is worth more than an evening of watching a progress bar.

3. The refresh bug might not be cosmetic. The obvious reading is "the status label is wrong." The one to rule out first is whether a never-completing job holds a concurrency slot forever — because that is a queue-stall mechanism, and "system just sits" is exactly what 07-23 reported when 3287 entries went in.

The afternoon — assets in, and the screen disagreed with the code

The build went on device, the 2.6d manual and release notes were written and copied into assets byte-exact, and the settings label moved to 2.6d. Then the queue panel was photographed while actually working, and three things fell out that no amount of reading the source had produced.

  1. The ETA's finish date is three days out while its duration is exactly right — so the duration-to-clock maths works and only the date component is wrong.
  2. Corridor jobs marked Done keep counting tiles. Three captures minutes apart show TOPO and TOPO+ climbing by hundreds while sitting under COMPLETED. Completion is being stamped before the work stops, which also means the ETA is computing its rate from a duration shorter than the real one.
  3. SAT is frozen at exactly 15 tiles while its siblings climb. It should be the largest of the three, carrying three layers where the others carry fewer.

The good news arrived in the same capture: corridor jobs do register as completed, which closes the morning's worry and narrows the refresh bug to the refresh branch alone. Row detail, promote arrows, HOLD, concurrency, segmentation and — best of all — the scoped counts all render correctly: CANCEL ALL (6) beside CLEAR ALL (3), six cancellable against three clearable. That is the answer to the 07-23 incident working exactly as designed.

⚠ Where I was wrong today, twice, the same way

I removed "Hold" from the manual because it wasn't in the screenshot. It was simply hidden — there was nothing in the queue to hold. Minutes earlier I had explained away SAT's 15 tiles with a benign theory that the next two captures killed. Both were the same error: treating one screenshot in one state as a complete inventory. An idle panel shows what is actionable, not what exists.

Worth holding onto because the project keeps rewarding the opposite instinct. The segmentation investigation died on four theories before a log line settled it; the scroll bug survived four reasoned fixes before one printed number explained it; and today the screen contradicted the code twice in an hour.

Lessons

  • A matching symptom is not a matching cause. Patch I failed because the previous bug's fix was scope-illegal in a different container. Recognising a familiar shape is a hypothesis, not a diagnosis.
  • When several variations of one mechanism keep failing, change the mechanism. Four scroll fixes tuned parameters on a Column; the fix was a different composable.
  • Instrument first. One printed scroll max=0 settled in a glance what four rounds of reasoning could not.
  • Measure one variable at a time. The corridor number was taken before the z-cap deliberately, so the model change is attributable on its own and the cap can be measured on top.
  • One state is not an inventory. Absence from a screenshot is not absence from the app, and a single plausible explanation is not a diagnosis.
  • Look at the thing. Three defects surfaced in one photograph of a working panel that hours of reading the source had not produced.
