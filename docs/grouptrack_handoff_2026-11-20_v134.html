⛔⛔⛔ A DOTFILE DECIDES WHETHER 229,178 TRAILS SURVIVE (MARKERDR-2026-11-18)

This is the most consequential finding of the day, and it is an ANDROID finding as much as an iOS one. It was only visible because Fred insisted the app start at the beginning rather than mid-road.

What happened. First run of the real startup road reported “housekeeping says needs reload” and a banner. The trails table had gone to 0. Tracks (130) and waypoints (595) survived. The mechanism, measured in the shared code. GtStartupHousekeeping.kt declares const val SCHEMA_MARKER = ".schema_2026-09-03A", and jobSchemaConverge gates on it: if the marker is absent it runs DELETE FROM trails plus DELETE FROM trail_properties, ALTERs the missing columns, writes the marker, and returns needsReload = true. The marker is a dotfile in the GroupTrack root.

The root cause is the capture, not the app. The Nov 6 Droid 1 directory capture contains no dotfiles at all. Seeding the simulator from it produced a GroupTrack root with a full database and no marker — so converge did exactly what it is written to do, and cleared the 322 trails that were in view at the time.

Why nine months of Android never saw it. Android only ever reaches two states: a fresh install (no marker, but the trails table is empty, so the clear is a no-op and the marker is written) or an existing install (marker present, converge returns immediately). Seeding creates a third state — full data, no marker — which the code has never been asked to handle, and which it handles destructively by design.

Confirmed by repair: re-seeded with the marker now present → 229,178 trails intact, no clear, no banner.
