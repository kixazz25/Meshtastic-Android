WHAT THIS IS

The end-of-day state of the seam work for the iPad/iOS port: how many objects actually carry a seam, which are in service (port them) and which are not in service (remove them with a record), the process for inspecting the rest, and what still stands between us and an iOS build.

Today's deliverable was not code. It was method. We began the day able to say what code exists and whether it produces correct bytes, and unable to say whether it runs. That third question is Fred's own rule from 11-13 17:32 — "is the function even executed" — and until today it had no tooling, so it had been applied by hand to exactly one function (CONVDEAD-2026-11-14). It now has four instruments and a reproducible script, and the first time it ran it overturned an answer that reference counting had given twice.

1 · THE RESEARCH — what today established

1.1 Two instruments, opposite blind spots, and no third

  • Certification proves the paths that ran produced correct bytes. It is silent on paths that never ran. Osm15g can be 231,365 SAME / 0 DIFF while the raster branch beside it never executes once. A passing cert and a dead branch are perfectly compatible.
  • The seam / import scan sees every file that exists, by what it imports. It cannot tell whether any of it runs — so it billed a dead branch as seam work.
  • Neither answers "is it executed." That was the gap.

1.3 Why it hid for ten days past the 11-01 VECONE cutover

The seam list's unit was the FILE. The dead code's unit is the BRANCH.

  • ConvoyDownloadQueue.kt — 17 shared refs, so the whole file counted PORTED, including the 2.7e raster branch its own line 295 admits it still carries.
  • ConvoyMapSourceScreen.kt — 2 shared refs, counted PORTED, and holds 94 dead lines (SlotCard 820-876, ApiKeyRow 940-976, both 0 calls) behind a live route repurposed to map-source credits on 11-13 (SRCCREDITS-2026-11-13).

A file-granularity instrument has no way to say "half of this is dead." Once as "already done," once as "work to do" — never as "delete."

1.4 Four rules earned today

  1. Verify by DECLARED NAME, never by filename. ConvoyDownloadQueuePanel.kt declares DownloadQueuePanel; a filename grep reported 0 refs for a composable with 4 live callers. This morning's 16 route removals were safe precisely because the tool matched declarations.
  2. A reference means nothing without its GUARD. A call site inside a dead branch is a reference to nothing.
  3. A count means nothing without a NAMED CALLER and one hop to a root. "Someone calls it" is the aggregate claim that failed all day (Fred 16:22).
  4. Every run carries a BUDGET. Osm15g's 733 s against a 737 s expectation was trustworthy at once; Import15e's 20 minutes against 187 s was unambiguously wrong. Four stalls today came from optimistic estimates against a 180 s cap — the rule binds the estimator too.

2A · THE BLOCKING SET — what must be addressed before the iOS model is genned

FRED 16:40"I am concerned with all seams that must be addressed prior to the iOS model being genned. Categorizing them, analyzing if they are in use, and then fixing each set type."

The correction this section makes: the 685 mechanical rows were written below as "no decision needed," which is true and was the wrong emphasis. They need no decision, but they are the bulk of the blocking work. 685 functions is what stops the model compiling; the 212 are only the part that needs us to talk.

The distinction that decides what actually blocks

No file in app/ ever builds for iOS. The iOS build consumes grouptrack-shared only. So a seam blocks the iOS model only when that function's behaviour is needed on the iPad. That splits the 945 three ways:

  • BLOCKSiPad needs the behaviour, and it touches a seam → the logic moves to shared and the Android API behind it needs a socket. This is the real blocking set.
  • PORTiPad needs the behaviour, no seam → straight move to shared, no socket, no decision.
  • STAYSAndroid-only plumbing the iPad reimplements → stays a front door in app/, may keep using Android APIs freely, never needs to build for iOS. Not a blocker at all.

THE MISSING MEASUREMENT — tomorrow's first job

We do not yet know the size of category 1, because which of the 113 files hold behaviour the iPad needs is a judgment per function, not a grep. The earlier register figures ("141 iOS-bound files, 82 non-portable surfaces") come from the same source that produced 59 and 76 without recording what they counted, so they are not carried into this doc. They may be right; they are not re-derivable, which is the same defect this doc exists to end.

Until that split is made, the honest statement of scope is: 945 seam functions exist; an unknown subset of them blocks the iOS build. Stating a blocking number before the split is measured would repeat exactly the error that billed the dead raster branch as seam work.

THE SEQUENCE, as Fred set it (16:40)

1 · CATEGORIZE — every seam function into the three categories above. Done by seam type, file by file, using the 113-file concentration order. The two mechanical types (CONTEXT 593, LOGGING 454) can be categorized in bulk; the other ten are per function.
2 · ANALYZE IF IN USE — the three columns (gt_seamactive_v4): referenced, executed, and whether each call site is guarded, with the caller named and one hop to a root. Default KEEP. Not-in-use rows leave the blocking set entirely and go to §3.1 for removal with a record.
3 · FIX EACH SET BY TYPE — one solution per seam type, applied across every function carrying it, rather than file by file. Order is cheapest-and-widest first:
  • LOGGING 454 → Kermit. Mechanical find/replace. Largest single win.
  • CONTEXT 593 → the socket that already exists in several forms (GtStorage, GtImportPlatform, GtFiles). Certified 17-G2a.
  • COMPOSE_LOCALS 75 → LocalContext is the genuine Android tie in panels. Compose Multiplatform publishes under androidx.compose.*, so the panel imports are already portable; only this local needs replacing.
  • NOTIFY 64 → one notification socket. Likely collapses to a single decision for all 64.
  • INTENTS 54 → the file-picker / open-with family. Needs the iPad equivalent (document picker) plus the three MIME types.
  • THREADING 42 → coroutines, already in the shared module.
  • GRAPHICS 22 · RESOURCES 18 · SAF 13 · WORKMGR 11 · PKGMGR 3 · VIEWMODEL 3 — all small. WORKMGR is a day, not a phase.

Solving by type is the whole point of the exercise (Fred 11-15): identify the type, group it across the codebase, solve for the seam type once. Twelve solutions cover 945 functions. Doing it file by file would be 113 passes over the same twelve problems.

4 · TOMORROW'S INSPECTION PROCESS

DEFAULT IS KEEP (Fred 16:04): "if we error it will be leaving in the function we cannot rule out." A wrong keep costs one socket. A wrong removal costs a working app. Nothing is called dead unless both instruments agree.

Step 1 — run the three-column pass. From a terminal, NOT the tool bridge (180 s cap; four stalls today). Budget under 60 s.
python3 ~/Downloads/gt_seamactive_2026-11-15_v4.py with GT_REPO / GT_LOGS / GT_ROWS / GT_OUT / GT_TSV / GT_SITES set.
Step 2 — triage its verdicts. ACTIVE rows need no discussion: port them. Only two buckets come to us.
Step 3 — read GUARDED ONLY rows together. Every caller sits inside a condition. The callsites TSV gives each guard verbatim. We read the condition and decide whether it can be true on an iPad. This is the column that would have caught raster.
Step 4 — trace CANDIDATE rows together. No caller and no execution. Walk the flow from app knowledge, as we did for the queue.
Step 5 — UNDECIDABLE rows KEEP. No log text of their own means no execution signal. Undecidable is never dead.
Step 6 — then the mechanical 685. LOGGING → Kermit (find/replace). CONTEXT → the socket that already exists in several forms. No per-function decision; the work is the same whether the function is hot or cold, so reviewing them would cost more than doing them.
Why the mechanical ones skip review: the point of asking "is it active" is to avoid work that need not be performed (Fred 15:53). For CONTEXT/LOGGING the work is a one-line substitution, so the review costs more than the work it would save. For the other ten types each function is a design decision, which is where activity matters.
