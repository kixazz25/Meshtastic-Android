⛔⛔ The storage answer

The All Files Access declaration was rejected 09-10 — "Access to device storage not required" — and the appeal came back rejected. An extension request is in, asking for time to publish a compliant build. ⚠ That buys TIME, not the argument.

⛔ Fred: "I cannot publish with that in the manifest."

What the research established

  • OsmAnd does not have this permission. Issue #16059, open since Dec 2022, never granted. They ship offline maps inside their own folder tree and call it "certainly a crippling mechanism" — but it plainly works. ⛔ Any declaration built on "there is no alternative" invites that comparison.
  • ⭐ The argument that might have worked, found last: riders back their map store up to SD cards and restore it to replacement devices. App-private storage makes that impossible. That is data portability, and it fits Google's own permitted uses far better than performance.
  • ⚠ Arguments discarded: "the user downloads it, not the app" (the app builds the URLs, queues, retries and writes the files) and "it is third-party public-domain content" (the policy is about which process wrote the file).

🔴 The plan — a clean install, not a migration

⭐ Ten serious users is the number that decides it. A migration needs the permission to read the source, so it would take two builds and a gap — and would still strand anyone who skipped the first.

What riders do: export routes and tracks with the share function, uninstall, delete Documents/GroupTrack and Documents/my_tracks, install, reimport. Trails and maps re-download.

⛔ THE EXPORT IS NOT OPTIONAL. Graduated routes exist only as database rows — a WIP draft is a file and survives, but graduation stops maintaining one. Without the export they are gone.

⚠ ~17 GB of maps and about an hour of trail import per rider. Worth saying plainly.
