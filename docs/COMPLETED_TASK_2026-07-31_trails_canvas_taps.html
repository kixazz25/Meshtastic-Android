COMPLETED — 2026-07-31 · Trails display, canvas renderer, tap fixes

Graduated out of the Living Master. Six files, 249 insertions. Thirteen builds.

Two bugs closed that had been misattributed for months, one diagnosed to a specific July commit, and a route-mode design settled that is smaller than what it replaces.

⭐⭐ 1 — TRAILS: the six-month "not fixable because of volume" bug

SpatialDbManager.queryTrailsByViewport used LIMIT with no ORDER BY. SQLite therefore returned whichever rows it reached first — rowid order, i.e. OSM import insertion order, which carries no spatial meaning.

At z8 roughly 89,536 Utah trails matched the bbox and 500 drew. Any viewport change returned a DIFFERENT arbitrary 500. Nothing was ever misplaced — the membership churned.

What identified it — both from behaviour, neither from code

  • "Seems to load bands by longitude." A Geofabrik extract walks its own spatial index, so insertion order carries a rough geographic sweep. The first 500 by rowid is a STRIPE, not a scatter.
  • "Adding Arizona places the trails below the tracks." Utah imported first and holds the low rowids, so every Arizona trail sorted after every Utah trail. Import order made visible.

⭐ Volume was never the variable. smoothFactor is a per-polyline screen-space tolerance and behaves identically at 500 artifacts or 89,000. The story that this was unfixable because of trail count made a prediction — that doubling coverage would worsen it — and that prediction failed.

⭐ And the tap test is what redirected the whole hunt. Taps fired on trails where they were DRAWN, proving Leaflet placed them exactly where the data said. The data was never wrong; there was just an arbitrary subset of it.

The fix

ORDER BY (CASE WHEN name IS NULL OR name = '' THEN 1 ELSE 0 END),
         ((max_lat-min_lat)*(max_lat-min_lat)+(max_lon-min_lon)*(max_lon-min_lon)) DESC

Named first — OSM carries no carto_code, so name is the only quality signal. Then largest bbox extent (squared diagonal, no sqrt needed for ordering, both columns already indexed). Plus minZoom 11 and a 10,000 row cap as a safety valve, not the mechanism.

⚠ Why tracks were never affected: a few hundred exist, so their cap never binds. That is also why it appeared to "resolve at z12" — that is simply where viewport trail density drops under the cap. No z12 threshold exists in the code.

⭐⭐ 2 — CANVAS RENDERER: tolerance had never worked

renderer: L.svg({ tolerance: 44 })

tolerance is an option of L.Canvas. L.SVG ignores it. Under SVG, hit-testing is done natively by the browser against the <path> element — so the effective tap target was the stroke width, 3 pixels. On both maps, since at least 07-08.

Device evidence: ~40 taps at z18, 3 hits, 0 trails.

⛔ Note this was suspected of the OPPOSITE — that a 44px halo was swallowing taps at OSM density. It was doing nothing at all. And commit ef00baca8 had raised it from 18 to 44 believing it worked.

Fix: both maps to L.canvas. ⭐ Tracks pinned to L.svg() per-layer so polylineDecorator keeps the per-path geometry its arrows need — Leaflet takes a renderer per layer, not only per map.

⚠ Canvas also removes the one-DOM-element-per-path cost that ANR'd the WebView at 120,000 trails. The z11 gate and 10,000 cap are worth revisiting now that constraint is gone — separately, with its own test.

⭐ 3 — CONVOY LONG-PRESS WAYPOINTS

Seven long-presses produced ZERO console output while taps logged cleanly. convoy_map.html uses map.on('contextmenu'), and Leaflet 1.9 removed its own tap handler — it relies on the browser firing a native contextmenu. ConvoyScreen.kt:938 installs a setOnTouchListener on the WebView (the planner has none), which intercepts before View.onTouchEvent — and onTouchEvent is what starts the long-press timer.

Fix: detect the long-press in that listener — 500 ms timer, 20 px move slop — and call longPressAt(x,y), which converts a container point to a latlng and calls the EXISTING bridge. pendingWaypoint and the dialog were complete all along; only the gesture never arrived.

⚠ Timer state is held in remembered arrays, not MutableState — the listener lives in update = { } which re-runs on every recomposition, and state mutated from a touch event would reinstall the listener mid-gesture.

⭐ Canvas later restored native contextmenu as well, so onMapLongPress now fires twice per press from two paths. Harmless (second write wins) but the timer is now redundant.

⭐ 4 — addPointMode DEFAULTED TRUE

var addPointMode by remember { mutableStateOf(true) }
    // Tap:Route(on)/Artifact(off) — consumed by onMapTap next build

"Next build" never came. The flag shipped defaulted ON, so every planner track tap was suppressed — device-confirmed as PLANNER SUPPRESSED by addPointMode with no route ever drawn. Convoy has no such guard, which is why the two maps behaved differently.

The only assignment is :1256 — addPointMode = armed — so the value still comes from arming; it just no longer STARTS armed. The guard itself is correct and stays.

⭐ Fixing it also restored planner long-press, since :553 reads the same flag.

⚠ METHOD NOTE — thirteen builds, and why

Seven hypotheses were tested and eliminated on trails alone before the cause was found; four more on convoy taps. Every one was a plausible mechanism, and every one was disproven on device.

⭐ What actually solved both bugs was reasoning about BEHAVIOUR, not code — the longitude banding, the Arizona ordering, the tap test, and "planner has popups and convoy doesn't, which is backwards". Each was decisive and none came from reading source.

⚠ The structural cost driver is patchy instrumentation. Tap handlers log, bridges mostly do not, state writes never do. Every hunt begins by spending a build to see anything at all. A one-time tracing pass across tap → bridge → state → composition, kept permanently, would repay itself immediately.

⭐ Fred, at the end: "our errors were at 30,000 feet and we were dealing in the details." State the rule in English first and check the code against it — not the reverse. Both real fixes came from that direction.
