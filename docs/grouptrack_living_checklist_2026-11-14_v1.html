WHAT THIS DOCUMENT IS — and what it is not (Fred, 2026-11-14 20:46)

Fred's words, verbatim, because they define the whole thing:
"the living checklist is our kick the can issues by release. they are the sideboards that wreak havoc once we start down the rabbit hole. our goal is a good problem definition and anticipated solution so we can address without distracting from the task at hand. these are the little tasks that are close enough or a distraction and we never get back to them. they should be tie[d] to a release and commented on the living checklist, there will be a lot of them once we start certifying."

So the job of an entry is to let the item be PUT DOWN safely. Two fields carry that weight: a problem definition good enough that nobody re-derives it, and an anticipated solution so picking it up is work rather than thinking. An entry without those is a reminder, not a checklist item.

⚠ IT IS NOT A STATUS TRACKER, AND IT IS NOT A HISTORY. Closed items are REMOVED, not struck through — completed work is archived in a per-release completed-activity doc (Fred 09-09), and the living master carries open design and the durable rules. Keeping closed items here is what made a half-finished item read as open for six weeks on 08-29.

Why it is its own file as of 11-14: it was a 39 KB section inside the living master, which had grown to 803 KB — 54% of which was eleven superseded daily START HERE sections that were appended and never pruned (11-11 alone was 240 KB). Fred 20:43: "we are supposed to be pruning activities from eod when they are finished.... how can it be so large." Same finding as 09-09 at 1.1 MB: "it is becoming all docs."

THE THREE DOCUMENTS, after 11-14:
· LIVING CHECKLIST (this file) — kick-the-can issues, tied to a release, problem + anticipated solution. Pruned as items close.
· LIVING MASTER — open design, the durable rules that outlive their release, one pointer line per extracted release.
· EOD / HANDOFF — the SHORT-RANGE PLAN only: the next 2–3 days of activity, derived from this checklist and the open items. Pages, not hundreds of KB.

ENTRY 2 The track list shows an alias as a second track

problemThe same ride appears twice in the track select panel. The list joins aliases and renders a row per alias, so one track with one alias yields two entries. Both open the same track, because they are the same row — UNIQUE(geom_hash) makes two rows with one hash impossible, and the pair shows the same hash.
anticipated solutionOne entry per track_id, primary name displayed; the alias participates only in resolving what the rider typed or tapped. A query fix, not a data fix — nothing in the table changes and the alias is correct and kept.
classAn alias is for MATCHING, never for LISTING. D22 (show the name the search matched) is a result-annotation rule, not a listing rule. Routes, rides and waypoints carry aliases too — expect this class there.
comment11-14: severity LOW — cosmetic, nothing lost or mis-selected, but it reads as a retrieval failure, which is how it was reported. Unverified: the extension DB was never opened, so the alias text and its write date are unconfirmed (one small pull and one query). If the alias turns out to be a path-safe form of the name (/ → _) written back as an alias, the fix moves upstream and D34 could not have caught it.

CERT GAP Two holes the step 17 certification does not cover

Cheap, and it restores field diagnosability without touching the certified port.

DO NOT TOUCH iosMain/text/GtMathLog.kt:125 — the "Division by zero" warning is correct

problemThe compiler warns Division by zero on return -1.0 / 0.0. It looks like a bug and is not.
anticipated solutionNONE — leave it. Negative infinity is the correct IEEE result for log(0), mirroring __math_divzero. The file is a bit-exact port of ARM's optimized log() (the B[] polynomial, INVC/LOGC tables, fma, N=128) so iOS produces identical bits to Android's libm. Rewriting the line as Double.NEGATIVE_INFINITY is harmless; touching anything else in the file breaks the bit-exactness that is its entire purpose.
