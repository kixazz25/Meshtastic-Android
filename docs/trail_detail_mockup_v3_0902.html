ONLY POPULATED FIELDS SHOW. With 36 columns and most of them sparse, empty rows would be pure noise — the third card is the honest common case, and saying so plainly is better than eleven blank lines.

THE CLASSIFICATION BLOCK COMES FIRST because it answers "why is this line this colour". source frames everything under it: a forestry/access road from UGRC is a recorded fact, the same category from OSM is inferred from a surface tag.

⚠ source value is carto_code_source — what the source actually said, kept so a mapping change never destroys the original.

⚠ SOURCE NAMES ARE THE REAL ONES. osm and ugrc_utah_trails are internal ids and mean nothing to a rider; the catalogue already carries proper labels. And no OSM jargon — a "way" is a TRAIL.

★ ROUGHNESS IS THE FIELD THAT CHANGES A DECISION. OSM's smoothness is written as VEHICLE CAPABILITY, not terrain: very_bad is high-clearance, horrible is 4WD, very_horrible is ATV or tractor, impassable is nothing wheeled. On the motorized set: very_bad 4,737 · horrible 987 · very_horrible 338. Only 8% coverage — but where it exists it is the only field that says whether a machine physically gets through, so it earns its place on the record and in the route narrative. Shown translated, with the raw token beside it for anyone who wants it.

★ SURFACE GOES ON THE COMPARE TABLE TOO (Fred, 09-02): "just append the surface type to each trail — that will tell us how long on this surface type." The table already sorts by total mileage, so the surfaces you are actually riding land at the top. Blank stays blank rather than pretending.

⚠ PLUMBING GAP: land_status, use_type and our carto_code live on the trails table, but ArtifactDetailPanel reads detailFields, which comes from trail_properties. So it cannot see the three fields that matter most today — that has to be fixed before this panel can be built.
