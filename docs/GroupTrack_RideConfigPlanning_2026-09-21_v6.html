For the GroupTrack ↔ Natak Mesh conversation. Field attributes, process flows, and the API surface each side owns. Companion to the Communications Layer Design and the Nucleus Integration Design. Self-contained.

⭐⭐⭐ THE ONE-LINE SUMMARY

Nothing is typed. One generated value names the ride's network AND its Meshtastic channel; everything a device needs — that value, the keys, the radio parameters — arrives in the ride config and is applied automatically.

⭐ PREFERRED PATH: the Nucleus-based IP attach. Join the node's network, the config comes down, the device applies it to itself and its radio. The other delivery paths exist so nobody is stranded, not because they are the plan.

1 — The three identifiers

⛔⛔ WE DO NOT OWN THE CHANNEL ID. That is a hard stop from Meshtastic — its length, format and semantics are theirs and can change.

ValueOwnerVisible toRule
Long descriptionGroupTrack⭐ Rider, on every screen and panelAlways a long, readable description. What a rider recognises the ride by.
Channel IDMeshtastic constrains itNobody⭐ AUTO-GENERATED: GT + a system-generated unique id. Sized to fit. Never typed, never displayed.
Network IDGroupTrackNobody types it⭐⭐ DERIVED — EQUAL TO THE CHANNEL ID. The WiFi network a node broadcasts carries the same GT+unique value as the Meshtastic channel name. It arrives in the ride config, and the app joins the network with it. Eleven characters sits well inside WiFi's 32-byte limit for a network name.

⭐⭐ ONE VALUE, THREE THINGS. The generated id is the Meshtastic channel name, the WiFi network name — and, through Natak's frequency_slot 0 (frequency derived from the channel name), the radio frequency too. Two nodes given the same ride config land on the same channel, the same network and the same frequency, with no human input anywhere.

🔴 OPEN — the network password. With nothing typed, it must also arrive in the ride config: either carried as a value, or derived with the Meshtastic PSK from one ride secret (the KDF below). Decide which, and confirm Natak's node config accepts a network password we supply.

⭐ Generating the channel id removes the truncation trap. An 11-character limit does not matter when the value is generated to fit rather than derived from something a human typed — and if Meshtastic moves the limit, only the generator changes.

⚠ THE KEYS ARE DERIVED, NOT SHARED. A WPA2 passphrase and a Meshtastic PSK differ in format and length and cannot be the same value. One password feeds a KDF; each transport gets a correctly formatted key. ⛔ The derivation must be identical on every build and versioned from day one — two riders on different releases deriving different PSKs from one password is a silent, total failure.

🔴 OPEN: what makes the generated id unique, and across what scope? Two clubs generating independently must not collide — central issuance, or enough entropy that collision is negligible.

2 — Field attributes: THE RADIO CONTRACT (48 fields)

⭐⭐ SOURCE OF TRUTH: app/src/main/assets/convoy_apply_list.json. This is the contract between GroupTrack and the radio — the same fields the user manual documents for config. 48 fields in six groups.

⭐ THE GOVERNING RULE: the config changes only these fields. ANYTHING NOT LISTED IS LEFT AS IS. Applied via the existing apply-list process (ConvoyApplyListScreen), which already archives the radio's prior state before touching anything.

⛔ THIS LIST HAS NO IP SURFACE AT ALL. It is purely the Meshtastic radio. Everything the Nucleus needs is a SEPARATE contract that Natak defines — see section 5.

⚠ Three fields that sound alike and are not

⭐⭐ 2A — WHAT CHANGES WHEN WE MOVE TO TAK PACKETS

Most of these 48 fields exist to MANAGE AIRTIME — how often a packet is sent, how far a rider must move before one is, and what other mesh traffic competes. Fred 09-20: "most of our config has to do with changing values to optimise packet delivery, distance requiring packet send, frequency of packet send, and minimising any other mesh activity."

⭐ Once the APP emits TAKPacket, cadence and distance become APPLICATION decisions — changed in a release, not on a device.

⛔⛔ BUT THE RADIO DOES NOT STOP DOING ITS OWN THINGS. If it keeps broadcasting its own Position packets (portnum 3) alongside the app's TAKPackets (portnum 72), airtime DOUBLES rather than falling. So the TAK move is not "fewer settings" — it is some settings turned DOWN OR OFF to stop the radio competing with the app.

⛔⛔ AND THAT COLLIDES WITH A CORE PROMISE. A radio ATTACHED to the app should suppress its own position broadcast. A STANDALONE radio with no phone MUST keep broadcasting, or it vanishes — and "hand someone a radio and they appear" is a core promise of this product. Same fields, OPPOSITE settings, depending on whether an app is present.

🔴 SO THE CONFIG CANNOT BE ONE VALUE PER FIELD for position. Either two profiles (app-attached / standalone), or the app toggles the radio's own broadcast when it connects and restores it when it disconnects. Decide before building.

⭐⭐ 2B — COMPRESSION

Compression is already IN the protocol. From core/proto/.../meshtastic/atak.proto:

message TAKPacket {
  bool is_compressed = 1;   // "Are the payloads strings compressed for LoRA transport?"
  ...
  oneof payload_variant {
    PLI     pli    = 5;
    GeoChat chat   = 6;
    bytes   detail = 7;     // "Generic CoT detail XML.
                            //  May be compressed / truncated by the sender (EUD)"
  }
}

⭐ And Natak already does it: "I'm using meshtastic takpacket sdk to handle the CoT → Meshtastic compression/transmission pipeline."

🔴 QUESTIONS FOR NATAK:

  1. WHAT METHOD? The proto records WHETHER a payload is compressed, not HOW. We need the algorithm, or both sides cannot interoperate.
  2. Does the app compress, or the bridge? If the app emits compressed TAKPackets and the bridge compresses again, that is wasted work — or a broken payload.
  3. Is PLI compressed at all? A PLI is already tight — five numeric fields. Compression may add overhead rather than save it on the packet we send most often.
  4. What does detail truncation do? "May be compressed / truncated" — truncated how, and does a receiver know it was? A silently truncated payload is the worst kind of data loss.
  5. What is the actual on-air size of a compressed PLI vs an uncompressed one? ⭐ That is the number that answers the congestion question.

⚠ Worth knowing before we emit anything: if GroupTrack sends TAKPackets in a form the bridge expects to compress, and they arrive already compressed or in an unexpected form, the failure will be silent — packets that decode as garbage or not at all.

4 — Process flows

F1 — CREATE CONFIG (leader)

Mesh Radio menu. Builds a file holding the config: generated channel id, derived keys, region, preset, hop limit, and whatever position parameters survive the TAK move. Saved under ride name + date, owned by club, leader or ride.

F2 — APPLY CONFIG

List available configs → select → archive current state FIRST → apply to the radio and/or to the Nucleus.

⭐⭐ F3 — REQUEST OVER THE NETWORK (the preferred path)

⛔ NOBODY PUSHES. THE RIDER REQUESTS; THE LEADER'S NODE RESPONDS. The request is the consent — no endpoint exists for a stranger to reconfigure someone's radio.

  1. Rider connects to the network — they already hold the name and password.
  2. Rider REQUESTS the config from the leader's node.
  3. Node returns it.
  4. Device applies it to itself and its radio, archiving first.

F4 — RESTORE

⭐ Select an earlier named config and apply it. Same flow as F2. Nothing extra exists.

⭐ THE LOCAL CONFIG STORE — and why RECEIVE ≠ APPLY

A rider may receive a config a month or two before the ride. Importing it must leave it stored and inert; applying is a later, deliberate step. ⭐ That store is a local version of the hosted database — and the backend, when it returns, delivers INTO it rather than replacing it.

Interim delivery by email

GPX for tracks and waypoints goes by email and loads through the existing import process; maps follow the geometry. ⛔ Decide whether the config travels with it — a config carries derived keys, and an emailed key is forwardable.

Three paths to a configured radio

PathNeeds
⭐⭐Pull over the IP networkPREFERRED. A Nucleus present, rider connected.
⭐Apply from my deviceThe local store. Works with no Nucleus at all.
⚠Apply from any devicePhysical access only — any Android can configure any radio. ⭐ Guarantees nobody is stranded; ugly, and not the plan.

⭐⭐⭐ 7 — The config lifecycle: complete, apply, restore

GroupTrack initiates every step. The Nucleus completes configs it does not keep, applies them only when told, and keeps its own history so any earlier state can be restored.

⚠ Corrected 2026-09-21 (v6). v5 had the node store a staged config until the ride. That fails because rides can be set months in advance: one staged slot would tie the node up for months, and several upcoming rides could not be prepared at once. Completing a config and applying it are now separate.

1 — Complete (any time, including months ahead)

GroupTrack sends the ride config down. The node validates it, computes its derived values, and returns the finished config. The node stores nothing. GroupTrack keeps the completed config in its library and can distribute it to riders immediately.

⭐ GroupTrack compares what came back with what it sent — anything the node rejected or adjusted surfaces at home, not at the trailhead.

🔴 Needs a new endpoint. Today PUT /api/v1/config always replaces the saved config, and apply?dry_run=true compares against what is saved. Ask: a validate-and-derive call that returns the completed config and saves nothing — e.g. POST /api/v1/config/complete.

2 — Apply (just before the ride)

The leader selects the ride in GroupTrack's Apply config list. GroupTrack sends the completed config down and the node:

  1. writes its current config to a history file, labelled and timestamped;
  2. applies the new one.

A dry run first shows the leader what will change. The node restarts onto the ride network, and GroupTrack rejoins it on its own — it generated the network ID.

Today: PUT /api/v1/config → POST /api/v1/apply?dry_run=true → POST /api/v1/apply. 🔴 Ask: save the previous config to history as part of every apply — in one step on the node, so no apply can happen without the previous state being kept.

3 — Restore (after the ride)

GroupTrack reads the node's history, the leader picks an entry, and the node reapplies it — which itself goes through step 2, so the ride config is kept in history too.

🔴 Ask: history endpoints — list the entries (label, saved at), read one, reapply one. e.g. GET /api/v1/config/history, GET /api/v1/config/history/{id}, POST /api/v1/config/history/{id}/apply.

⭐ Why the history lives on the node, not in GroupTrack

Only the node knows its true previous state. Its config may have been set from Natak's own web UI, from another leader's tablet, or before GroupTrack was ever used — and the leader's tablet may be lost or replaced. A history kept on the node survives all of those. GroupTrack's job is to navigate it, not to be it.

What the history must capture

  • Both halves of the node — the WiFi mesh identity and the radio. A restore that brings back one without the other leaves a node split across two networks.
  • A label GroupTrack can show — the ride name and date (or "Home, 2026-09-20" for a node's own setup), so the leader picks from names, not timestamps. 🔴 Ask: a free-text label field in the config that validation accepts and history keeps.
