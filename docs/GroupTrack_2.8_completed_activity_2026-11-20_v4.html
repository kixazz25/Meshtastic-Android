⛔ OPENED 2026-11-20 — RIDE TEST ITEM 5: THE GROUP FIT LEAVES NO ROOM AHEAD (C28-26355)

⛔ 2.8a C28-26355 · GROUPFIT70 — the group view fits the middle 80%; Fred wants 70% so the trail ahead is visible

Fred 11-20 10:52: "it also appears that the group view ta[ke]s the whole map vertically so you can[not] see the path [you] are riding. group view should consume ~70% of map so it stays centered and shows trail ahead."

MEASURED — the padding exists and the number is 0.1. Both group call sites pass it: GroupTrackScreen.kt:547 ("GROUPFIT-2026-10-26: the middle 80%") and :564 (the HUDFIT-2026-11-03 selection fit), each calling fitBounds([lats], [lons], 0, 0.1). The page turns that into pixels at vec_spatial.js:249-250:

var px = (pad && pad > 0) ? Math.round(Math.min(c.clientWidth, c.clientHeight) * pad) : 0;
map.fitBounds([[w, s], [e, n]], { padding: px, maxZoom: 18 - GT_ZOFF, duration: 0 });

So 0.1 on each side leaves the group the middle 80%. With riders strung along the direction of travel, 10% beyond the lead cart is not enough ground to see what is coming — which is the complaint.

fix — pad 0.1 → 0.15 at BOTH call sites (:547 and :564), giving the middle 70% with 15% clear at each end. Update the two comments; "the middle 80%" becomes wrong the moment the number changes, and a stale comment is what cost us C28-26351 today.

⚠ TWO THINGS TO KNOW BEFORE PICKING THE NUMBER.

  • The pad is scaled by the SHORTER side — Math.min(clientWidth, clientHeight). In landscape, the riding mode, that is the height. So 0.15 yields 70% of the height but a larger share of the width, because the same pixel padding is a smaller fraction of a wider viewport. If "70% of the map" means 70% in both directions, the padding has to be computed per axis, not from the minimum.
  • "Shows trail ahead" and "stays centered" pull in different directions. Symmetric padding keeps the group centred with equal room fore and aft. Genuinely favouring the ground ahead means asymmetric padding — MapLibre's padding accepts {top, bottom, left, right}, so more room at the top is available once "My dir" holds the heading up (C28-26354). Fred asked for centred at 70%, so that is what this card specifies; the asymmetric version is a later choice, not a correction.

⚠ DO NOT change the unpadded call sites. :771, :1081, :2304 and :2983 call fitBounds with no pad argument, so px = 0 and the box fills the map. That is correct for restoring a saved viewport or a stored bbox, where the bounds are the intended view.

⛔⛔ THE SDK TRAP THAT WOULD HAVE BRICKED A RADIO (LORAWRITE-2026-11-20)

The SDK's setLoraConfig / setPositionConfig helpers must not be used for a partial update. Their initial is Config.X.Builder().build() — a FRESH EMPTY SECTION — so whatever the block builds is what gets sent. Setting two fields would reset every other field in that section to its proto default, LoRa region among them, and an unset region means the radio will not transmit legally. A first version of our code did exactly that; reading the helper body is what caught it.

Correct form, and the comment is in the file so it is not re-introduced: getConfig(section) → newBuilder() on what the RADIO holds → set only the managed fields → setConfig.

⛔ TWO GENERATIONS OF THE SAME PROTO (PROTOGEN-2026-11-20)

The SDK's published org.meshtastic:protobufs is a Wire javaInterop build — Builders, no copy(). Our own core/proto is the opposite: copy() exists and newBuilder() THROWS. So iosMain code against the SDK uses x.newBuilder().also{}.build() and commonMain/Android uses x.copy(...). The same expression cannot be shared between them. This is a permanent property of the two dependency sets, not a transition state.
