0 · THE GOVERNING RULE — OPEN PAYLOADS, PRIVATE PROCESSES (Fred 10-02)

Fred: "Every payload and packet handed off between device and services must be open source and then hidden by a process."

  • Open: every payload and packet crossing between a device and a service — the ride package, the config doc, TAK messages, mapLoads, the service contract's plain data — is a published, open format.
  • Private: the work done on it — the planner, the trail model, the corridor method, the configurator — runs inside a process (a plugin, or GroupTrack's 3.0 server) and is not part of the format.
  • This is R2 (plain data) raised to a product rule: what crosses is open; what computes is behind the door.

1 · Why — Fred's decisions, 10-02

  • iPad: GroupTrack stays standalone; a vanilla Meshtastic install + an open-source GroupTrack plugin coordinates the hand-off. Configuration is handed off to Meshtastic ("a clean break").
  • Android: separation stays minimal — one install; the API is built in the same app now and can be separated later; the implementation calls today's proven code, never replaces it. Never rebase Android on experimental mesh code.
  • Shape: "one install, two unaware implementations and a service layer between them." The plugin is a mesh/IP TAK messaging plugin.
  • The line: check-in, radio connect, role swapping, the broadcast frequency of payloads and receiving vanilla TAK-aware packets are services; applying our rules to that data is a GroupTrack function.
  • TAK is fundamental to the process: message formats and exchanges are GroupTrack's; GroupTrack requests frequency and method; the mesh/IP layer implements them — two layers.
  • The config doc requests what; the service decides how. Processes and data are independent of the implementation — don't wait for new hardware (Nathan's): it is a transport behind the wall; the data contract is revised additively or a service is added.
  • Licensing: the GPL fork makes the whole Android app open source — fine now; separation for scale (~40,000) is an open decision; building to this contract keeps that path open (section 11).

THE DIVIDING TEST for any feature: getting something to or from a radio or a network → a Layer 2 service. Deciding what the data means for the group, or what is said and when → Layer 1, GroupTrack.

3 · The three separation rules — applied to every service

RuleWhat it meansHow it is enforced
R1 · ONLY DOORLayer 1 reaches a transport only through the contract. No Meshtastic (or any transport) type, call, import or UI in Layer 1. No if (mesh) / if (ip) in GroupTrack code — behaviour differences come from capabilities().Gradle modules: Layer 1 + contract in :grouptrack-tak; implementations in their own modules; Layer 1 has no dependency on them or on Meshtastic → a violation does not compile.
R2 · PLAIN DATA, NO SHARED STATEEverything crossing is GroupTrack's own simple data: strings, numbers, enums, the config doc as JSON, result types. No transport objects, no live handles, nothing that works only in one process. No global read by both sides — each side owns its state; the other sees it only through a call's parameters or replies (e.g. the callsign and role are passed INTO deliver/setReporting, never read by the service from GroupTrack's check-in).The contract package contains only data classes/enums/interfaces of its own; review check: every parameter and return type is defined in :grouptrack-tak or is a Kotlin primitive/collection/JSON.
R3 · EXPECT FAILUREThe other side may be asleep, absent or unable. Every call returns a result that can say failed (why) or not supported; long calls are cancellable; nothing blocks forever (the 10-02 stranded-import lesson).Every call returns a sealed result; every implementation has a timeout; the IP stub answers every call — so the app is tested running with no mesh present.

⛔ NO CONVERGENCE FIXES (Fred 10-02): a fix is made inside an implementation or to the contract (additively) — never by reaching around the door, passing a transport object through "just this once", or branching on the transport in Layer 1. A fix that would need any of those means the contract is missing something: add it to the contract, give every implementation an answer (even not supported), and record it here.

Review checklist for every change touching this layer: (1) does Layer 1 still compile without any transport module? (2) is every new type plain and defined in the contract? (3) does every new call have a failure and a not-supported answer, and does the IP stub implement it? (4) does Layer 1 branch on the transport anywhere? (must be no) (5) is the change recorded in this document?

8 · Modules and build sequence

Modules: :grouptrack-tak (Layer 1 types + the contract) · :grouptrack-mesh (Android mesh implementation; may depend on Meshtastic) · :grouptrack-ip (stub) · the app (Layer 1 logic, depends on :grouptrack-tak only for transport). Rule: nothing in Layer 1 depends on :grouptrack-mesh, :grouptrack-ip or Meshtastic.
  1. Modules + contract — compile, nothing calls them.
  2. Mesh implementation — delegating to today's code only.
  3. IP stub — answers all seventeen.
  4. Call sites move one screen at a time, each tested on Droid 2; riders see no change.
  5. Retire the old menu.
  6. The no-mesh test: run the app on the IP stub alone — planning, ride map, check-in all behave (Ride Map with "no radio").
  7. Later: the iPad plugin (Meshtastic iOS TAK service + config hand-off format) and Nathan's hardware as implementations.

9 · Change policy — new hardware, new needs

  • Additive only: new fields in the config doc (a new section) and in plain-data results; new calls with a not supported answer in every implementation.
  • A new device = a new implementation of the same contract, plus a row in the capability matrix.
  • Never a transport-specific branch in Layer 1 (R1); never a transport object across the door (R2).

10 · Test plan

  • Each service on device (Droid 1/2): connect, list, forget, reconnect; preview/apply/verify; saved configs; reporting frequency; deliver/receive TAK; check-in; END.
  • The no-mesh run on the IP stub (section 8, step 6).
  • The full ride flow on mesh — unchanged for riders (field test with real distance waits for January in Utah).
  • Build check: Layer 1 compiles with the transport modules removed.

11 · Licensing paths (not legal advice — confirm with a lawyer before scale)

  • Today: GroupTrack Android is a GPL-3 fork → the whole app is GPL; keep the source public and Meshtastic's notices. In-app separation does not change that.
  • Path 1: stay open source; paid value on the 3.0 servers (not distributed → not GPL-bound).
  • Path 2: separate for real — GroupTrack becomes its own app beside a vanilla Meshtastic install (as on the iPad); this contract is step 1 of that. Released versions stay GPL.
  • iPad: GroupTrack's own code + the open-source plugin built from open standards (TAK, Meshtastic's published config file/share link) → permissive licence possible; if it ever needs Meshtastic source it becomes GPL and runs as a separate component.

12 · Rejected — and why

  • Rebasing Android on the Meshtastic KMP SDK (0.1.0): experimental under a working app (Fred: never).
  • Forking Meshtastic-Apple: Swift, a second upstream, GPL/App Store conflict for a third-party fork.
  • A separate Android plugin install now: two apps to keep alive, no engineering gain; legally no change while GroupTrack is the fork.
  • Waiting for Nathan's hardware: it is a transport behind the wall; processes and data are known now.
  • TAK message building inside a transport: TAK is Layer 1 — both transports carry the same messages.
  • Single fixes that reach around the door: they re-converge the layers (section 3).

15 · Parity is proven by tests

A contract test suite states each service's required behaviour (results, failure answers, not-supported answers, timeouts). Both implementations must pass the same suite — Android on Droid 2, Apple on a test iPad. Passing it is what "the same services" means; shared modules are optional.

16 · Feasibility spikes — prove the end state before building

  1. iPad connects to a Meshtastic radio and reads its config (Bluetooth + protocol).
  2. iPad writes a config and verifies it (C9).
  3. iPad sends and receives a TAK report with an Android GroupTrack on the same channel (D12/D14, cross-platform tracking).
  4. The link holds with the screen off for 30+ minutes (background).
  5. Two apps exchange a message through an App Group (Personal ↔ plugin).
  6. One GroupTrack panel runs under Compose Multiplatform; a map page runs in WKWebView with its bridge (look and feel).
All six pass → build both platforms' hand-offs and services together against one contract and one test suite. One fails → that service changes shape in the contract first, before anything depends on it.

17 · iPad product structure and look-and-feel

  • GroupTrack Personal — the base app for every rider: both maps, trails, routes, Route+ and the planner, ★ Create a Ride, send/open rides, offline maps, record your track. GroupTrack's own code (Layer 1), no Meshtastic code.
  • Group Comm plugin (Fred's name) — our headless, open-source fork of Meshtastic's radio services (no Meshtastic menus or screens): pairing, setup, check-in config, roles, TAK. On iPad a plugin is a second app from the same developer, linked through an App Group (keeps Personal's licence separate) — or built into one app (then the whole app is GPL). Android ends up the same way: the fork headless, GroupTrack drawing every screen (retire the scanner screen, RADIO SETTINGS and the MESHTASTIC SIDE MENU at the point of contact).
  • Look and feel as close to Android as technically possible: maps and docs identical (same files); panels near-identical (Compose Multiplatform); logic identical (shared). Differs only where iOS decides: system permission prompts, back navigation, share sheet/file picker, background rules.
  • Single-install option (plugin built in, all GPL) remains available under licensing path 1.

21 · Open formats — the ride package and mapLoads

Fred: "Our JSONs are clean, platform-independent hand-offs of ride-related data for GroupTrack and possibly ATAK. The more open, the better the product and the plugin positioning." And: "We will publish a standard API with map-load info, passed as JSON from our payload."

  • Publish the spec (permissive licence): the ride package and the config doc — fields, units, required vs optional; sample files and a validator.
  • Versioned, additive only (formatVersion): new fields may appear; existing ones never change meaning.
  • Built on existing standards: GPX (route, track, waypoints), TAK/CoT (messages), Meshtastic channel URL (network); GroupTrack adds the bundle (date and time, trailhead, notes, mapLoads).
  • The format is open; the data is not always. A private ride carries its network key — the invite stays the secure carrier, sent only to invited riders.
  • GroupTrack shares rides, not trails (Fred 10-02): route descriptions, distances, trail names and features — produced works under OpenStreetMap's licence. The trail database is not distributed → no share-alike. Attribution in every ride package and export: "© OpenStreetMap contributors".
