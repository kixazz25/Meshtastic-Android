2.6h — THE IMPORT RELEASE

2026-09-09 · restored and redefined · not for the first public release

⛔ ONE SUBJECT: the import is too slow and too Utah-only

Fred, 09-09: "we will not rush something this big into the first public release." Early access ships on what exists today. This is what follows it.

Measured on Droid 2, 09-09, Utah, end to end: 1,762 seconds. Roughly 20 minutes of base import plus 10 for rider trails — and the rider-trail half only applies to someone who has imported their own tracks, so a NEW rider sees about 20.

⚠ THAT ~20 MINUTES IS THE BIGGEST INSTALL RISK IN THE PRODUCT. It is what the store listing and every Facebook post has to warn about.

⛔ THE FALSE START, AND WHY IT FAILED

EXTRACTORDER-2026-09-09 moved classifyRow above decodeLine so geometry was only decoded for rows that survived. Sound reasoning, no measurable gain: 792s before, 868s after.

⭐ THE GEOMETRY DECODE WAS NEVER THE COST. It is 425,000 individual SQLite lookups against osm_way_tags, one per row. Moving them earlier does not make them fewer. ⚠ I measured what could be SKIPPED and assumed it was what was EXPENSIVE. Those are not the same thing, and the profile should have come first.

⚠ DECIDE: the reorder is harmless and correct but buys nothing. It is in the early-access AAB. Keep or revert.

⭐ THE ACTUAL FIX

Ask the tag table ONCE which ids can never be rideable, hold them in a HashSet, and let the extract loop skip them with a membership test. ~280,000 lookups become one indexed query.

⛔ AN EXCLUDE LIST, NOT A KEEP LIST. Anything the query does not understand stays in and is classified properly. A keep list silently drops whatever the rules learn to handle next.

⛔ AND ONLY THE ROAD-CLASS GROUP IS SAFE TO SKIP. The legally-shut rows — access=private, motor_vehicle=no — are KEPT by the classifier and labelled, so a rider can see why a trail is not offered. Excluding those would change what lands.

⚠ Every exclusion mirrors a rule in OsmTrailClassifier. If the classifier changes and the query does not, ground is lost silently. The two must move together, and the safety checks in prefilter_check_2026-09-09.py are what proves it: unclassified must never be excluded (it is in on shape alone), and no row rescued by ohv, atv, motor_vehicle, motorcar or four_wd_only may be caught.

2 · Preprocess the downloads

Fred, 09-09: "the 10 minutes it takes to process the trails before step 7 will have all the data here for step 7." Fetch and tag ahead of the extract so step 7 opens with everything in place.

⛔ AN AREA DOWNLOAD MAY SPAN SEVERAL STATES

A state download is one PBF and one GeoPackage. An area download is N of each — Bar 10 crosses into Arizona, and the Nevada corner is right there. So this is not one job, it is a job per state, merging into one tag table.

⚠ The merge must be idempotent. A rider who has Utah and then downloads an area crossing into Arizona must not refetch Utah. osm_way_tags keyed on osm_id handles it — OSM ids are globally unique — but only if the table PERSISTS between downloads rather than being rebuilt.

🔴 OPEN, AND IT GATES EVERYTHING BELOW: does osm_way_tags survive between imports today, or is it dropped and rebuilt? If it is rebuilt, a second state download already pays the full tag cost again, and the ledger is meaningless until that changes.

3 · The per-state ledger

Fred, 09-09: "nounce the state selection list against the preprocessing successful state and remove them from eval."

Before preprocessing, take the states the download needs, subtract those already recorded done, fetch and tag only what is left.

⛔ RECORDED ON SUCCESS, NEVER ON START

A state marked done after a half-finished tag pass leaves a partial table nothing ever revisits. ⚠ That is the shape of the 09-07 marker problem — clearing two of three left the third standing down silently — and of clearTrailsOnce, which writes its marker AFTER the clear precisely so a crash retries.

⚠ AND IT MUST KNOW WHEN TO INVALIDATE

Geofabrik refreshes their extracts. Seen 09-09: 425,218 → 425,267 rows between two runs a day apart. A state done six months ago is stale. Store the date alongside the state so the policy can be decided later without redoing the structure.

4 · Resume an unfinished download

Fred, 09-09: "a start for a failed process at that process step ... using the failure at step as the pickup point."

Per state, the steps are: fetch PBF → build tag rows → prefilter → fetch GeoPackage → extract. The ledger records which one it died at; the restart re-enters there.

⛔ A STEP IS DONE ONLY WHEN ITS OUTPUT IS COMPLETE AND VERIFIED

A partly-written step RESTARTS. Only a verified one is skipped.

  • Files are easy. A PBF or GeoPackage of the expected size is a stat; a short one is a resume or a refetch.
  • ⚠ The tag pass is not. It is a table, not a file, and row count alone does not prove it finished — it proves it got somewhere. ⭐ SIMPLEST SAFE RULE: a tag pass that did not finish is redone from scratch. Minutes, not the twenty.

Where the resume check runs

⛔ NOT in StartupHousekeeping.run() — it checks its marker first and returns, so anything inside fires only on launches that clear and reload.

⭐ everyLaunch(ctx), after the authority gate resolves. That is the ungated pass built 09-08, and it already runs where shared storage is available.

⚠ ITS RULES APPLY: cheap, idempotent, non-destructive, never throws. A resume check that finds nothing pending runs on every launch forever, so it must cost almost nothing.

🔴 TWO THINGS TO DECIDE FIRST

  • Resume automatically, or ask? A 317 MB download restarting silently on mobile data is a one-star. Prompting is safer; automatic is smoother on wifi.
  • What counts as unfinished? A PBF at 90% is resumable. A tag pass that died mid-write is not. The ledger has to record which.

⭐ This connects to the existing checklist item — crashed-import restart from the manifest. Same problem at the stage level, and step 8 becoming a tracked stage on 09-08 was its prerequisite.

5 · Fifty-state land ownership

This is what makes the app Utah-only in practice. Only Utah has the ownership polygon layer, so land_status is null everywhere else and the private filter cannot work.

A rider in Colorado installs, waits twenty minutes, and gets trails with no ownership — which is a bad review and the honest reason the store listing has to name which states have good coverage.

⚠ CARRIED FROM THE EXISTING 2.6h LIST: a layer that lists PUBLIC land positively INVERTS the test. Utah's layer answers "who owns this"; a layer that answers "this is public" means absence is not private. Getting that backwards would mark public land private across a whole state.

⭐ And allPrivate() already samples every half mile plus both ends, with any public segment winning — so the sampling is settled. What is missing is the data source per state.

What this closes

Fred, 09-09: "that closes the door on trail accuracy or loading issues."

  • Loading — the prefilter and preprocessing cut the base import; the ledger stops a second state paying the full cost; the resume stops a failed download costing everything.
  • Accuracy — fifty-state ownership makes land_status real outside Utah, which is what the private filter and the router both depend on.
