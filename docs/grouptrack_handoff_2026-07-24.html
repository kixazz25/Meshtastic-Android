🔴 NEW OPEN — refresh never registers as COMPLETE

A map-source refresh job never reaches a completed state. Three consequences, in order of severity:

  • ⚠⚠ Does it hold a concurrency slot? If the entry never leaves a running status, startNextIfAvailable may count it against MAX_CONCURRENT indefinitely. That is a queue-stall mechanism — and "system just sits" is exactly what 07-23 reported. Check this first; it is the difference between a reporting bug and a throughput bug.
  • It starves the ETA. estimateRemaining() reads the last two COMPLETE entries and completedAt is stamped in markComplete. Same failure mode as patch A2 — a value that is never written, presenting as a silent UI absence rather than an error.
  • CLEAR cannot clear it — CLEAR means COMPLETE+FAILED+CANCELLED, so a non-terminal job is unclearable from the panel and accumulates.

Start here: grep -n "markComplete" app/src/main/java/com/geeksville/mesh/convoy/*.kt, then read ConvoyDownloadWorker's refresh branch end to end — does it return Result.success() without notifying the queue, or take a different terminal path?

⭐ Check ConvoyCorridorWorker in the same pass. The corridor worker deliberately duplicates the completion plumbing rather than sharing it — an accepted trade at design time. This bug is that trade coming due: if refresh can miss markComplete, so can corridor, independently. Confirming corridor stamps completion is a five-minute read that could save an evening of waiting on an ETA that was never going to appear.
