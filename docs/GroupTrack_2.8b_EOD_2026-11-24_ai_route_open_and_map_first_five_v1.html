private fun scoreSet(ks: List<Long>, poiAt: Map<Long, List<Poi>>): Double {
    val seen = HashSet<String>(); val byClass = HashMap<String, Int>(); var v = 0.0
    for (k in ks) for (p in poiAt[k] ?: emptyList()) {
        if (!seen.add(p.name)) continue
        val n = (byClass[p.fclass] ?: 0) + 1
        byClass[p.fclass] = n
        val base = if (p.fclass == USERPIN) USERPIN_BASE
            else if (p.fclass in VIEW) 3.0 else if (p.fclass in WATER) 2.0 else 1.0
        v += base / (1.0 + 0.22 * (n - 1))
    }
    return v
}

DIMINISHING RETURNS BY ARRIVAL ORDER. The first viewpoint is worth 3.0, the second 3.0/1.22, the third 3.0/1.44. So the same set of POIs in a different order yields a different number — not a tie, a different score. seen.add(p.name) compounds it: which duplicate survives is also decided by arrival order.

Inside scoreSet the iteration is over ks (a List) and poiAt[k] (a List), so the function is deterministic given its inputs. The non-determinism is in the ORDER OF ks and in the sequences that select candidates.

ONE SUSPECT ELIMINATED, AND IT IS THE RIGHT ONE TO ELIMINATE FIRST

JPQ is shared code — a hand-written priority queue at GtRoute.kt:204, whose header (:36) states it reproduces “java.util.PriorityQueue's own sift-up / sift-down, so equal distances leave in the same order”. Identical on both platforms by construction, so the Dijkstra queue cannot be the cross-platform difference. (Whether the reimplementation is faithful to the JDK is a separate question, and it would affect both platforms equally.)

THE MECHANISM, STATED PLAINLY

HashMap / HashSet iteration order differs between the JVM and Kotlin/Native → the sequence fed to scoreSet differs → the score differs → different routes. The carriers are the sites where an unordered collection is ITERATED rather than merely looked up:

  • :1421 anchorNet = comps.maxByOrNull { it.size }
  • :1962 byComp.values.sortedBy { it.second } — HashMap.values
  • :1995, :2139, :2156 sortedByDescending { scoreSet(…) } — Kotlin's sort is STABLE, so it preserves whatever order the unordered collection handed it

81 unordered collections sit in the search; these are the ones on the scoring path.

⛔ AND A DESIGN QUESTION UNDERNEATH IT — FRED'S CALL, NOT CLAUDE'S

scoreSet discounts by arrival order within a route. So on the same device, one route's POIs traversed in a different order score differently. If the intent is “the third viewpoint adds less than the first”, that is order-count dependent, not order-sequence dependent, and could be computed per class and then discounted — which would be identical on both platforms whatever the iteration order, and arguably more correct on Android too.

TWO POSSIBLE FIXES, and they are not the same work:

  1. Determinise the sequence — sort by a stable key (trail or junction id, ascending) before every iteration of an unordered collection on the scoring path. Keeps today's scoring behaviour exactly, including its order-dependence, and makes the two platforms agree.
  2. Make the score order-independent — count per class, then apply the discount. Changes Android's numbers, so it is a product decision and would need re-certification against 2.7e.

⇒ (1) is the port fix. (2) is a product question. They can be done in that order: determinise first, get the platforms agreeing, then decide separately whether the order-dependence should exist at all. Both are CODE REVISIONS and need approval before anything is written.

WITNESS for (1): same recipe, same trailFilter, same route set in the same order on both devices. Fred's 19:00 run is the before-reading, so the negative witness already exists.

Fred: “the first two tracks are identical. the third has minimal trail and mil[e]age difference. but it is definitely the scoring issue[:] math functions performed in different sequence will provide d[iff]erent results.”

THE SYMPTOM PATTERN IS THE SIGNATURE OF FLOAT ACCUMULATION ORDER. Routes 1 and 2 identical, route 3 differing minimally: clear winners have a margin far larger than any last-bit discrepancy, so they are stable; route 3 was a near-tie that a last-bit score difference flipped. A logic difference would not produce “top two identical, third barely different” — it would diverge everywhere or nowhere.

⇒ SO THERE ARE TWO ORDER EFFECTS IN scoreSet, NOT ONE. The section above described only the first:

effectwhat it produces

⭐ AND IT MEANS DETERMINISING THE SEQUENCE IS NOT ONE OF TWO OPTIONS — IT IS THE NECESSARY FIX. Counting per class fixes (a) but NOT (b) — the summation order would still vary, so near-ties would still flip. The per-class question is a separate product decision ON TOP, never a substitute. The two were presented as alternatives above; that was wrong.

⇒ TOMORROW'S ITEM 2 IS THEREFORE SINGULAR AND BOUNDED: sort by a stable key (trail or junction id, ascending) before every iteration of an unordered collection on the scoring path — :1421, :1962, :1995, :2139, :2156 — and re-run Broken Ridge on both devices expecting the same route set in the same order, route 3 included.
