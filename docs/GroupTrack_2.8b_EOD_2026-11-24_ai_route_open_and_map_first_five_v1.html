⭐⭐⭐ CORRECTION, 18:41 — URLSession IS NOT MISSING, AND THE SIM *CAN* DOWNLOAD

Fred, flagging his own assumption: “I do not know if we can test Internet file download in sim. I am assuming.” Measured: it can, and the code is already there.

GtIosHttp.kt has implemented NSURLSession on iOS since 11-16 (GTIOSHTTP-2026-11-16, 10,350 bytes): a real fetch() over NSURLSessionConfiguration.defaultSessionConfiguration() / NSURLSession.sessionWithConfiguration / dataTaskWithRequest, with documented request and resource timeouts and a deliberate design note REJECTING a shared session (one session serialises its tasks). It provides two services, deliberately not merged because five behaviours differ between their Android originals: IosHttp : GtHttp (:144) and IosMapSpecEnv : GtMapSpecEnv (:185).

AND IT IS WIRED: GtIosEnv.kt:224 — override val http: GtHttp = IosHttp, with the env table at :195 recording it as “HttpURLConnection → NSURLSession”. The trail import’s own Overpass calls already run over it at measured budgets of 60,000 ms and 180,000 ms (GtTrailImport:212/:251/:287), and TileJSON at 6,000 ms (GtMapSpec:117).

⇒ SO THE SIMULATOR CAN DOWNLOAD. It uses the host Mac’s network stack, and the iOS HTTP path exists and is installed. Internet download testing is a stage-one item, not a device-only one.

⛔ THE ACTUAL GAP IS NARROWER AND SPECIFIC: A BYTES FETCH. GtHttp declares exactly one method — fun get(url: String, readTimeoutMs: Int): String? (GtImportEnv.kt:68-71) — text only. AND THE SHAPE IS FRED’S OWN 11-21 RULE: “my gu[ide] [f]o[r] extending the services (like w[e] did for multiple attachment emails) is to build [a] second service for that use case rather the[n] retouching all existing service consumers.” ⇒ a second method beside GtHttp.get, not a change to it — exactly as emailAll was added beside email.

⛔⛔ AND TWO SDK TRAPS ARE WAITING THERE, BOTH RECORDED AS INVISIBLE UNTIL REAL HARDWARE (commit 22a3475fe). These are not speculative — they are known and dated, so the first hardware session should look for them deliberately rather than discover them:

  1. A PARTIAL CONFIG UPDATE SILENTLY RESETS THE REST OF ITS SECTION. The SDK’s setLoraConfig / setPositionConfig helpers start from an EMPTY section (Config.X.Builder().build()), so using them for a partial update resets every other field in that section to its proto default — LoRa region among them, and an unset region means the radio will not transmit legally. Always getConfig → newBuilder() on what the RADIO holds → set only the managed fields → setConfig.
  2. TWO GENERATIONS OF THE SAME PROTO. The SDK’s published org.meshtastic:protobufs is a Wire javaInterop build — Builders, no copy(). Our own core/proto is the opposite: copy() exists and newBuilder() THROWS. So iosMain code against the SDK uses x.newBuilder().also{}.build() and commonMain/Android uses x.copy(…). The same expression cannot be shared.

⚠ HONEST NotSupported on iOS, by platform difference rather than omission: forget() (no unpair API — the rider uses iOS Settings), onBoxWifi (LoRa only), radioName() (Android’s store is in core/data), RadioEntry.paired (iOS does not expose the bonded list). Those are explained divergences, not gaps.

⚠ THE ONE CAVEAT THAT SURVIVES THIS: step 15 certified the ENGINES through harnesses, not the ROWS through the UI. So each row still owes gate 3 — exercised on the sim — even though nothing beneath it is in doubt.

3. METHOD FOR THE TRAIL / CANDIDATE-SET DIFFERENCES BETWEEN THE DEVICES

WHAT WAS MEASURED TODAY: the two devices build identical networks — 24 features, 2,891 trails, 4,218 junctions on both. There is no engine difference and no feature-finding difference.

THE ONLY DELTA: Droid land_status IN ('PUBLIC','PRIVATE') vs iPad IN ('PUBLIC','PRIVATE','RESTRICTED'). A filter-state difference.

THE METHOD, in this order, because each step is meaningless without the one before it:

  1. Set LAND identically on both devices by hand.
  2. Re-run the same build on both: Broken Ridge, 55-80 mi, 12-18 mph (today’s run, so there is a baseline to compare against).
  3. Compare the recipe’s trailFilter BYTE FOR BYTE first. If the predicates differ, nothing downstream is comparable and the route sets must not be looked at yet. This is the gate.
  4. Only then compare the route sets — and if the predicates matched but the routes differ, the cause is OPEN 2 (tie order), not the filter.

⭐ NOTE: OPEN 3 removes this difference at its source. Once the route-build predicate stops reading the display filter, the two devices cannot disagree about the candidate set no matter what is ticked. Hand-matching the filters is the measurement; OPEN 3 is the fix. Do OPEN 3 and this comparison becomes a regression check rather than an investigation.

⛔⛔⛔ THE ONE HAZARD THAT WILL LOOK LIKE A DEFECT ON THE SIM (MARKERDR-2026-11-18)

A seed or restore WITHOUT THE DOTFILES SILENTLY CLEARS EVERY TRAIL. This already happened to the iPad sim: seeding from the Nov 6 Droid 1 capture gave a full database with no dotfiles, so jobSchemaConverge did exactly what it is written to do — DELETE FROM trails + DELETE FROM trail_properties — and cleared the 322 trails then in view. Tracks (130) and waypoints (595) survived, which is what makes it look like a trail bug rather than a seeding artefact. Re-seeded with the marker present: 229,178 trails intact, no clear, no banner.

The gate is GtStartupHousekeeping.SCHEMA_MARKER = ".schema_2026-09-03A", a zero-byte dotfile in the GroupTrack root. Also at risk in the same root: .db_schema_version, .trails_cleared_2026-09-02B, .nomedia.

THE THREE RULES, ALL THREE OR TRAILS ARE LOST SILENTLY:

  1. INSTALL → LAUNCH ONCE → THEN RESTORE. The first launch writes the marker on an empty database, where the clear costs nothing. (Fred: “what that means on the real iPad is we have to install once before downloading and restoring db.”)
  2. COPY OVER THE TOP, NEVER REPLACE THE DIRECTORY. A delete-then-write carries the marker away and the next launch clears the trails again.
  3. FILE BY FILE, WITH A SKIP LOG. Never a single whole-tree copy.

⚠ TO VERIFY BEFORE THE FIRST SIM RESTORE, and currently UNCONFIRMED: gt_sidebyside_v7.sh:159 uses ls -A, so the newer capture tool should include dotfiles. Unrun. Until it is confirmed, treat every capture as dotfile-free and check for .schema_2026-09-03A in the seed before launching. That one check prevents a false trail-loss report.

AND THE VERIFICATION IS ONE-DIRECTIONAL: after a restore the device legitimately holds the baseline PLUS leftovers (“our installs are non destructive and we cannot remove files during our refresh”). Every baseline file must be present and md5-equal; extra files are LISTED, never failed. A symmetric diff fails every time and trains you to ignore it.

4.7 ⛔⛔⛔ THE iPAD CERTIFICATION SEQUENCE — ONE RESTORE, AT THE END (Fred, 18:23)

THE ORDER — a certification sequence, not a setup convenience:

  1. NEW INSTALL. The install is itself a process under test, not a prerequisite to the tests.
  2. IMPORT TRAILS AND WAYPOINTS. The iPad builds its own data.
  3. IMPORT TRACKS, etc. Each import process exercised in turn, so a failure names one process.
  4. THEN, once the processes are certified: RESTORE DROID 2’S DATABASE for the side-by-side test.
  5. INCLUDING A RE-IMPORT OF TRAILS — identical results on all THREE machines (Droid 1, Droid 2, iPad). That re-import is the cross-device certification key, not a data-loading step.

⛔ WHY “ONCE” IS A CONSTRAINT, NOT A PREFERENCE. Restoring earlier destroys the thing being certified: an iPad carrying Droid 2’s database can no longer prove that ITS OWN install and import processes produce the right data — the data is simply someone else’s. So the restore comes after process certification, and it happens once.

⇒ This corrects 4.6 above where it reads as “the sim carries new install through DR restore.” That span is true of the SIM and of the Droids. The iPad is restored exactly once, at step 4. The disaster-recovery record describes the baseline as “a restore point used repeatedly” — true for the Droids and the sim, not for the iPad.

⇒ And it sharpens the stage split: the SIM certifies what CONSUMES data; the iPAD certifies what ADMITS it (the 11-18 data-ingress cut). Steps 1-3 are exactly the admitting side, which is why they cannot run on the simulator — and why the sim work is not a rehearsal for them but a different, parallel certification.

⚠ AND THE MARKERDR RULES IN 4.6 APPLY TO STEP 4 IN PARTICULAR, because it is a single irreversible shot: install → launch once → then restore, copy over the top, file by file with a skip log. A step-4 restore that carries off .schema_2026-09-03A clears every trail on the next launch, and with only one restore budgeted there is no second attempt to notice it on.
