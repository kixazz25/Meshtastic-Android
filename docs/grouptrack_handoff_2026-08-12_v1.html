⛔ Two real defects found by reading, not by guessing

The ZOOMSLOT cap had never fired

corridorTiles computed zTop from the slot cap and logged it, then passed zMax to both stampPoint calls. Only stepDeg used the capped value. So topo corridor downloads had been stamping z17/z18 all along while the log claimed z16.

⚠ That made download and delete agree by accident; they now disagree deliberately — capped download, uncapped delete, which is the safe direction.

The funnel asked for tiles that cannot exist

HTTP 400: https://mt3.google.com/vt/lyrs=y&x=-1&y=4&z=4

At z4 the world is sixteen tiles wide and the funnel buffer is ninety degrees of longitude, so lon - buffer ran off the west edge and lon2tile returned −1.

⭐ That is why four unrelated tracks all reported failed=20 — at those zooms the buffer dominates the track completely, so every Utah track produced the same handful of impossible URLs. Identical counts across unrelated tracks was the tell. No coverage was ever missing.

🔴 ROUTE MODE — found, part-fixed, NOT closed

Symptom: route planning disarms on pan and zoom. Points stop dropping AND artifact popups come back.

⭐ Both symptoms are one cause — that is the tap rule working correctly on a flag that was wrongly cleared. __routeMode false means the artifact handlers stop returning early (popups fire) and the map click handler stops forwarding to Android.onMapTap (no vertex lands).

FOUND: a bare window.__routeMode = false; inside the map tap-wiring block in grouptrack_map.html. Guarded by map.__routeTapWired — but that property lives ON THE MAP OBJECT, so a rebuilt map passes the guard and the reset fires again. Removed in 6257587e8.

⚠⚠ STILL DROPS OCCASIONALLY. Fred, after the fix: "seems to be better on pan but still drops out occasionally." There is a second disarm path and it is not identified.

⚠ THE STALE-ASSET PROBLEM — Fred’s morning question

A Samsung device did not reflect the revised HTML after an update.

⛔ CLEARING THE CACHE IS NOT AN AVAILABLE REMEDY ON THIS APP. A cache clear triggers a settings/state restore that comes back WITHOUT all-files authority, and the create-if-missing DB open can then write empty schemas over good data. Same catastrophe class as the 08-01 loss — triggered by something that is harmless on a normal app.

It must be fixed in CODE:

  1. Cache-buster on the asset URL — file:///android_asset/grouptrack_map.html?v=<versionCode>. The query changes every build, so a stale entry cannot be served. ⭐ Self-maintaining, and the one that actually forces it.
  2. setCacheMode(LOAD_NO_CACHE) on the WebView settings. Simpler, but a hint rather than a guarantee for file:// assets.

⭐ Do both. ⚠ And it explains at least some of the 08-11 evening: a device running new Kotlin against old HTML would behave exactly as described and defeat every bisect.

🔧 The tools were broken and nobody was told

⛔⛔ where_used_raw.txt had been generating 24 KB against a 481 KB function universe — for days — and reported success every run.

Cause: step 1 greps a HARDCODED list of about sixty names from the radio and ride era. Nothing from the map work was ever added. Proof: a grep of the generated index found ZERO occurrences of four current map symbols that have plenty of call sites in the source.

⚠ It cost real time. Hunting the route-mode reset, the index that should have listed every writer returned nothing — not because they are unused, but because they were never on the list.

⭐ FIXED, and the fixed index is what solved it: the search set is now DERIVED from function_universe_raw.txt. 24 KB → 2,099,813 bytes, and one grep then eliminated every Kotlin path and left only the JS.

⚠⚠ BUT THE FIX WAS LOST when recommit_docs_v14.sh was restored from a backup. Last night’s run reported 254 call sites — it is back to the old behaviour. Use gen_xrefs.sh for research (all four indexes, no git, nothing that can stall), or re-apply the fix to the recommit script.
