Convoy Download Queues Panel Width Fix
COMPLETED TASK · 2026-07-22 · shipped in Rel 2.6c

The problem

On the Convoy map the DOWNLOAD QUEUES panel rendered broken: the CLEAR DONE button wrapped to ONE LETTER PER LINE down a vertical column, and queued entries fragmented with digits scattered down the right edge. The same panel on the Planning map rendered correctly. Downloads themselves were unaffected — progress, tile counts and controls all worked; this was purely visual.

Discovered while recapturing manual screenshots for 2.6c: the Convoy queues capture was unusable as documentation.

Root cause

The two panels are separate hand-mirrored copies, not a shared component. grep -rn "DOWNLOAD QUEUES" returned two independent render sites, and Convoy's carries the comment "Real download-queue monitor (matches planning "DOWNLOAD QUEUES")" — a duplicate that had drifted from its model.

Both wrap the same inner DownloadQueuePanel composable at identical font sizes. Only the outer Surface modifier differed:

// Convoy  (ConvoyScreen.kt ~1453) - BROKEN
modifier = Modifier
    .align(Alignment.TopEnd)
    .statusBarsPadding()
    .padding(top = 32.dp, end = 8.dp)
    .width(260.dp)

// Planning (ConvoyMapViewerScreen.kt ~814) - CORRECT
modifier = Modifier
    .align(Alignment.Center)
    .padding(16.dp)
    .fillMaxWidth(0.90f)

On the test device (800px wide) a fixed 260dp is roughly ONE THIRD of Planning's 90%-of-screen width. Identical content forced into a third of the space wraps per-character — hence the vertical "CLEAR DONE".

The fix

Bring Convoy's modifier chain in line with Planning's. .statusBarsPadding() and .padding(top=32,end=8) were dropped — they existed only to tuck the panel under the top-right QUEUES button, which is irrelevant once centered.

Decisions + rejected alternatives

  • Centered vs wider-but-still-top-right. Considered keeping TopEnd and merely widening to ~360dp / fillMaxWidth(0.55f) (less map obstruction). REJECTED — Fred asked for parity with Planning, and parity also means the manual screenshot matches across both maps.
  • ⭐ Substituting the Planning screenshot for the Convoy one in the manual. Proposed as a shortcut while the bug was still live. REJECTED: it would depict a screen that does not exist in the app, and would specifically HIDE the bug (a cropped Planning panel lays out correctly). Failure mode: a tester sees mangled text, checks the manual, sees a clean panel, concludes their install is broken → false bug report.
  • Interim honesty. Before the fix was authorized, the BROKEN capture was embedded with a "Known issue (V2.6c)" note directing users to the Planning panel for a clearer view. Once the fix shipped, the image was replaced and the note deleted.
  • Freeze question. ConvoyScreen.kt is the FROZEN file. Proceeded because the change is a Compose layout attribute in a self-contained panel — nothing near the WebView, JS bridge, Leaflet, self-saving setView, or MapStateStore (the layered process the freeze protects). Verified by grep that Convoy's panel is a separate copy, so Planning could not regress.

Implementation

Patch script patch_convoy_queues_width_2026-07-22.py, per standing conventions: uniquely-dated, written to /c/Users/kixaz/Downloads/, dry-run by default (--apply to write), count==1 anchor guard with clean abort, idempotent marker guard, CRLF detection and preservation, timestamped .bak. The anchor was validated against the exact source text before delivery.

Dry-run: 1 anchor match, CRLF detected. Applied clean. assembleGoogleRelease BUILD SUCCESSFUL in 11m 03s — no imports needed (Alignment.Center, padding, fillMaxWidth all already used in the file).

Verification

Installed to Droid 2 and reopened Convoy → QUEUES. Confirmed: panel centered at 90% width; CLEAR DONE reads horizontally; HOLD / CANCEL ALL / CLEAR DONE in a proper row; queued entries intact with tile counts aligned; layout matches Planning. Recaptured and embedded in the 2.6c manual, replacing the broken interim image.

Lessons

  • Hand-mirrored duplicates drift. A comment saying "matches planning" documented an intention, not a guarantee. Where two screens must look alike, share the component or expect divergence.
  • Grep before assuming a component is shared. Had these been one component, changing the width would have regressed Planning; two greps established independence before any edit.
  • The freeze is about a layer, not a file. Compose layout attributes in ConvoyScreen.kt are safely changeable; the map/JS/Leaflet/state-store tangle is not.
  • Ship the honest picture. Documenting a known issue accurately beat depicting a screen that doesn't exist — and the note cost nothing to remove once fixed.
