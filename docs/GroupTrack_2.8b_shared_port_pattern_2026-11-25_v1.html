3 · SCREENS — THE RELOCATION RULES

  • Same package as the Android original (com.geeksville.mesh.convoy / .grouptrack under commonMain) so no call site's imports change.
  • A distinct Gt… name for the shared screen (GtDownloadQueuePanel); the Android original keeps its NAME and SIGNATURE as the HOST ADAPTER, so every Android caller is untouched.
  • Callbacks and values, not a new interface — the GtAlertSettingsPanel template: "this panel raises callbacks and does not own dialogs." Fred chose option 2 (11:50). Callbacks thread into the private row composables.
  • CODE RULE 1: no defaults on the shared screen's parameters — each host wires every one; the patch script checks all are passed (row 1: 16/16).
  • Body unchanged. Only the platform lines are swapped. Pre-existing behaviour is carried faithfully, bugs included (e.g. HOLD does not recompose until the queue changes, on both).
  • A host-drawn piece is a @Composable slot (panel: @Composable () -> Unit) so its callbacks are wired once, in the host.

5 · PANELS — THE CHROME STANDARD

  • Every frame is GtPanel (GtPanel.kt:216): title, HELP (by help id), ISSUE, ✕; MOVE and HIDE when stays = true. Fred 12:05 chose this over keeping Android's older inline frame, so Android's queue frame gained ISSUE / MOVE / HIDE.
  • The frame is a shared composable too (GtDownloadQueueMonitor) — both hosts call it; neither re-builds it.
  • Chrome SLOTS (GtPanelChrome: QueueSummary, DownloadSettingsPanel, …) are implemented per host, and each implementation CALLS THE SHARED SCREEN. A "not attached yet" text in a slot is the marker of an unported row.
  • A chrome object that needs screen state gets a nullable slot set by the screen — the opener pattern, CODE RULE 1 reason stated (the chrome is an object and outlives the screen). Row 1: GtPanelChromeIos.queue, set where dlQueue is built. Unset = log and say so on screen (SKIPLOUD), never blank.

  • No per-host open flag. Row 1's first iPad draft used a local queuesOpen; withdrawn for the launcher. Android still has its local queuesOpen (four openers) — see open items.

7 · THE PATCH METHOD — WHAT EACH SCRIPT MUST DO

  • Dated name, never reused (a fix is _v2, the old one renamed _DO_NOT_RUN_<reason>). First output line names every creation. One file, or say why not (row 1 had two two-file patches, both stated up front).
  • Dry run by default; Claude runs it against the live repo from the container BEFORE Fred is given the apply command.
  • Anchors must match exactly once; check the PREMISE (the file is the one expected, the shared target exists, the previous patch is applied); replace a block by VERIFIED LINE RANGE (first line, last line, the line after, markers inside).
  • Post-checks count, they do not test absence across a whole file — a phrase that also sits in a comment makes "absent" fail (5b v1).
  • Backup first; on a failed verify restore; a two-file patch restores both.
  • ⛔ THE ESCAPE TRAP (twice on 11-25): a \u25BC-style escape that Claude writes into a file is saved as the GLYPH, so a relocation stops being faithful (4a v1) and an anchor stops matching (4c v1). Build escapes from characters (chr(92) + 'u203a') and self-test that the file holds the escape text, not the glyph.
  • After a fast build (~7-8 s), prove it compiled: the class from compileGoogleDebugKotlin must be newer than the changed source (app/build/intermediates/built_in_kotlinc/googleDebug/compileGoogleDebugKotlin/classes/…). Done after 3, 4b, 4c, 5b — all real.
