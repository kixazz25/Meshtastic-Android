1 · The day in one line

We built the automated tile refresh, ran it end to end, and the run told us the design was wrong.

The corridor delete works — 617,255 tiles removed across 88 tracks on Droid 2, verified against a prediction that differed only by a change Fred made in between. But watching it run surfaced the arithmetic that kills the design it belongs to: a full store refresh at real scale is 50-60 GB and days of downloading. The redesign that came out of that is in 00-MIGRATION-V2 and it is smaller, additive, and has no irreversible step.

4 · The design conclusion

"This is a trail riding decision. Google maps is available ONLINE in either map as soon as the change in map sources is made."

⛔ The migration concerns OFFLINE STORED TILES ONLY. Online rendering switches instantly.

"Refreshing 50-60 GB of data is just not an option."

Which is why mandatory-delete-then-rebuild cannot be offered. Full detail in 00-MIGRATION-V2; the short version:

  • Delete becomes OPTIONAL everywhere, default off. Replace overwrites in place, so the delete is only for reclaiming space. With it off the operation is ADDITIVE — no point of no return, no permanent gate.
  • Areas stay on original map data until refreshed. Nothing blank, nothing deleted; only Esri\u2019s label overlays are lost.
  • Option 2 = corridors and areas, each optional. Option 3 = leave maps in place, with optional immediate corridor refresh. Option 1 = clear and start over, for anyone uncertain.
  • ⭐ The scan\u2019s real job is helping the user choose, not verifying the delete.

6 · Method notes worth keeping

  • ⚠⚠ RENAMING A PATCH RENAMES THE MARKERS IT LEAVES BEHIND. New failure mode from the never-reuse-a-name rule: patch 07e was re-issued as 07f, and patch 07g then anchored on the 07E marker that no longer existed. The guard caught it and refused the write.
  • ⛔ A LOCAL DECLARED INSIDE if (showDownloadPanel) CEASES TO EXIST WHEN THE PANEL CLOSES — and was also 300 lines below its use. TWO faults in one placement, ~36 cascade errors from one root. Same trap as the 08-01 webViewRef error.
  • ⭐ PATCH GUARDS SHOULD CHECK ORDERING, NOT JUST PRESENCE. The fix patch added "declaration index must precede use index" and "each var declared exactly once" — both derived, both would have caught the above at patch time instead of after a 2m13s build.
  • ⭐ FILTER THE FILE, NOT THE STREAM (re-learned). ./gradlew ... | grep buffers and the terminal looks identical whether the build is working or wedged. Redirect to a file and tail it from a second window.
  • ⚠ A CHAIN OF &&-LINKED GREPS DIES ON THE FIRST EMPTY RESULT — everything after it silently never runs, and reads as "the code does not exist". Use semicolons.
  • ⚠ git diff --stat DOES NOT SHOW NEW FILES — an untracked file looks like a failed patch. Check git status or grep the file directly.
  • ⭐⭐ THE DESIGN GOT SMALLER EVERY TIME FRED ASKED WHAT WE WERE TRYING TO ACCOMPLISH. Started as a new worker file plus an atomic four-part queue patch with a deliberate build-breaking window; ended as one function calling four existing production components in order. The atomic patch disappeared entirely because deletes never enter the queue.
  • ⚠ I OFFERED TO ROLL BACK WHEN THE TREE WENT RED. Fred said continue; the errors were one misplaced declaration block. The rollback would have cost the evening.
  • ⚠ I ASSERTED THINGS ABOUT THE PANEL FROM MEMORY AND WAS WRONG TWICE (hold-state invisible; slot-is-not-the-store). Read before claiming.
