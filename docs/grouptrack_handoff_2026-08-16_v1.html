⛔⛔ The headline — a plain reinstall was deleting both databases

Root cause

The v3 delete-gate in SpatialDbManager.init() was gated on db_schema_marker in SharedPreferences (app-private). The databases it deletes live in Documents/GroupTrack/ (public). An uninstall wipes the marker and not the data, so every reinstall read marker was 0, concluded "pre-v3", and deleted both files.

08:15:02.463  DB v3 migration: delete grouptrack_spatial.db = true
08:15:02.503  DB v3 migration: delete grouptrack_data.db = true
08:15:02.514  DB v3 migration: spatial-clean=true extension-clean=true (marker was 0)
08:15:02.978  Spatial DB: 0 trails, 0 tracks, 0 waypoints, 0 routes

⭐ Three wipes in twelve hours traced to this one defect — 08-15 23:22, 08-16 07:10, 08-16 08:15. Not a failed open, not an authority problem: the app deliberately deleted the data because it could not tell "never migrated" from "migrated, then reinstalled." The authority canary ran 340 ms BEFORE the deletion and passed.

⭐⭐ AutoResyncHost's conviction is WITHDRAWN. Killing it on 08-15 was correct — vestigial startup migration opening the DB pre-authority — but it did not cause these wipes, and yesterday's EOD credited it with the whole thing.

⚠ This is the inverted form of the guard specced after 08-01: marker absent + external DB present = fresh install over existing data → STOP. The marker was designed as a stop condition and implemented as a delete trigger.

The fix — two commits, two independent halves

CommitWhat
233e61e50Marker moves to a FILE, .db_schema_version, beside the DBs so its lifetime matches theirs. Read order file → legacy prefs → 0 (the prefs fallback carries existing installs across; without it the fix would itself have wiped every current install once). Plus a row-count guard: populated DBs mean already-migrated whatever the marker says → stamp and skip. An unreadable count returns −1 and is treated as populated — refuse to delete on uncertainty.
c503b3247Stamp-if-missing. Caught on device, not in review: an install whose marker came from legacy prefs reached neither writing branch, so the file was never laid down and the install stayed protected by app-private state — the exact mismatch being fixed.

Certification (Droid 2)

  • Install over live data → marker file appears containing 3, sizes unchanged.
  • Uninstall → marker survives in Documents/, prefs gone with the package.
  • Reinstall → no migration block in the log at all, and Spatial DB: 152200 trails, 88 tracks, 559 waypoints. Byte-identical sizes.

⭐ That proves the marker path, not the row guard catching a miss — belt and braces verified independently.

⚠⚠ The diagnosis correction — record this, not the first story

Grant all-files, return, screen stayed declined; force-close then passed immediately. Claude's theory was a settle race and built a 5×400 ms retry loop on it.

The logs disproved it the moment they existed: every retry read realStorage=false through attempt 4, and the successful grant passed on attempt 0. The retries never rescued a grant.

Real defect: LifecycleResumeEffect evaluated once and latched StorageDeclined with nothing left to re-evaluate. Latched state, not a timing race. The fix that mattered was re-evaluating on resume. ⭐ A fix built on an unverified theory can pass its test for a reason unrelated to the theory — the instrumentation added in the same patch is the only reason this did not ship recorded as a race that never existed.

Also fixed: Exit was a dead button — popBackStack() from the nav START destination has nothing to pop and no-ops. Now finishes the activity.

New: gate logging, tag ConvoyGate — adb -s <serial> logcat -s ConvoyGate. ⚠ MediaProvider "Failed to update quota type for .authority_probe" is noise, present on clean passes too.

✅ API 36 — the April blocker does not exist

⭐⭐ The all-files toggle does NOT grey out at target 36 on Android 16. Confirmed on device. This kills the whole worst-case branch: no force-off-then-grant, no gated explainer bracketing two OS-settings trips, no double-prompt UX. That question is why this branch exists.

Nothing in Android 16's documented behaviour changes touches MANAGE_EXTERNAL_STORAGE — the API-36 storage changes are photo-picker/selected-media. April's retreat to 35 was far more likely the record-vs-UID divergence than a platform rule.

⚠ Naming, so it stays out of the release notes: Android 16 IS API 36. There is no "Android 16 API level 15." From Aug 31 every update must target 36; API 35 only keeps a published build discoverable.

⚠ Method — what today reinforced

  • The cheaper test passing is not evidence the expensive one will. Clear-cache passed byte-identical and would have been accepted as proof the install work was done. Fred pushed for the uninstall/reinstall anyway — that is the run that found the defect.
  • Capture the log before the buffer rolls. 353,608 lines; the answer was three I/ lines in it. Five-minute diagnosis instead of another evening.
  • A guard and the thing it guards must share a lifetime. App-private state protecting public-storage data. It reads as correct in review because both halves are individually sensible — look for the shape wherever a flag decides whether to touch data that outlives the flag.
  • Instrumentation before theorising, again. The gate emitted nothing, so its decisions had to be inferred from platform quota noise. One log line per evaluation turned the next question into a reading — and immediately disproved the theory a fix had just been built around.
  • cat -A when an anchor spans lines. A sed-derived anchor missed a blank line; the patch aborted at anchor 6 of 6, no write, tree clean. Re-issued as ...16b.py with the rationale in the header rather than reusing the name.
  • Unplug the protected device. Droid 1 was on the bus with an uninstall queued next. Two devices attached means a missing -s errors rather than picking one, so the real exposure was a mistyped serial — still a stop-and-unplug moment on 89K trails with no backup.
