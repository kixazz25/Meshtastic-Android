Communications layer — design v7

2026-09-15 · v7 — CORRECTED: the APP creates the config and the utility applies it (v6 had this backwards). Plus the save/restore boundary — round-trip on one device works on ANY radio; only the cross-device transplant is T1000-E only.
LEVEL 1 of the three-layer separation. Level 2 (group visibility) follows in its own document. Self-contained for a fresh conversation.

⭐⭐⭐ THE PRODUCT IN ONE SENTENCE (GroupTrack, 09-15): "One setup for temporary or permanent network IDs, and joining that net is all a user must do."

The rider sees TWO FIELDS: network name and password. Everything else — Meshtastic channel and PSK, WiFi mesh SSID and key, Nucleus enrollment, IP config, which transport carries what — is invisible, always.

⭐ THIS IS THE ACCEPTANCE TEST FOR THE WHOLE LAYER. If a rider ever has to know which transport they are on, or configure anything twice, level 1 has failed. That is a better test than any code metric because it is the thing the product is for.

⚠ It is also the honest measure of the gap to ATAK. TAK expects a trained operator with a data package. This is closer to joining a wifi network — and that simplification IS the product, which is exactly the market Natak Mesh says it wants to reach and cannot with the TAK model.

⭐⭐⭐ THREE TARGET CUSTOMERS — this is why each goal exists

CustomerHardwareConfig path
1 Existing commitment to mesh hardware Their own radios, any family SELF-CONFIGURED to a distributed spec, per ride. We publish the spec; they apply it.
2 No mesh, small budget T1000-E AUTOMATED FROM THE APP, per ride. The one radio we configure ourselves.
3 Lead riders and club organisations Multiple Nucleus JOIN A WIFI NETWORK FROM THE ANDROID. Enrollment — no radio config at all.

⭐⭐ THE TIERS ARE NOT PARALLEL MARKETS — THEY COMPOSE INTO ONE RIDE. Tier 3 carries the other two: a club with Nucleus nodes provides the bridge that makes tier 1 and tier 2 riders visible to each other. That is the mixed network this whole design exists to serve.

⭐⭐ AND IT SETTLES WHO PAYS. Tier 2 is a $50 entry with no ongoing cost. Tier 3 is the club spending real money on infrastructure that benefits everyone. The revenue is where the budget already is — a club buying infrastructure, not ten individuals each finding $200.

⛔ Why tier 1 gets a spec and not code

Meshtastic is a raw open-source standard and it is still evolving. Chasing config parity across a hardware ecosystem that moves underneath you is a losing job for a solo developer, and it is not what this product is for. Mesh people want the config and they will apply it.

⛔⛔ SUPPORTING A DEVICE AND CONFIGURING A DEVICE ARE DIFFERENT COMMITMENTS. Any Meshtastic radio can participate in a ride — it sends position packets and GroupTrack reads them. What is limited is which devices get CONFIGURED FROM THE APP. ⚠ Record this so it is not relitigated: tier 1 needs no code, and "supporting them properly" with in-app config is the thing not to build.

🔴 DELIVERABLE: the distributed spec. Channel name, PSK derivation, modem preset, hop limit, region — precise enough that a competent Meshtastic user gets it right first time. ⭐⭐ SUPERSEDED IN PART: this is now a SCREEN read from the live ride, not a static document — see "read from the Nucleus, deliver three ways" below. The manual section remains as a fallback.

⛔⛔ AND IT IS NOT JUST CHANNEL NAME AND PSK. THE RIDE DEPENDS ON POSITION PARAMETERS — broadcast interval and distance threshold drive the app. A rider on the right channel with a 60-second interval is not in the same ride as one at 3 seconds, whatever key they share. ⚠ If the spec omits them, a tier-1 rider joins correctly and still behaves wrongly — and that failure looks like our app is broken rather than like a config mismatch.

⭐ WHICH ALSO GIVES TIER 1 A CLEAN SUPPORT BOUNDARY: if the spec was applied, it works; if not, it does not. We publish the spec and we are done. No support for how they applied it.

⚠ The one unsolved piece, and how small it is

Getting a channel name and PSK onto a standalone mesh radio that is NOT a T1000-E, from a device the rider is carrying. The current in-app path works for the T1000-E only.

⭐ It does not block the architecture — layer 1's design is unchanged by how a radio got configured. It blocks the RIDER EXPERIENCE, and only for hardware we do not recommend. The customer model above is what resolves it: tier 1 self-configures, tier 2 is the device we automate, tier 3 never touches radio config.

⛔ WHY THE CURRENT PATH IS T1000-E ONLY — root cause

The method builds a radio config from a SAVED IMAGE OF A T1000-E, injects new values via protobuf, and writes the whole thing back. So the image carries device-specific content — firmware release level, device config, hardware-specific fields — and applying it to a different radio writes a T1000-E's identity onto it.

⚠ NOTE THE SCOPE — it is the TRANSPLANT that is device-bound, not save/restore. Reading a radio's own config and writing it back works on ANY device; see "save/restore already exists" below.

⛔ IT IS A WHOLE-CONFIG RESTORE WEARING THE CLOTHES OF A CONFIG EDIT, and whole-config restores are device-bound by nature. Meshtastic's own docs say the same of --export-config: it is a backup for THAT node. ⭐ It is also the blind write rejected elsewhere in this document, arriving through a different door.

⚠ AND CHANNEL-ONLY IS NOT THE ESCAPE. The obvious fix — use the channel-set mechanism, which carries no device identity — does not work, because the ride also depends on POSITION parameters (broadcast interval, distance threshold). Those are device/position-module config, not channel config. That is precisely why the method had to carry more than channels, so it ended up carrying an image, so it is device-bound.

⭐⭐ WHICH IS THE ARGUMENT FOR STANDARDISING THE HARDWARE, NOT FOR SOLVING IT. Natak's model works because they control the device. Open in-app config to arbitrary radios and you are tracking an ever-changing config surface across hardware you do not own, with results that depend on the skill of whoever holds the radio or on a developer's knowledge of options that keep moving. ⛔ That is the nightmare. The three-customer model is the answer: T1000-E for tier 2, Nucleus for tier 3, a published spec for tier 1. No in-app config for arbitrary devices, ever.

The three layers, for context

LAYER 1 — COMMUNICATIONS (this document). GroupTrack: "the point of contact is the mesh messages being forwarded to a receiver in GroupTrack. This communication layer should support mesh radios AND a standard IP network stack, both of which can contribute nodes to the same group layer."

LAYER 2 — GROUP VISIBILITY. "Identifies all network traffic from IP or mesh sources, assigns unique node IDs, blends IP and mesh devices, tracks GPS locations, and creates a map layer that plots the lead cart's track as well as all other nodes' locations."

LAYER 3 — THE STANDALONE ANDROID APP. Own-device tracking, trails, maps, recording, routing. Works with no radio present. ⛔ Nothing in layer 3 may reference layer 1 or 2 at all, not even to ask whether they exist.

⭐ THE GOVERNING RULE (GroupTrack): "Mesh has to look and function like the IP plugin. Any interaction between radios and GroupTrack belongs in that comms layer." Mesh gets no privileges. If anything above layer 1 knows what a radio is — pairing, connection state, channel config, signal quality — the boundary is in the wrong place.

⭐⭐ LEVEL 1 DELIVERABLE GOALS

G1 — Standard config for LoRa and IP nets, distributed before rides

A network config definition: name, password, and whatever each transport derives from them. Distributed ahead of a ride so a club arrives configured. ⭐ One artifact, several delivery routes — enrollment over the air at the trailhead, an emailed file, a QR code, or a leader-run setup utility. Applying it is ONE code path regardless of how it arrived, which keeps the fallbacks cheap.

⚠ Two groups riding the same area is the case that proves this matters. Same LoRa frequency, same 5.8 GHz band, two convoys. Without distinct identity and keys they see each other's traffic — forty nodes of congestion on a mesh that already saturates at four.

G2 — Network IDs issued, not invented. THREE OWNERS.

OwnerTenure
Club / orgPermanent, reserved. The club's identity — survives leaders coming and going.
Ride leaderPermanent, reserved. Belongs to the PERSON, usable across any club they lead for.
One-time ride keyDeployed per ride, with an expiration date.

Central issue is what makes collision impossible; a locally generated config can never guarantee it.

⭐⭐ EXPIRY IS WHAT MAKES THIS A SERVICE RATHER THAN A GIVEAWAY. Without it a leader draws one key and uses it forever, and the reserved tiers have no value. With it, the reserved tiers ARE the product and the one-time key is genuinely one-time.

⭐ ENFORCEMENT: self-describing, offline. The expiry travels INSIDE the config and the app enforces it — no check-in, no signal needed, which matters because a trailhead has none. Sign it if tamper-evidence is wanted. ⚠ A rider could edit an unsigned one; for a recreational product that is the honest security level.

⭐ ON EXPIRY, DELETE THE SAVED NETWORK (GroupTrack) — it simply stops being available to select, which fits the wifi model exactly. No enforcement mechanism, no error state, no interruption.

⛔ BUT NEVER WHILE IT IS ACTIVE. A key expiring at midnight must not pull the network out from under riders still out on the trail. Remove it on the next launch when it is not the active network. Rule: expiry blocks JOINING, never STAYING JOINED.

⚠ And say so. A network that silently vanishes from the list looks like a bug. One line — "this ride's network has expired" — prevents a support question, and is the natural moment to fall back to the rider's own network.

⭐ LATE JOINERS ARE NOT AN EXPIRY PROBLEM. GroupTrack: "if wifi exists on the leader device he only needs a password to join." The leader's node is broadcasting — a late rider needs the password and nothing else. Nothing to issue, nothing to download, no signal. ⚠ The LoRa side is the part that is not automatic — a bare radio is not listening to the leader's AP. Which is what G3 solves: derive both transports from name + password and "just tell them the password" works for LoRa too.

⭐ A natural home for the paid service — a club registers and holds a permanent network identity; a leader draws one for the day. Fits the V3 backend already built through Phase B.

⛔ BUT IT MUST WORK WITH NO SIGNAL. A trailhead usually has none. So: pre-issued blocks the leader collects while in coverage, and a collision-resistant local fallback (club prefix + random) for the leader who did not plan ahead — which is most of them.

G3 — Two fields for the rider; keys are GENERATED

Network name + password. The password is NOT the key — it derives it. GroupTrack: "I prefer generates it. Hides the complexity."

⭐⭐ AND IT IS WHAT MAKES "JUST TELL THEM THE PASSWORD" WORK ON BOTH TRANSPORTS. A late rider joins the leader's WiFi with a password like any network — but their LoRa radio needs a channel and PSK, and it is not listening to the AP. If both derive from name + password, a rider given those two things is on both transports with nothing transmitted. The derivation was never only about key strength.

⭐⭐⭐ AND THE CHANNEL NAME AND PSK MUST AGREE WITH THE NETWORK NAME AND KEY. One derivation feeds both transports: the rider types name and password, the app derives the WiFi key, derives the channel PSK, applies the channel URL to the radio and enrolls the Nucleus. Two fields in, two devices configured. ⭐ Which makes the ANDROID THE SOURCE of the configuration rather than a conduit for it — nothing has to be fetched, emailed or scanned in the normal case, because the app has the inputs.

⛔⛔ THIS PUTS THE ENTIRE JOIN MECHANISM ON ONE POINT. Two riders on different builds deriving different PSKs from the same password is a silent, total failure. The derivation must be identical everywhere and versioned from day one — see the traps below.

⭐ Two further reasons, and the second matters architecturally: strength (riders pick weak passwords, and a PSK taken verbatim from "ride2026" is a weak PSK), and decoupling — a Meshtastic PSK and a WiFi key have different length and format rules, so deriving both means the rider's input never has to satisfy either.

⛔ TWO TRAPS, both standard and both fatal if missed:

  • Deterministic and identical on every device. Same KDF, same parameters, same salt policy — and the salt is probably the network name, since there is nowhere else to get one. Different keys from the same password means nothing connects.
  • It can never change once riders have joined. Altering the derivation in a later release silently splits a club into old-build and new-build riders who cannot see each other. Version it from day one.

G4 — Joining is wifi-shaped: a saved-networks list, one active

GroupTrack: "This is standard wifi config selection with the exception that we need to apply to Raspberry and mesh radios." ⭐ So no ride lifecycle, no stack, no automatic restore. The rider picks their home network again when they are done, exactly as on a phone. That removes the "explicit end of ride" and "restore after a crash" problems entirely.

⛔ WHAT IS NOT STANDARD IS APPLYING ONE SELECTION TO TWO DEVICES — the Meshtastic radio's channel and the Nucleus's WiFi mesh, different mechanisms on different hardware. That is the layer 1 work: one act of joining, two things configured underneath.

⚠ The failure mode is PARTIAL APPLICATION — the radio takes the new channel, the node does not. The rider is half-joined and it looks like the app is broken. Apply both or neither, and say which failed.

G5 — One interface, two directions, TAKPacket on the wire

Publish my own state; receive other nodes'. ⭐ The payload is TAKPacket and that decision is already made for us — see the wire-format section below.

⛔ But the internal model must NOT become TAKPacket. Parse at the boundary into ConvoyNode, emit at the boundary. Otherwise a tactical vocabulary leaks upward and every future change has to be expressible in a military schema.

G6 — Two implementations at stage 1

Mesh (BLE to a bare radio) and IP (sockets over the Nucleus AP). Both satisfy the same interface. A third — internet/uplink — fits later with no change above the line.

⭐⭐ AND THE SPLIT IS CLEANER THAN "two implementations" SUGGESTS. Natak: the Nucleus "natively transports any IP traffic out to the Wi-Fi mesh... grabs the traffic we decide, converts, compresses and forwards to the Meshtastic radio for transmission. It also handles receiving, decompression and sending to the tablet back across the AP." So on a Nucleus the tablet speaks IP in BOTH directions and may never speak Meshtastic at all — layer 1 there is a single socket implementation. ⚠ The BLE implementation exists only for riders with NO Nucleus. Tier 3 is pure IP; tier 2 is where the app does everything it does today.

🔴 CONFIRM WITH NATAK: does the tablet ever need to speak Meshtastic directly when a Nucleus is present? One sentence from him settles the shape of layer 1.

⚠ The V3 Nucleus has NO BLUETOOTH, so a Nucleus-attached radio is reached over TCP to meshtasticd, not BLE. Two connection paths inside the mesh implementation, neither visible above it.

G7 — Transport identification passed up: IP, mesh, or BOTH

Layer 1 tells layer 2 how each rider is reachable. Derived from what layer 1 actually knows — which connections are live locally, and which transports a given node's packets arrived on. Not inferred upward from payload content.

⭐ "Both" is the interesting value — that is the rider who is bridging. It is also how layer 2 can eventually answer "who is still reachable if we lose the Nucleus", which is a real safety question.

⛔ Layer 2 may DISPLAY transport. Nothing in its logic may BRANCH on it.

G8 — Connection lifecycle owned entirely here

Pairing, connect, drop, reconnect, permissions. Layer 2 never knows a connection exists, let alone that one failed.

G9 — Cadence and airtime budget live here

⭐ Congestion is a TRANSPORT fact, not a product fact. The mesh implementation throttles; the IP implementation does not need to. Layer 2 asks for "my position published" and does not care what that costs.

G10 — Failures reported, never swallowed

A transport that cannot deliver says so. ⛔ This week's lesson made structural — silent nothing is how two days disappeared.

⛔⛔ THE GAP BETWEEN 4 AND 25 IS THE MOST IMPORTANT NUMBER IN THIS DOCUMENT. Likely explanation: flood rebroadcast multiplication. Meshtastic floods — every node that hears a packet rebroadcasts it up to the hop limit. So ten riders is not ten transmissions; it is ten times the relaying nodes in range. Nathan's figure is a bandwidth calculation; ours is observed congestion. ⚠ Put it to him — it affects how he tunes his forwarding module.

⭐⭐ LOWER POWER MULTIPLIES TRAFFIC. A low-power radio reaches fewer nodes directly, so packets need more hops, and every hop is airtime everyone waits through. A high-power node is not just longer range — it is a congestion REDUCER for the whole group.

⭐ GROUPTRACK'S RATIO: one high-power IP/LoRa node per three low-power radios. ⚠ Placement matters as much as count — distributed through the string (lead, middle, sweep) rather than one in four by position in a list.

⚠ TWO SETTINGS IN TENSION: update rate and hop limit. A low hop limit keeps local traffic local — which suits a convoy, where the riders who matter are the ones ahead and behind. But it cuts against the rider who dropped ten miles back, and that is the rider the product exists for.

⛔ CONGESTION IS A PROPERTY OF THE GROUP, NOT OF ONE RADIO. Testing two or three units tells you almost nothing about ten, because rebroadcast multiplication is where it breaks. Needs real riders on real ground — January, in Utah.

⚠ Hardware reality — this may force a device re-evaluation

⛔ AND THE COMMENT ON FIELD 1 IS DECISIVE: "Enable WiFi (disables Bluetooth)." A radio that joins WiFi can no longer be reached over BLE — you would talk to it over TCP instead, which is exactly what the Nucleus does with meshtasticd.

⚠ IT IS HARDWARE-DEPENDENT and the protobuf cannot tell you which. The field exists on every device because it is one shared schema; setting it on a radio with no WiFi silicon does nothing.

⛔ Why a written method is hard: the solution is device-targeted

GroupTrack: "it only works for T1000-Es. That is the problem with writing the method — the solution is targeted, the screen values presented are unique to the device." Config surfaces differ per device family: different fields, different sequences, different reboot behaviour. Writing a path means writing one per family, each needing that hardware in hand to develop and test.

⚠ AND DRIVING THE SCREENS HAS THE SAME PROBLEM IN A DIFFERENT SHAPE. Simulating the manual process — presenting screen titles, controlling values, navigating, waiting for reboot and reconnect — still encodes per-device knowledge, just as a script of screens rather than a set of calls. The matrix does not go away; it moves. ⚠ It also re-exposes the Meshtastic UI surface that MESHSEP-0904 was folding away, and a Meshtastic release that renames or reorders a screen breaks the sequence silently.

⭐⭐⭐ THE MECHANISM ALREADY EXISTS — CHANNEL URLs

Meshtastic has two config-transfer mechanisms, and the second is exactly the shape a ride needs.

MechanismScopeFit
--export-config / --configure <file> EVERYTHING — radio, module and channel settings, as YAML ⛔ Wrong tool. Writes the whole config, so a rider's own settings are clobbered. This is the blind write already rejected.
Channel URL (--seturl <URL>) CHANNELS ONLY — the channel set, including names and encryption keys ⭐⭐ Exactly right. A ride needs a channel name and a PSK and nothing else.

⭐⭐ THE CHANNEL URL SOLVES THREE PROBLEMS AT ONCE:

  • It is channel-scoped, so read-modify-write stops being a concern — the mechanism cannot touch the rider's other settings because it does not carry them.
  • It is a shareable string. That is the distributable config artifact G1 asks for, already defined and understood ecosystem-wide. It is what the Meshtastic app's own channel-share QR code encodes.
  • It is device-agnostic. Channels are a protocol concept, not a per-model screen — which removes the device matrix from the part of config we actually need to set.

⭐ AND OUR FORK ALREADY HAS IT. The Meshtastic app generates and applies channel URLs natively — the CLI is one front end to a mechanism that lives in the protocol and in the app we forked. 🔴 Grep for ChannelSet/getChannelUrl/setChannels before designing anything: we are very likely EXPOSING an existing mechanism rather than building one.

⛔⛔ SECURITY — THIS CONFIRMS THE EMAIL-DISTRIBUTION CONCERN. Meshtastic's own documentation warns that exported configs contain private keys, channel PSKs and WiFi passwords, and to share or store them with extreme caution. ⚠ A channel URL IS the key — anyone holding it is on the ride. An emailed config is therefore a key sitting in an inbox: forwardable, on a shared family account. Decide deliberately whether the distributed artifact carries the key or a join token that must be redeemed. Not a reason to avoid email — a reason to design it.

⚠ The CLI itself is Python on a computer and is NOT available to us on Android. What transfers is the URL format and the underlying channel-set mechanism, which the app implements natively.

⭐⭐⭐ THE RESOLUTION — THE APP CREATES THE CONFIG; THE UTILITY APPLIES IT

The app is the AUTHORITY for a ride's configuration. It issues the config source — permanent for a club or a ride leader, temporary for a unique ride — so it already holds the values. Nothing has to be read back from anywhere.

The app already saves every config before applying a new one and lets the rider restore any point. So "reproduce it later" is solved and G4's saved-networks model is partly built rather than merely designed.

⚠ WHO RUNS THE CONFIG — and what a browser cannot do

The Python CLI runs on a computer with the radio attached over USB or serial. ⭐ Which means a Raspberry Pi with a radio on serial — a Nucleus — can configure its own radio directly, with no Android involved. That is almost certainly how Natak does it, and it explains why their model is "preconfigured per group": the node has always been able to do it locally.

⛔ THERE IS NO PYTHON ON ANDROID, AND A BROWSER CANNOT REACH THE RADIO. A web page has no reliable USB, serial or BLE access on Android — WebUSB and Web Bluetooth are Chrome-only, permission-gated, and cannot drive a Meshtastic device over BLE. A hosted tool cannot configure a radio attached to the tablet.

⭐⭐ BUT IT DOES NOT NEED TO. The web app's job is to GENERATE the config, not apply it — issue the network ID, derive the channel name and PSK, produce the channel URL. That is a string, deliverable by API call, link or QR code. Applying it is the Android's job, natively.

WhereDoes what
Web / backend (AWS + REST API, already built)Issues the ID, derives keys, produces the channel URL. ⭐ ID issuing and config generation in the same place.

⭐ THE HONEST LINE: the T1000-E gets trailhead configuration; everything else gets configured at home. Which makes the hardware recommendation do double duty — recommend the T1000-E and most riders never see a PC.

⭐⭐ THE MODEL — read the device, present what it has, change what we need

GroupTrack: "retrieve the values from the existing device, populate the screen from the values, normal maintenance functions, and then change the values used by the app."

⭐ This inverts the problem and removes most of the device matrix. We do not encode what each model should have — the device tells us what it has and we edit specific fields. A device with extra fields shows them; one without does not. ⭐ Same principle as the ensureInit fix of 09-15: test the data, do not assume the shape.

⛔ READ-MODIFY-WRITE, NEVER BLIND WRITE. Pull the current config, change only what the ride needs (channel name, PSK), write it back with everything else intact. A blind write clobbers settings the rider set for their own reasons.

⚠ SCOPE CONSEQUENCE: if the screen shows the device's real config, riders will edit other things there. That is arguably good — one place for radio settings instead of bouncing to the Meshtastic app — but it grows G12's communications menu into a device manager. Decide deliberately.

🔴 CHECK BEFORE BUILDING: radio config is AdminMessage over the mesh protocol, not a UI operation, and our fork is a fork of the app that already does it. Grep for AdminMessage/beginEditSettings/commitEditSettings — we may be EXPOSING an existing mechanism rather than building one. ⚠ Unverified.

⚠ THIS IS THE SECOND THING DRIVING THE DEVICE RE-EVALUATION (the first was the WiFi capability split). The supported-hardware list and the architecture keep turning out to be the same decision. If the recommendation is the T1000-E and everything else is "configure it yourself in the Meshtastic app", a targeted solution for one device is honest and cheap. Supporting five families properly is a different product.

The target configuration

Mesh-only riders on cheap radios, with a bridged Nucleus in the group doing conversion in both directions. Nathan: "The Nucleus handles all the routing/forwarding... the tablet/phone just runs the app, everything else runs onboard the radio."

⭐ So the bridge is a DEVICE function, not an app function — on a Nucleus. GroupTrack emits once, to the AP, and the node fans it out to both networks. Layer 1 collapses for Nucleus riders to "send and receive over a socket."

⭐⭐ AND A BARE-RADIO RIDER SEES EVERYTHING. Other LoRa riders directly, and the IP riders because a Nucleus already converted and transmitted them. From that rider's point of view it is all just mesh traffic — their app sees one group, not two networks. The layer-2 rule satisfied by hardware rather than by code we write.

⚠ CONDITION: it needs a Nucleus in the group. Ten T1000-E riders and no Nucleus is a LoRa-only group — fine, and it works, but nobody is bridging because there is nothing to bridge.

⛔ MESH IS NOT A COURTESY TIER. $50 vs $150–200 means most riders will carry LoRa, and the rider who is separated — off the WiFi mesh, out of sight — is exactly who the product exists for. Anything GroupTrack REQUIRES must work on a bare radio. Everything richer is an enhancement for riders with a Nucleus.

⭐ The Nucleus does not make LoRa better; it takes riders OFF it, leaving airtime for those who need it. That is the pitch: a club buys infrastructure, not ten individuals buying $200 each.

⛔ Rejected — and why

Would leave us exactly where we are now with better packaging. ⛔ Someone will reach for it as the obvious Android answer; it fails the one requirement that matters. GroupTrack: "I do not want to publish my software in the mesh open-source world."
  • Repurposing a Meshtastic field to carry role. Every field is load-bearing; short_name is 4 characters and changing it is a device config change that persists past the ride. And a rider would have to change it on the radio, which is the cost we are removing.
  • Requiring role on the wire. ⚠ Group.role DOES travel — the earlier claim that it could not was wrong — but local lead selection remains the better default: no configuration, no election, no conflict when two riders claim it, and it works before any role is received.
  • Bundling multiple riders' positions into one packet. Structurally impossible — oneof, no repeated field, and sender identity is the packet's from.
  • Lifting an ATAK CoT plugin. ATAK plugins ARE ATAK — built against its SDK, running in its process. ⭐ What we want is a CoT/TAKPacket parser-serialiser, and TAKPacket already gives us that.
