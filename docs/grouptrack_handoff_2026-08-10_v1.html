SAVE MAPS on a route’s artifact panel derives and queues a corridor, same pipeline as tracks. getRoutePoints firing proves the fallback chain resolved from the routes table.

⭐⭐⭐ The design collapsed from a cross-file refactor to three small commits because the device schema says CREATE TABLE routes (... geom_hash TEXT NOT NULL, UNIQUE(geom_hash)) and insertRoute already computes it. The hash is content-addressed and unique in both tables, so the same hash means the same geometry wherever stored — no artifact-type parameter, no QueueEntry field, no inputData change, no worker change.

⚠ The 07-27 note had this right all along. The 08-06 note claiming routes lacked geom_hash was WRONG and drove a much larger design. ⭐⭐ CHECK THE SCHEMA BEFORE DESIGNING AROUND A DATA MODEL.

⛔ NOT done, and it blocks GPX import: insertRoute does newId() → INSERT OR IGNORE → return id. On duplicate geometry nothing inserts and a fabricated id is returned. Fix: read back the surviving route_id by geom_hash. The panel path does not need it.

⛔⛔ What the tester’s run exposed

1 — Rotation destroyed a running migration. FIXED, untested.

MainActivity had no configChanges, so Android recreated it on rotation and took the composable — and the coroutine the delete runs on — with it. Fred: "just leave the screen open unless an action is taken to end it. period."

⭐ Chosen over rememberSaveable deliberately: saving state rebuilds the panel but the coroutine is still cancelled — it would look alive while doing nothing. Keeping the activity keeps the WORK. ⚠ A swipe-away still ends it.

2 — STRANDED: delete completed, submit never ran.

Corridors removed, queue empty, coverage gone, no indication anything was wrong. ⭐ Recovery is a re-run — already-deleted corridors skip at ~0.4 s each and it reaches the submit. ⚠ The app cannot DETECT this state. A launch check for "coverage removed, nothing scheduled" would turn a confusing hour into a prompt.

3 — A successful delete was recorded as FAILED.

First pass logged failures; the second popped through in seconds, which is the signature of nothing left to delete. The tiles came off and the record said otherwise. The delete and recordCompletedDelete are not atomic, so a failure in the RECORD is indistinguishable from a failure to DELETE.

⚠ This is what made an hour of diagnosis necessary, and on a destructive operation it is worse than cosmetic — a user either re-runs needlessly or believes their data survived when it did not.
