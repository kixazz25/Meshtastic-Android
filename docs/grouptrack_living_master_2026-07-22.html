⭐ FIRST OPEN ITEM — Unsegmented download bypasses (enqueue())

DO FIRST root-caused 07-22, not yet patched

Symptom (Fred, on device): artifact/track imports with “download maps” selected produce SAT submissions of 62,000+ tiles in a single queue entry, despite segmentation capping cells at 50,000.

Root cause — two callers bypass segmentation entirely

Every area origin routes submitDownload → enqueueArea → segmentCells (≤50K per cell). But two callers call bare DownloadQueueManager.enqueue(), which computes the whole box in ONE entry via calculateTiles (ConvoyDownloadQueue:127) with no split and no cap:

  • SpatialDbManager.kt:1973 — downloadMapsForTrackHash(), the track-import “download maps” path. This is the 62K source. Bypass is commented and was once VALID: “Use enqueue() … NOT enqueueArea() (grid-cell split → empty for a sub-cell-sized per-track box → totalTiles=0)” — true against the OLD fixed-12-mile gridCells, which steps in 12-mile increments from south and returns NOTHING for a box smaller than one step.
  • ConvoyViewModel.kt:989 — startDownload(context, pending), called from ConvoyScreen:472; fed by setPendingDownload at ConvoyScreen:645 and :876. NO stated reason for the bypass — it simply predates segmentation. (The nearby comment “Enqueue to background download queue instead of inline coroutine” refers to an older refactor, not to segmentation.)

⭐ The blocker is CLEARED — migration is safe

segmentCells (ConvoyTileDownloader:254) cannot return an empty list: val n = Math.max(1, Math.ceil(sizeTiles / segCeilingTiles)) floors the count at 1, and it slices the ACTUAL bbox into n fractional pieces rather than snapping to a fixed grid. A tiny per-track box therefore yields exactly ONE cell covering that box. The documented reason for the SpatialDbManager bypass is dead. (Verified by reading source 07-22.)

Fix

Route BOTH callers through the existing feeder submitDownload → enqueueArea → segmentCells. Do not call segmentCells directly — it needs sizeTiles = the layer-aware real volume (quickEstimate × slotLayers); enqueueArea already computes that, and a wrong sizeTiles would under-split and reproduce the bug in a new place. SpatialDbManager.getTrackBbox() already exists as the correct replacement shape (“returns the bbox … so the caller can feed box 1 (source selection) and submitDownload, identical to the area path”) — the import path apparently still calls the older downloadMapsForTrackHash.

⚠ Dependency — may not fully resolve on its own

sizeTiles comes from quickEstimate, which has the KNOWN source-awareness bug (was hardcoded z18). A bad estimate under-splits even after migration. Test entry sizes after the migration; do not assume the 62K is gone.

⭐ METHOD FIX (durable) — blast-radius rule amended

STANDING RULE Fred 07-22: “we have a history of not removing old code that continually bites us.”

The segmentation migration was done thoroughly on the paths people thought about (enqueueArea; enqueueRefresh was brought to parity 07-22) but two direct enqueue() callers were never migrated. Same class of miss as fix7f (convoy call site) and fix8b (on-screen BACK) — a “second call site” failure.

AMENDED RULE: when replacing a function, grep for callers of (a) the OLD function, (b) the NEW function, AND (c) any LOWER-LEVEL function the old one wrapped (here: bare enqueue() and calculateTiles). A symbol/xref index shows declarations, NOT call sites — grep remains source-of-truth for call sites. And delete the replaced function in the same commit so it cannot masquerade as a live path later.
