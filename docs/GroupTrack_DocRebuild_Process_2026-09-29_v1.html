Documentation rebuild — the process

2026-09-29 v1 · defined this morning, to start and finish this week · internal (resume context) · to be embedded in the living checklist's documentation section tonight

0 · The goal, and the principles it rests on

Goal: a new version of the rider documentation (manual, Quick Start, release notes) that matches the app as it is now, built from the app's own click paths, with only the screens that changed recaptured — and the old version kept complete, images included.

  1. The manual mirrors the click tree (Fred 09-29). Every clickable on every panel is traced through its call stack; the traces form indented path hierarchies; the manual's twisties follow them. Only one layer is open at a time — the current path — so the manual is a focused cookbook, click by click. (The manual's accordion already works this way: opening a section closes its siblings; a link opens exactly its path.)
  2. The process is the identity; the letter is its position (Fred 09-29). Letters A, B, C … and section numbers re-sequence when menus change; the content under a process name (Help, Search, Map Features …) moves as a whole section when its screens have not changed. So: section ids, folder names and image names are keyed by process; letters and numbers are applied last, from the current order.
  3. Launch points barely changed; additions sit at the bottom, in one area (Fred 09-29). Most existing sections keep their place; new features with complex navigation append at the end of their menus. Removals are the only thing that shifts letters (e.g. Work with Rides B and E).
  4. Capture only what is designated (Fred 09-29): screens whose code changed after the image was taken, and new screens. Every designated capture gets a placeholder at its exact step in the process, before capturing starts.
  5. Old version saved complete; new version built beside it (Fred 09-29). Nothing is edited out of the old one.
  6. Documentation follows decisions (Fred 09-28): open issues with screen or process impact are settled before the screens they touch are documented or captured.

3 · The processes to create

Each: purpose · inputs → outputs · the tool · who does what · done when. TOOL = a script or page Claude writes (dated, new name every revision) · FRED = on the laptop or tablet · CLAUDE = here.

P1 · Archive the old version, complete

Purpose
Keep the current documentation exactly as it is — text and all 112 images — before anything is rebuilt.
Inputs → outputs
manual v23, Quick Start v61, release notes v15 → GroupTrack_ARCHIVE_2.7pre_manual_2026-09-28_v23.html (identical copy; the images are inside it) + the same for the Quick Start and release notes + GroupTrack_ARCHIVE_2.7pre_images_2026-09-28.zip: every image extracted, named NNN_<section-id>_<slug>.jpg, with index.csv (number, section id, section title, caption, size, SHA-1, perceptual hash).
Tool
TOOL docarchive_2026-09-29.py CLAUDE runs it here.
Done when
The archive copies are byte-identical to v23/v61/v15; the zip holds 112 images and a 112-row index; Fred stores them in AllDocs.

P2 · The navigation cross-reference (the click tree)

Purpose
The truth of the app's navigation: every clickable, its label, what it opens, down every path — including panels shown by state over the maps.
Inputs → outputs
the repo at the freeze build → navigation_xref_2026-09-29.txt (or later date): 1 the click tree · 2 each panel with its file's last commit date · 3 state flags → panels · 4 every clickable, flat · 5 clickables with no action (check by hand).
Tool
TOOL navxref_2026-09-29.py (built this morning; read-only) FRED runs it from the repo root and uploads the .txt CLAUDE reviews the tree against the known panels (GRP Awareness, check-in, SELECT CART, Map Features …) and refines the script if anything is missed (new name each time).
Done when
Every launch point and every 09-28 panel appears in the tree; section 5 is empty or each entry explained.

P3 · The process registry — the spine everything hangs on

Purpose
One table of processes (stable identities), their place in the click tree, their manual section, their images, and the date their code last changed. Every later step reads it; nothing else holds structure.
Row
process id (stable, = manual section id, e.g. m-search, m-wr-import, m-grpawareness) · display name · parent process · order among siblings · letter / number (derived, never typed) · source composables (from P2) · code last-changed date · status (keep · moved · changed · new · removed) · images (from P5) · designation (from P6).
Inputs → outputs
P2 tree + manual v23 sections (ids, titles, nesting) + P4 label map → GroupTrack_ProcessRegistry_2026-MM-DD_vN.html (reviewable table) + process_registry.json (for the scripts).
Tool
TOOL registry_build_….py CLAUDE builds and matches; unmatched sections and unmatched tree nodes are listed for decision FRED reviews.
Done when
Every v23 section maps to a process or is marked removed (with its reason); every tree node that a rider uses maps to a process; Fred has approved the order.

P4 · The label map — drag the new labels onto the items

Purpose
For each lettered picture (launch panels: the ride map, the planning map, the Meshtastic rail, the Work with Rides menu, and any other the manual letters): show the panel with its old labels in their old positions, and let Fred drag the new labels onto the items — this becomes the high-level navigation (Fred 09-29).
The page
GroupTrack_LabelMap_2026-MM-DD_v1.html — one tab per lettered picture. Left: the current screenshot (freeze build) with ghost badges where the old letters were and a list old letter → process. Right: new badges (A, B, C … generated from the registry's order) to drag onto the picture. Unplaced badges and old badges with no new home are listed (new / removed). Export writes labelmap.json: per picture, per badge — letter, process id, x/y as a fraction of the image. Nothing is stamped into the image.
How letters show
DECISION Proposed: letters become HTML overlays positioned on the image from labelmap.json, instead of being drawn into the picture. Then a future relabel changes only the JSON — the image never needs re-stamping, and the letters stay crisp at any zoom. (Fallback: stamp them into the image with a script.)
Tool
TOOL the page (self-contained, works offline in a browser) FRED drags and exports CLAUDE feeds the JSON to P3 and P8.
Done when
Every lettered picture has every new badge placed; the registry's letters match the export.

P5 · The image inventory, and each image's age

Purpose
For each of the 112 existing images: which process and step it belongs to, and when it was captured — so it can be judged against the code's last change.
Dating, three ways (best first)
  1. Match to the original capture files. The images came from files on Fred's drive (adb screencaps, Android Screenshot_YYYYMMDD-HHMMSS files, capture folders). A script scans a folder Fred names, computes a perceptual hash of every picture, matches each manual image, and takes the date from the file name or its modified time. TOOL imagedate_match_….py FRED runs it on the laptop over his capture folders; uploads the result CSV.
  2. Stale markers — visible elements that did not exist, or changed, after a known date. Examples: GroupTrack Mesh Radio Setup in the rail (gone 09-28) · Mesh where GRP Awareness now is (09-28) · a plain REC where ✔ CHK IN › REC is (09-27) · SELECT CART alone where CHECKIN / SELECT CART is (09-28) · a full-width Ride Planning button (halved 09-28) · Review / apply saved configs · blurred-halo text (after the legibility fix). CLAUDE runs text recognition (upscaled) to flag candidates, then checks each image visually.
  3. Fred's knowledge for anything left undated.
Output
GroupTrack_ImageInventory_2026-MM-DD_v1.html: thumbnail · number · section/process · caption · date (and how it was found) · stale markers found.
Done when
Every image has a date or a stale marker or Fred's call.

P6 · Change detection — what needs recapturing

Rule
For each image: RECAPTURE if its process's code changed after the image's date, or it shows a stale marker, or the legibility change affects it · KEEP otherwise (the section moves whole, relabelled) · REMOVE if its process is removed. For each process step with no image: NEW capture.
Output
GroupTrack_CaptureDesignations_2026-MM-DD_v1.html: by process, in click-tree order — each image with its designation and reason; each new capture with the exact screen and state to capture (what to open, what to select, which ride).
Tool
CLAUDE applies the rule from P2 dates + P5 inventory FRED approves (can promote a KEEP to RECAPTURE, or the reverse).
Done when
Approved: the capture list is final.

P7 · The capture tree — one folder per step of each path

Purpose
Folders that mirror the click path: each function call in the stack is its own subdirectory; Fred captures the screen at each level (Fred 09-29).
Naming
By process, not letter, with a two-digit order prefix for sorting: 03 Rides/07 Work with rides/02 Import a ride/. A relabel never renames a folder. (The capture tree is issued only when revisions are finished — Fred 09-27.)
In each folder
CAPTURE.txt — what to capture here, in order (from P6), or KEEP — no capture needed. Only designated folders ask for pictures.
Capturing
TOOL cap.sh (dated name) run inside a folder: takes the next NN.png from the capture tablet and appends date, time, tablet, and the freeze build to capture.log — so every new image carries its date and build (fixing the finding in section 1). FRED captures, zips the tree, uploads.
Tool
TOOL GroupTrack_CaptureFolders_2026-MM-DD_v3.sh generated from the registry (replaces v2).
Done when
Every designated folder has its pictures; capture.log shows the freeze build throughout.

P8 · Build the new manual (and the old one stays untouched)

Purpose
The new version's structure, from the registry, before any new picture arrives.
Steps
  1. Start from manual v23. For each process in registry order: move its section whole (keyed by id) into its new place; retitle with the derived number and letter.
  2. KEEP images stay. RECAPTURE images are swapped for a visible placeholder at the same spot (a framed box: "Picture coming — <process> / NN: <what it shows>"), replacing the invisible comments. NEW captures get placeholders at their exact step.
  3. REMOVED sections leave the new manual (they stay in the archive).
  4. New sections (09-28 panels) are created at their place in the tree with the narrative from P10.
  5. Letters on pictures become overlays from labelmap.json (if the P4 decision is overlays).
Tool
TOOL manual_rebuild_….py CLAUDE
Output
grouptrack_manual_2026-MM-DD_v24.html — the new version, with placeholders.
Done when
Every archived section is accounted for (kept · moved · changed · removed — with reason); every designated capture has exactly one placeholder.

P9 · The image injector — pictures into their placeholders

Purpose
Put Fred's captures into the new manual automatically, in click-path order.
How
Reads the uploaded capture tree: folder → process → that process's placeholders in order → 01.png, 02.png …; resizes and compresses to the manual's standard (450×720 portrait / 720×450 landscape JPEG, as now); embeds each with data-proc, data-captured, data-build attributes from capture.log — so the next rebuild can date every image automatically. Reports leftover pictures and unfilled placeholders.
Tool
TOOL imageinject_….py CLAUDE
Done when
Zero placeholders left; zero leftover pictures (or each explained).
