All Files Access — declaration draft

2026-09-10 · for the Permissions Declaration Form in Play Console

⛔ Read this before you submit

The reviewer's finding was "Access to device storage not required" — they are not disputing that you use it, they are saying the job can be done another way. So the declaration has to answer one question only: why can this not be done with MediaStore or the file picker?

⚠ The previous declaration argued online maps and access time. That is a performance argument, and a reviewer can read "it would be slower" as "it would still work." The argument below is different: the APIs are technically incapable of the operation, not merely slower.

The strongest ground you have

SQLite cannot open a database through the Storage Access Framework. Android's SQLite API takes a filesystem path. SAF hands out content:// URIs and file descriptors. There is no supported way to open, query, or write a SQLite database over a SAF URI — this is a documented limitation, not a performance characteristic.

GroupTrack's map tiles are stored in MBTiles, which is SQLite. The trail database is SQLite. So the alternative the reviewer is pointing at cannot perform the operation at all.

And MediaStore is a media index. It catalogues images, audio and video for the gallery and media apps. A tile database is not media, is not indexable by MediaStore, and cannot be read through it.

⭐ That is the case. It is technical, it is checkable, and it does not depend on the reviewer believing a speed claim.

⚠ The question they may ask back — be ready for it

"Why not getExternalFilesDir()?" App-private external storage needs no permission at all, holds any amount of data, gives a real filesystem path, and SQLite works there normally.

That is a fair question and it has a real answer, but you should decide which answer is true for GroupTrack before you write it:

  • The rider owns the data. A rider downloads 50–60 GB of maps over days or weeks. In app-private storage that is invisible to them — they cannot back it up, move it to a new phone, copy it to an SD card, or see what is using their space. In Documents/GroupTrack/ it is theirs.
  • It survives a reinstall. Rebuilding a rider's maps is roughly a month of downloading. App-private storage is erased by uninstall and by Clear Data.
  • Riders share map sets. One rider downloads an area and copies the files to another's device rather than both spending a month on it.

⛔ Only claim the ones that are actually true and visible in the app. If riders cannot currently share map sets through a documented feature, do not put it in the declaration.

Draft — core functionality description

GroupTrack is an offline navigation app for off-highway vehicle riders. Riders ride in places with no cellular coverage, so every map, trail and route they need must already be on the device before they leave.

The core feature that requires All files access is the offline map store. Riders download map tiles by region or along a route corridor and build a personal store that commonly reaches 50–60 GB. The app reads from that store continuously while the map is on screen, and writes to it during downloads that run for hours.

The store is held in Documents/GroupTrack/ as MBTiles files and SQLite databases. Without access to it the app cannot draw a map, cannot plan a route, and cannot show a rider where they are — which is the entire purpose of the app.

Draft — why the privacy-friendly alternatives cannot be used

MediaStore cannot be used. MediaStore indexes images, audio and video. Map tile databases are not media files, are not indexed by MediaStore, and cannot be opened or queried through it. There is no MediaStore collection that holds this data type.

The Storage Access Framework cannot be used. The map store consists of MBTiles and SQLite database files. Android's SQLite API requires a filesystem path; SAF provides content:// URIs and file descriptors. A SQLite database cannot be opened for reading or writing through a SAF URI. This is a limitation of the API, not a performance trade-off — the operation is not possible.

The system file picker cannot be used. The picker is designed for a user to choose individual documents. Drawing a single map screen reads many tiles from the store, and this happens continuously as the rider moves. There is no point at which a rider could meaningfully pick a file, and no workflow in which doing so would make sense.

The data belongs to the rider, not the app. A rider's map store represents days or weeks of downloading. Holding it in app-private storage would make it invisible to them — they could not back it up, transfer it to a replacement device, or see what is occupying their storage — and it would be destroyed by an uninstall or a Clear Data, costing them the entire download again.

Draft — how the app is broken without it

Without All files access, GroupTrack cannot read the offline map store. The map draws nothing. Route planning has no trail data to plan on. A rider in an area with no cellular coverage — which is the situation the app exists for — has no map, no route and no position on a trail.

There is no reduced mode of the app that works without this. The offline map store is not a feature alongside others; it is what the app is.

⚠ Before you submit

  • The listing must document this prominently. Policy requires the core functionality to be described in the app's description. ⭐ Check that the full description says plainly that the app stores offline maps on the device and that this is what makes it work without signal. If it only implies it, fix that first.
  • The app must prompt clearly for the permission. Policy requires apps to "clearly prompt users to enable All files access under Special app access settings." ⭐ The authority gate does this — make sure the wording on that screen explains WHY, not just that it is needed.
  • Some forms ask for a video. If so: launch, show the permission prompt and what it says, show a map drawing offline with the device in airplane mode, show the downloaded map store. ⭐ Airplane mode is the single most convincing thing you can show.
  • ⚠ Do not repeat the earlier wording. The rejection says "not resolving the previously communicated policy issue" — if the new declaration reads like the old one, it will be read as no change.

⛔ If it is refused again

Be clear-eyed about this now rather than in a week. The fallback is getExternalFilesDir() — app-private external storage. It needs no permission, no declaration and no review. SQLite works there. The map store works there.

⚠ What it costs: the map store no longer survives an uninstall or a Clear Data, and riders cannot see or manage their own map files. For a rider with 50 GB downloaded, an uninstall would mean rebuilding from nothing.

⭐ That is a real product decision, not just a technical one — and it is worth deciding what you would do before the appeal comes back, so a refusal is a known path rather than a crisis.
