2.8: fix the navxref label pairing; record the reachability method

TOOLING FIX -- the navigation xref mislabelled every ListItem row (living
master T1, #navxref-label-defect).

label_near() searched FORWARD 1600 chars from the clickable and returned the
first string found. A Material3 ListItem puts its label FIRST and
`modifier = Modifier.clickable{}` LAST, so the window ran past the closing paren
into the NEXT row and took ITS headline. Labels came out shifted one row up
against actions, and the first label of each run was lost -- "Edit rider
profile" appeared ZERO times in the index, and "Change Map Sources" was reported
as calling onNavigateToProfile().

That mattered because the walkthrough is the instrument for REACHABILITY (the
cert proves faithfulness, the xref proves completeness, only the walkthrough
proves a user can get there), and V1 leans on it.

THE FIX, in a NEW tool file (golden rule): GroupTrack/commands/navxref_2026-11-13.py,
from navxref_2026-11-09.py with label_near changed and nothing else.
gen_xrefs_v3.sh selects by `sort -V` on the filename, so the new date is picked
automatically. ⚠ The tool is in the Drive commands folder, NOT this repo, so it
is not in this commit -- only its regenerated output is.

When the clickable is inside a ListItem, read BACKWARD -- but NOT "the last
string before pos", which is the supportingContent text and would be a second
wrong label. It must be the first Text(...) AFTER the last headlineContent,
anchored to the last `ListItem(` within 800 chars. Requiring both anchors ties
the label to THIS ListItem and not a neighbouring row's. Strictly conditional:
without those anchors the original forward search runs unchanged.

VERIFIED by holding the ACTION constant and comparing labels across 387 parsed
pairs: 4 changed, 383 untouched, clickables still 418.
  onNavigateToProfile()        "Change Map Sources"           -> "Edit rider profile"
  onNavigateToMapSources()     "Send issue reports by email"  -> "Map source credits"
  showConversionRecord = true  "CLOSE"                        -> "View conversion record"
  trailClearAsk = true         "Remove all trail data?"       -> "Remove all trail data"
The last two were not previously known: the old code was taking a BUTTON label
and a DIALOG TITLE from further down the file.

WHY Q4 AND Q5 EXIST, since it is the durable lesson: certifying back to callers
caught everything that STOPPED being called, which is what the convoy-app move,
one map and removing the tick all did. It cannot catch code that never stops
being called -- a branch behind a gate that can never vary (isVector() =
cached ?: true) stays reachable on paper and unreachable in fact. And "port AS
IS" governs HOW a member is ported, never WHETHER: dead code ports perfectly,
agrees on both sides, passes certification, and is then carried on two platforms
forever. The rule is now stated: port AS IS -- but only what is REACHABLE.
