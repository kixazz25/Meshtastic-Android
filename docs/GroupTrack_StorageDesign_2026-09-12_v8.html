Storage design v8 — complete

2026-09-12 · self-contained: written so a fresh conversation can pick this up cold · supersedes v7 — the maps handling changed

The situation

GroupTrack is an Android OHV/convoy trail app (Meshtastic fork, repo C:\\Users\\kixaz\\Meshtastic-Android, branch feature/convoy-event-ride, app id com.grouptrack.android). It keeps its data in shared storage at Documents/GroupTrack and Documents/my_tracks, which requires MANAGE_EXTERNAL_STORAGE (All Files Access).

2026-09-10: Google rejected the All Files Access declaration — "Access to device storage not required." The appeal filed the same day was also rejected. An extension request is in, asking for time to publish a compliant build.

⛔ Fred: "I cannot publish with that in the manifest." The permission comes out. Everything must live in app-private external storage (getExternalFilesDir()), which needs no permission at all.

⭐ And Google's rejection notice named the way out

The Storage Access Framework. ACTION_OPEN_DOCUMENT_TREE lets the rider pick a folder; the app receives a persistable URI with read AND write on that tree, and can copy the contents into its own storage. No permission, no declaration, no review.

⭐⭐ THAT CHANGES THE WHOLE PLAN. Earlier designs assumed a migration needed the permission it was trying to stop using — which forced a three-release sequence, or a clean install where every rider lost everything. Neither is needed.

Who this affects

  • Ten serious riders, all on Play builds. ⭐ The new build installs as a normal update — no uninstall needed — and the picker offers their data.
  • ⚠ Fred's two devices are sideloads (Droid 1 8624SBCEDF00001789 — the field device whose data matters; Droid 2 24039703201775 — sacrificial). Different signing key from Play builds, same package name, so moving them to a Play build needs an uninstall first. Their data survives it: it is in Documents, not app storage.
  • ⚠ Open testing is live serving 29321101 from 09-07. The rejection blocks UPDATES on every track, internal included — but the app is still installable.

⛔ Maps — measured, and the design changed three times

⚠ AND SOME RIDERS HAVE 50 GB. Fred, 09-12: "I have users with 256 GB and 50 GB of maps." ⛔ For them re-downloading is WEEKS, not a weekend — which is what makes the copy worth offering at all.

⛔ WHY "COPY ONE, DELETE ONE" DOES NOT SOLVE THE SPACE PROBLEM

The obvious idea is to copy each source then delete it, so the headroom needed is only the largest single file rather than the whole store. ⛔ But SAT.mbtiles IS a single 16 GB file. It cannot be split, so the device needs 16 GB free whatever the order. ⭐ The per-file loop earns its place for a DIFFERENT reason — see resumability below.

⭐ SO: CHECK THE SPACE AND ASK

usableSpace on the destination against the size of maps/.

  • It fits — offer the copy, with an honest estimate of how long. An hour or more for 16 GB; several for 50.
  • It does not fit — do not offer it, and say WHY. ⚠ A rider who sees nothing offered assumes an oversight; a rider told "you need 16 GB free and have 4" understands.
  • ⭐ Either way the rider may decline and re-download. That must read as a normal choice, not a failure.

⭐ Maps go LAST, and are independently recoverable

⛔ THE ORDER SETTLES A REAL FAILURE MODE. Fred, 09-12: "then we have not moved anything and the next start begins again."

Maps FIRST was considered and rejected. If the rider agrees, it runs for three hours, and it fails — nothing has migrated. Their data is still external, the migration still has to happen, and they have lost an evening for nothing.

MAPS LAST: the 415 MB of databases, routes, tracks and settings — the irreplaceable part — is safe within MINUTES. Maps become a separate step that can fail, be abandoned or be resumed without touching any of it.

The sequence

  1. Picker — one grant on Documents
  2. Copy GroupTrack — excluding maps/
  3. Copy my_tracks
  4. Maps — space check, offer, then per file: copy, verify, delete the source, next

⭐ WHY PER FILE, GIVEN IT DOES NOT HELP THE SPACE

Resumability and progress. Copying 16 GB as one operation shows nothing for an hour and loses everything on a failure. ⚠ Per file, a failure on the third leaves the first two done — and the next attempt skips them, because the source is gone and the destination exists.

⛔ THE TRIGGER STAYS ON STEPS 1–3

Maps never copying must NEVER make the migration re-run. The rider's real data is already safe, and re-running the copy over internal data they have since used is far worse than maps living somewhere else.

⛔ And maps/ moves to Documents/maps

When the data copies complete, Documents/GroupTrack is removed — but maps/ is inside it and may not have been copied yet.

⭐ SO MAPS ARE MOVED UP TO Documents/maps AND GroupTrack IS DELETED. Fred, 09-12: "moving maps under Documents is the best solution. We know exactly where it is and the migration progressed to that point."

⛔ THE ALTERNATIVE WAS REJECTED FOR A SPECIFIC REASON

Leaving Documents/GroupTrack in place to hold maps would work, and it is less moving. ⛔ But Fred, 09-12: "it masks the location of where we are retrieving other components — we could run fine until we finish copying maps."

That is the whole argument. A stale reference — one of the 23 sites, or something not yet found — would keep reading the old folder and nobody would notice. The app runs, reads the old spatial DB, looks correct. Then maps finish, the folder goes, and it breaks weeks later with nothing obvious to connect it to.

⭐ Removing GroupTrack immediately makes a wrong path fail LOUDLY on the first launch. ⚠ Same reasoning that preferred renaming to -EXT over deleting in the earlier design.

⚠ VERIFY BEFORE BUILDING: does the move actually work?

A rename within a granted tree needs DocumentsContract.moveDocument(), and not every provider supports it. ⛔ The fallback — copy 16 GB then delete — is not a fallback at all.

⛔ PROVE THIS ON DEVICE FIRST. If the move is unsupported the whole maps-outstanding design has to change, and finding that out after building it would be expensive.

The flow — and it is a GATE

⛔⛔ INCOMPLETE MIGRATION BLOCKS THE HOME STATE ENTIRELY. Fred: "if the import and delete are not completed we gate the home state launch."

⚠ WHY. The home state picker imports ~145,000 trails and takes about an hour. A rider who skips the migration, imports fresh, and THEN wants their old data has wasted the hour and created a merge problem. ⭐ The gate removes that case rather than handling it.

The sequence

  1. App starts, creates its empty structure in getExternalFilesDir().
  2. Is the completion flag set? If yes, proceed normally — never ask again. If no, present the migration and go no further.
  3. Rider grants a tree. ⭐ The app then LISTS it — DocumentFile.fromTreeUri() then listFiles() — and sees for itself what is there.
  4. Copy GroupTrack contents over the empty install, maps/ and *-journal excluded.
  5. Copy verified → maps/ DELETED, same pass, grant live.
  6. Copy my_tracks contents.
  7. Write the completion flag and the record. Proceed. The home state picker runs only if trails are still needed — which after a successful copy they are not.

⭐ A NEW INSTALL GOES THROUGH THE SAME PROCESS

Fred: "should go through the migration process with no directories to select. Same process." ⭐ No special "I have nothing to import" button — which was the earlier design and was a mistake, because a rider tapping it by reflex would lose everything.

The rider grants a tree; the app looks inside; there is no GroupTrack and no my_tracks; it records the migration as resolved and carries on. One tap, and they never see it again.

⭐ DECIDED: ONE BROAD PICK ON Documents

Fred, 09-11: "one broad pick by user for documents. We pick it up from there."

The rider grants Documents ONCE. The app then lists it and finds GroupTrack and my_tracks for itself — both, one, or neither.

⭐ WHY IT IS THE RIGHT TRADE:

  • One tap, not two. Two narrow picks means asking twice and handling the case where they grant one and not the other.
  • It answers "is there anything there?" Two narrow picks cannot — without a grant the app is blind, so a rider with nothing to import would be asked to find a folder that does not exist.
  • A new install goes through the identical path. Grant, look, find nothing, resolve. No special case and no "I have nothing" button to tap by reflex.

⚠ THE COST, STATED PLAINLY: the grant is read AND write over everything else the rider keeps in Documents.

⛔⛔ SO THE RULE IS ABSOLUTE: THE APP READS EXACTLY TWO FOLDERS. Fred, 09-11: "I do not want to pick beyond select GroupTrack and my_tracks. Then everything comes over." The grant is on Documents only because that is the one place from which both can be found — it is NOT a licence to look at anything else in it.

⚠ Nothing the grant provides enforces that. It is a discipline in the code. ⛔ A future change that walks the tree for any other reason — scanning for importable files, tidying, looking for something helpful — is a trust violation however well intentioned, and it would be invisible to the rider who tapped once.

⭐ AND INSIDE THOSE TWO, EVERYTHING COMES

Fred: "too much is better than not enough." A recursive copy takes whatever is there at whatever depth — JSON, logs, dotfiles, all of it — to the same relative place. ⭐ That is why the design is an EXCLUSION list: anything the app gains later arrives on its own rather than being forgotten because nobody updated a manifest.

⚠ It does mean some clutter follows the rider — autoresync_receipt.json (from a feature that is now dead code), segmentation_analysis.json from July, track_sync.log. ⛔ DO NOT TRIM IT. Every exclusion is a judgement that can be wrong, and a stale JSON costs kilobytes. The two exclusions that exist — maps/ for size and *-journal for correctness — are there for reasons; adding more on tidiness grounds is how something load-bearing gets dropped. ⚠ The three .trails_cleared_* markers in particular look like clutter and are not: they stop housekeeping re-firing.

⚠ And the grant is PERSISTABLE. Take only what is needed: if nothing further requires it after the copy, do not persist it at all — a one-shot grant that dies with the session is the smaller ask, and the flag means it is never needed again.

⛔ IT PERSISTS UNTIL RESOLVED

Every startup presents the same option until the flag is set. ⚠ A rider who taps past it would quietly lose their trails AND keep 17 GB of dead files, and know neither. The gate makes that impossible.

⛔ The completion flag — and why it is a FLAG, not a disk check

Fred: "we want to set a flag that data has been moved once completely. Do not want someone to save a document called GroupTrack or my_tracks and have an issue."

THAT IS THE WHOLE ARGUMENT. Documents is the RIDER'S folder. Anything can end up in it. A migration that decides what to do by looking for a folder NAME would re-fire on an unrelated file months later and offer to import over live data.

⭐ So the flag governs, and nothing else does. Set = never ask again. Unset = ask. It supersedes the earlier "is the internal spatial DB still an empty schema?" test, which was cleverer and less reliable.

⚠ It lives in internal storage, so it survives everything except an uninstall — which is correct, since an uninstall wipes internal storage anyway and a reinstall genuinely should offer the migration again.

⚠ "Resolved" includes "nothing found." A new install that grants a tree with no GroupTrack in it is resolved, not pending.

⭐ The record — because troubleshooting is the point

⛔ ONCE STORAGE GOES INTERNAL, adb shell cat AND ls STOP WORKING on the app's files — Android/data is blocked to the shell on Android 11+, and run-as is refused on release builds. ⚠ Every diagnostic used during development this week stops working. That is the reason this record exists.

Three steps to recap, each with its result:

  1. GroupTrack contents copied — item count, bytes
  2. my_tracks contents copied — item count, bytes
  3. maps/ deleted — bytes reclaimed

What it must hold to be troubleshootable rather than merely reassuring

  • Per item: name, source bytes, destination bytes, matched yes/no. ⭐ That tells you WHICH file failed, not that something did.
  • The failure itself — the exception message, not just "failed."
  • The tree URIs granted — so you can see whether they picked what you expected.
  • Timestamps per step — these distinguish a hang from an error.

⭐ The flag file and the record are the same file. One JSON in internal storage, written as each step completes.

Where to read it: somewhere out of the way. ⭐ Fred suggested the radio control menu — riders do not wander in there. ⚠ And it needs a SHARE button, because that is the only way a rider's record reaches you.

⚠ The ordering constraint that survives every redesign

⛔ THE COPY MUST HAPPEN BEFORE ANYTHING OPENS A DATABASE. Copying over an empty install is safe ONLY while those empty schemas are closed. An open SQLite file written underneath produces corruption invisible until something reads the damaged page.

⚠ StartupHousekeeping.run() calls SpatialDbManager.init(), so by the time the authority gate resolves today, the databases ARE open.

⭐ SpatialDbManager.close() (line ~2536) closes both AND clears initialized, so a reopen re-resolves the path. Both halves matter — a close leaving initialized true hands back a stale handle pointing at the old location, which is precisely the map-source fallback lock fixed on 2026-09-10.

⛔ The picker solves the DATA. It does not solve the PATHS.

23 sites still resolve to shared storage, and every one must point at internal before the permission leaves the manifest — otherwise the app writes somewhere it cannot read back.

⛔⛔ Why an earlier sweep missed them — the durable lesson

Thirteen sites were found and fixed on 09-11 by grepping Environment.getExternalStorageDirectory(). These 23 use getExternalStoragePublicDirectory(DIRECTORY_DOCUMENTS). TWO APIs, ONE DESTINATION.

⭐⭐ GREP FOR THE DESTINATION, NOT THE API. Search the string literals — "GroupTrack and "my_tracks — because those cannot be spelled two ways.

🔴 The real problem of the next session — not the redirects

⛔ getExternalFilesDir() NEEDS A CONTEXT, AND THESE ARE OBJECT SINGLETONS. MapStateStore has no Context anywhere.

GroupTrackStorage (created 09-11) currently takes an OPTIONAL Context and falls back to the public path — correct while nothing had moved, useless once it must resolve internal.

⭐ The manifest declares MeshUtilApplication (AndroidManifest.xml:108), whose onCreate runs before everything — the natural place to hand the accessor a context. ⚠ It is an UPSTREAM Meshtastic file, so that is a change outside the convoy tree.

⚠ And the authority gate has to go

With no permission to check there is nothing to gate.

✅ Background location is SAFE. ConvoyScreen:1315 has its own bgLocationLauncher and :1396 checks the permission, so removing the gate does not lose location. ⚠ Verified 09-11 — it was the one thing that could have broken tracking silently.

⛔ BUT THE GATE IS THE NAV START DESTINATION (ConvoyNavigation.kt:61), and ConvoyRoutes lives in org.meshtastic.core.navigation — a DIFFERENT MODULE, outside the convoy tree. Removing it changes where the app boots.

⛔ AND StartupHousekeeping.run() IS CALLED FROM THE GATE. It clears trails, runs the ALTERs and installs the palette. Kill the gate and housekeeping needs a new home — it cannot simply be dropped. ⚠ The migration gate needs a home too, and it is the same problem.
