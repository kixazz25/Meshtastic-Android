GroupTrack: moving to TAK reports, and how we extended the radio model

For Nathan Boyette, Natak Mesh · from Fred, GroupTrack · 26 September 2026

What this is. A report of what we built and measured this week, not a request to change how you configure your radios. Your eleven-value radio model was our starting point. This explains how GroupTrack moved its position reporting to TAK without CoT, which values we added to your model to make that work, what we found on real hardware, and the few things we would like to agree with you.

1. In short

  • Every GroupTrack radio now reports in TAK. The radio runs the TAK_TRACKER role, and each position report is a TAK packet carrying its own callsign. No CoT, no XML, no Wi-Fi and no TAK server are involved on a ride.
  • We kept your radio values and added a reporting group: how often and when a radio reports, and its GPS. That takes the managed set from your eleven to nineteen values. All nineteen are written and then read back and verified.
  • The added GPS and position values make a radio restart a second time after it is written. We found that the tablet then holds a dead Bluetooth link it believes is alive, and fixed it with a closing step: wait 30 s, then always one clean disconnect and reconnect.
  • GroupTrack's standard preset is now MEDIUM_FAST (it was LONG_FAST). With two radios, channel use fell from about 22% to 4–5%.
  • Radios on different presets cannot hear each other. You run SHORT_FAST, so a Nucleus on a GroupTrack ride needs to run the ride's preset. See section 7.

2. From position packets to TAK reports

Before

GroupTrack drew each rider from Meshtastic's own messages: position packets for the location, and the node list for the name. A rider's name existed only if their node information had reached the tablet, and a radio with no tablet attached was little more than a number on the map.

Now

Each radio runs the TAK_TRACKER role. On the T1000-E, on firmware 2.6.11, that makes the radio itself send a TAK packet (TAKPacket, version 1) on port 72 at every report. Each packet carries:

  • the callsign (taken from the radio's owner name);
  • the position: latitude, longitude, altitude, speed and course;
  • the TAK group: role and team colour (today the firmware defaults, Team Member and Cyan);
  • the battery level.

So every report identifies its sender by itself. A radio with no tablet appears on every map under its callsign, as soon as its first report arrives.

What is required, without CoT

Only the radios themselves, set up consistently:

  1. The role TAK_TRACKER on every radio.
  2. The same channel and key, and the same preset, on every radio on the ride.
  3. The owner name set to the rider's callsign, because it becomes the TAK callsign.
  4. GPS on, and the reporting values (section 3), which now set how often TAK reports are sent.

Nothing else: no ATAK app, no server, no XML. GroupTrack decodes the TAK packets directly on the tablet.

Two copies of every report. A receiving radio passes each TAK report to the tablet twice: the over-the-air original, with the callsign in compressed form (is_compressed=true, unreadable as text), and a copy the receiving radio has already decompressed. GroupTrack uses only the decompressed copy, so each report is handled once, with a readable callsign. A tablet's own radio's reports arrive only as the compressed original, since there is no second radio to decompress them, which is fine: a tablet takes its own position from itself.

3. Your radio model, and what we added

We started from your eleven values: the owner name, the LoRa settings (region, preset, frequency slot, hop limit, TX power), the device role, and the channel (name and key). GroupTrack writes them the same way, as the same kinds of change. To make the radios report usefully by themselves, we added a reporting group.

The principle: GroupTrack manages only the values GroupTrack uses. Those nineteen are written, then read back and verified one by one. Everything else on the radio stays as it was. Before the first write, GroupTrack saves the radio's full configuration (As found), so a radio can always be returned to exactly how it was.

How the values are written

In three groups, each followed by the same wait. This is your settle, plus the forced Bluetooth cycle from our earlier tooling:

  1. 1a: the owner name.
  2. 1b: LoRa, device and position together, as one edit (begin, write, commit).
  3. 2: the channel.

After each group: a 15 s settle (the radio restarts by itself after most config writes), then disconnect → 3 s → reconnect, then wait for the connection (up to 60 s).

4. What we found: the second restart

The symptom. After an apply, each tablet still saw the other radio, but not its own, until the rider disconnected and reconnected by hand.

The cause. Your process writes LoRa and channel values, and each group causes one restart, which your single wait fits exactly. The position and GPS values we added make the radio restart again, after the tablet has already reconnected. Android does not notice the dead Bluetooth link straight away, so the tablet reports connected while the radio is restarting underneath. Every check that trusts that state passes wrongly, and the tablet never receives its own radio's record, which is sent only in the exchange when a connection opens.

The fix. After the last group, GroupTrack waits 30 s, then always does one clean disconnect and reconnect, whatever the connection state says. Only then does it check that it holds its own radio's record (one more automatic cycle if not), and verify.

Relevant to your radio API (request R14). If you add the position values to your API, the same second restart is likely to appear, and the same closing step (wait, then one clean reconnect) should cover it. For your own use, though, the timing that matters is the bridge's relay interval, not the radio's position settings, so R14 is optional (section 7).

5. TX power 0 means the radio's maximum

GroupTrack's default TX power is 0, which Meshtastic treats as the radio's own maximum within the region's legal limit. That lets one default suit every radio: a T1000-E and a 1 W radio each transmit at their own full power, and neither is capped, nor ever raised above the legal limit.

What we observed: the radio accepted 0 and stored and reported the resolved value, 30 dBm. So a literal read-back sees expected 0, got 30. GroupTrack now treats an expected 0 as "any positive power the radio reports", so the verify passes, and the radio is not rewritten on every apply.

6. MEDIUM_FAST, measured

We moved GroupTrack's standard preset from LONG_FAST to MEDIUM_FAST (your 8+ miles line of sight on it helped settle that), and the fastest smart-position rhythm from 3 s to 4 s.

LONG_FAST, one radio still hand-set to a 3 s broadcast~22%

What we take from it: the reporting values mattered as much as the preset (correcting one radio roughly halved the load before any preset change), and MEDIUM_FAST halved it again.

The range trade-off. MEDIUM_FAST has about 5 dB less link budget than LONG_FAST. On our T1000-Es, that turns roughly 1⅓ miles between radios on LONG_FAST into an expected ¾ to 1 mile on MEDIUM_FAST. That's an estimate, to be measured on trails in January. Our guidance to riders will be:

  • keep within about ¾ mile of the rider ahead;
  • strong radios (1 W, a good external antenna, mounted high) at the lead, the tail, and in the middle of long groups. A better antenna helps receiving as much as sending, so every link that includes a strong radio is longer, and relays favour them naturally.

Your 30 dBm radio-only unit would fit that backbone role exactly.
