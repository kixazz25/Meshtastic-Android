⭐ Two flags for one concept — still unresolved

Kotlin addPointMode and JS window.__routeMode mean the same thing and nothing keeps them in sync. Proven divergent 07-30:

TrackTap: PLANNER bridge id=8f8c39b1… addPointMode=true
TrackTap: PLANNER SUPPRESSED by addPointMode
— while every ARTIFACTTAP line in the same session read routeMode=false.

Route mode was off. The Kotlin flag was on. Every track tap died at that guard.

⚠ Fred's framing, and it is the right one: route mode is the wrong predicate. It means "Route+ is open". What actually needs guarding is "the next tap places a vertex". The fix is one flag, one setter, both sides updated from the same call — and the narrow name, not the screen-state name.

⛔ Note item 3b's fall-through guard currently keys off __routeMode. If the predicate changes, that has to change with it or it drifts again.

⚠ Process lessons — both cost real time today

1. Build on verified work, not on an empty queue. Items 1 and 2 were validated an hour before we built. We held them to bundle item 3, which was still diagnostic — and item 3 introduced a defect (3b) that forced a second build anyway. Worse: items 1 and 2 could have been tested and certified in that window. Bundling does not just delay verification, it entangles it — if one item misbehaves the others are implicated until proven otherwise.

2. Never bundle diagnostics with fixes. Settled work and exploratory work have different risk. Item 3 was instrumentation written because we did not understand the tap layers; putting it in the same build as two verified fixes let the unknown break the known.

3. Check source timestamps against the APK before testing. Twice today we tested a binary that predated the change — once losing a whole tap session. Twenty seconds of ls -la against forty minutes of rebuild.
