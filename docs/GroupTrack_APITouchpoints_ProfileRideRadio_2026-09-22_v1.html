Profile → ride → radio: the API touchpoints

2026-09-22 · v1 · the surface between the committed tables (0dd20cd3d, 1a758a8d9, 37153e7d0) and the radio processes being rebuilt in 2.7.

One direction only: identity and rides are written first, and the radio is handed the result. Every call below is com.grouptrack.core — pure Kotlin, no Android, no database — with SQLite implementations in the app. The radio never reaches past this line.

4 · The rules that keep it one-way

RuleWhy
The radio layer never reads the databaseIt is handed a NetworkConfig and an identity. No ConvoyMasterConfig.load(context) scattered through screens
The radio layer never generates anythingNo ids, no keys, no defaults. Generation lives in profile maintenance — one write path
Five screens become one processApply list, apply radio, reconnect wait, verify, master success → apply() with progress, then verify()
Snapshots move into the databaseradio_snapshots is already committed and dormant; the JSON files under convoy_backups/ retire with the cluster
Identity comes from the profileThe rider never types a long name again. Callsign is set once, at first launch

Build order

  1. Profile at first launch — nothing broadcasts a callsign until this exists.
  2. Leader setup and organizations, with the network generator underneath (GT id, key, base values, TX cap, base version).
  3. Ride creation and the .convoy file — export and import on the new tables.
  4. RadioService — snapshot, apply, verify, restore — built beside the old screens and proven on device.
  5. Reroute the menu, then delete the 16 files (blast radius: 7 app files + core/navigation/Routes.kt).
  6. Roster, roles and the survey at track save.
