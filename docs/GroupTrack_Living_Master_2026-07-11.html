The unified process (one spine, many origins, many destinations)

ORIGIN → NORMALIZE → EXPAND → CHOP → FETCH → [RETURN POINT] → WRITE → DESTINATION, pluggable at both ends.

  1. ORIGIN → (bbox, source-set) — the only place origins differ.
  2. NORMALIZE → (bbox, [sources]) — origins collapse to one canonical request; downstream is origin-blind.
  3. EXPAND → layers — each source → its layers via the source def (SAT → base + 2 overlays). "One SAT request → 3 destinations" happens here.
  4. CHOP → queue items — bbox → bounded cells; (layer, cell) = one queue item.
  5. FETCH → tiles — the ONE place the "miracle" varies: HTML per-tile, or batch export+unbundle, chosen per-layer by whether it has a batch process.
  6. RETURN POINT → uniform (type, z, x, y, bytes) stream — both transports emit this.
  7. WRITE → destination — the write contract resolves type → its .mbtiles and inserts.

Two fan points: fan-in at front (many origins → one canonical request); fan-out at back (one request → EXPAND layers → CHOP cells → many tiles → many DBs). Three extension points: add an origin = step 1 only; add a transport = step 5 miracle only; add a destination (new layer/type) = free.

MBTiles-only hard cutover (the decision)

Dual-path loose+MBTiles DROPPED — no state-file mode switch, no read/write fork, no Step-0 state-resolver. The ~5 map-invested testers re-download once. Storage format changes; HTML fetch survives. This supersedes the earlier "Steps 0 state-resolver → 1 write-fork → 2 read-fork → 3 batch-fetch" plan and the dual-path coexistence. GPX/track DBs stay separate. Worst case to design for: a tester at 80–90 GB of tiles (loose-file model = millions of files = the bloat/brick/slow-delete root cause).

Two-pass build
  • Pass 1 — move current transport to spatial-DB storage. HTML fetch unchanged; only the WRITE changes (loose files → MBTiles). Covers all origins + all readers. MapView unchanged. = the V2.6 tile work + the "simplify" goal.
  • Pass 2 — add a batch transport capability. New FETCH miracle built ALONGSIDE, gated off (layer.batch?.process), Esri first, provider-agnostic. Never touches Pass 1's storage — just a new way to feed the same write. Build-alongside-and-gate.
Write contract + the two "miracles"

Intercept at the RETURN POINT; everything above it is untouched. Two producers emit (type,z,x,y,bytes) into ONE shared write contract (MBTilesStore.insertTile + TileCodec + type→file resolve + y-flip):

  • Miracle #1 (Pass 1): per-tile HTML write, redirected <cache_dir>/z/x/y.png → <cache_dir>.mbtiles.
  • Miracle #2 (Pass 2): batch .tpkx → unbundle → same stream → same DBs.

The contract is producer-blind — that's why Pass 2 reuses Pass 1's write. Open: single insertTile vs transaction-batched insertTiles (faster for batch bulk); Miracle #2 streaming per-bundle vs collect-whole-package.

Schema — one MBTiles per TYPE (resolved 4 ways)

One MBTiles file per TYPE (= cache_dir = old directory name). No type column; base/overlay declared in each file's metadata; compositing at the Leaflet layer, not in storage. Confirmed by: (1) the render stacks separate per-type layers (we're not rewriting MapView); (2) the MBTiles spec mandates one tileset per file; (3) Esri best practice = base+reference separation; (4) Esri delivers per-service.

Canonical: tiles(zoom_level, tile_column, tile_row, tile_data) + metadata(name, value) + MANDATORY CREATE UNIQUE INDEX tile_index ON tiles(zoom_level, tile_column, tile_row). WebP yes; NEVER JPEG for overlays (kills alpha). FLAT vs NORMALIZED per type. PMTiles REJECTED (immutable — GroupTrack patches incrementally). TMS y-flip to settle.

DB naming = old directory names: cache_dir = type = old folder = convoy://tiles/<type>/… URL segment = .mbtiles filename. All download origins through the SAME area submission (audit + blast radius)

The unified process only holds if every origin funnels through the one area submission. Test per origin: does it end at the area submission with (bbox, sources), or bypass it (a second engine)?

  • AREA — user-drawn bbox + selectable sources = the canonical engine.
  • TRACK — bbox derived by padding the track's lat/long extents ½ mile + preference-sourced set → routes through area submission.
  • ROUTE — "dupes track": same adapter shape (pad route extents → resolve sources from preference → area). Confirm it shares track's path.
  • IMPORTED ARTIFACTS — an imported task WRITES A NEW ARTIFACT; the download panel has a "yes" import-maps toggle; if yes → the FIT PROCESS requests a map download for this track, right after track creation. So it is NOT a separate engine — it triggers a track-style download via the fit process → converges through track.

Prove the list exhaustive with a grep — enumerate every caller of the queue submission + every path reaching ConvoyTileDownloader/ConvoyDownloadWorker; classify each as canonical / adapter / rogue-bypass. May be unnamed origins — from code, not memory. Build a blast-radius process inventory (every process touching tile download/write + what it does) from the xref docs + code so a change doesn't underestimate what it breaks.

Source-set policy per origin: area = selectable; track/route = preference-default; artifacts = via track (likely track's preference).

Front-end standardization — WHY (inherit the large-bbox splitting)

Make each non-area origin a pure origin adapter — produce (bbox, source-set) and submit through the same area submission.

Primary reason: inherit the area process's large-bbox splitting. The area submission already chops a big bbox into bounded queue items (gridCells/tileBoundsLatLon) — real, tested. Track/route/artifacts on their own paths duplicate or lack it. Routing their bbox through the same submission → they inherit splitting for free. Triple duty: (i) splits big areas today; (ii) splits track/route/artifact downloads once standardized; (iii) sizes batch export jobs in Pass 2 (one split item = one Esri job under the 100k cap).

Other reasons: origins gain source control (fixed → selectable); convergence happens before the return point by construction → Pass 1's write-redirect is provably one seam. Confirm: does the area submission cleanly take (bbox, sources), or is it entangled with the drawing UI? If entangled, extract a pure (bbox, sources) → submit core first.

Pass 2 — batch transport (Esri) full design
  • Core: the unit of variation is the provider's PROCESS, not just a key. Invoke the provider's own download+unbundle; one handler per provider protocol, reused across all its sources; the source def names the process + supplies parameters. One EsriExportTilesProcess serves all Esri sources.
  • Schema: per-layer batch block — { "process":"esri_export_tiles", "export_endpoint":"<MapServer>/exportTiles", "package_format":"tpkx", "requires_key":true, "api_key_param":"token", "max_tiles_per_job":100000 }. process = dispatch key. No block → HTML per-tile.

⭐ ROUTE-STATE PERSISTENCE & TEARDOWN — ⭐ #1 NEXT BUILD (resume here) OPEN

Problem (observed)

The route nav box disappears; states don't change as they should. Route-planning state is not reliably persisted across navigation, nor reliably torn down on exit. Two repro triggers (with a route open): (a) open/touch another item; (b) close the artifacts panel. Two failure modes: (1) route disappears from the map entirely; (2) route stays drawn but goes dead/inert (geometry visible, controls gone/unresponsive).

Root cause (located from xref)

Route mode is held in var routeMode by remember { mutableStateOf(false) } — ephemeral Compose state — at TWO independent copies: ConvoyMapViewerScreen.kt:129 and ConvoyScreen.kt:197. Both drive ONE shared window.__routeMode in convoy_map.html. Teardown = ~8 scattered hardcoded calls per screen of setRouteMode(false); clearBuildLine(); (ConvoyMapViewerScreen 955/1044/1075/1112, arm-on 996/1020, resume 1154; ConvoyScreen 1608/1684/1716/1743, arm-on 1648/1671, resume 1775). No single teardown funnel.

This one fact explains both failure modes: touching another item / closing the panel recomposes or orphans the remember boolean → Kotlin routeMode resets/desyncs but JS gets NO matching setRouteMode(false); clearBuildLine(). Disappear = a path fired clearBuildLine / a redraw overlaid it. Stays-but-dead = Kotlin routeMode went false so controls detach, but JS still shows the line.

Intent — Fred's 3 requirements
  1. Persist route-planning state in the MAP JSON so nav away + back restores it (survives recomposition/nav, which remember does not).
  2. States unique per map — Planning (grouptrack_map.html) vs Convoy (convoy_map.html) must not collide on the shared JS flag; the two booleans need per-map identity.
  3. ⚠ SUPERSEDED by the 07-08 hard rule (below): NOT "every exit ends it." ⭐ ESRI TILE DOWNLOAD STRATEGY — 4-phase plan (planning session 2026-07-09) STRATEGY

Origin (07-09): the V2.6b batch transport plan (Esri exportTiles → .tpkx → unpack) was de-risked and found unavailable. Curl against the keyed Location Platform imagery service (ibasemaps-api.arcgis.com/.../World_Imagery/MapServer?f=json, HTTP 200 with the AAPT key) returns only tileInfo — no exportTilesAllowed. The keyed Location Platform endpoint is per-tile only; exportTiles lives on the separate tiledbasemaps.arcgis.com "for Export" instance (a different org/subscription entitlement). So the .tpkx batch plan is dead on the current account, and V2.6b pivots to tile-fetch concurrency on the free endpoint (speed-up, not a transport rewrite).

The cost reality. Esri Location Platform = 2,000,000 tiles/month free, then $0.15/1,000 flat (no volume tiers; high-volume only via Esri sales). Real GroupTrack usage: track download 200–300k tiles, area download ~500k tiles, heavy users ~100 GB ≈ 10.8M tiles. A 100 GB cache is a lifetime accumulation (≈900k/mo over a year, under the free tier) — but one-shot bulk on a metered key is financially impossible. Key honesty: the concurrency rewrite speeds downloads up, it does NOT reduce tile volume — on the free tier, faster just means faster accumulation (today's 100 GB caches were built under the free tier). Demand-shaping via cost only works on a paid path.

The four phases:

  • Phase 1 — NOW / BETA: free arcgisonline.com endpoint for everyone; the concurrency patch speeds it up at no cost and no licensing dependency. (This is the immediate V2.6b work.)
  • Phase 2 — OPTIONAL PAID PERSONAL TIER: users who want the faster keyed endpoint and/or big pre-downloads foot their own bill via their own entitlement (BYO-key / ~$100 ArcGIS Personal-Use). Cost self-selects and self-limits. Note: a personal license is still PER-TILE — not the batch/redistribution product.
  • Phase 3 — ENTITY ACCOUNT: past enough $100 personal accounts, it pays to shift to one ArcGIS org/enterprise account + shared key behind the backend proxy + negotiated volume pricing (also the central usage dashboard/billing + the 3.0 key-security model). Crossover economics unknown — depends on Esri's negotiated volume quote (the single deciding number; not published).
  • Phase 4 — FULLY OPTIMIZED ENDGAME: download-once / serve-many with dedup across the whole user base. Riders cluster in the same popular areas, so each region is fetched from Esri once and amortized across everyone who rides there — cost stops scaling with users and scales only with unique geography (bounded, slow-growing). Also solves key security (key server-only) + speed (users pull from GroupTrack) + control (one cache/dashboard/bill).

Phase-4 distribution refinement — self-managed AREA PACKS (Fred, 07-09). Rather than run a live tile CDN, self-manage distribution: a batch process pulls/builds an area's .mbtiles once, hosts the finished file (FTP or file host / URL+catalog), and GroupTrack devices fetch + import the pre-built .mbtiles into MBTilesStore. Much lighter infra (a file server, not a mapping service) and fits the app's existing MBTiles-file world (store already reads .mbtiles; X-plore flow already moves tile files; import is close to Pass 1). Productized = "download this area pack" through the same download pipeline, pointed at pre-built packs instead of Esri tiles.
