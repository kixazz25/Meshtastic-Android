🔴 04 — 2.6e RELEASE TASK: SNAP-2 APPLIES TO TRAILS ONLY

2.6e route planning only — NOT track recording

⭐⭐ Fred 07-29: "tracks can appear on map but snap2 should not be applied to tracks." Route planning snaps to trails only. Tracks keep rendering and stay tappable for details.

Two independent reasons it is right, not a workaround:

  1. Coverage. Track-snapping existed because UGRC's 49,125 trails left real ground unreferenced. At 89,527 OSM trails that gap is largely closed.
  2. lineId correctness. A snapped vertex stores lineId, and a track's lineId is per-rider — ten riders on one trail produce ten tracks with ten IDs. Snapping a route to a track never denoted shared geometry, so it was already wrong for the lead-cart contract.

⭐ SNAP-2 HAS TWO APPLICATIONS AND ONLY ONE CHANGES. Fred: "i am talking about route planning, not track recording. snap2 applies to each cart's track recording individually currently." The recording side snaps each cart's track ONTO trails — it consumes trails as targets, never tracks — so removing tracks from the target set cannot break it. ⚠ One track per cart per database currently.

Likely small: stop passing the track list to RouteManager.snap(lat, lon, trails, tracks, 30.0). Snap eligibility separates cleanly from display and from tap-for-details.

⚠⚠ VERIFY: this AVOIDS the whole-line bug, it does not fix it. A recorded track is ONE continuous LineString while curated trail networks are pre-segmented — that is why dropping a point ingested the whole track and trails behaved. But Geofabrik ships OSM ways, and a long way is a long single LineString. Test route-drawing on one deliberately long OSM trail before concluding the symptom is gone.

⛔ Do NOT physically split stored tracks or trails. Changing geometry changes geom_hash → breaks dedup and orphans every lineId. If a fix is needed it is linear referencing in Kotlin: record the snapped POINT and its position along the line, never the line's whole geometry.

⭐⭐ THE onX BENCHMARK (Fred 07-30) — the structural case

onX is vector-based, does three presentations, allows the map to be changed, at ~¼ our storage. Our own device data agrees: the 07-26 delete log showed one SAT job walking three near-identical stores at z18 (SAT 10,295 · SAT_LABELS_TRANSPORT 10,292 · SAT_LABELS_PLACES 10,294).   • Vector is paid once and serves every presentation. One dataset restyled client-side gives satellite-with-labels, topo and road. Raster pays the full price per presentation — five stores today.
  • Switching maps becomes free — a consequence of the data being geometry rather than pictures. Not matchable with raster at any storage budget.
  • Vector stops at ~z14 and the client renders deeper. Since z15–18 is ~98% of raster tile count, vector does not shrink those levels — it removes them.
  • ⭐⭐ DOWNLOAD TIME IS A RELIABILITY METRIC, not a storage complaint (Fred). "8 hours to download an area that will not be ridden." A long job fails partway, needs retry logic we know is imperfect, demands mains power, and gates ride-readiness. The yardstick is time-to-ride-ready and probability of completion. Every open queue defect is amplified by long jobs and materially reduced by short ones.

⛔ CORRECTION TO MY OWN ANALYSIS: I talked the saving down to ≈20% and let that stand as if it settled the question. It answers a narrower one — retiring one label store, on one corridor, in one presentation. The "whole-state road vectors don't shrink with corridor" objection holds for a single corridor in a single presentation and stops being decisive once amortised across three presentations and repeat rides in a region. I was defending a narrow reading of a number instead of testing the case.

⭐ What stays true regardless: satellite imagery is raster, permanently — roughly the ~21,700 floor. The saving is everything that is not photography.

Convoy is a fork/extension of core Meshtastic's messaging. 🔴 STILL OPEN — the A/B decision

(A) BRIDGE — convoy is its own native iOS app consuming mesh messages from the separate Meshtastic app over a local port. Less code; adds a runtime dependency + iOS-lifecycle fragility. (B) FORK — import Meshtastic's BLE/mesh and extend, as on Android. More work; no runtime dependency; same architecture as Android. Trade: effort favours A; field reliability + Android-sameness favour B. For an off-grid safety app, "bridge dies if iOS backgrounds the neighbour app" is a real mark against A — leans B, not decided.

Settled

  • Three surfaces split on connectivity: PC = planning-only web app (no mesh, no radio, online) · Android + iPad = off-grid native convoy execution. Convoy cannot be web.
  • SwiftUI REJECTED for presentation — does not port to a browser, zero reuse of the Android web layer. Swift's only job on iPad is the native shell (mesh source + WebView host + JS↔native bridge).

  • KMP is the natural target — logic is already Kotlin; migration is incremental, expect/actual is literally "configured API resolves per platform." Does not let you fork Meshtastic-Apple (that is Swift); produces a shared logic module a Swift shell consumes.
