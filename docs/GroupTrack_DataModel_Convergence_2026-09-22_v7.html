The flow

Config inheritance — the rules (Fred, 2026-09-22)

Organization is the top level, with an optional relationship to a ride. Leader is the second level, with an optional relationship to an org and to a ride: a leader can inherit the org's config (channel, keys and config data) or have their own. A ride inherits the org's config through the leader's config, and a ride can generate a new config if the leader requests it.

StepRule
1 · RideThe leader requested a new config for this ride → the ride's own config
2 · LeaderOtherwise → the leader's effective config: their own, or their org's if they inherit it
  • ⭐ Select, never merge — a level inherits a whole config (channel, keys, config data together); no field-level overrides.
  • Invariant: every ride has exactly one leader (V3 rides.organizer_id is already NOT NULL). So there is no default rule — resolution always ends at the ride or the leader (Fred).
  • Invariant: every leader has an effective config — own, or the org's. The first time a leader without one creates a ride, one is generated (2.7: the leader's named event config).
  • The path always runs through the leader: an org ride whose leader has their own config uses the leader's.
  • ⭐ The default is not part of the ride model — it is the out-of-the-box SETUP config (Fred): a known-good configuration that proves a radio configures correctly and connects to the app. The upgrade lands a radio on it, and it is what you test with. No ride resolves to it, so its effectively public key carries nothing real.
  • ⚠ Resolved when applied; the .convoy file carries the values current when sent (riders are offline). An org rotation after sending needs a re-send by email, or a server push at V3.

Keys — local and server keys are independent; sync maps them (Fred, 2026-09-22)

Riders and organizations are created on the device with a unique LOCAL key. Local and server keys may differ, so a mapping happens during sync. A tablet never waits on the server to create anything.

EntityCross-platform key
Riders (users), organizations, rides, enrollments, surveys, followsMapped — local key ↔ server key
Spatial artifactsgeom_hash — the content is the key; no mapping
ConfigsThe GT id — it is the network name and must be identical on every device; no mapping
  • One device table, sync_keys — entity type · local key · server key · synced at. A row exists only once synced, so no entity table carries an empty "server id unknown" column (CODE RULE 1).
  • ⛔ NOT parents-before-children (Fred): parents are OPTIONAL in the local model — an org is optional for a leader and for a ride; a rider needs no org. The only required relationship is every ride has its leader. So sync works by reference, not by hierarchy:
    • An empty optional reference goes up empty — a ride with no org syncs as a ride with no org; nothing waits for a parent that doesn't exist.
    • A present reference is resolved on demand — if it points to a record not yet synced, that record is synced first, then the reference is translated (to the server key going up; to a local key, with a new sync_keys row, coming down). No global order.
    • The one required reference always resolves — a ride's leader exists on the device that created it.
    • These optional references meet CODE RULE 1: each has its documented reason — the relationship is optional by design.
  • ⚠ Retries must be safe: each upload carries its origin — device + local key; the server keeps it and recognises a repeat instead of creating a duplicate (a lost reply at a trailhead must not make a second ride).

Resync strategies — what moves, in which direction, and who wins

Scope (Fred, 2026-09-22): the models become cohesive on both platforms, with a clear resync strategy for every entity. The code that performs it is 3.0. Estimated two days — the content stayed the same; it moved into new structures. The real design work is the ride config process (inheritance) and the spatial side on AWS.

Three principles that remove most conflicts by design

  1. Content-addressed identity — spatial artifacts are keyed by geom_hash; the same geometry is the same thing on both sides.
  2. Immutable configs — a config never changes; rotation makes a new one. Configs cannot conflict.
  3. One writer per field — leader owns the ride, rider owns their survey and their reply, the server owns organizations. Only the rider's own profile has two writers.
