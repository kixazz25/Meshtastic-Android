1. Why the network costs so much

Network distance bears almost no relation to straight-line distance.

legstraight linenetworkratio
Trailhead → Rock Quarry Spring11.7 mi 21.3 mi1.8 : 1
Cooper Knoll → Trailhead12.7 mi 28.5 mi2.2 : 1
Rock Quarry → Panguitch Lake Resort~2 mi 32.9 mi~16 : 1
Cooper Knoll → Lake View Resort~2 mi 2.2 mi1 : 1

Two points two miles apart can cost 33 miles or 2, depending entirely on whether the trails happen to connect. A rider looking at a map cannot predict this, and that is the whole argument for showing it rather than making them guess.

Supporting conditions, same run:

  • Main connected component is 51% of nodes — half the network is fragments joined to nothing
  • Only 91 of 214 POIs snap to the routable network within half a mile
  • The Panguitch trailhead itself snapped 3,814 ft — over half a mile from anything routable

2. The design

Fred, 08-24: "we are adding intelligence to the point drop to ensure the points are realistic to the mileage ... then a scoring model that includes high scored user points ... the rest is adding scoring and mileage."

Stage 1 — live feasibility while pins are being dropped

Not a gate at the end. Every drop recomputes and redraws.

on each dropwhat the rider sees
Snap to nearest node on the main component How far the pin moved. A point that snaps to a fragment is unreachable and says so — a different problem from being far.
Rebuild the distance matrix Running total: "your points now need at least 93 miles"
Solve the exact tour The shortest route so far, drawn on the map, updating as points are added and removed
Report the marginal cost What THIS pin added. 32 miles reads very differently from 2.

⭐ THE LINE IS THE EXPLANATION

Fred: "while we are doing this we can show the shortest route as it evolves between point selections."

A number saying 93 miles is abstract. A line jumping thirty miles across country and back to reach one pin is immediately obvious, and it shows the visiting order too — which is not the order they were dropped.

Stage 2 — the scorer, unchanged

On PROCEED the tour becomes the skeleton and its length the floor. ceiling − tour is the surplus, and the existing engine spends it backfilling features and avoiding retrace.

⭐ THE ENGINE DOES NOT FORK. A rider point is a feature worth a great deal more, nothing else. Explore mode is the same call with no user points and the whole budget as surplus.

Which also means a point it cannot afford is simply not picked up, rather than the search failing — and that is exactly what "to the best of my ability" should mean on the summary panel.

⚠ ZERO SURPLUS IS THE COMMON CASE, not an edge case. At Panguitch three points cost 93.5 against an 80 ceiling. The scorer must handle a negative or zero surplus gracefully — the route is then just the tour — rather than assuming it always has miles to spend.

⚠ RUN THE DIJKSTRAS SEQUENTIALLY AND RELEASE EACH. The 08-23 OOM was 112 simultaneous distance tables with boxed keys on a 256 MB heap. Eleven is nothing, but the habit costs nothing either.

4. Decisions taken

QuestionDecision
Hard limit on points? No. The rider watches the number climb and stops. Blocking would hide the option of raising the mileage band instead.
Mileage editable during pin drop? Yes — it is the other half of the trade. A rider seeing 93 miles may raise the ceiling rather than drop a point, and cannot if the control was left behind on the setup panel.
Style of the evolving line? Provisional — thinner, dashed, distinct. It is a feasibility sketch, not the ride. Cleared when the search starts so real routes are not drawn over it.
Subset search — "which of your ten fit"? Held back. It cleans up after a bad situation; live feedback prevents it. And the data says the answer is often none, which is not a useful thing to compute.
Seed points from an existing track? Nothing to build. Fred: "a user can display his track on the map, pick things he liked and then run the engine." The track is already displayable and the pin drop already exists — the app need not know a track was involved.

5. Implementation notes

  • Dijkstra must return PATHS, not just distances — predecessor tracking. The evolving line needs the geometry. Cheap, but it changes what the matrix function hands back, and it is worth writing that way from the start rather than retrofitting.
  • Drop any point unreachable in EITHER direction, not just from the trailhead. Same-component membership makes a one-way failure unlikely, but unlikely is not checked, and an infinite entry reaching Held-Karp returns infinity for a reason nobody can see.
  • Duplicate POIs exist. Scenario B drew "Navajo Lake Spring" twice, 0.01 miles apart. Dedup the pool before offering it.

6. Also measured — dead-end spurs

Fred, 08-24: "a trail that is a spur with no feature at the end is a dead end trail. But it must have a view, a cave, a water feature. Some go 300 yards and dead end in the middle of nowhere."

1,388 dead-end spurs on the main component. Only 38 — 2.7% — have a feature on them.

The clean cut is "short AND featureless", not length alone. At 300 yd that removes 606 and loses none of the 38 worth riding. Median spur length 0.198 mi. This is a data cleanup, not a scoring change — a 300-yard stub ending at nothing is a digitising artefact and no retrace penalty makes its presence correct.

7. ⚠ Caveat on every number here

The prototype ran against D:\nav_test\grouptrack_spatial.db, which holds 216,616 trails across several states and reported 276,407 corridor edges at this anchor.

Droid 2, holding Utah alone, reported 27,215 edges and 62 POI nodes for the same anchor and built four routes with no OOM.

The queries are identical — both a bbox overlap with the same argument order — so the difference is the DATA. The shape of these findings holds; the magnitudes should be re-measured against a single-state copy before any threshold is set from them.

One thing that caveat settles positively: the 08-23 REACH = ceiling / 3 OOM fix is holding comfortably. 27,215 edges and 62 POI nodes on device, against the 53,711 edges and 112 POI nodes that exhausted the heap. A 60×60 mile cap on the corridor box is belt-and-braces rather than urgent — the current formula gives 53.4×53.4 at an 80-mile ceiling and only exceeds 60 above a 90-mile band.
