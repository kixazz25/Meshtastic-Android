What the feature does

The user downloads a Geofabrik state extract in their browser. The app detects it, adopts it, reduces it to a small local database, and stages it for import. GroupTrack never obtains, hosts, or distributes OSM-derived data — which is what keeps ODbL share-alike off Fred entirely rather than merely mitigated.

Architecture rules (durable)

RuleStatement
R1Stage is DERIVED FROM DISK, never stored. No status field anywhere.
R2Only the zip and the skinny are recovery points. The .gpkg never is.
R3Existence means COMPLETE — .part + atomic rename.
R5Derivation happens at MOMENTS: panel open, job done, return from background.
R7On ACQUIRE entry, sweep debris only. Never blind-delete the directory.
R1's unplanned payoff. Because stage derives from disk, the panel can be destroyed and recreated and lands in exactly the same place. That rule was written for crash recovery — it is what makes C3's area-selection handoff possible with no state flag at all: row 3 closes the panel, the map's bbox submission relaunches it, and nothing needs preserving across the gap.

C1 ACQUIRE

  • MediaStore query, not a filesystem scan — browser-agnostic and location-independent. findCandidates() queries MediaStore.Downloads.
  • adoptCandidate() copies via ContentResolver.openInputStream → .part → atomic rename. Not renameTo — content:// plus cross-volume.
  • probeDownloads() returns a sealed AcquireProbe: NotFound / BadFile / Found / Several. Deliberately no StillDownloading — Android browsers are indistinguishable from "not done yet".
FIELD FIX — dated filenames. Geofabrik serves the same product under two spellings: utah-latest-free.gpkg.zip and arizona-260728-free.gpkg.zip. The probe demanded "latest" and reported "extract not found" for a 610 MB file sitting in Downloads. Now accepts either.

Slug derivation strips the trailing -latest or a trailing 6–8 digit date. Not "text before the first hyphen" — that would reduce north-carolina-260728 to north, and nobody would notice until a two-word state.

C2 REDUCE

The catalog — what gets extracted is data, not code

assets/osm_layers.json declares each layer's source table, target table, columns, and optional filter. Fred: "a json to control items placed in skinny import file … so we edit json rather than recompile code."

An asset alone would not have delivered that — assets are baked into the APK, so editing one still means a rebuild. The catalog is therefore read from an on-disk override at /sdcard/Documents/GroupTrack/config/osm_layers.json if present, falling back to the asset. Public directory on purpose: run-as is blocked on release builds, so app-private storage is not reachable by adb push.

A broken override falls back and logs rather than bricking the feature. The failure mode of a hand-edited config is a typo, and a typo should cost you your customization — not the import.

Shipped state: trails, places, natural enabled; pois present but disabled. Flipping one boolean and pushing an override is how you find out whether 48k POIs help or clutter — without a rebuild and without another 610 MB unzip.

The decoder

Ported from osm_gpkg_subset_v2_2026-07-27.py, itself written because v1 would have lied: it emitted WKT as "lon lat, lon lat" at fixed precision while the app writes comma-with-no-space and shortest-round-trip Double.toString(). Every feature would have reported as new.

THE SIGNED-BYTE TRAP. Python's blob[3] is unsigned 0–255; Kotlin's Byte is signed. A direct transcription of (blob[3] >> 1) & 0x07 sign-extends and returns the wrong envelope size — which starts the WKB read at the wrong offset and yields plausible garbage coordinates, not an exception. Every byte read masks 0xFF first.

⚠ Correction made during the work: the GPKG flags byte uses only bits 0–5, so it never exceeds 0x3F and cannot sign-extend on valid input. The mask there is defensive. The mask that is genuinely load-bearing is in geomHash, where SHA-256 digest bytes are uniformly distributed and roughly half exceed 0x80.
One thing got simpler in Kotlin. The Python contorted itself to imitate Double.toString() and carried a warning about exponent notation near the prime meridian. In Kotlin we are the authority — whatever Double.toString() emits is by definition what the app emits. The edge case does not get handled; it stops existing.

Point layers run first — the decoder self-test

After the GPKG header a point is two doubles: almost nothing to get wrong in the body. So a bad envelope offset shows up against a town you recognise in seconds, rather than silently poisoning 89,536 linestrings where it is invisible. Any point outside the layer's own declared extent aborts the run before trails are written.

Validated on the PC first: Phoenix decoded 0.05 km from its known position, 1,581 of 1,581 Arizona places inside the declared extent.

Progress model

Fred: "a simple counter per type, what % of that type has processed, check box when type is completed" and "time is preferred just relative to each type being transferred."

No blended bar, no whole-job ETA. Unzip moves BYTES; passes move ROWS; per-row cost differs by orders of magnitude between a 1,581-row places pass and a 134,242-row trails pass. Each type owns its denominator, and the rate window never crosses a type boundary — carrying a rate across one is exactly how the shipped download ETA came out ~50× long.

⚠ Two bugs found by using it, and their real causes

1. PRAGMA journal_mode=OFF returns a row. SQLite reports back the mode it settled on, making the statement a QUERY — and Android's execSQL rejects anything returning data. The Python does the identical thing legally, because sqlite3.execute does not care. The transcription was faithful; the assumption that both APIs tolerate the same statement was not.
2. Progress rows never ticked — and the throttle was NOT the cause. My first diagnosis blamed the 30-second publish interval. Fred's observation — "unzip logged progress, only trails did not" — ruled that out, since a throttle would hit both equally.

Real cause: WorkManager DISCARDS progress Data on a terminal state. getProgress() is empty once a worker finishes, so the worker's final forced publish is real but unreadable. Earlier layers escaped because a LATER pass published while still RUNNING and carried their completed state along. Nothing follows trails. Fixed in the panel: a SUCCEEDED state means every layer completed, by definition.

The 30-second tick was a contributing error — sized against my estimate of 8–20 minutes per pass when reality was 40 seconds end to end.

⭐ The storage move

The working directory was originally in getExternalFilesDir(). On a release build that is unreachable by anything: run-as blocked by signing, adb blocked by Android 11+, no file manager can browse Android/data.

Two consequences: an extract could not be inspected without writing an export feature to work around a directory choice; and a user who downloaded the wrong state had no way to delete a 610 MB file from inside the app or outside it — the only exit being Settings → Clear Storage, which also silently revokes All Files Access, breaking the feature they were escaping from.

Moved to Documents/GroupTrack/osm/ with one-shot migration on first path resolution. The planning state file already lived in Documents/GroupTrack/state for exactly this reason — the decision was on record and had not been applied here.

⚠ Files now survive uninstall and are not cleared by Clear Storage. Right for a 610 MB extract, but it makes CANCEL the only cleanup path.

CANCEL — every stage needs a way out

Fred, on being unable to remove a wrong download: "that is not really handy because we cannot get rid of it now."

CLEANUP existed but was armed only at IMPORT, so at EXTRACT it was greyed out — the one control that would have helped was disabled precisely when needed.

The general lesson, worth more than the button: the pipeline was designed as a forward path, and the only reverse gear was parked at the end of it.

CANCEL sits at the bottom of the panel rather than beside EXTRACT — bottom placement removes the misfire risk instead of mitigating it, and needs no RowSpec or StageRow change. It also closed a gap neither of us had named: there was no way to stop a running extract. The worker already checked isStopped; nothing called cancelUniqueWork.

⭐ Verification — the evidence C2 is correct

Device-built skinny compared against one built by the validated Python:

device rows whose geom_hash exists in the reference: 89,448 of 89,536 (99.902%)

shared osm_id, disagreeing hash: 58
  GEOMETRY CHANGED : 58     real OSM edits between the two extracts
  FORMAT DIFFERS   :  0     would have been a port bug
Several of the 58 have identical point counts but different coordinates — exactly what a mapper nudging a trail looks like. Had the WKT contract diverged, all 89,536 would have mismatched, not 58. This proves the envelope offset AND the WKT contract byte for byte, which is what makes geom_hash dedup trustworthy.

⛔ Lesson: verify identity before diagnosing behaviour

Hours were lost to adb commands pointed at com.geeksville.mesh — the Kotlin package. The installed application id is com.grouptrack.android, renamed for Play. Source package and application id are independent.

Every dead end traced to that one error: empty ls, an rm -rf that deleted nothing, a false "Arizona is gone" reading, and three invented theories (Android 11 restrictions, secondary volume, MediaStore ghosts). pm list packages | grep -i geeksville returns nothing and would have ended it in the first minute.

When several unrelated commands all return "not found", suspect the path, not the platform.
