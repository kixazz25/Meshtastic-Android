Route lifecycle — SETTLED MODEL (full detail; Item 1 to build)

A route is EITHER an in-progress draft (JSON file) OR a completed spatial-DB row — never both. The JSON is interim storage holding the SAME data the completed-save consumes (the vertex chain), so a route can be picked up, redisplayed, and editing continued. Graduation writes the DB row and deletes the JSON.
  • R1 Either/or — draft-file XOR DB-row. Graduation: write row + delete draft.
  • R2 Identity — in-progress identity = the typed NAME (set at New). Route id is assigned ONLY at graduation to the spatial DB, under DB dedup rules. No route id exists while a route is a draft. Draft world = name; DB world = id. (This replaced an earlier "currentDraftId" framing — the in-progress key is the name, not a generated id.)
  • R3 Save exits — EVERY save (completed or in-progress) EXITS route mode. To continue editing an in-progress route: Save In Progress → then RE-SELECT it from the In-Progress list. There is NO mid-session "save & continue" and NO in-place state promotion. Save closes; select reopens. (This simplification was made deliberately this session to remove the messy mid-session promotion path.)
  • R4 State fixed at launch — the entry row is the launch fork: New ⇒ NEW for the whole session; Select In-Progress ⇒ RESUMED for the whole session (carrying the name). The adaptive Save/Discard screens read this fixed state; it does not change mid-session.
  • R5 Writes minimal — the ONLY writes are: create-draft, overwrite-draft, insertRoute(+delete-draft on graduate), delete-draft. Roll-back, discard-new, and cancel NEVER write.
  • R6 Both maps — identical on ConvoyScreen (convoy map, LF) and ConvoyMapViewerScreen (planning map, CRLF), driving the shared RouteManager singleton; toolbar ConvoyRouteToolbar CRLF. cat -A before every patch (endings flip across commits, esp. after git restore).
  • R7 Vertices not wkt — the draft stores the FULL vertex chain (lat, lon, lineId, lineType, segmentIndex, t, snapped); wkt/bbox are DERIVED at graduation by replaying buildWktAndBbox, so a resumed draft graduates through the IDENTICAL completed-save path. Vertices-not-wkt preserves true editing on resume.

Section field for same-name multi-segment items (NEW cleanup item — Fred surfaced 2026-06-05)

The geom_hash already does its job (dedup + identity) — that is NOT the issue. The ACTUAL problem is the recurring human question "why does this trail appear multiple times?" FIX: add a separate section field on the row. On import, when multiple rows share a name but have DIFFERENT hashes (genuinely distinct segments), assign section 1, 2, 3… to those rows. A name with a single row gets NO section (displays plain — no "section 1" on a one-piece trail). The hash is the DETECTOR (confirms the rows are distinct); the section is STRUCTURED DATA, not text baked into the name.
  • Why a separate field, NOT a number in the name string: the segments always appear back-to-back, so a number jammed into the display name ("Cedar Pass 2") is noise. As a field: (1) the stored name stays clean ("Cedar Pass") so search / group-by-name still work naturally; (2) section is a real value you can FILTER on, sort by, count — not a string to parse back out; (3) singletons simply have no section, so no ugly "Section 1" on a one-piece trail. Display shows section as a quiet SECONDARY element (e.g. "Cedar Pass · 2" or a sub-label), available for filter/display logic.
  • Trigger: on import, for a name with N rows and N distinct geom_hashes, set section = 1..N on those rows; single-row names leave section null/0.
  • Scope (like NULLs, import-only): only arises on IMPORTS. In-app created routes/tracks get a deliberate unique name at creation (R2 — typed name is identity), so they never hit this. The section assignment belongs on the import path; display reads the field.
  • Relationship to the two other naming items (keep distinct): (1) NULL → 'Not Named' (fallback for nameless); (2) same-name multi-segment rows are VALID, do not merge (copies==distinct_geom — confirmed); (3) THIS — add a structured section field (1..N) to same-name distinct-hash rows so the user sees numbered sections and stops asking why a trail "repeats".
  • Open for the design pass (decide then): display format for the extras ("· 2" vs a sub-label vs a column); numbering/ordering basis (import order, spatial/connected order, arbitrary-but-stable); whether section also feeds a "show all sections of this trail" filter. (Assign-at-import is DECIDED — see below — so it's no longer open.) Folds into Item 3 (My Tracks display refactor).
  • CHOSEN MECHANISM (2026-06-05): an end-of-import SQL pass that (a) fixes NULLs: UPDATE … SET name='Not Named' WHERE name IS NULL, and (b) populates the separate section field for same-name multi-distinct-hash groups. Numbering: first occurrence is IMPLIED (blank/null section — displays as just "Cedar Pass"); additional occurrences get 2, 3, … N to mark their uniqueness on the map. So only the EXTRAS carry a visible number; the first looks normal. Writes to section, NOT name — keeps name clean and searchable.
  • RESOLVE AT IMPORT, NOT AT READ (decided 2026-06-05): the name/section is read in TOO MANY display/filter places to control the numbering at read time. geom_hash size (reference fact)

  • geom_hash = SHA-256 over the raw WKT = 256 bits / 32 bytes. Stored as TEXT hex digest = 64 characters per row (base64 would be ~44). At ~49K trails ≈ 3 MB of hash text — trivial. Collision probability effectively zero at this scale; safe identity key. (Per-type UNIQUE(geom_hash) is what makes the multi-segment trails coexist as distinct rows.)

⚠️ DB lifecycle on schema change — release artifact, NOT install-path logic (Fred refined 2026-06-05)

CORRECT MODEL: removing the existing DB is a deliberate RELEASE artifact, tied to a SCHEMA CHANGE — not something the install or update process does. Rationale: the automatic rebuild already covers the normal case (if data does not exist, the app rebuilds it — existing behavior). So normal install/update needs NO special DB handling. You only add a deliberate DB-removal step, gated to schema-change releases: that release clears the old DB so the automatic "no data → rebuild" lands on the NEW schema.
  • The inversion: do NOT burden the install/update path with detect-and-check-pre-existing-DB logic (an earlier framing this session). The automatic rebuild-if-absent already handles the normal case. Control belongs at the RELEASE, which actually KNOWS whether it changed the schema — the install path doesn't and shouldn't.
  • How it works: (1) normal release, no schema change → do nothing; existing DB is used; if absent, auto-rebuild. (2) schema-change release → the release carries the DB-removal artifact → old DB removed → auto-rebuild produces the new schema. Removal only ever fires on a schema-change release.
  • Second option — build/load/unload hook: this same release-time point gives a place to LOAD / TRANSFORM / UNLOAD data when required, instead of plain remove. So the artifact is a release-time DB-lifecycle hook: DEFAULT = remove (let auto-rebuild happen); OPTIONAL = load/transform/unload for a schema change that must PRESERVE user data across the migration.
  • CONTROL SURFACE — "save and reload data" checkbox (Fred 2026-06-05): a single checkbox on the schema-change release artifact gives FULL control of the DB upgrade path: unchecked → remove DB → auto-rebuild fresh new-schema DB (data discarded — for re-derivable data); checked → save existing data → rebuild on new schema → reload data into it (data preserved across migration). One switch covers both upgrade strategies, chosen per release at the point where the release knows what its schema change requires. Net upgrade matrix: normal release → nothing fires; schema-change + unchecked → remove + auto-rebuild; schema-change + checked → save→rebuild→reload.
  • HOME = the release JSON (app artifacts): the control lives in the release JSON as part of the app artifacts — two fields: db_name_to_delete (which DB the schema-change release removes) and a reinstall_data flag/checkbox (the save-and-reload control). The release carries the intent; the app reads it at the schema-change boundary.
  • ⚠️ SHAPE DELIBERATELY DEFERRED — do NOT specify the reload mechanism now: we do NOT need any code or shape for the data save/reload yet. When it's actually needed it could be "rename existing DB and repopulate with logic" OR "a simple table unload and load" — but we do not give it that shape until we HAVE to use it. The release JSON reserves the control point (which DB, whether to preserve); the HOW is decided at the moment a real migration defines its requirements. (Same principle as the rest of the method: don't build/specify a mechanism before a concrete need defines it — specifying the reload shape now would be guessing at requirements we don't have.)
  • Why this is better than per-install detection: (a) no new logic in the hot install/update path; (b) decision sits where the knowledge is (the release knows the schema changed); (c) leverages the existing auto-rebuild instead of duplicating it; (d) the same hook scales to data-preserving migrations via the load/unload option.
  • Background that prompted this (tonight): tester uninstalled 2.4 → installed 2.5 (new install, schema changed 2.4→2.5).
