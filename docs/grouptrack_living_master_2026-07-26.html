🔴 NEW OPEN ITEM #1 — TURN OFF MAP REFRESH ON SOURCE CHANGE (do first)

DO FIRST stop-the-bleeding, not a root-cause fix

What happened (07-23, on the shipped 2.6c build)

The REPLACE/refresh function on the map-source select screen “does not behave”: it spawned 3287 downloads in the queue, lat/long spanning the whole continental US. Downloads then stopped working entirely (“system just sits”).

⚠ Cancel All does NOT persist. Cancel appeared to clear the queue, but all 3287 jobs resurfaced on restart — the clear happens in memory and is never written to disk, so loadQueue re-reads the stale file every launch. This is the boot-loop mechanism, demonstrated — just without a crash.

⛔ No recovery path exists on a release build. adb run-as = access denied (debuggable only). X-plore CANNOT reach Android/data/com.geeksville.mesh/ and offers no grant option — Android 13+ removed third-party file-manager access to Android/data entirely; MANAGE_EXTERNAL_STORAGE explicitly excludes it and the document-tree picker refuses it. Only root, adb-on-debuggable, or the app itself can read there. The only escape is Clear-App-Data.

Resolution this time: the queue eventually drained on its own (ended at 4 entries processing normally). App data was NOT cleared — but the queue file was never inspected, so the bad bbox was never captured.

The decision (Fred 07-23)

Turn off the JSON write / auto-refresh when a map source is changed. Refresh becomes manually requested as an Area download — which rides the already-hardened submitDownload → enqueueArea → segmentCells path. This removes the thing that spawned 3287 entries without needing the bounds bug diagnosed first.

Build notes

  • Scope it first: sed -n '255,290p' ConvoyMapSourceScreen.kt (the enqueueRefresh call site at :271) and the state at :81-83 (refreshSlot / refreshTileCount / refreshEnqueued). Determine whether refresh fires AUTOMATICALLY on source selection or sits behind a button — that decides whether to gate the call or disable the control.
  • DISABLE, don't delete. Gate it behind a clearly-marked constant or comment it out. The bug is still undiagnosed and the path will be wanted when it's revisited — deleting now means reconstructing later.
  • ⚠ This does NOT fix Cancel All. The persistence failure is a separate defect: any future bad queue still resurrects on restart. Turning off refresh removes the most likely source of a bad queue and buys time; it does not close the hole.
  • ⛔ DO NOT run replace-map-source again until this ships — recovery costs an hour and possibly all app-internal data.

Root cause still open (for when it's revisited)

Leading hypothesis, unverified: the bbox handed to enqueueRefresh is not the user's viewport — a default/zero-initialised value, or swapped bounds arguments. Bounds-order is already the standing suspect for the “map REFRESH no longer works” regression; these may be one defect. Note 3287 ≈ ceil(enormous/50K) — segmentation worked correctly on garbage input, so the bug is upstream of segmentCells. Compare sed -n '255,290p' ConvoyMapSourceScreen.kt against sed -n '218,250p' ConvoyDownloadQueue.kt side by side for argument order. Also read sed -n '440,490p' ConvoyDownloadQueue.kt — :473 declares val bad = File(..., "download_queue/" + QUEUE_FILE), suggesting some quarantine handling already exists, and it is likely the same function where cancel's persistence is failing.

🔴 NEW OPEN ITEM #2 — RECOVERY SYSTEM FOR APPLICATION-PROTECTED DATA (the “Repair Area”)

NEW 07-23 full design below — buildable

Why this exists

07-23 proved that bad on-disk state in filesDir is unreachable AND unrecoverable on a release build except by Clear-App-Data. The app itself has unrestricted access to its own filesDir — the OS only blocks other apps — so the escape hatch must be built INTO GroupTrack.

⭐⭐ KEY CONSEQUENCE: filesDir holds radio configs, radio backups, users, rides and events — not just the queue. Clear-App-Data is NOT a clean fallback: it destroys every radio backup and the master config alongside the bad file. (Tracks and TILES survive — they live outside app storage in Documents/GroupTrack/data/ and /maps/.) This is exactly why per-file repair is worth far more than a reset button.

Design — the flow

  1. Password gate. Threat model is NOT snooping — it's a tester deleting the wrong thing while following phone instructions, or tapping through out of curiosity. A build-time constant checked against a text field is sufficient (anything in the APK is extractable; the gate exists to make the action deliberate).
  2. Test for repair-area existence FIRST. If one exists → WARN + DISPLAY CONTENTS, and allow adding a new (different) item.
  3. Extract — ONE ENTITY AT A TIME via file picker. NO MASS COPY (“that is too scary”). Each extract writes TWO copies: the working file into the repair area (Downloads), and a pristine pre-edit snapshot into the dated archive.
  4. Edit the file in the repair area, with normal tools.
  5. Copy back AS A GROUP (see below), then remove the repair area.

State rules

  • NO REPLACEMENT of an already-staged item without an EXPLICIT DELETE. Re-extracting the same filename is REFUSED — it would silently overwrite the working copy (and any editing done) with a fresh pull from filesDir. The repair area is effectively append-only; removal is always a deliberate act.
  • DISPLAY what's staged. CANCEL-AND-RETURN discards the repair area, writes nothing to filesDir — and KEEPS the dated archive (an abandoned repair still leaves evidence of the original state).

⭐ The repair area is a HOLDING area — copy-back is GROUPED

Items are staged across separate one-at-a-time extracts, and the contents are copied back as a group — the staged set is the unit of repair. Extraction is one-at-a-time; restoration is grouped. Rationale: related files that must change together (users + rides, or a config + its backup) would leave inconsistent intermediate state if restored individually.

⭐ Archive naming + retention

Archived files are DATE AND TIME STAMPED — a unique occurrence per extract — held 30 days. Timestamp (not just date) so two repairs of the SAME file on the SAME day cannot collide or silently overwrite each other; every extract is its own recoverable point-in-time snapshot. Mirror the filesDir structure so different files can't collide either:

Documents/GroupTrack/saved/2026-07-23_141205/download_queue/download_queue.json

⭐ The retention sweep runs ON APP OPEN, EVERY OPEN — not on repair-screen entry. A phone that did one repair months ago must not quietly hold stale copies forever just because nobody revisits the screen. Keep it cheap, non-blocking, and fail-safe — a sweep error must NEVER block or crash startup.

⭐⭐ The manifest JSON — work order + audit record

Finishing a repair writes/updates a manifest saying “apply this repair on startup.” It is not just a flag — it carries the work order and makes the apply crash-safe.

{
  "created": "2026-07-23T14:12:05",
  "status":  "pending",
  "problem": "<WHAT ARE WE SOLVING>   — captured at EXTRACT time",
  "repair":  "<WHAT CHANGES DID WE MAKE> — captured at COPY-BACK time",
  "items": [
    { "source":   "repair/download_queue.json",
      "target":   "download_queue/download_queue.json",
      "archived": "saved/2026-07-23_141205/download_queue/download_queue.json" }
  ]
}
  • problem and repair are captured at DIFFERENT moments. The problem is known when you start (prompt at extract); the repair description isn't known until you finish (prompt at copy-back).
  • target settles the destination-mapping problem — recorded at extract time, so there is no guessing and no user re-selection at apply time.
  • Crash-safe: status stays pending until the group write fully succeeds; if the app dies mid-apply the next launch sees pending and retries. Clear only on success. Combined with all-or-nothing validation, a half-applied restore is impossible.
  • Single source of truth: the manifest is also what the repair screen reads to display staged contents, rather than inferring from a directory listing.
  • Placement: in the repair area (Downloads) so it travels with the staged files and is readable/editable. Startup code must tolerate a missing or malformed manifest by simply skipping the apply.

⭐⭐ Apply on RESTART, not on exit

Apply-on-exit still races: Android doesn't guarantee clean shutdown, subsystems may be mid-write on the way down, and saveQueue firing during teardown is the same mechanism that made Cancel All appear to work and then resurrect. Apply at startup, VERY EARLY — before loadQueue, before MapStateStore, before anything opens a filesDir file. That is the only genuinely quiescent moment: nothing holds a handle, nothing has read state into memory, nothing can overwrite the repair afterward. This also resolves the live-handle hazard — the download worker hasn't started yet.

Startup order: APPLY FIRST, then the 30-day sweep (housekeeping must not delay the repair). ⚠ The apply must be as fail-safe as the sweep — an exception there would block startup, the exact failure this feature exists to prevent. Wrap it, log it, leave the marker pending for a retry, and let the app boot regardless.

⭐ Applied-repair HISTORY

On successful apply the record moves to a persistent history file with outcome + applied-timestamp appended (applied, or failed + reason). History persists; the manifest is consumed. Value: three weeks later, “has anyone hand-edited this file, and why?” becomes answerable — a question that is currently unanswerable at all. Keep history entries indefinitely (they're small text); losing the record of what changed is worse than losing the copies. Note a history entry's archived path will eventually point at a purged file once the 30-day sweep runs — fine, as long as the entry says so.

Still open

  • Validate before overwriting — at minimum, confirm each staged JSON parses. Restoring a truncated file would manufacture the exact poison-file scenario this feature exists to escape. With a grouped copy-back: validate EVERY staged item first and abort the whole group if any fails.
  • Auto-backup the current filesDir file(s) before the group write, making the restore itself reversible.

Cheaper complements (consider alongside, not instead)

  • “Reset download queue” button (~30 lines) — clears memory AND deletes the file atomically. Would have solved 07-23 in one tap.
  • Diagnostic mirror — copy queue state to Documents/GroupTrack/ on every save, making it readable via X-plore with no browser at all. Would have shown the 3287 entries and the bad bbox immediately.

NOTE: access and resilience are alternative solutions to the same problem. The repair area makes emergencies survivable; loadQueue tolerant-parse makes them rare. Both are wanted; neither replaces the other.

🟢🟢 NEXT BUILD — OSM TRAIL IMPORT (designed 07-26, ready to patch)

DESIGNED, NOT BUILT Extends trail coverage and snap-2 reach by importing OSM tracks/paths alongside UGRC/BLM. Independent of the renderer decision — it is data, not display.

⭐⭐⭐ THE MANDATE (Fred) — this governs every design choice below

"We are doing a lot of manual steps. This has to be a repeatable rinse-and-repeat process when we are finished. IMPORTS DONE BY USERS."

⛔ Any design requiring a PC, a downloaded script, a hand-typed bbox, or a file moved between machines is WRONG. The bar is the flow that already exists for the 8 catalog sources: open the app → Method B → pick an area → import. Identical to importing UGRC.

⛔⛔ THE LICENSING CONSTRAINT (Fred) — no OSM data on GroupTrack infrastructure, ever

"Cannot put on AWS for licensing reason, has to be a temporary transport structure that is destroyed."

An AWS endpoint serving OSM-derived GeoJSON would be distribution by Fred and would trigger ODbL share-alike. So: nothing OSM-derived is hosted, cached or served from GroupTrack infrastructure — not even transiently. This kills the "AWS endpoint speaking ArcGIS-REST" idea outright, and it is the correct call.

⭐ THE COMPLETE LICENSING POSITION: user's device fetches public OSM data → user's device transforms it → user's device imports it → transport structure destroyed → only the user's own local DB holds the result. GroupTrack never obtains, hosts, or distributes OSM-derived data. Attribution still applies to what is displayed. Consistent with treating OSM exactly like the Utah trails database: a separate source, user-initiated import of a publicly available dataset, not shipped as a derivative product.

⭐⭐ THE KEY INSIGHT (Fred) — the ArcGIS contract IS GeoJSON

buildUrl appends f=geojson, so what httpGet receives and insertFeature parses is a plain GeoJSON FeatureCollection. There is nothing Esri-specific in the RESPONSE — only in the QUERY STRING.

So OSM adapts to a format the importer already speaks. The work is in the FETCH, not the pipeline. Everything downstream is already source-agnostic: insertTrail, source-uid dedup, the INSERT/DROP/ALIAS decision, trail_properties, logIngestion, writeTrailAreaJson.

The flow, end to end

  1. User picks an area (existing Method B UI).
  2. App queries Overpass directly from the device — [out:json];way["highway"~"^(track|path)$"](S,W,N,E);out geom; (out geom; returns way geometry inline, so no node resolution).
  3. App transforms Overpass elements[] → the ArcGIS-shaped GeoJSON FeatureCollection the importer consumes.
  4. Existing insertFeature loop runs unchanged.
  5. Transport structure destroyed. Simplest form = never persist it (transform in memory, let it be garbage-collected). If it must be inspectable mid-import, cacheDir and delete on completion — never shared or app-visible storage.

⚠ WHY THE ACCESS TAGS MUST COLLAPSE TO ONE FIELD: fieldExtras collects every non-core catalog key, but insertFeature only READS four — motorized, surface, county, manager/steward. Anything else is parsed and silently dropped. Live proof: usgs_national_trails declares atv, motorcycle, ohv50 and none of the three ever reach the DB. Emitting OSM's four access tags separately would send them nowhere.

⭐ carto_code stays BLANK on first import

carto_code drives trail line colour, and that mapping is duplicated in THREE hand-synchronised places: ArtifactDetailPanel.kt (~:316, which carries an explicit PAIRED-EDIT WARNING), convoy_map.html (FROZEN), and grouptrack_map.html. Colour keys off the leading digit, so blank falls through to cyan "Unspecified" — visually distinct from every coded government source, honest (OSM has no carto classification), and it touches none of those three files. Assign a real code later, deliberately, once seen rendered. (Alternative "0 - OSM Community" costs a three-file paired edit including a frozen file.)

⚠ TWO TRAPS THAT WILL BITE IF MISSED

  • PAGING. ArcGIS pages via resultOffset/resultRecordCount; the loop is hasMore = features.length() >= PAGE_SIZE (PAGE_SIZE from max_records, default 2000). Overpass does not page — one bbox query returns everything. A response of ≥ max_records features would loop forever re-fetching the same page (dedup skips the rows, but the import never terminates). Either treat an Overpass source as single-page, or chunk the bbox.
  • file:// IS NOT AN OPTION. httpGet does URL(urlStr).openConnection() as HttpURLConnection — that cast throws on a file:// URL. A local-file source is impossible without touching that method.

What actually has to be written

  1. source_type in trail_sources.json — arcgis_rest (default, all 8 existing) | overpass.
  2. buildUrl branches on it — Overpass POST/GET body instead of the Esri query string.
  3. Response transform branches on it — elements[] → FeatureCollection with the mapped property names. This is where OSM semantics live (the Yes/No collapse, the uses synthesis), so insertFeature stays untouched.
  4. Catalog entry #9 — osm_trails, JSON only.

⚠ highway=track with no access tag → leave motorized_allowed BLANK, do not guess "Yes". A track is by definition wide enough for a vehicle, but that is physical capability, not legal access — and legal access is the entire purpose of that column. A wrong Yes is worse than an empty field.

⭐⭐ Why 2.7 and not later — the sequencing argument

The dominant cost is not MapLibre. It is operating on frozen code. ConvoyScreen.kt is frozen to protect the Kotlin↔JS↔Leaflet↔setView↔MapStateStore tangle — and a tracking rewrite must open exactly that tangle anyway. So the choice is: rewrite that layer ONCE with MapLibre as the target, or TWICE. Convoy tracking may benefit more than the map does — live cart positions are the textbook case for data-driven styling (heading, speed, staleness, lead-cart status driving symbol rotation and colour from feature properties, instead of rebuilding markers).

⭐⭐ The cross-platform multiplier

Per the 07-04 planning session, the presentation layer is ALREADY web and is the ~90% shared surface for iPad and PC; SwiftUI was rejected for presentation precisely because it gives zero reuse of it. MapLibre GL JS is a web library — it runs identically in an Android WebView, an iPad WKWebView, and a PC browser. So this is a one-time change to the layer all three surfaces inherit, and the PC planning app gains the most (terrain and vector styling with no offline-tile constraint).

⚠ The corollary is a real risk: doing the tracking rewrite on Leaflet bakes Leaflet into the layer iPad and PC are both waiting on — a long-tailed decision made by omission.

🔴 OPEN ITEM — REFRESH DOES NOT LOG AS A COMPLETED JOB (new 07-24)

NEW 07-24 A map-source refresh job never registers as completed.

⚠ Why this is bigger than a cosmetic status

  • It may be why the ETA has no samples. estimateRemaining() reads the last two COMPLETE entries and completedAt is stamped in markComplete.
