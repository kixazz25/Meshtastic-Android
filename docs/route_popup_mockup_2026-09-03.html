✅ Already stored — this is a read, not new work
  • Miles and the hours range — on the route row as miles, hoursLow, hoursHigh. The range matters: showing only the low end tells a rider the day is shorter than it may be.
  • The prose narrative — written at build time into route_notes, and already exported as GPX <desc>. Nothing needs generating.
  • Trail names with mileage — the same data the compare table sorts by, so the trails carrying the most miles come first.
  • Surface per trail — the lookup shipped today for the compare table works here unchanged.
⚠ Points along the way — needs a decision

There is no "POI" concept on a route today. Three candidates, and they are not the same thing:

  • Waypoints near the line — the rider's own, plus imported ones. A corridor query, and the only source that carries a rider's local knowledge ("gate may be closed").
  • The pins that built the route — already in the recipe, but they are inputs, not places. A rider did not mark them as interesting.
  • Named features the narrative mentions — free, but prose, so there is no distance to show against them.

⭐ Waypoints are the honest answer — they are the only one a rider deliberately placed. Distance-along-route is derived, not stored, so it needs computing when the popup opens.

⛔ Not available — do not design around it
  • Trail width. UGRC's restrictions field is 0.0% populated; OSM's width tag is 155 ways in 93,000. And designated_uses in our own database has no "OHV Wide" at all — 633 rows say "OHV designated" and that is the whole of it.
  • ⭐ The nearest useful thing is "4wd only", 2,143 rows, and roughness where OSM recorded it. Both say what a machine needs rather than how wide the trail is.
⚠ Two import bugs found while checking this
  • designated_uses holds the literal string "null" on 712 rows — it will print as "null" on any card that shows it.
  • 866 rows hold "321", an untranslated code.
