Summary

Three reported defects on the planning map — popups unreliable on trails, no popup at all on tracks, waypoints impossible to drop while route mode was on — turned out to have one root cause and two unrelated contributors. The root cause had been present for as long as the file existed and had never been visible.

Commits: e84117e83 plus the follow-up carrying items 4 and 5.

⭐⭐ ROOT CAUSE — a script block that killed itself at parse time

grouptrack_map.html opened with a <script> block at :9-72 whose first statement was:

map.on('click', function(e) { ... Android.onProximityTap ... });

map is not created until :731. The block threw Uncaught TypeError: Cannot read properties of undefined (reading 'on') at parse time and died entirely, taking two things with it:

  1. Android.onProximityTap was never registered. Short taps never reached Kotlin — which is why onProximityTap had never logged anything.
  2. showProximityPopup was never defined. It is the only definition in the codebase; ConvoyMapViewerScreen.kt:578 calls it by name through evaluateJavascript. Even a successful proximity query had nothing to render into.

The block also held __legacy_proximity_unused, dead by its own comment, whose unbalanced tail produced a second error — Uncaught SyntaxError at the closing tag.

⚠ NONE OF IT WAS EVER VISIBLE. The planner had no WebChromeClient, so every console message went nowhere. Confirmed pre-existing against HEAD~1 — not a regression from any 2026-07-30 change.

How it was found — the method, not the luck

Four theories were worked and discarded before the evidence arrived, each plausible and each wrong:

  • Route mode stuck true — killed by the log: routeMode=false at tap time.
  • Popups bound conditionally at draw time — real defect, fixed, but not the cause.
  • Missing stopPropagation — real, and the 547 ms double-fire proved it, but downstream.
  • Stale bridge capture on the detail panel — still open, unrelated.

⭐ What broke the deadlock was adding a WebChromeClient — eight lines that turned on instrumentation already written and dark. `ARTIFACTTAP` had been logging in convoy since long before; the planner's console had simply never been connected.

THE LESSON: before theorising about behaviour you cannot see, check whether the channel that would show it is connected. An unread log is worse than no log — it looks like evidence of absence.

The two contributors

A. Popups bound conditionally at draw time

The planner bound popups only when route mode was off, at draw time (:249 trails, :401 waypoints, :440 routes). But setRouteMode's suppression works by stashing and unbinding on entry and rebinding on exit — it assumes popups are always bound. A layer drawn during route mode had nothing to stash, so the restore found _savedPopupContent == null and it stayed popup-less permanently. Convoy binds unconditionally (:468/:617/:657), which is why the two maps differed here.

Fix: bind unconditionally; suppression stays with setRouteMode.

B. Missing stopPropagation, and the correction it needed

The log was decisive: trail taps fired twice per gesture, 547 ms apart; track taps fired once. The only difference was L.DomEvent.stopPropagation(e) in the track handler. Without it, the layer click opens the popup and propagates to map.on('click'), whose own popup (autoClose, closeOnClick) closes it again — "same trail, some popup, some don't".

⛔ MY ERROR, CAUGHT BY FRED BEFORE IT SHIPPED: I added stopPropagation unconditionally. Route planning works by tapping ON trails, and swallowing the event at the layer means the vertex never gets placed. Item 3b added the early return the track handlers always had — if (window.__routeMode) return; BEFORE stopping propagation. The pattern was in front of me twice and I did not carry it across.

The waypoint block — a mitigation that became the bug

onMapLongPress carried if (addPointMode) return. Fred's history: it was added because popups were not responding, so long presses were repeated attempts at a popup that dropped waypoints instead. The mitigation treated the symptom of the root cause above.

Fred's rule, now implemented: long press always registers a waypoint, in every state. ⚠ Order mattered — restoring it before the popup fix would have restored the original frustration, so both went in the same build.

Snap radius — a unit mismatch, not a tuning problem

Popups hit-test in pixels (L.svg({tolerance: 44})); snap used a fixed 30 metres. They only agree near z17:

zoom44 px on the groundsnap was
z1821 m30 m
z1685 m30 m
z14340 m30 m

⭐ That is why a tap could pop a trail's name and still free-place the vertex — both behaviours were correct, measuring different things. Radius is now derived from the zoom that was already crossing the bridge on onViewportChanged and being discarded, clamped 15–150 m. VERIFIED z14–z18.
