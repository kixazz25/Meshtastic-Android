Ride config — planning document

2026-09-20 · For the GroupTrack ↔ Natak Mesh conversation. Field attributes, process flows, and the API surface each side owns. Companion to the Communications Layer Design and the Nucleus Integration Design. Self-contained.

⭐⭐⭐ THE ONE-LINE SUMMARY

A rider joins a network with a name and a password. Everything else — the channel, the keys, the radio parameters — arrives as a config and is applied automatically.

⭐ PREFERRED PATH: the Nucleus-based IP attach. Join the node's network, the config comes down, the device applies it to itself and its radio. The other delivery paths exist so nobody is stranded, not because they are the plan.

1 — The three identifiers

⛔⛔ WE DO NOT OWN THE CHANNEL ID. That is a hard stop from Meshtastic — its length, format and semantics are theirs and can change.

ValueOwnerVisible toRule
Long descriptionGroupTrack⭐ Rider, on every screen and panelAlways a long, readable description. What a rider recognises the ride by.
Channel IDMeshtastic constrains itNobody⭐ AUTO-GENERATED: GT + a system-generated unique id. Sized to fit. Never typed, never displayed.
Network ID + passwordGroupTrackRider, typed once⭐⭐ BOOTSTRAP ONLY — the sole purpose is getting a device onto the IP network.

⭐ Generating the channel id removes the truncation trap. An 11-character limit does not matter when the value is generated to fit rather than derived from something a human typed — and if Meshtastic moves the limit, only the generator changes.

⚠ THE KEYS ARE DERIVED, NOT SHARED. A WPA2 passphrase and a Meshtastic PSK differ in format and length and cannot be the same value. One password feeds a KDF; each transport gets a correctly formatted key. ⛔ The derivation must be identical on every build and versioned from day one — two riders on different releases deriving different PSKs from one password is a silent, total failure.

🔴 OPEN: what makes the generated id unique, and across what scope? Two clubs generating independently must not collide — central issuance, or enough entropy that collision is negligible.

⭐⭐ 2.2 Moving to TAK data shrinks this list

Once the APP emits TAKPacket (portnum 72), update timing is an APPLICATION decision. Cadence, content, who is included and what a separated rider receives stop being device settings and become things a release changes.

⚠ But the PROCESS stays identical — same wizard, same archive, same apply. Fewer fields, unchanged mechanism.

⛔ What does NOT change: the radio still needs channel, PSK, region, preset and hop limit. And airtime is still airtime — the app choosing a rate does not create capacity.

3 — Ownership model

⭐ A RIDE is an EVENT. A CONFIG is a NETWORK IDENTITY. A ride REFERENCES a config. Today they are conflated — the channel fields live per-ride, so a club cannot hold a permanent identity reused across rides.

OwnerTenure
Club / orgPermanent, reserved
Ride leaderPermanent, reserved — belongs to the PERSON, across clubs
One-time rideExpires

⭐⭐ CONFIGS ARE NAMED BY RIDE NAME + DATE — WHICH MAKES RESTORE FREE. "The prior config" is not a special case; it is the previous entry in the list, and restore is the same operation as apply. A rider's own home setup is just another named config sitting alongside the rides. Nothing extra to build.

4 — Process flows

F1 — CREATE CONFIG (leader)

Mesh Radio menu. Builds a file holding the config: generated channel id, derived keys, region, preset, hop limit, and whatever position parameters survive the TAK move. Saved under ride name + date, owned by club, leader or ride.

F2 — APPLY CONFIG

List available configs → select → archive current state FIRST → apply to the radio and/or to the Nucleus.

⭐⭐ F3 — REQUEST OVER THE NETWORK (the preferred path)

⛔ NOBODY PUSHES. THE RIDER REQUESTS; THE LEADER'S NODE RESPONDS. The request is the consent — no endpoint exists for a stranger to reconfigure someone's radio.

  1. Rider connects to the network — they already hold the name and password.
  2. Rider REQUESTS the config from the leader's node.
  3. Node returns it.
  4. Device applies it to itself and its radio, archiving first.

F4 — RESTORE

⭐ Select an earlier named config and apply it. Same flow as F2. Nothing extra exists.

⭐ THE LOCAL CONFIG STORE — and why RECEIVE ≠ APPLY

A rider may receive a config a month or two before the ride. Importing it must leave it stored and inert; applying is a later, deliberate step. ⭐ That store is a local version of the hosted database — and the backend, when it returns, delivers INTO it rather than replacing it.

Interim delivery by email

GPX for tracks and waypoints goes by email and loads through the existing import process; maps follow the geometry. ⛔ Decide whether the config travels with it — a config carries derived keys, and an emailed key is forwardable.

Three paths to a configured radio

PathNeeds
⭐⭐Pull over the IP networkPREFERRED. A Nucleus present, rider connected.
⭐Apply from my deviceThe local store. Works with no Nucleus at all.
⚠Apply from any devicePhysical access only — any Android can configure any radio. ⭐ Guarantees nobody is stranded; ugly, and not the plan.

⚠ The trailhead path needs the leader's node present. A group with no Nucleus has only the stored path — so email delivery is not optional for them.

5 — API definition: what is required of the Nucleus

⭐ GroupTrack defines the REQUEST. The vendor implements the RECEIVER. Nothing here is Natak-specific by design — the same contract should let us approach other LoRa/WiFi vendors.

RequirementWhy
READServe the current ride config on request⭐⭐ THE ENDPOINT RIDERS USE. F3 depends entirely on it.
WRITEAccept a network identity; provision the node AND its attached radioLeader provisioning their OWN node only
ARCHIVE + RESTORESave prior state; be able to reapply it⛔ METHOD IS NATHAN'S — they are his devices. He chooses which backup parameters constitute a full reapply.
AUTHOn write and restore⚠ He flagged internet-facing security has not been a focus
RESULTAtomic success/failure⛔ His node holds TWO things — WiFi mesh identity AND the radio. A half-applied config is a node split across two networks.
SETTLINGHow long after a change before the mesh is usable~60 s with a reboot today. The app must wait, not fail.

⭐⭐ STATE THE RESTORE REQUIREMENT AS AN OUTCOME, NOT A FIELD LIST: applying an archived config must return the node to a WORKING state on its previous network — not merely the same values. Testable, and it leaves the method entirely to him.

⭐ Named configs make the ask smaller than "build me an undo" — he needs the same named list, because applying an older entry IS the restore.

🔴 Outstanding questions

  1. ⭐⭐ Does the bridge relay ONLY TAKPacket (portnum 72), or generate a CoT event for ANY Meshtastic position (portnum 3)? A plain radio with no phone still broadcasts on 3. "Hand someone a radio and they appear" is a core promise — if the bridge only carries 72, that rider is visible on LoRa and invisible on the IP mesh.
  2. Does the node keep ONE prior config or a HISTORY? One is simpler; a history matches what GroupTrack already does.
  3. Nucleus config over USB or IP — which, and how?
  4. Exact multicast group and port the bridge reads and writes.
  5. Our packet size and preset, which he asked for — likely the explanation for our congestion figures.
  6. Onboard GPS on the Nucleus: does it, could it, and can it publish to connected clients?

⚠ The framing

⭐⭐ His model is a preconfigured team. Ours is individuals who join and switch per ride. He ships a standard config applied per group at build time; a GroupTrack rider belongs to several clubs and joins a different ride each weekend. That gap is the difference between ATAK and the SxS market he says he wants to reach — and closing it is what a partnership delivers.
