⛔⛔ The correction that matters most today

⚠ I argued that OHV designation supersedes ownership and step 8 could be deleted. WRONG.

⭐⭐⭐ Fred: "that is used to eliminate many rural roads that cluttered the map in order to get trails in public areas."

Ownership is CLUTTER REMOVAL, not labelling. A driveway and a public forest road are both track_grade in OSM with no distinguishing tag — the only thing separating them is whose land they are on.

⛔ So ownership and OHV designation do DIFFERENT JOBS and disagree in BOTH directions: public land with OHV closed (ownership says go, rider must not); private land with permission (ownership says stop, trail is rideable).

⭐⭐ SCOPE, REACHED TWICE INDEPENDENTLY: the western 10–12 states. Fred: the western land pattern — vast federal holdings threaded with ranch roads — is unique. Eastern states are mostly private with public land in discrete parks; the ambiguity barely exists. 🔴 Cheap January test: import one eastern state from OSM and look.

⭐ Federal trail data found — national, not per-state

  • BLM Ground Transportation Linear Features — Limited Public Motorized Trails subset, plus OHV_DSG_PUB_POLY (where OHV use is permitted under CFR). GeoJSON.
  • ⭐⭐ USDA Forest Service FSGeodata — national trails plus which vehicle types are allowed and their SEASONS OF USE. That is motorized_allowed at national scale — the field 07-27 found missing everywhere. Nobody else shows seasonal closure. ⚠ Needs conversion from shapefile.

⛔ ESRI REST caps at 1000 records per request — Utah's 49,125 need paging. Our UGRC import must already handle it; check how.

⭐ Sequence: BLM and Forest Service first. Per-state portals are the long tail.

⭐⭐⭐ The vision — what the separation is for

RIDE DEFINITION IN. AWARENESS OVERLAY OUT.

Layers 1 and 2 take a ride definition — network name, keys, radio settings, ride identity — and produce a map layer of who is where. Nothing above them knows about transports, radios, node merging or channels.

⭐⭐ TESTABLE END STATE, better than the import count: layers 1 and 2 must work with NO LAYER 3 PRESENT. Feed them a ride definition, get an overlay.

⭐ Which makes it portable — GroupTrack's app becomes ONE CONSUMER of the overlay, not its owner. GPX/KML are universal; GroupTrack-specific fields ride in a container other apps skip.

⚠ Cross-app delivery is one-directional — a distribution channel, not a technical partnership.

⭐⭐ COMPETITIVE POSITION: onX Offroad HAS group tracking and it is Starlink/cell based. Our product exists in the gap they cannot serve — and they have validated the category for us. ⛔ Which argues AGAINST the plugin idea: they would need our TRANSPORT, not our layer.

⭐⭐ V3 re-understood

The backend was not abandoned — it was waiting for something worth handing off to. A ride definition carrying route, trailhead, maps and radio config is only valuable if the app can DO something with each. In April it could not.

⭐⭐⭐ And that closes the comms-layer loop: "how does a rider get the channel name and PSK?" — the same way they get the maps. It is a field in the ride definition.

⭐⭐ It also resolves the leader conflict: the NETWORK has no leader (Natak), the RIDE does (ours), and the ride is created before anyone leaves home.

Flow: publish → follow → notify → enroll → ride. ⭐ Following is already built. ⭐ Cold start is smaller than it looks — most of V3 is single-club and works with zero network effect.

⛔ April docs are HISTORY, not a plan. 🔴 First task when V3 resumes is a RECONNECTION — what exists in code vs what the docs say. A walkthrough beats reading. ⚠ AWS is IP-restricted and renewal is MARCH — fix access before March.

Natak Mesh — answered, and one question outstanding

⭐ Bridge mode is NOT gone — only its UI. The module still runs bidirectionally and now carries voice over LoRa. The node relays, not the app.

⭐ TAKPacket confirmed — he uses the Meshtastic TAKPacket SDK. SA on 239.2.3.1:6969, chat on 224.10.10.1:17012.

⭐⭐ PARALLEL MESH, not failover. Every CoT packet goes over BOTH WiFi and LoRa with deduplication, LoRa rate-limited. His reason: "the polling required to get quick network switching between wifi and Lora is very tough to get right." Do not choose a transport — send both and dedupe.

⛔ NO LEADER NODE — none privileged, none required, all identical.

⭐ Config: channel URL, web UI, ~60s reboot. Can read existing config and choose whether to overwrite. ⚠ No API, web UI only — but he is open to building one.

⚠ He asked US a question: what is our packet size? He runs small packets at a high-speed LoRa preset. If we are on a slower preset that alone could explain 4-vs-25 — checkable in our own config.

🔴 OUTSTANDING: does the bridge relay only TAKPackets, or generate a CoT event for ANY Meshtastic position it receives? A bare T1000-E with no phone still broadcasts on portnum 3 — "hand someone a radio and they appear" is a core promise.
