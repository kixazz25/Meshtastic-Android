0 — THE ONE-PARAGRAPH SHAPE

The AI route is not a route search that collects scenery along the way. It is the inverse: find the features, work out which combinations of them are reachable in a round trip inside the mileage window, score each combination, and return the best six. The engine's own header states the objective at :61 — poiValue - miles * 0.06, described there as “a CHEAPEST-PATH search wearing a POI costume” — and at :82, “a POSITIVE-SCORE FLOOR IS REQUIRED.” The governing design rule is at :68: “PENALISE, DO NOT FILTER” — rather than generating thousands of candidates and ranking them, find the best, penalise its edges, and re-solve, so ride 2 is the best ride that AVOIDS ride 1.

Stages 1–5 — the graph (read in part)

  • Components — :1893-1905 numbers them by walking g.lAdj.keys, a HashMap key iteration. :1421 then picks anchorNet = comps.maxByOrNull { it.size }, which takes the first on a size tie.

Stage 5b — feature discovery: loadPoisGrid:1695-1735

  • One SQL query: SELECT name,fclass,lat,lon FROM reference_points WHERE lat BETWEEN ? AND ? AND lon BETWEEN ? AND ?, bound at :1710.
  • ⛔ IT HAS NO LAND OR RESTRICTION FILTER OF ITS OWN — only the box bounds and fc in JUNK (:1716). This is why matching the TRAIL filters on both devices changed nothing (Fred, 19:00): the feature query never consulted them.
  • Attachment: a 3×3 cell sweep, nearest usable graph node by if (d < bd) — a STRICT test, so the first row wins a tie — and the POI is kept only if bd <= POI_BUF_MI (0.5 mi). A POI with no usable node within half a mile is discarded entirely.
  • ⚠ The box doubles are bound as TEXT via raw Double.toString(), at all seven bbox call sites (:367 :404 :437 :581 :732 :871 :1710), none through GtJava.jd — the service this project built precisely because Double text differs JVM vs Native (GtJava.kt:24, certified in 15a over 524,768 checks). Round-trip may make it harmless; UNMEASURED, so not claimed. Note also that :1710 binds box[0],box[1],box[2],box[3] while :367/404/437/732 bind box[1],box[0],box[3],box[2] — reversed. Understand before touching.
  • The cap: :1993-2002, if (poiAt.size > maxPoi) — sorts descending by scoreSet, .take(24), then poiAt.keys.retainAll(top). The losers are DELETED, not reordered. :1988-1992 records how much it matters: “capping at 14 gave rides of 3 features, at 24 the same ground gave rides of 7.”
  • ⭐ :2029 var poiNodes = poiAt.keys.toList() — poiAt is a HashMap, so this line freezes hash iteration order into a List, and that List seeds every stage below.

Stage 6 — the distance matrix (:2039-2043)

val terms = (origins.map { it.first } + poiNodes).distinct(), then one full dijkstra(t, g, pen) per term, with dist(a,b) reading out of it. The queue is JPQ (:204), a hand-written heap whose header (:36) says it reproduces “java.util.PriorityQueue's own sift-up / sift-down, so equal distances leave in the same order” — shared code, identical on both platforms by construction. :932's improvement test is strict (if (nd < (dist[nb[0]] ?: MAX))), so an equal-cost alternative never displaces the incumbent.

Stage 7 — the out-and-back filter (:2051-2058)

val keep = poiNodes.filter { p ->
    val a = dist(ok, p); val b = dist(p, ok)
    a != null && b != null && a + b <= req.milesHigh
}
perOrigin[ok] = keep
log.i { "origin $onm: ${keep.size} of ${poiNodes.size} features usable" }

[stated] Fred described this before reading it, 19:43: “I think what happens is we measure the shortest round trip to the poi and only include the poi if i[t] is reachable in a round trip.” Correct, and the code's own section title is “out-and-back filter”. :2047-2049 explains the leverage: removing ONE feature removes every combination containing it — “dropping 4 of 14 leaves 1,024 instead of 16,384, and none are ever generated.”

MEASURED REJECTION RATE: 9 of 24 at Broken Ridge (Droid 1, 11-24). The frozen 2.7e gold records “55 of 81 features usable” on other ground (RouteExplorerCertOld.kt:1741) — 26 of 81 thrown out. Roughly a third of candidates die here, so its boundary is densely populated.

Stage 8 — the pair table and the clique bound (:2070-2101)

  • The pair test: the minimum ride holding both A and B is origin->A + A->B + B->origin. If d1 + d2 + d3 > req.milesHigh the pair can never share a ride, so every combination holding both is dead at every size and never generated. :2074-2076: without it, “sizes 13 down to 6 generated and rejected 3,302 combinations for ZERO results — most of the old 67.8s.”
  • The clique bound: :2090-2100 builds a greedy clique — for each seed in pois, add every p with no impossible pair against the group so far, and keep the largest. ceilingSize is the result, logged at :2101 as descent starts at N features (of M).
  • ⚠ A greedy clique is order-dependent by construction. Adding one feature forecloses others, so a different traversal order over the same inputs can return a different-sized clique. Both loops iterate pois = perOrigin[ok], a List — ordered, but its order was inherited from :2029. And if (grp.size > best) is strict, so the first clique wins a size tie.

Stage 9 — the descent (:2103-2201)

  • :2156 val ranked = poiNodes.sortedByDescending { scoreSet(listOf(it), poiAt) } — [stated] Fred's “loaded in a table descending by the value of the feature”, verbatim. Kotlin's sort is STABLE, so every tie and near-tie keeps the order poiNodes handed it.
  • :2157 val working = ArrayList<Long>(), filled from ranked with two early exits: if (working.size >= workingMax) break (40) and if (survivorsOf(…) >= enrichN) break (20). ⚠ The second means WHERE THE SEARCH STOPS depends on what got in first, not only on what is in the table.
  • Per origin, pool = working.filter { it in perOrigin[ok] }, then sizes descend from minOf(pool.size, testedCeil[ok] ?: ceilingSize) down to 1 (AIFEATFLOOR-2026-11-10: one feature is enough for a ride). Within a size, the longest ride first — :2106: “a rider who asked for up to milesHigh wants the fullest.”
  • :2201 logs working array N feature(s) of M; G combos, K killed by the pair table, S solved.
  • Enrichment: :2221-2227 sorts candidates compareByDescending { combo.size }.thenByDescending { miles } (stable again) and enriches only the top enrichN = 20; :2282 logs the result.
  • Return fill and variations (AIRETURNFILL-2026-11-11): :2299 / :2362-2366 penalise used edges with PENALTY = 2.2 so the ride comes back by another trail and fills toward the ceiling; :2351 rejects anything over MAX_RETRACE_PCT.
  • The six: :2428 for (c in finalC.take(wantRides)), logged at :2430 as ride: N mi, K features.

3 — WHY THE SAME DATABASE RETURNS DIFFERENT ROUTES

[stated] Fred, 19:57: “cannot [for] the life of me figure why they return different routes from the same db.” The answer is not that the data differs. It is that this engine is built to AMPLIFY a last-bit difference into a different route, and it has to be.

To return six rides in under a second from a 2,891-trail network, the engine prunes hard and early, and every prune is a knife-edge decision. Each of these converts an arbitrarily small numeric difference into a different branch:

  1. a + b <= 80.0 (:2055) — a float comparison against a hard constant. a and b are Dijkstra sums of hundreds of haversines. A POI whose round trip lands near 80.000 mi is admitted or expelled by the ninth decimal, and the loser takes every combination containing it.
  2. d1 + d2 + d3 > 80.0 (:2084) — same, but it kills a pair, and with it a whole branch of the enumeration at every size.
  3. The greedy clique (:2090-2100) — order-dependent by construction, and ceilingSize is where the entire descent begins.
  4. Three stable sorts over possibly hash-ordered input (:1995 :2156 :2221) — a stable sort preserves whatever order it was handed, so ties resolve by hash accident, seeded at :2029.
  5. survivorsOf(…) >= enrichN (:2168) — an early exit on accumulated results, so fill order decides where the search stops.
  6. Two strict comparisons — :932 Dijkstra improvement and :1729 POI attachment. First-wins on every tie.

AND THE PROJECT ALREADY KNOWS THE INPUT CAN DIFFER IN THE LAST BIT. GtMathPort exists because Apple's libm and Android's disagree there: the 15e certification measured cos(0.68089…) as Apple …5005 against Android …5006. Feed that through a few hundred summed haversines and into decision 1 above, and one POI changes side.

THIS IS WHY THE SYMPTOM LOOKS THE WAY IT DOES. [stated] Fred, 19:02: “the first two tracks are identical. the third has minimal trail and mil[e]age difference.” Rides 1–2 are clear winners with a margin far wider than any last-bit discrepancy, so they are stable. Ride 3 was a near-tie. A logic difference would not produce “top two identical, third barely different” — a boundary flip is exactly what does.

HOW IT PRODUCES THE VISIBLE SYMPTOM ([stated] Fred 20:35: "every one of those routes is south of the trailhead, every route on the android is north"; 20:36: "droid 1 has no routes south"): Droid keeps a spring 22.9 mi NORTH, iOS keeps two 15-20 mi SOUTH → different usable sets (15 vs 14) → different pair tables (51 vs 41 bad pairs, an order-independent set size) → different cliques → iOS exhausts its rich northern combinations after three rides and the descent falls to 3-feature rides, which is where the southern features enter. iOS: #1-#3 ALL NORTH (6,6,5 features) then a cliff to #4-#6 (3 features, dipping south), only 8 distinct candidates for six slots against Droid's 13.

⭐ SCORING IS ELIMINATED, PROVEN ARITHMETICALLY. Every iOS score reproduces bit-for-bit when recomputed from class counts alone on a third machine with a different libm. scoreSet is Σ base/(1+0.22k) over per-class counts — no coordinates, no distances, no libm. So n peaks is one fixed double on any IEEE-754 machine (2→5.459016393442623, 3→7.5423497267759565, 5→10.94532332328967, 6→12.3738947518611). The score for a given feature set CANNOT differ between platforms. One narrow caveat: a MIXED-class ride could differ in the last bit, since float addition is not associative — it does not arise here, as all eight rides are pure peaks.

⚠ AND THE SCORING IS NEARLY DEGENERATE ON THIS GROUND. Only two distinct solo scores exist in the whole universe: 3.0 (21 peaks + cliff) and 2.0 (3 springs). So :1995's sortedByDescending { scoreSet(…) } ranks almost nothing — it is 21 items tied, then 5 tied, and .take(24) means "all 21 peaks and the cliff, plus 3 of the 5 springs chosen by hash order." The 3.0/2.0 class weights do no work in Utah peak country, and ride ORDER is decided by :2221's thenByDescending { miles } tiebreak, not by score.

⚠ TWO INSTRUMENT FLAWS IN THE 11-24 DUMP, for whoever reads those files: (1) ceiling_size is read AFTER the descent, and ceilingSize is mutated during it — the dump shows 2 for Droid where the log printed descent starts at 7, so the dump's ceiling figure is not the clique bound and the 2-vs-4 comparison is invalid; move the read to just after :2101 in v2. (2) usable_features and bad_pairs are computed over different 24-member sets, so they are not directly comparable either.

7c — THE FIX, IN THREE INDEPENDENT PIECES (Fred's design, 20:43-20:51)

1. DETERMINISE THE CURRENT CAP — the port fix, required, a few lines. Add a secondary key to :1995 so tied features resolve identically on both platforms, and change :2029 poiAt.keys.toList() to .keys.sorted() so the clique seed order stops inheriting hash order. Both are needed — the same 24 can still diverge downstream without the second. ⭐ Recommended tiebreak: distance from the trailhead, ascending — stable AND defensible ("when two features score the same, prefer the one the rider can reach"), which keeps Rock Spring at 8.6 mi over Terry Spring at 20.1 mi and makes Android's behaviour better rather than merely reproducible. ⚠ Sorted order is not hash order, so Android's output moves: re-certification against Droid 2 is the gate.

2. MOVE THE CAP TO AFTER THE PAIR TABLE — removes the arbitrary choice at its root. [stated] Fred 20:48: "combine all the point in their combos… and the lowest scoring features are eliminated." Resequence: discover ~35-40 → Dijkstra matrix over all of them → out-and-back filter → pair table → CAP HERE, dropping features with no feasible partner first, then lowest-scoring, down to 24 → enumerate. The combinatorial step still never sees more than 24. ⭐ This fixes the divergence STRUCTURALLY, not with a tiebreak: feasibility is a property of the data, so no iteration order can change it. THE EVIDENCE FOR IT: 13 of the 24 features appeared in NO candidate at all, while two slots went to isolated springs — the cap rations a scarce resource by a criterion that does not predict use. ⚠ THE ONE THING TO MEASURE, NOT ASSUME: the matrix is one Dijkstra per term, so 40 features is 40 solves against today's 26. corridorBox's header records the failure mode exactly — "53,711 edges, and an OutOfMemoryError at java.lang.Long.valueOf while building 112 Dijkstra tables." 26 is fine, 112 is fatal; run 30 / 40 / 50 at Broken Ridge and watch memory and wall time. If it strains, :665 already says what to do: unbox the distance table, do not shrink the box.

3. INSERTION-FIRST CONSTRUCTION — removes the cap entirely. A 2.9 redesign. [stated] Fred 20:51: "starting [with] the … combo and ending when a working combo exceed[s] the mileage, working on the highest point features together and then adding the lowest features till we run out of miles or features." That is the orienteering / prize-collecting formulation, and it is the design intent already in the header at :68 ("PENALISE, DO NOT FILTER… find the best, PENALISE its edges, re-solve") and :61 ("a CHEAPEST-PATH search wearing a POI costume"). The loop: seed with the highest-point features that sit together → grow by insertion while it fits → stop when the next addition would exceed milesHigh → backfill with the lowest-value features that still fit → penalise this ride's edges → re-solve for the next, six times. ⭐ WHAT IT DELETES rather than fixes: maxPoi (nothing discarded before reachability is known, so tonight's bug becomes impossible) · ceilingSize and the greedy clique at :2090 (the stop condition is the mileage budget, not a size bound) · the subset enumeration and most of the pair table that exists to prune it. Three mechanisms removed, all three of them sources of defects. And the insertion machinery is already written and certified — enrichment :2227 and the return-fill :2342 (if (add < 1.0 || curM + add > req.milesHigh) continue) are exactly "add a feature if it fits"; they move from post-passes to the main loop. ⚠ RISKS: greedy finds a good set, not provably the best — a feature that looks weak early but unlocks a rich cluster can be missed, and Droid 2 is how to measure whether that matters. And determinism is still required inside the new design: with 20 peaks tied at 3.0, "the highest-point features" ties constantly, so the seed and every insertion need an explicit tiebreak or the bug is rebuilt in a new place.

SEQUENCING: 1 tomorrow (it is a bug, and cheap) → 2 with its own before/after certification → 3 as 2.9. Each is independently shippable, and each makes the next easier to certify because the baseline stops moving.

⚠ COST HEADROOM, MEASURED 11-24: Droid 339 combos / 95 killed / 244 solved; iOS 642 / 407 / 235. Against the 3,302 combinations that once cost 67.8s, this ground runs orders of magnitude below where cost ever hurt — but it is ground-dependent, and a dense area yielding a ceiling of 10-12 is where a larger pre-cap would bite. ⇒ Do not raise maxPoi; spend it better.

THE CONTRACT:        combos -> array
  1. BUILD     one combo per seed, greedy cheapest-insertion while the closed tour fits
  2. COMPLETE  any feature in no combo gets a singleton -- nothing is lost before ranking
  3. RANK      total score, then feature count, then shorter tour
  4. FILL      from combo #1 down, add each combo's not-yet-present features, stop at 24

⇒ THE ARRAY BECOMES AN OUTPUT OF COMBO ANALYSIS, NOT AN INPUT TO IT. And that is why this matters more than finding the distance difference: the present direction AMPLIFIES. A feature missing the round-trip threshold by a fraction of a mile removes every combo containing it, which collapses the clique, shortens the descent, and drops the product through to 3-feature filler rides. A marginal numeric difference becomes a structural one. Inverted, a marginal distance difference makes only MARGINAL combos differ — which is already visible in the 11-24 data: rides #1 and #2 are byte-identical on both devices because they have margin, and everything below them is where the amplification took hold. ⇒ The fix makes the engine TOLERANT of a distance difference rather than requiring it to be eliminated — which was never winnable across two libm implementations.

STRAIGHT-LINE vs DIJKSTRA — each doing only what it can. [stated] Fred 21:00: “you need t[o] use [dijkstra] to prove the clusters are reachable and valid”; 21:09: “you cannot do this with real data[,] just use raw distance between points… poly lines built and thrown out with total point counts.” Both hold, because straight-line distance is a LOWER BOUND on trail distance:

straight-line polylines   EXCLUDE   cheap O(n^2); proves INFEASIBILITY only; never a false negative
Dijkstra on survivors     INCLUDE   exact; the only thing that proves feasibility
scoreSet over valid combos  RANK     fill the array with unique points to the cap
